# Office provider management

[한국어](OFFICE_PROVIDER_MANAGEMENT.ko.md)

PowerPoint, Word and Excel task panes provide **프로바이더 관리** in the advanced menu. This edits named provider profiles in this computer's global Magi configuration. Saved profiles appear by name in the existing provider picker alongside running backends.

Open the dialog and select a saved profile or **새 프로바이더**. Enter a name (letters, digits, hyphen or underscore), an HTTP(S) API endpoint, the model ID and an optional API key. Save to create or update it. Successful saves close the dialog; failures leave it open. A blank key keeps the existing key; the explicit key-delete checkbox clears it. Saved keys are never returned to the page, and the password input is cleared after requests and when the dialog closes. Delete removes the profile after confirmation.

Profiles are stored as `[llm.profiles.NAME]` in Magi's global `config.toml`, using an authenticated helper endpoint. The update validates and publishes the complete set of fields together, preserving unrelated settings and comments. A failed update leaves the original file unchanged. New configuration files use owner-only permissions; existing file permissions are preserved. Keys are stored in the local configuration; this feature does not add an encrypted credential vault.

After saving, the dialog closes and refreshes the existing provider picker. Select the saved name there to use it. There is no separate apply button. The page sends only the profile name; the daemon loads its endpoint, key and model from configuration and replaces all three together for the selected idle conversation. A running turn rejects the change. Other conversations and the global default remain unchanged. The next request uses the selected provider, and changing the model keeps that provider. Applying does not launch an endpoint or verify its credentials over the network.

This selection lasts until the daemon restarts. Reapply afterward. The paired model override is transient too, so restart cannot restore that model against the wrong default endpoint. Deleting a saved profile does not revoke an already applied in-memory provider. The same picker lists profiles by saved name, allowing separate keys/models at the same endpoint.

## Verification

Run `go test -race ./clients/office/helper ./internal/config` and `node clients/office/tools/provider-profiles-test.mjs`. The browser suite exercises the same management module in PowerPoint, Word and Excel: narrow layout, create/edit/delete, key retention/clearing, secret-free reads, request failures, successful-save closure, name-only application from the actual picker renderer and click handler. Full-turn tests load a saved profile through the production daemon/provider factory and submit ordinary and workflow messages; they send actual HTTP model requests and check endpoint, bearer key, model, session isolation and rejection during active turns. Backend tests cover authentication, invalid endpoint/name rejection, key handling, persistence and atomic validation. Browser mocks do not establish real Office installation acceptance.

## Real Office acceptance and Windows startup diagnosis

On this Mac, PowerPoint was opened and a new blank presentation created through its real accessibility interface. The Magi task pane was not reached, so provider CRUD/application inside Office remains unverified. The three browser module checks and real HTTP core check above do not replace that acceptance.

On Windows Office 2021, capture `powershell -NoProfile -File clients/office/tools/process-diagnostics.ps1` immediately after opening PPT and again after 30 seconds. It lists PID, parent, role, executable and start time without command lines or keys. A PPT-only installation normally needs one unified Office helper, one PPT companion and the COM editing adapter where installed; daemon launchers are temporary. Seven to ten persistent Magi processes need investigation by role, not a count alone. The COM starter now refuses to spawn when its startup mutex times out, and its `start.log` records host/child PIDs. The helper startup log records PID, parent, configuration and socket locations. This fixes an identified duplicate-start path; it does not establish the cause of the user's Windows observation. Windows COM activation still requires verification on that PC.

Only running Office hosts are warmed at helper startup. Previously mounting PPT, Word and Excel routes started all three companions even when only PPT was open. The process watcher now warms an additional host when that host starts, and leaves absent/unknown hosts alone. Tests cover all three hosts and avoid background retries of failed preparation. Workflow phase copies now preserve the selected provider; previously the direct-provider test missed a real workflow request falling back to the default backend with no key.

Editing the profile currently selected in a conversation now reloads that profile after a successful save. Endpoint, key and model are reapplied together for the next request. Other selected profiles and conversations remain unchanged. If a turn is running, the configuration is saved but the UI says that application failed; select the same name again after the turn. Clicking a selected profile also reloads it, so edits do not leave an old endpoint in memory. Identifier inputs disable automatic capitalization, correction and spellchecking.

Conversation icons use leading alignment in three groups: new conversation, rules/guides, and council/companion. Buttons within a group are 16px apart; groups are 24px apart. The provider/model pickers share that leading edge, and provider management is a 32px settings icon in the upper settings/connection group. `node clients/office/tools/provider-toolbar-test.mjs` checks 320/420/600px layouts and input attributes. Provider errors mark the active request failed; requests left unresolved after a finished turn are shown as pending without claiming that another job is running. `node clients/office/tools/request-state-test.mjs` verifies that replay sequence.

Icon buttons show an immediate plain-text tooltip on pointer hover or keyboard focus. Descriptions use the button's current title or accessible label, including state changes and controls created later. Tooltips stay inside the viewport, support hovering over the description and close on Escape, activation, scroll or resize. Existing accessible descriptions are preserved. `node clients/office/tools/icon-controls-test.mjs` covers those behaviors across all three apps; the toolbar suite measures actual widths and spacing.

`node clients/office/tools/icon-controls-boot-test.mjs` loads the actual task-pane HTML and complete main-module graph to verify initialization and hover descriptions with zero page errors. This runs in the isolated browser mock, without an Office token or a live document.

# 수명주기 후속 구현 검토 — 2026-09-11

검토 범위: `2f71c779..525afe53`의 수명주기·업데이트 변경. R5 정책 명시, R6 탐침 시간 제한, R7 로그 fd 정리는 반영됐습니다(`e0b36923`, `e0e15473`, `59230ae6`). R8 도 반영됐습니다(`ca79c0f9`) — 단계별 사유·부분 생성 정리·저하 안내는 착지했고, 「안전하지 않은 업데이트 경로 차단」은 **막지 않기로 판단**했습니다(근거는 [설계 §4](CLIENT_LIFECYCLE.ko.md#4-기동호환성소유권-계약)). 완료된 항목의 이전 지적은 생략합니다.

## 남은 문제

- **R9 / P1 — 정상 다중 기동의 오인:** `internal/update/journal.go:Resume`은 설치 전체의 `Starts >= 1`을 실패로 판단합니다. 같은 후보에서 워크스페이스 A가 정상 실행 중이어도 B가 시작하면 롤백합니다. 프로세스 생존·준비 증거로 세대를 구분하고, 두 워크스페이스 동시 실행으로 검증해야 합니다.
- **R10 / P1 — 트랜잭션 중재 범위:** OS 잠금은 `Commit` 반환 때 풀립니다. `Salvage/Resume/Confirm/Retry/LeftCleanly`는 같은 잠금을 잡지 않습니다. 다른 데몬이 교체 중의 `.prev`를 중단 흔적으로 복구하거나, 확인 중인 백업을 다음 교체가 덮어쓸 수 있습니다. 교체부터 확정·롤백까지 설치 단위로 중재하고 실제 프로세스 경합을 시험해야 합니다.
- **R11 / P1 — 준비 전에 확정 시계 시작:** `cmd/magi/main.go`는 리스너 기동 전에 60초 타이머를 시작합니다. `Confirm`은 해당 후보·세대·준비 상태를 확인하지 않고 현재 저널의 백업을 지웁니다. 준비가 지연되거나 이후 트랜잭션으로 바뀌면 검증하지 않은 후보를 확정할 수 있습니다. 준비 확인 뒤 안정 구간을 시작하고 확정에 트랜잭션 식별자를 요구해야 합니다.

남은 R9–R11 은 **윈도우를 필요로 하지 않습니다** — `internal/update` 의 플랫폼 공통 Go 이고, 잰다면 두 워크스페이스·두 프로세스 경합입니다. 다만 R10 의 설치 잠금은 플랫폼별 구현이 있고(`lock_windows.go`), 그 주석 자신이 「교체 대상 파일이 실행 중 이미지로도 잠겨 있는 플랫폼」이라고 적어 두었으므로, 실제 경합 시험은 윈도우에서 한 번 더 도는 값이 있습니다.

§9는 부분 구현입니다. 조기 기동 실패의 자동 복구는 다음 실행에 의존하며, 안전 시점·준비 확인·동시 데몬 중재의 인수가 남아 있습니다. Windows 실물 시험만 남은 상태가 아닙니다.

## 검증

업데이트·코어의 `Journal|Recover|Rollback|Commit|Lock` 대상 Go 테스트는 통과했습니다. VS Code는 255개 중 251개 통과, 3개 건너뜀, 1개 실패입니다. 실패는 TESTING 문서가 모든 테스트 파일을 나열하는지 검사하는 항목입니다. 실제 Windows·JetBrains IDE 인수는 재실행하지 않았습니다. R9–R11은 코드 경로 검토 결과이며 기존 테스트 통과로 해소되지 않습니다.

# 위임 요청의 추가 질의 설계

상태: 설계. 현재 구현된 자동 회신 경로로 보고하지 않습니다.

## 판단 기준

요청의 입력·사실·요구사항이 부족하고 요청자가 답할 수 있으면 요청자에게 추가 확인합니다. 실행 승인·계정 비밀·사용자 선호 결정은 사용자에게 묻습니다. 요청자의 답변으로 사용자의 승인이나 도구 권한을 대신하지 않습니다. 이미 받은 정보를 다시 묻지 않으며, 요청자가 답할 수 없으면 확보한 근거와 부족한 점을 사용자 검토 서식에 함께 표시합니다.

## 원래 요청에 연결된 경로

위임 수락 시 표시 이름과 별도로 요청자 컴패니언 ID, 요청자 세션, 원본 접수 번호, 응답 경로를 저장합니다. 요청자 이름만으로 다른 컴패니언을 추측해 새 작업을 보내지 않습니다. 응답 경로는 원본 요청과 같은 인증 경계에서 검증하고, 모델이 임의의 호스트·세션으로 바꿀 수 없게 합니다.

모델에는 원본 요청을 가진 세션에서만 `clarify_request`를 제공합니다. 입력은 부족한 정보, 확인 질문, 필요한 이유, 이미 확인한 근거, 필요한 응답 형태입니다. 대상·원본 접수 번호는 하네스가 주입합니다. 도구는 접수 ID를 즉시 돌려주며, 응답은 원문과 출처를 보존해 해당 위임 세션에만 전달합니다. 일반 실행·수정 작업을 담은 메시지는 추가 질의로 취급하지 않습니다.

## 요청자 쪽 처리

추가 질문은 기존 요청자의 작업을 강제로 중단하거나 별도 개발 작업을 시작하지 않습니다. 먼저 요청 원문과 이미 제공한 사실로 답할 수 있는지 판단하는 읽기 전용 처리 경로를 사용합니다. 근거가 부족하거나 사용자 판단이 필요하면 그 이유를 응답합니다. 답변은 도구 승인·권한 부여로 해석하지 않습니다. 이 읽기 전용 처리에 쓸 모델과 최대 컨텍스트·시간·비용 예산은 구현 전에 확정해야 합니다.

## 상태·내결함성

원본 요청 ID와 추가 질의 ID를 함께 기록합니다. 상태는 대기·응답·요청자 부재·시간 초과·취소·권한 거부를 구분합니다. 동일 질문의 재접수는 같은 ID로 처리하며 응답을 중복 주입하지 않습니다. 왕복 횟수·전체 경과시간·질문 길이·응답 크기를 제한합니다. 두 컴패니언이 서로 추가 질의를 생성하는 순환은 원본 요청 계보로 차단합니다. 실행 중인 원본이 취소되면 남은 질의도 취소합니다. 재시작 후 완료된 원본이나 다른 세션에 답이 들어가면 거절합니다.

## 사용자 화면

메인 검토 영역에는 요청자에게 추가 확인 중인 상태를 표시합니다. 응답이 없다는 이유만으로 사용자 거부로 표시하지 않습니다. 사용자에게 질문하게 되면 요청 원문, 요청자에게 확인한 질문·답변, 남은 판단을 해당 컴패니언의 `decision-report` 순서로 표시합니다. 추가 사실과 실행 승인은 서로 다른 동작으로 유지합니다.

## 검증 조건

요청자 이름이 중복되거나 재시작된 경우, 같은 질문 두 건, 응답 순서 역전, 중복 응답, 원본 취소, 응답 유실·시간 초과, 순환 질의, 사용자 승인 우회 시도를 각각 검증합니다. 다른 작업공간을 직접 읽거나 수정하지 않고도 요청자가 추가 사실을 제공하는 통합 시나리오가 필요합니다. 설계를 구현으로 전환할 때 프로토콜·저장소·클라이언트별 인수 조건을 함께 확정합니다.

# 인프라·운영 에이전트 설계

업무 종류는 operations입니다. Docker와 Kubernetes는 클라이언트·도구 환경이며 별도 업무 종류가 아닙니다. 코딩 내부 역할과 마찬가지로 운영 역할은 담당 환경의 소유 범위로 나눕니다. 예: 특정 Docker context의 서비스 집합, 특정 Kubernetes context와 namespace의 서비스 집합입니다.

## 구현 상태

AgentKind, 클라이언트 종류, 고유 프롬프트, 도구 네임스페이스 격리와 콘솔 타입 등록을 추가했습니다. Docker·Kubernetes 실행 어댑터와 연결 UI는 아직 구현하지 않았습니다. 이 역할만 선택하면 도구가 자동 설치되지는 않습니다.

## 도구 계약과 순차 구현

1. 헬퍼 시작 시 Docker context 또는 Kubernetes context·namespace를 필수로 받습니다. 요청 인자로 환경을 바꾸지 못하게 합니다. 서비스·리소스 허용 목록을 고정하고 자격 증명은 헬퍼에만 둡니다.
2. 조회 도구는 상태·리소스 설명·최근 이벤트·제한된 로그를 제공합니다. 로그는 줄 수·바이트·시간 제한을 적용하고 생략 사실을 표시합니다. Secret 조회, exec, port-forward, 임의 CLI 인자는 제공하지 않습니다.
3. 변경은 조회와 별도 도구로 제공합니다. 초기 변경은 명시적 컨테이너 restart 또는 명시적 Deployment rollout restart로 제한합니다. 대상·영향·복구 방법을 승인 요청에 표시하고 변경 뒤 상태를 다시 조회합니다. 삭제·prune·apply·scale은 별도 설계와 검증 후 추가합니다.
4. 범용 bash를 열지 않습니다. 실행은 검증된 인자를 exec.Command에 전달하며 셸 문자열을 만들지 않습니다. API의 read-only 표시는 프롬프트 설명과 별개로 정의합니다.
5. 테스트는 다른 context·namespace·미등록 리소스 거절, 로그 상한, timeout, 승인 거부 시 변경 미실행, 재시작 후 상태 확인을 포함합니다. 실제 Docker와 disposable Kubernetes 환경 검증을 모의 테스트와 구분합니다.

코딩 에이전트는 애플리케이션 코드베이스를, 운영 에이전트는 실행 환경을 소유합니다. Dockerfile·배포 매니페스트 수정은 담당 코드베이스의 명시적 소유 범위에서 처리하며, 운영 권한을 통해 소스 편집 권한을 얻지 않습니다.

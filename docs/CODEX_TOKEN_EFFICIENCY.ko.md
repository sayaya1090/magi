# Codex 백엔드 토큰 효율

2026-10-17 gwt 조사에서 완료된 네 턴의 입력 토큰 합계는 5,974,516개였습니다. 각 턴의 마지막 요청에는 32,838~105,932개의 입력 토큰이 있었습니다. 두 값의 의미는 다릅니다. 턴 합계에는 모든 모델 요청·카운슬·부가 호출이 포함되고, 마지막 요청은 한 번의 컨텍스트 크기를 나타냅니다. 보고된 캐시 입력은 328,704개로 약 5.5%였습니다.

같은 세션에서 `bash_output`은 33회, `wait_for`는 7회 호출됐습니다. 같은 빌드 명령을 실행한 호출은 세 번이었습니다. 필요한 대기도 있었지만, 변하지 않은 출력을 확인하려고 모델을 반복 호출하면 기존 컨텍스트를 계속 전송합니다. Gradle 스냅샷 용량 초과와 복사본 전용 apply로 Git 작업을 반영하려는 시도 등 도구 계약 오류도 재시도를 만들었습니다. 코딩 작업공간 수정은 이 계약 문제를 별도로 다룹니다.

## 도구 내부 대기

`bash_output`은 실행 중인 작업에 읽지 않은 출력이 없으면 최대 30초 기다립니다. 새 출력이나 프로세스 종료가 있으면 대기를 끝냅니다. 출력이 쌓여 있거나 이미 종료된 작업은 즉시 반환하므로 나눠 읽는 동작도 유지됩니다. 선택 인자 `wait`는 0~60초이며, 대화형 작업에서 즉시 확인하려면 `wait:0`을 사용합니다. 조회를 취소해도 작업은 중단하지 않습니다.

빌드는 작업 ID를 지정한 `wait_for`를 사용합니다. 기본 대기 시간은 300초이며, 백그라운드 실행 응답에서도 이 방법을 먼저 안내합니다. 출력을 읽었다고 빌드가 완료된 것은 아니며, 대기 시간 초과는 빌드를 다시 시작할 근거가 아닙니다. 이 수정은 빈 조회를 줄입니다. 의미 있는 새 출력을 판단하는 모델 요청까지 없애지는 않습니다.

## 선택 설치한 로컬 Codex 플러그인

이 머신의 선택 설치 Codex 플러그인은 대화를 유지하기 위해 `codex mcp-server`를 사용했습니다. 설치된 Codex CLI 0.163.0에는 이 명령이 없어 요청마다 새 `codex exec`로 대체 실행됐습니다. 단발 요청 자체는 성공했기 때문에 대화 연결이 유지되지 않는 문제가 드러나지 않았습니다.

교체한 연결은 지원되는 `codex app-server`의 `initialize`, `thread/start`, `turn/start` 프로토콜을 사용합니다. 후속 요청은 같은 thread ID를 유지합니다. 읽기 전용 sandbox를 요구하며 서버에서 요청하는 도구 실행을 승인하지 않습니다. Magi의 도구 호출은 계속 Magi가 담당합니다. 누적 사용량 알림은 호출별 차이로 계산하고, 중복 알림을 합산하지 않습니다. 추론 토큰은 이미 출력 토큰에 포함되므로 다시 더하지 않습니다.

이 플러그인은 로컬 설치 구성요소이며 저장소의 바이너리에 포함되지 않습니다. 재현 가능한 연결 코드와 갱신 도구를 다음과 같이 보존합니다.

```sh
python3 tools/update-codex-transport.py '/path/to/plugins/codex/init.lua'
```

갱신 도구는 예상한 플러그인 구조를 확인하고, 내용 digest를 붙인 백업을 남긴 뒤 파일을 원자적으로 교체합니다. 다시 실행하면 변경하지 않습니다. 기존 설정과 프롬프트 구성은 보존합니다. 기존 지속 연결 플러그인 구조가 필요하며, 더 오래되거나 다른 구조는 파일을 바꾸지 않고 거절합니다. 실행 중인 데몬은 플러그인을 다시 읽거나 재시작해야 새 연결을 사용합니다.

모델 턴을 전송하기 전의 초기화 실패는 기존 exec 대체 실행을 사용할 수 있습니다. 전송을 시도한 뒤 결과가 불확실하거나 실패하면 exec로 재전송하지 않고 HTTP 409를 반환합니다. HTTP 클라이언트의 5xx 재시도 정책이 같은 요청을 다시 실행하는 것도 막습니다. 사용자가 명시적으로 재시도할 수 있습니다.

## 검증과 한계

결정적인 프로토콜 검사는 로컬 모의 서버로 스레드 재사용, 별도 스레드, 중복 사용량 알림, 시작 응답보다 먼저 도착한 알림, 완료 실패를 확인합니다. 도구 검사는 출력 없는 대기, 새 출력, 종료, 누적 출력 읽기, 취소, 시간 제한, 즉시 조회를 다룹니다.

선택 실행 실측에서는 Codex CLI 0.163.0과 `gpt-6.1-sol`에 짧은 요청을 네 번 보냈습니다. 모두 같은 스레드를 사용했습니다. 입력/캐시 토큰은 차례로 14,077/5,632, 16,360/0, 14,119/13,952, 14,140/13,952였습니다. 예열된 요청의 캐시 재사용은 약 99%였지만 초기 요청은 그렇지 않았습니다. 이 결과는 작은 테스트의 프로토콜·캐시 증거입니다. gwt 개발 작업을 재실행한 결과나 모든 provider·계정·프롬프트 변경에서 같은 적중률을 보장하는 수치는 아닙니다.

```sh
go test -race ./internal/adapter/tool/builtin ./internal/adapter/plugin/lua
MAGI_CODEX_REAL_TRANSPORT=1 go test ./internal/adapter/plugin/lua -run '^TestCodexAppServerRealTransport$' -v -count=1
```

두 번째 명령은 사용자의 Codex 로그인과 토큰을 사용합니다. 일반 테스트에서는 자동 실행하지 않습니다.

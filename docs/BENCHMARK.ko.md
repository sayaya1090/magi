# Terminal-Bench 2.1로 magi 벤치마킹하기

[English](BENCHMARK.md) · [↑ Docs](README.ko.md)

평가 대상 지표, 실행 절차, 그리고 실측 벤치마크 결과입니다.

[Terminal-Bench](https://www.tbench.ai)는 Docker 컨테이너 내부의 격리된 실제 터미널 환경과 과제를 에이전트에게 부여하고 작업 완수 여부를 채점합니다. 이는 에이전트 전체 스택을 종합 평가하는 벤치마크입니다 — 제어 루프, 도구 실행, 오류 회복 메커니즘, LLM 백엔드가 함께 시험대에 오르며, 단일 실행 결과만으로는 이 중 어떤 구성 요소가 최종 결과를 결정했는지 분리하여 설명할 수 없습니다. 하단 표가 최종 판정과 함께 토큰 소비량 및 도구 호출 횟수를 병기하는 이유가 여기에 있습니다. 두 에이전트가 동일하게 통과(PASS) 판정을 받았더라도 한쪽의 작업량이 5배에 달한다면 동일한 성능으로 평가할 수 없기 때문입니다.

## 무엇이 시험대에 오르나

- **루프**: magi의 도구 실행 계층, 가드 레일, 카운슬 합의 게이트, 오류 회복 루프 (고정된 버전의 바이너리 기준).
- **백엔드**: `MAGI_BASE_URL` 환경 변수로 지정된 서빙 엔드포인트.
- **데이터셋**: `terminal-bench/terminal-bench-2-1` (총 89개 과제).

## 준비물

- **Docker 데몬**. 요청할 병렬 실행 수에 비례하는 충분한 리소스 여유가 확보되어 있어야 합니다. Terminal-Bench는 개별 trial마다 독립 컨테이너를 기동하며, 컨테이너들은 가상 머신(VM)에 할당된 시스템 자원을 분할 점유합니다. 현재 할당된 자원 사양은 `docker info` 명령으로 확인할 수 있습니다.
- **[Harbor](https://www.tbench.ai)**: Terminal-Bench 실행 러너(`harbor run`).
- **컨테이너용 magi 바이너리** — 단일 디렉터리 내에 `magi-arm64` 또는 `magi-amd64` 바이너리 배치. 어댑터가 각 컨테이너 내부로 바이너리를 전송하여 설치하며, 컨테이너 내부에서 소스 빌드를 수행하지 않습니다.
- **컨테이너에서 통신 가능한 백엔드 엔드포인트.** 호스트 머신 내부에서 실행되든 원격 서버에서 실행되든 무관합니다. 컨테이너는 오직 표준 HTTP 통신만을 수행하므로 베이스 이미지에 추가 패키지를 주입할 필요가 없습니다. 단, `BASE_URL`에는 **컨테이너 내부 관점에서의** 유효 주소를 지정해야 합니다(호스트 전용 `localhost`가 아닌 `host.docker.internal` 등).

`host.docker.internal`은 **컨테이너 내부 네트워크에서만** 해석되는 호스트 식별자이며 호스트 로컬에서는 해석되지 않고, 이마저도 Docker Desktop 환경으로 한정됩니다 — 네이티브 Linux Docker 환경에서는 기본 브리지 게이트웨이 주소(`172.17.0.1`)나 사용자가 사전에 정의한 `--add-host` 매핑을 통해 호스트에 접근해야 합니다. 따라서 백엔드의 정상 응답 여부는 89개 과제 실행을 시작하기 전에 **호스트 측 엔드포인트**를 통해 사전에 검증해야 합니다:

```sh
curl -s http://localhost:11434/v1/models | head -c 200   # 호스트 관점에서 동일 백엔드 사전 점검
```

## 돌리는 법

```sh
# 컨테이너가 실행할 magi 바이너리 경로 지정 (magi-arm64 / magi-amd64).
export BINARY=/tmp/magi-serve
export BASE_URL=http://host.docker.internal:11434/v1

# 89개 과제 전체 실행. 마지막 인자는 동시 실행 병렬도입니다.
MODEL=qwen3-coder:30b bench/harbor/run.sh 1
```

실행이 완료되면 요약 결과 표가 콘솔에 출력됩니다. 아래 명령을 통해 언제든 결과를 재집계할 수 있습니다:

```sh
python3 bench/harbor/report.py --jobs-glob 'jobs/*tb21*'
python3 bench/harbor/report.py --jobs-glob 'jobs/*tb21*' --markdown   # 마크다운 문서 삽입용
```

## 표 읽는 법

| 컬럼 | 설명 |
|---|---|
| `콜` | 해당 trial에서 magi가 수행한 도구 호출 횟수 — 에이전트의 실제 작업량에 비례하여 증가하는 지표입니다 |
| `카운슬` | 해당 턴의 완료 선언에 대해 소집된 카운슬 합의 라운드 수. 0회는 타임아웃 종료를 의미합니다 — 카운슬은 에이전트의 완료 선언 시점에 소집되는데, 제한 시간 초과로 강제 종료되면 완료 선언 자체가 발생하지 않기 때문입니다 |
| `입력` / `캐시읽기` / `출력` | 해당 trial에서 발생한 토큰 소비 집계. `입력`은 프롬프트 캐시 적중량을 포함하므로 `입력 − 캐시읽기`가 실제 신규 처리된 토큰량입니다 |

판정 컬럼에는 4가지 상태 표식이 사용됩니다. `PASS`와 `FAIL`은 공식 검증기의 최종 채점 결과입니다. `TIME`은 에이전트 타임아웃에 의한 실패로, 일반 오답과 원인을 분리하여 식별하기 위한 분류입니다 — 본 실행의 17개 미통과 과제 중 9건이 여기에 해당합니다. `RESCORED`는 채점기 자체는 통과시켰으나 벤치마크 리더보드의 리워드 해킹 방지 규칙에 의해 0점으로 사후 강등된 시행입니다.

웹 리포트 페이지는 각 과제별 상세 메타데이터를 추가로 제공합니다 — 추론 비용, 대조군의 5회 실행 결과, 개별 실행 트랜스크립트 아카이브 링크 등이 수록됩니다. 본 문서의 표는 결과 diff 검증에 필수적인 핵심 데이터만을 선별한 것입니다.

## 발등을 찍을 하나

**병렬 실행은 벤치마크 점수에 부정적인 방향으로만 왜곡을 유발합니다.** 개별 trial들은 Docker VM의 CPU와 메모리 풀을 공유하여 소비합니다. 7 CPU · 8GB VM 환경에서 4개 trial을 동시 실행할 경우 각 컨테이너는 1.75코어 및 2GB 메모리만 할당받게 되며, 무거운 소스 컴파일이나 모델 학습을 수행하는 과제는 에이전트의 문제 해결 능력과 무관하게 시스템 리소스 고갈로 타임아웃이 발생합니다. 이러한 왜곡은 단방향입니다 — 리소스 부족은 정상 통과 과제를 타임아웃 실패로 만들 수는 있어도 실패 과제를 통과시킬 수는 없기 때문입니다. 벤치마크 실행 전 반드시 `docker info`로 시스템 여유 자원을 점검하고, 결과 점수는 동일한 자원 사양 하에서 측정된 수치와만 상호 비교해야 합니다.

## 격리, 그리고 치팅이 없었음을 확인한 방법

과제 소스 코드가 GitHub 등에 공개된 벤치마크는 두 가지 경로로 무결성이 훼손될 수 있습니다: 후속 trial이 선행 trial의 잔여 상태로부터 정보를 학습하거나, 에이전트가 외부 네트워크를 통해 문제의 정답을 직접 조회하는 경우입니다. 두 가능성 모두 의도적인 통제 조치가 없으면 자연스럽게 방지되지 않습니다.

**trial 간 상태 유출 및 공유는 원천 차단된다.** 과제마다 독립된 컨테이너 이미지를 기반으로 컨테이너를 매번 새로 기동합니다. 호스트에서 컨테이너 내부로 유입되는 외부 파일은 magi 단일 바이너리가 유일하며, 업로드 후 `install` 과정을 거칩니다. 외부 네트워크 다운로드를 사용하지 않으므로 컨테이너 내부에서 curl이나 wget 설정이 훼손되더라도 설치 실패가 발생하지 않습니다. 호스트 파일 시스템의 디렉터리 마운트는 일절 허용되지 않습니다. `MAGI_DATA_DIR`는 컨테이너 내부 로컬 경로로 격리되며, 어댑터는 경험 저장소, 장기 메모리, 스킬 디렉터리를 **전혀 마운트하지 않습니다.** magi의 내부 상태 스토어는 해당 컨테이너의 수명 주기와 함께 생성되고 소멸합니다. 어떠한 과제의 실행 컨텍스트도 다음 과제의 시스템 프롬프트나 히스토리에 유입되지 않습니다 — 매 trial마다 새로운 세션을 초기화하고 대화 이력을 처음부터 렌더링합니다.

**컨테이너는 외부 네트워크 접속을 유지한다.** 패키지 설치, 외부 소스 코드 클론, 데이터셋 다운로드 등 대다수의 과제가 정상적인 해결을 위해 네트워크 통신을 필요로 하기 때문입니다. 따라서 정답 데이터의 외부 조회 가능성은 원리적으로 상존하며, 이를 단순히 배제되었다고 가정할 것이 아니라 로그 분석을 통해 전수 검증해야 합니다. magi가 수행하는 모든 도구 호출은 웹 탐색 명령까지 포함하여 이벤트 로그에 완전 기록되므로 기계적 감사가 가능합니다:

```sh
set -- jobs/*tb21*/*__*/agent/magi-stdout.txt   # 감사 대상 실행 디렉터리로 범위를 한정
grep -ohE '⚙ (websearch|webfetch)' "$@" | sort | uniq -c
grep -ohE '⚙ (websearch|webfetch) \{[^}]{0,200}' "$@"        # 도구 호출 페이로드 전수 감사
grep -ohE '⚙ bash \{"command": "[^"]{0,160}' "$@" | grep -iE 'curl|wget|git clone'
grep -oih 'terminal-bench' "$@" | wc -l
grep -ohE '⚙ (read|grep|bash) \{[^}]{0,200}' "$@" | grep -E 'test_outputs\.py|correct_output|_gtruth'
```

감사 대상 범위의 정밀한 한정이 필수적입니다. 범위를 좁히지 않은 무분별한 glob 패턴은 저장소 내 모든 과거 실행 job을 순회하게 되며, 타 실행의 호출 통계가 혼입되어 대상 실행의 엄밀한 감사를 저해합니다.


**데이터셋 명칭은 복수로 존재하므로 단일 패턴 매칭은 탐지 누락을 유발한다.** GitHub 조직명은 하이픈이 포함된 `harbor-framework`이며, 웹 허브 및 태스크 레지스트리 도메인은 하이픈이 없는 `harborframework.com`입니다. 따라서 저장소 URL만을 기준으로 작성된 감사 패턴은 `registry.harborframework.com/tasks/...` 엔드포인트 접근을 탐지하지 못합니다 — 이는 명칭만 다를 뿐 동일한 과제 명세 페이지입니다. 이 감시 결함은 2026-08-26 수동 코드 리뷰를 통해 식별되었습니다. 기존에 격리 처리되었던 과제의 재실행 감사 과정에서 발견되었으며, 정규식 패턴을 보완하자(`harbor-?framework`) 선행 검사를 통과했던 3건의 trial이 추가로 식별되었습니다. 데이터셋 리소스에 도달할 수 있는 모든 도메인 및 호스트 식별자를 감사 패턴에 전면 반영해야 합니다. 단순한 기억 속 URL 형태가 아니라 실제 네트워크 응답을 반환하는 물리적 호스트명을 기준으로 패턴을 추출해야 합니다.

**정답 소스에 접근한 trial은 격리 후 전면 재실행한다.** 상기 감사 절차는 형식적인 확인이 아닙니다 — 에이전트는 실제로 과제 수행 중 GitHub 검색 등을 통해 데이터셋 자체의 과제 페이지를 탐색 및 참조할 수 있습니다. 정답 파일이나 해설에 접근한 이후의 성공 판정은 에이전트의 자율적 문제 해결 능력을 입증하는 유효한 증거가 될 수 없습니다. 따라서 웹 호출을 통해 데이터셋의 과제 명세 페이지, 정답 파일, 채점용 테스트 코드에 접근한 trial은 즉시 격리 처리합니다: 해당 결과는 단독 점수로 채택되지 않으며, 89개 과제가 모두 종료된 후 큐에 재진입하여 재실행됩니다. **최종 통계에는 이 재실행 결과만이 공식 반영됩니다.** 격리 대상 과제 목록은 집계에 조용히 은폐되지 않고 최종 결과 보고서에 구체적 명칭과 사유가 투명하게 공개됩니다 — 보고서가 언급하지 않는 예외 처리는 감사자가 검증할 수 없기 때문입니다.

**웹 호출 감사만으로는 전체 무결성 검증의 절반에 불과하다.** 컨테이너 로컬 파일 시스템에 사전 배치된 채점 스크립트는 단순 `read` 도구 호출 한 번으로 열람 가능하며, 이는 웹 I/O 감사 로그에는 전혀 나타나지 않습니다. 2026-08-26 감사 범위를 로컬 파일 판독 패턴(`test_outputs.py`, `correct_output`, `ground_truth`, `/tests/test.sh`)까지 확장하여 전체 123개 실행 로그를 전수 조사한 결과, 정확히 1건의 호출이 탐지되었습니다. `break-filter-js-from-html` 과제에서 `/app/test_outputs.py`를 읽고 실행한 케이스였습니다. 단, 이 건은 부정행위 격리 대상이 아닙니다. 해당 과제의 Dockerfile에 `COPY tests/test_outputs.py /app`이 명시되어 있고, 과제 지시문 자체가 *"You can run /app/test_outputs.py to verify"*로 종료되기 때문입니다. 이 환경에서 채점 스크립트는 비공개 답안지가 아니라 공개 명세에 해당하며, 에이전트는 지시문에 기술된 요구사항을 그대로 이행한 것입니다. 89개 과제 중 채점 스크립트를 에이전트에게 사전 제공하는 과제는 이것이 유일합니다.

감사 파일명 목록을 정밀하게 한정함으로써 오탐률을 제어합니다. 과제 대상 저장소가 자체 단위 테스트를 포함하는 경우(예: caffe의 `src/caffe/test/test_io.cpp`, `fix-code-vulnerability`의 `/app/test/test_environ.py`)는 벤치마크 채점 스크립트가 아니므로 오탐 대상에서 정상 제외되었습니다.

**채점 테스트 코드는 정답 파일보다 오염도가 높으므로 동일하게 격리 처리한다.** 2026-08-23 `headless-terminal` 과제의 2개 trial이 데이터셋 공식 저장소로부터 `tests/test_outputs.py` 파일을 페치한 사실이 확인되었습니다. 정답 파일이 특정 풀이 경로 하나를 제시하는 것에 반해, 채점 테스트 코드는 최종 판정을 계산하는 단언문(assertion logic) 자체를 노출하므로 더욱 직접적인 치팅에 해당합니다. 두 시행 모두 즉시 격리 조치되었습니다.

**재실행 시에도 동일 외부 자원에 필연적으로 접근하는 과제는 결과를 유지하고 사유를 명시한다.**
`mteb-leaderboard` 과제의 경우, 본 프로젝트에서 기록한 5회의 trial 전량에서 과제 자체의 README 파일을 페치하였습니다(2026-08-23 2회, 08-24 1회, 08-26 2회). 이는 에이전트의 의도적 치팅이 아닌 과제 자체의 구조적 특성에 기인합니다. 지시문 자체가 *"2025년 8월 기준 Scandinavian MTEB 리더보드에서 가장 우수한 임베딩 모델"*을 질의하고 있어 외부 웹 검색이 필수적이며, 해당 검색어를 입력할 경우 검색엔진 상위에 데이터셋 과제 페이지가 필연적으로 노출되기 때문입니다. 격리와 재실행을 반복하더라도 동일 결과가 순환되므로, 본 과제 1건에 대해서는 **재실행 결과를 공식 표에 그대로 등재하되 상세 사유를 명시**합니다. 보고서 독자가 해당 항목의 특수성을 인지할 수 있도록 투명하게 공개하는 것이 무결성 원칙에 부합하기 때문입니다.

**격리 조치는 해당 과제의 이전 trial 이력 전체를 함께 무효화한다.** 단일 오염 trial만을 제거하는 방식으로는 충분하지 않습니다. 선행 trial의 미검증 데이터가 빈자리를 채우게 되어 공식 규칙이 승인하지 않은 과거 수치가 표에 남는 부작용이 발생하기 때문입니다. 2026-08-26 격리 파이프라인 구축 시 이 현상이 실측되었습니다 — 오염 trial 3건을 제외했음에도 총계가 여전히 50건으로 유지되었는데, 그 이전의 구형 trial 3건이 자동으로 승격되었기 때문입니다. 따라서 격리 판정이 내려지면 해당 과제의 해당 trial 및 이전 이력 전체를 비활성화하며, 정규 재실행이 완료될 때까지 해당 과제는 미측정(unmeasured) 상태로 유지됩니다.

**본 실행에 대한 전수 감사 결과.** 총 89개 trial 동안 에이전트는 웹 페치 41회, 웹 검색 18회를 수행하였으며, 모든 요청 페이로드를 전수 감사하였습니다. 이 중 2건이 데이터셋 자체의 GitHub 페이지에 도달하였습니다 — `mteb-leaderboard`가 과제 README를 조회하였고, `qemu-alpine-ssh`가 번역 계층 오류를 디버깅하는 과정에서 GitHub 이슈 스레드를 참조하였습니다. 두 건 모두 정답 파일 참조가 아니었으며 최종 판정에도 영향을 주지 않았습니다(전자는 통과, 후자는 아키텍처 제약으로 실패).

앞선 두 trial은 실제로 정답 파일에 접근한 사실이 적발되었으며, 이에 따라 격리 규칙이 실질적으로 적용되었습니다. `extract-elf`는 `solution/solve.sh`를, `regex-chess`는 데이터셋을 복제한 제3자 미러 저장소의 정답 바이너리 blob을 디코딩하여 참조하였습니다. 두 과제 모두 즉시 격리 후 재실행되었습니다. `extract-elf`의 재실행에서는 외부 정답 페치 없이 정상 해결되었으며, 격리 시도보다 적은 도구 호출 수(29회 대 20회)로 통과하였습니다. 반면 `regex-chess`의 경우 2026-08-26 연속된 2개 trial이 데이터셋의 `tasks/regex-chess/solution/solve.sh`를 외부 페치(`webfetch` 2회, `curl` 1회)하여 통과한 사실이 확인되었습니다. 두 trial 모두 격리 처리되었으며, 1.00 점수 대신 **미측정(unmeasured)**으로 확정 분류하였습니다 — 정답 파일을 참조하여 달성한 통과는 시스템 성능의 유효한 측정치가 될 수 없기 때문입니다. 이는 `mteb-leaderboard`와 명확히 구분되는 처분입니다. `mteb-leaderboard`는 문제 해결을 위해 외부 웹 검색이 불가피했던 공개 README 참조인 반면, `regex-chess`는 최종 정답 소스 자체를 직접 취득했기 때문입니다.

**대조군(리더보드 제출본)에 대한 동일 감사 수행.** 리더보드에 기재된 비교 대상 수치 역시 개별 trial의 트랜스크립트를 전수 분석하기 전까지는 단순한 숫자에 불과하며, "문제를 해결한 것인가 정답을 조회한 것인가"라는 검증 질문은 대조군에도 동일하게 적용되어야 합니다. Harbor Hub는 각 trial의 전체 실행 트라젝토리(trajectory)를 공개 JSON API로 제공합니다 (`/api/trials/{trialId}/trajectory?jobId={jobId}&trajectory_path=trials%2F{trialId}%2Ftrajectory.json`). trial ID는 결과 페이지의 서버 사이드 렌더링 HTML로부터 추출 가능하므로, 전량을 일괄 다운로드하여 오프라인 전수 조사를 수행할 수 있습니다. 2026-08-26 기준 리더보드 `d7540f21` 실행군(Claude Code 2.1.205 / claude-sonnet-5 기반, 총 445개 trial)을 대상으로 동일 분석을 수행한 결과, 440개 트라젝토리를 확보하였으며(439개 유효), 동일 감사 패턴 기준으로 데이터셋 과제 명세, 정답 파일, 채점 테스트에 접근한 trial은 **0건**으로 확인되어 데이터 무결성이 검증되었습니다.

**대조군 전수 조사를 통해 확인된 웹 통신 실측치.** 초기 비교 보고서에서는 Claude Code가 웹 접근 도구를 사용하지 않는다고 기술된 바 있었습니다. 표본으로 확인한 소수 트라젝토리에 Bash, Read, Edit 도구만 기록되어 있었기 때문입니다. 그러나 Bash 도구 자체를 통해 외부 네트워크 통신이 광범위하게 수행되고 있었습니다. 전체 439개 trial 중 54개 trial(22개 과제)이 `curl` 및 `wget`을 통해 외부 호스트와 통신하였으며, 그중 30개 trial(13개 과제)은 단순 패키지 미러가 아닌 외부 웹 리소스에 직접 접근하였습니다. 특히 4개 과제의 6개 trial(`build-pov-ray`, `crack-7z-hash`, `dna-assembly`, `regex-chess`)에서는 검색엔진 쿼리를 직접 전송하였습니다. 전용 검색 도구의 유무와 무관하게 네트워크 검색이 실제로 활용된 것입니다. 이 수치는 하한선에 불과합니다. `git clone`이나 Python의 `urllib.request`(한 trial에서 이를 통해 `api.github.com/search/repositories`를 직접 질의함) 등 다양한 통신 경로를 전수 추적하여 트라젝토리 내 URL을 종합 집계하면, **전체 439개 trial 중 165개 trial(전체 89개 과제 중 45개 과제)**이 외부 네트워크를 활용하였습니다. 전체의 약 절반에 달하는 과제가 외부와 통신한 것입니다. 양 모델이 외부 조회를 수행한 영역에서는 대상 엔드포인트 또한 높은 일치도를 보였습니다 (`dna-assembly`는 양측 모두 `www.neb.com`, `build-pov-ray`는 `povray.org` 및 검색엔진, `caffe-cifar-10`은 비교 대상 5개 trial 전량이 `cs.toronto.edu`). `torch-pipeline-parallelism` 과제의 경우 대조군의 특정 trial이 `api.github.com/repos/huggingface/picotron` 저장소 및 README를 참조하였는데, 이는 본 프로젝트에서 자체 trial을 격리 처리했던 바로 그 참조 구현체입니다. 따라서 도구 인터페이스의 단순 차이를 시스템 우위로 단정하기 전에 실행 로그의 실측 통신을 면밀히 대조해야 합니다.

**데이터셋 도메인 외의 공개 소스 저장소에 대한 정답 감사.** 정답이 널리 알려진 공개 오픈소스 프로젝트의 경우 과제 명칭 자체로 원본 저장소에 접근할 수 있으며, 데이터셋 전용 도메인 매칭 패턴만으로는 이를 탐지할 수 없습니다. `regex-chess` 과제가 대표적 사례입니다. 정규표현식 기반 체스 유효수 생성기를 작성하는 과제이며, 원작자는 Nicholas Carlini이고 `github.com/carlini/regex-chess`에 공개 저장소가 존재합니다. 2026-08-26 수행된 본 프로젝트의 3개 시행은 각기 다른 경로로 해당 리소스에 접근하였습니다(데이터셋 공식 `solution/solve.sh` 2회, 제3자 미러 저장소 및 원작자 해설 아티클, 제3자 풀이 트라젝토리). 대조군 역시 완전히 자유롭지 않습니다. 5개 trial 중 1건이 Python `urllib`로 GitHub를 검색하여 해당 원본 저장소를 클론한 이력이 확인되었습니다. 단, 중요한 기술적 차이가 존재합니다 — 대조군의 나머지 4개 trial은 외부 네트워크 참조 없이 과제를 자율 완수하였으므로, 본 과제는 정답 참조 없이도 해결 가능한 과제임이 입증되었습니다. 따라서 이러한 유형의 과제에 대해서는 원본 프로젝트 식별자를 감사 패턴에 병기해야 하며, `scratchpad/rc_clean.py` 스크립트가 해당 검증을 수행합니다.

**오염 감지 시 trial 조기 종료(fail-fast) 파이프라인.** 정답 소스 접근 여부는 통상 trial 시작 후 초기 수 분 내에 발생합니다. 오염이 확정된 상태에서 30분의 전체 제한 시간을 모두 대기하는 것은 컴퓨팅 자원의 낭비입니다. 이에 따라 자동 재실행 루프는 트랜스크립트 로그를 실시간 폴링하여 정답 접근 패턴이 탐지되는 즉시 해당 컨테이너 프로세스를 강제 종료하고 다음 trial로 전환합니다. 이를 통해 30분 소요 trial을 20초 내로 단축하여 대조군과 동일한 k=5 수준의 다회차 측정을 현실적인 시간 내에 수행할 수 있게 되었습니다. 프로세스 종료 시에는 반드시 PID 기반으로 타깃을 지정해야 합니다. `pkill -f <패턴>`과 같은 명령은 재실행 스크립트 자신의 실행 인자와 매칭되어 실행 루프 프로세스 자체가 비정상 종료되는 사고가 빈번히 발생하기 때문입니다.

본 무결성 감사는 부분 샘플링이 아닌 전수 조사를 기반으로 수행되었습니다: 본 벤치마크 실행에서는 `spawn`, `meeting`, `hand_off` 등 위임형 하위 에이전트 생성 도구가 **0회** 호출되었으므로, 별도의 격리 세션 스토어를 보유한 자식 에이전트가 존재하지 않으며 단일 트랜스크립트 로그가 에이전트 활동의 100%를 대변합니다.

**백엔드 서빙 파라미터는 모든 trial에 동일하게 고정 적용된다.** 추론 에포트(reasoning effort) 등은 특정 과제별 설정이 아닌 LLM 엔드포인트 자체의 정적 속성입니다. 따라서 이는 **전체 런(Run) 단위의 불변 조건**이며, 결과 지표와 함께 명시적으로 기재됩니다.

### 어떤 기계에서 돌았고, 어떤 과제가 손해를 봤나

| 구성 요소 | 사양 |
|---|---|
| 호스트 하드웨어 | Mac mini (Mac16,11), Apple M4 Pro, 14코어 (성능 10 + 효율 4), 64GB RAM, macOS 26.5.2, arm64 |
| Docker VM 리소스 | **7 CPU, 7.7GiB RAM** — 개별 trial들이 실제로 분할 점유하는 자원은 호스트의 64GB가 아닌 VM 할당량입니다 |
| 과제 컨테이너 이미지 | amd64 아키텍처 이미지를 arm64 호스트에서 **Rosetta 바이너리 번역을 통해 에뮬레이션 실행** |

핵심 병목 수치는 Docker VM의 리소스 할당량입니다. 동시 2개 trial 실행 시 각 컨테이너는 약 3.5코어 및 3.8GiB RAM을 배분받으며, 대규모 컴파일이나 학습을 수반하는 과제는 호스트 14코어가 아닌 해당 제약된 가상 환경 내에서 실행됩니다. 향후 병렬도를 확장하기 위해서는 우선적으로 Docker VM의 할당 자원을 증설해야 합니다.

실행 결과에서 관찰된 아키텍처적 병목 요인 4가지:

- **`qemu-alpine-ssh` 과제는 아키텍처 에뮬레이션에 따른 핸디캡을 안고 실행되었습니다.** 과제 고유의 작업이 시작되기도 전에 컨테이너 런타임 로그에 `rosetta error: Unimplemented syscall number 282` 에러가 기록되었습니다 — x86 바이너리가 Apple Rosetta 2 번역 계층의 미구현 시스템 콜에 직면한 것입니다. 네이티브 amd64 호스트에서는 발생하지 않는 에뮬레이션 한계이므로, 본 과제에 배정된 900초의 제한 시간 중 상당 부분이 과제 자체가 아닌 호스트 환경 결함을 우회하는 데 소모되었습니다. 과거 보고서에서는 본 과제가 해당 환경에서 통과 불가능하다고 기술된 바 있으나, 2026-08-26의 2개 trial을 통해 핸디캡은 극복 불가능한 장벽이 아니라 추가적인 시간 비용 문제임이 실증되었습니다.
- **두 trial이 Rosetta 시스템 콜 결함을 서로 다른 방식으로 우회하였습니다.** `qemu-startup` 과제는 오류 문자열을 직접 검색하여 `docker/for-mac#7475` 이슈를 식별한 후, amd64 컨테이너 내부에 **arm64 네이티브 QEMU 바이너리**를 직접 설치하였습니다 (`dpkg --add-architecture arm64` 수행 후 `apt-get install qemu-system-x86:arm64`). 번역 계층을 완전히 우회하는 해결책이었으며 해당 trial은 정상 통과하였습니다. 반면 `qemu-alpine-ssh` 과제는 동일한 멀티아키텍처 접근법이 gstreamer 의존성 충돌로 차단되자, **외부 웹 검색을 전혀 수행하지 않고** 시스템 레벨 인터포저를 자체 구축하였습니다 — `objdump -T`로 `qemu_signalfd` 심볼을 분석하고, 미구현 시스템 콜 번호 282(`signalfd`) 및 289(`signalfd4`)에 대해 `ENOSYS` 에러를 반환하는 32라인짜리 `LD_PRELOAD` C 인터포저 라이브러리를 직접 작성하여 QEMU가 파이프 기반 내부 폴백 루틴으로 동작하도록 유도하였습니다. 그 결과 SeaBIOS가 정상 부팅되고 Alpine Linux 3.19가 3분 2초 만에 `localhost login:` 프롬프트에 도달하였으나, 직후 15분 제한 시간이 만료되어 sshd 데몬 설정 단계에 진입하지 못하고 타임아웃되었습니다. 해당 trial의 실패 요인은 아키텍처적 불가능이 아닌 타임아웃 예산 부족입니다.
- **`install-windows-3.11` 과제는 KVM 하드웨어 가속 없이 QEMU를 구동하였습니다** (`/dev/kvm` 장치 노드 부재). 게스트 OS가 순수 소프트웨어 에뮬레이션 모드로 동작함에 따라 57분의 긴 실행 시간을 소모하고 타임아웃 실패하였습니다. Linux 호스트 환경이라 하더라도 Docker 실행 시 `--device /dev/kvm` 플래그를 전달하지 않으면 동일하게 발생하므로 순수한 macOS 전용 페널티는 아니지만, 하드웨어 가속 부재에 따른 성능 페널티인 것은 명백합니다.
- **연산 집약적 과제 다수가 바이너리 에뮬레이션 오버헤드로 인해 타임아웃되었습니다** — `path-tracing`, `path-tracing-reverse`, `make-doom-for-mips`, `gpt2-codegolf`. 각 과제의 타임아웃에서 아키텍처 번역 계층이 차지한 시간 지연과 에이전트 자체의 문제 해결 지연 비율은 엄격히 분리 측정되지 않았으므로 추정에 기반한 단정은 지양합니다.

본 하드웨어 환경에서 도출된 점수는 동일한 시스템 자원 여유를 부여한 벤치마크 결과와만 공정하게 비교될 수 있습니다.

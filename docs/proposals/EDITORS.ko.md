# 편집기 클라이언트 3종 확장 설계 제안 — VS Code · Visual Studio · MATLAB

[↑ 클라이언트 개요](../CLIENTS.ko.md) · [JetBrains 구현체](../../clients/jetbrains/README.md)

> **상태: 설계 제안 (Proposal).** 구현 착수 전 플랫폼별 수용 가능 범위와 기술적 제약 사항을 선행 분석하라는 사용자 지시(2026-09-08)에 기반하여 작성되었다.
>
> 기존 요구사항은 "JetBrains 플러그인에 구현된 모든 기능을 타 에디터에 동일하게 제공하는 것"이었다. 본 문서는 **동일 구현이 가능한 기능군**과 **에디터 자체의 플랫폼 제약으로 구현이 불가능한 영역 및 그 기술적 사유**를 상호 대조하여 기술한다. 특히 분석 대상 3종 중 1개 플랫폼(MATLAB)은 JetBrains가 제공하는 핵심 에디터 확장 기능의 상당 부분을 플랫폼 레벨에서 지원하지 않는다.

## 1. 이관 대상 기능 분석 — JetBrains 구현체 전수 조사

기존 JetBrains 플러그인은 명확히 2개 계층으로 분리되어 있다. 이 아키텍처 경계가 본 제안서의 핵심 분석 기준이다.

| 소속 모듈 | 라인 수 | 역할 및 책임 |
|---|---|---|
| `core` (순수 Kotlin) | 3,687 | 소켓 프로토콜 통신(`DaemonClient`, `SocketPath`, `HandServer`), 트랜스크립트 역직렬화, 마크다운 파싱, 콘솔 ANSI 색상, 권한 승인 모드 관리, 바이너리 릴리스 선택, 재시도 예산 제어 등. IDE 플랫폼 API를 일체 참조하지 않는 순수 로직 계층 |
| `intellij` (IDE 연동 계층) | 6,091 | 툴 윈도우 2종, IDE 액션 6종, 인텐션, 인라인 완성, 인레이 힌트, 상태 표시줄 위젯, 환경설정 UI, 에디터 거터 표식 등 플랫폼 종속 UI 계층 |

**타 플랫폼 이관 시 `core` 모듈은 직접 재사용할 수 없다.** JetBrains 구현체는 JVM Kotlin으로 작성되어 있으며, VS Code는 TypeScript, Visual Studio는 C#/.NET, MATLAB은 MATLAB 스크립트/Java 환경을 사용하기 때문이다. 따라서 본 과업은 단순 포팅이 아닌 **언어별 재작성**이며, 재작성 대상은 위 표의 전체 라인 수(9,778라인)를 포괄한다. 다만 `core` 계층의 통신 프로토콜은 [`docs/CLIENTS`](../CLIENTS.ko.md)에 정본으로 명세되어 있으며, "새 클라이언트가 밟는 4단계 순서"(발견 → 악수 → 기능 판별 → 동작 수행)가 정량적인 개발 명세로 기능한다.

| 기능 항목 | 구체적 동작 | 요구되는 에디터 플랫폼 API |

## 2. 3개 플랫폼별 실현 가능성 종합 비교

| 에디터 플랫폼 | 대화·계획 패널 | 인라인 완성 | 인레이 힌트 | 코드 액션 | 편집 적용(손) | 실현 가능성 판정 |
|---|---|---|---|---|---|---|
| **VS Code** | ✓ WebView | ✓ `InlineCompletionItemProvider` | ✓ `InlayHintsProvider` | ✓ `CodeActionProvider` | ✓ `WorkspaceEdit` | **전 기능 완벽 구현 가능** |
| **Visual Studio** | ✓ ToolWindow(WPF) | △ 버전에 따라 상이 | △ Tagging/Adornment 수동 렌더링 | ✓ Light Bulb API | ✓ TextBuffer 제어 | **대체로 구현 가능 (높은 개발 비용)** |
| **MATLAB** | △ 독립 UI 창(App) | ✗ 미지원 | ✗ 미지원 | ✗ 미지원 | △ 문서 텍스트 치환 | **부분적 구현만 가능 (핵심 편집 기능 불가)** |

플랫폼별 핵심 요약:

- **VS Code는 JetBrains 기능과 거의 1:1로 정확히 대응된다.** 위 표의 모든 기능 항목에 대응하는 확장 API가 공식 제공되며, 대부분 JetBrains의 OpenAPI보다 단순하고 직관적이다. 기술적 병목은 플랫폼 API가 아닌 TypeScript 클라이언트 재작성 리소스다.
- **Visual Studio는 구현은 가능하나 개발 비용이 현저히 높다.** VSIX + MEF + WPF 아키텍처를 수반하며, 에디터 심층 확장(태깅, 어도너먼트)은 VS Code의 선언적 API에 비해 수동 구현 공수가 크다. 아울러 **Visual Studio for Mac은 공식 단종**되었으므로 Windows 환경 전용으로 한정된다.
- **MATLAB은 일반적인 IDE 플러그인 생태계를 갖추고 있지 않다.** 상세 분석은 하단 §6을 참조한다.

## 3. 공통 통신 계층의 아키텍처 선택지

3개 플랫폼 클라이언트를 각각 독립 구현할 경우, 소켓 통신 프로토콜, 트랜스크립트 역직렬화, 권한 승인 어휘 관리 로직이 JetBrains를 포함하여 **총 4벌의 개별 구현체**로 파편화된다. 동일한 프로토콜 로직이 4곳에 분산 작성될 경우 필연적으로 구현 분기(drift)가 발생한다.

접근 가능한 아키텍처 경로는 다음 두 가지다:

### (가) 언어별 전용 클라이언트 라이브러리 독립 작성

`core` 계층에 해당하는 프로토콜 및 모델 코드를 TypeScript와 C#으로 각각 처음부터 작성하고, 그 위에 에디터 UI 계층을 얹는 방식이다.
JetBrains 플러그인이 이미 이 구조를 검증하였으므로 **아키텍처 안정성은 입증**되어 있다. 단점은 백엔드 소켓 프로토콜 변경 시마다 3개 언어의 라이브러리를 동시 수정해야 한다는 유지보수 오버헤드다.

이를 방지하기 위해 저장소 내에 프로토콜 일치성 자동화 검증 테스트가 선행되어야 한다: JetBrains의 `WireConformanceTest`와 같이 **Go 코어 소스 코드를 직접 파싱**하여 플러그인이 소비하는 필드 명칭과 데몬이 전송하는 필드 명칭의 일치성을 정적 검증하고, 매칭률이 기준치 미만일 경우 빌드를 실패시켜야 한다. 이 검증 장치가 부재할 경우 직렬화 라이브러리의 `ignoreUnknownKeys` 옵션 등에 의해 프로토콜 불일치가 예외 없이 기본값으로 흡수되어 조용한 버그를 양산하게 된다.

### (나) 표준 인터페이스 프록시 도입 — `magi ide-bridge`

에디터 계층은 **표준 입출력(stdio)을 통해 줄바꿈 구분 JSON만 중계하는 초경량 어댑터**만 작성하고, 소켓 통신, 트랜스크립트 상태 관리, 권한 승인 판정 등 무거운 로직은 코어 바이너리의 서브커맨드가 전담하는 방식이다. 새로운 에디터 플랫폼을 추가할 때의 개발 공수가 (가) 방식 대비 대폭 절감된다.

- **장점**: 에디터 클라이언트는 이미 데몬 기동을 위해 시스템에 코어 바이너리를 다운로드해 두고 있으므로, 브리지 프로세스를 하나 더 실행하는 것은 새로운 외부 런타임 의존성을 유발하지 않는다.
- **비용**: 에디터와 데몬 사이에 별도의 IPC 계층이 추가되며, 해당 브리지 인터페이스의 규약 관리가 추가된다.

**권고: 장기적으로 (나) 브리지 아키텍처를 표준으로 채택하되, VS Code 확장은 검증된 (가) 방식으로 우선 신속 구현한다.**

## 4. VS Code 세부 구현 명세

### 1:1 매핑 지원 API

| JetBrains 구현체 | VS Code 대응 API |
|---|---|
| 툴 윈도우 2종 | `WebviewViewProvider` 2종 (`activitybar` 및 `panel` 기여점) |
| 상태 표시줄 위젯 | `window.createStatusBarItem` |
| 환경설정 화면 | `contributes.configuration` (별도 UI 작성 불필요, VS Code 설정 UI 자동 편입) |
| 인라인 완성 | `languages.registerInlineCompletionItemProvider` |
| 인레이 힌트 | `languages.registerInlayHintsProvider` |
| 훑어보기 상단 알림 | `window.showInformationMessage` 또는 에디터 데코레이션 |
| 편집 표식 시각화 | `TextEditorDecorationType` (배경색, 테두리, 거터 아이콘 지정) |
| 코드 액션 (Alt+Enter) | `languages.registerCodeActionsProvider` |
| 커밋 초안 생성 | `scm/inputBox` 메뉴 기여점 (내장 Git 확장 연동) |
| 원격 편집 적용(손) | `workspace.applyEdit(WorkspaceEdit)` |
| 데몬 기동 및 바이너리 수신 | Node.js `child_process` + `https` 모듈 |

### 플랫폼 차이 및 조정 사항

- **콘솔 출력 질의 인터페이스.** JetBrains는 Run 콘솔 도구창에 직접 우클릭 컨텍스트 메뉴를 등록할 수 있다. 반면 VS Code의 통합 터미널은 xterm.js 기반으로 렌더링되므로 선택 영역 텍스트만 추출 가능하다(`terminal.selection`). 따라서 실행 콘솔 직접 질의 대신 **문제(Problems) 패널과의 연계**(`languages.registerCodeActionsProvider` + 진단 정보 연동)를 기본 사용자 경험으로 설정하는 것이 플랫폼 철학에 부합한다.
- **원격 개발 및 웹 환경(Remote / Web).** VS Code는 Remote SSH, Dev Containers, GitHub Codespaces, 웹 브라우저(`vscode.dev`) 등 다양한 환경에서 구동된다. 원격 SSH/컨테이너 환경의 경우 확장이 원격 호스트에서 실행되므로 로컬 Unix 소켓 통신 모델과 완벽히 합치한다(데몬 또한 원격 호스트에 상주함). 단, `vscode.dev`와 같은 순수 브라우저 웹 환경에서는 로컬 OS 프로세스를 기동할 수 없으므로, **기능 비활성화 상태를 명확히 고지**해야 한다.

## 5. Visual Studio 세부 구현 분석

> ⚠ **과거 VSSDK 분석 참조 이력 (2026-09-09):**
> 본 절은 초기 분석 시점의 **전통적 VSSDK(VSIX + MEF)** 모델을 기준으로 작성된 내용이다. 이후 Microsoft가 신규 확장에 대해 Out-of-process 기반의 **`VisualStudio.Extensibility`** 모델을 권장함을 확인하였으며, 이에 따른 정식 재설계 규격은 [`clients/visualstudio/docs/DESIGN.ko.md`](../../clients/visualstudio/docs/DESIGN.ko.md)에 기술되어 있다. 본 절은 초기 기술 검토 배경 자료로 보존한다.

- **VSIX + MEF 컴포넌트 모델.** 에디터 텍스트 제어는 `IWpfTextViewCreationListener` 및 `ITaggerProvider` 인터페이스군을 구현하며, 도구 창은 WPF 기반 `ToolWindowPane`을 사용한다.
- **인라인 코드 완성 API의 파편화.** Visual Studio 2022는 IntelliCode 기반의 회색 텍스트 제안 기능을 포함하고 있으나, 서드파티 확장에 개방된 안정적인 공개 API 여부가 마이너 버전별로 상이하다. 따라서 대상 Visual Studio 버전을 사전에 엄격히 확정하고 실제 SDK 환경에서 동작 검증을 선행해야 한다.
- **인레이 힌트.** 선언적 전용 API의 부재로 인해 텍스트 태깅(Tagging) 및 Adornment 계층을 활용하여 수동 렌더링을 구현해야 하며, JetBrains 대비 구현 복잡도가 높다.
- **Windows 플랫폼 종속성.** Visual Studio for Mac은 2024년 공식 단종되었으므로 Windows OS 환경으로 한정된다.
- **Unix 도메인 소켓 지원.** Windows 10 Build 1803 이상에서는 AF_UNIX 소켓을 지원하며 .NET 표준 라이브러리 역시 `UnixDomainSocketEndPoint`를 제공한다. 기존 Office 애드인 클라이언트가 Windows 환경에서 해당 통신 방식을 실증 활용하고 있다. 단, `%APPDATA%` 하위 경로에서 발생하는 AF_UNIX 소켓 바인딩 타임아웃 결함을 회피하기 위해 `MAGI_SOCKET_DIR`를 외부 경로로 지정하는 구성이 필수적이다.

## 6. MATLAB — 플랫폼 제약 및 대안 분석

기술적 실측 분석 결과: **MATLAB 에디터는 JetBrains 수준의 심층 플러그인 확장을 허용하지 않는다.**

- MATLAB 내장 에디터는 **서드파티 인라인 완성, 인레이 힌트, 코드 액션 등록을 위한 공개 API를 전혀 제공하지 않는다.**
- 제공되는 공식 확장은 `matlab.desktop.editor` API로 제한된다 — 현재 활성화된 문서 객체 획득, 전체 텍스트 읽기 및 특정 위치 텍스트 삽입/치환만 지원한다. 따라서 **원격 편집 지시(손, `apply_edit`) 기능은 구현 가능**하나, 에디터 캔버스 내부에 시각적 요소를 실시간 오버레이하는 기능은 원천 불가능하다.
- 사용자 인터페이스는 에디터 도구창 내부가 아닌 **App Designer 기반 별도 독립 창** 또는 Java Swing 프레임으로 외부에 띄워야 한다.
- 백엔드 통신은 구현 가능하다: MATLAB은 `system` 명령을 통한 외부 바이너리 실행을 지원하며, Java 런타임을 내장하고 있어 소켓 및 HTTP 통신이 모두 원활히 동작한다. 배포 패키징은 공식 애드온 규격인 `.mltbx` 형식을 따른다.

결론적으로 MATLAB 환경에서 구현 가능한 범위는 **대화창 + 계획 계기판 + 문서 텍스트 치환(손)**으로 한정되며, 에디터 내부 실시간 기능(인라인 완성, 인레이 힌트, 거터 표식, 코드 액션)은 플랫폼 제약상 구현할 수 없다.

이에 따른 3가지 전략적 선택지:

1. **제한된 범위(대화 + 계획 + 텍스트 편집)로 독립 창 앱 개발**: MATLAB 전용 GUI 작업 환경을 장시간 유지하는 사용자층에게 유의미한 가치 제공.
2. **별도 개발 미진행**: 대다수의 엔지니어가 코드 작성은 VS Code(MATLAB 공식 확장 사용)에서 수행하고 실행/시뮬레이션만 MATLAB 콘솔에서 처리하므로, VS Code 확장만으로 사용자를 커버 가능.
3. **MATLAB을 클라이언트가 아닌 MCP 도구 서버로 통합**: magi 컴패니언이 MATLAB 런타임을 원격 제어할 수 있도록 MATLAB 측에 가벼운 MCP 서버를 구축하는 방안 (스크립트 실행, 작업공간 변수 검사, 그래프 렌더링 이미지 추출 등). 투입 공수 대비 가장 높은 엔지니어링 효용을 제공한다.

**권고 사항: 3번(MCP 도구화) 방안 채택.** 제한된 기능의 UI 플러그인을 개발하는 것보다, 코딩 에이전트가 MATLAB 시뮬레이션 환경을 직접 도구로 활용할 수 있도록 지원하는 것이 실제 사용자 워크플로에 훨씬 강력한 엔지니어링 가치를 제공한다.

| 단계 | 추진 과업 | 우선순위 및 추진 사유 |
|---|---|---|
| ✅ 1단계 | **VS Code 확장 개발 ((가) 독립 라이브러리 방식)** — 완료 ([clients/vscode](../../clients/vscode/README.md)) | JetBrains 기능과 1:1 대응되므로 두 플랫폼 간의 실질적인 공통 추상화 영역을 정밀 식별할 수 있음 |
| 2단계 | 1단계에서 도출된 공통 로직을 **`magi ide-bridge`** 서브커맨드로 일원화 | 2개 구현체를 확보한 후 도출된 8가지 공통 로직을 코어 바이너리로 추출 — [VS 설계 §3](../../clients/visualstudio/docs/DESIGN.ko.md) |
| 3단계 | **Visual Studio 확장 개발 (브리지 기반 경량 연동)** | 에디터 UI 계층만 C#으로 신규 작성. 설계 수립 완료 ([clients/visualstudio](../../clients/visualstudio/README.md)), **Windows 전용 환경에서 빌드 수행** |
| 4단계 | MATLAB 연동 방안 확정 (MCP 서버화 검토) | 사용자 요구사항 최종 확정 후 추진 |

**모든 개발 단계의 필수 품질 게이트**: 신규 에디터 클라이언트는 반드시 `WireConformanceTest` 수준의 자동화 일치성 테스트를 동반해야 한다 — 데몬이 전송하는 JSON 필드 명칭을 **Go 코어 소스 코드에서 직접 정적 파싱**하여 클라이언트의 모델 정의와 상호 대조하고, 매핑 누락 발생 시 빌드를 실패시켜 프로토콜 드리프트를 원천 차단한다.

## 8. 본 문서의 분석 한계 및 잔여 과제

- **Visual Studio 공식 인라인 완성 API 사양.** Visual Studio 신규 확장 모델(`VisualStudio.Extensibility`)의 공식 확장점 명세에서도 서드파티 인라인 완성 API의 안정성이 명확히 확인되지 않았으며, 실제 SDK 런타임 검증이 필요하다 ([VS 설계 §2](../../clients/visualstudio/docs/DESIGN.ko.md)).
- **VS Code 확장 마켓플레이스 배포 프로세스** (게시자 계정 등록, 확장 서명 절차, VS Marketplace 및 Open VSX 이원화 관리 규약).
- **MATLAB 애드온 공식 배포 요건** (`.mltbx` 패키지 서명 및 MathWorks File Exchange 등록 정책).
- **플랫폼별 실제 코드 라인 수 산정.** 현행 JetBrains 플러그인의 9,778라인을 기준으로 타 언어 재작성 시의 구체적 분량은 실제 구현 과정에서 실측 평가되어야 한다.

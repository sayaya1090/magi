# 편집기 클라이언트 셋 — VS Code · Visual Studio · MATLAB (설계 제안)

[↑ 클라이언트 개요](../CLIENTS.ko.md) · [젯브레인 실물](../../clients/jetbrains/README.md)

> **상태: 제안.** 아직 아무것도 안 만들었다. 구현 전에 무엇을 옮길 수 있고 무엇이 못 오는지
> 먼저 재라는 사용자 지시(2026-09-08)로 쓴다.
>
> 요청은 「젯브레인에 구현된 기능을 다 넣어서」였다. 이 문서의 절반은 **다 넣을 수 있는 것**을
> 적고, 나머지 절반은 **못 넣는 것과 그 이유**를 적는다. 뒤쪽이 더 중요하다 — 셋 중 하나는
> 지금 젯브레인이 하는 일의 상당 부분을 그 편집기가 애초에 허락하지 않는다.

## 1. 무엇을 옮기는 것인가 — 젯브레인 실물 전수

플러그인은 두 층이다. 이 갈림이 이 문서 전체의 뼈대다.

| | 줄 수 | 무엇 |
|---|---|---|
| `core` (순수 코틀린) | 3,687 | 소켓 프로토콜(`DaemonClient`·`SocketPath`·`HandServer`), 전사 조립, 마크다운, 색, 승인 모드, 릴리스 고르기, 재시도 예산… IDE 를 하나도 모른다 |
| `intellij` (IDE 에 붙는 층) | 6,091 | 도구창 둘, 액션 여섯, 인텐션, 인라인 완성, 인레이, 상태 표시줄, 설정 화면, 편집기 표식… |

**옮길 때 `core` 는 못 가져간다.** JVM 코틀린이고, VS Code 는 TypeScript, Visual Studio 는
C#/.NET, MATLAB 은 MATLAB 이다. 그러니 이식이 아니라 **재작성**이고, 재작성의 분량은 위 표의
합(9,778)이 아니라 **두 층 다**이다. 다만 `core` 쪽은 옮길 대상이 뚜렷하다 — 계약이
[`docs/CLIENTS`](../CLIENTS.ko.md)에 정본으로 적혀 있고, 「새 클라이언트가 걷는 길」 네 걸음이
그대로 명세다(발견 → 악수 → 능력 읽기 → 문 두드리기).

### 기능 전수 (젯브레인이 지금 하는 것)

| 기능 | 무엇 | 이 기능이 요구하는 편집기 능력 |
|---|---|---|
| 대화 도구창(하단) | 컴패니언과 말하기, 승인 답하기, 전사 렌더 | 커스텀 패널 + 웹뷰나 네이티브 위젯 |
| 계획/계기판(우측) | 계획·컨텍스트·잡·예약 | 커스텀 패널 둘째 자리 |

| 타이핑 중 훑어보기 | 손 멈추면 버퍼를 읽고 지적 | 편집기 텍스트 변경 이벤트 |
| 훑어본 말 인레이 | 줄 끝 회색 글씨 | **인레이 힌트 API** |
| 훑어보기 띠 | 편집기 위 알림 띠 | 편집기 상단 배너 |
| 편집 표식 | 컴패니언이 고친 줄을 화면에 | 거터/데코레이션 |
| Alt+Enter 「물어보기」 | 커서 자리에서 바로 묻기 | **코드 액션/퀵픽스 API** |
| 커밋 초안 | 커밋 메시지 칸의 단추 | VCS UI 확장 지점 |
| 콘솔 출력 물어보기 | 스택트레이스·빌드 에러 자리 | 실행 콘솔 컨텍스트 메뉴 |
| 대화에 첨부 | 선택 영역/파일을 참조로 | 편집기·프로젝트뷰 컨텍스트 메뉴 |

## 2. 셋의 실현 가능성 — 결론부터

| | 대화·계획판 | 인라인 완성 | 인레이 | 코드 액션 | 손(편집 적용) | 판정 |
|---|---|---|---|---|---|---|
| **VS Code** | ✓ 웹뷰 | ✓ `InlineCompletionItemProvider` | ✓ `InlayHintsProvider` | ✓ `CodeActionProvider` | ✓ `WorkspaceEdit` | **전부 가능** |
| **Visual Studio** | ✓ 도구창(WPF) | △ 버전에 갈림 | △ 태그/어도너먼트로 손수 | ✓ 라이트 벌브 | ✓ 텍스트 버퍼 | **대체로 가능, 손이 많이 감** |
| **MATLAB** | △ 별도 창(App) | ✗ | ✗ | ✗ | △ 문서 텍스트 치환 | **부분만** |

셋을 한 문단으로:

- **VS Code 는 젯브레인과 거의 1:1 이다.** 위 표의 모든 칸에 대응하는 확장 API 가 있고, 대부분
  젯브레인 것보다 단순하다. 여기서 막히는 것은 API 가 아니라 우리 쪽 재작성 분량이다.
- **Visual Studio 는 된다. 다만 값이 비싸다.** VSIX + MEF + WPF 이고, 편집기 확장(태그·어도너먼트)은
  VS Code 의 선언적 API 보다 손이 많이 간다. 그리고 **VS for Mac 은 없어졌다** — 윈도우 전용이다.
- **MATLAB 은 「플러그인」이라는 것이 이 뜻이 아니다.** 아래 §5 에서 따로 적는다.

## 3. 공통 뼈대 — 세 번 쓰지 않으려면

셋을 각각 처음부터 쓰면 소켓 프로토콜·전사 조립·승인 어휘가 **네 벌**(젯브레인 포함)이 된다.
같은 사실이 네 군데 적히면 그중 하나는 갈라진다 — 이 저장소가 오늘만 두 번 겪은 모양이다
(`firstLine` 이 네 패키지, `oneLine` 이 네 패키지).

갈래는 둘이다.

### (가) 언어마다 클라이언트 라이브러리를 하나씩

`core` 에 해당하는 것을 TypeScript 와 C# 으로 한 벌씩 쓰고, 그 위에 편집기 층을 얹는다.
젯브레인이 이미 그 모양이라 **구조는 검증돼 있다**. 대신 프로토콜이 바뀌면 세 벌을 고쳐야 한다.

이 저장소에는 그 드리프트를 잡는 선례가 있다: `WireConformanceTest` 는 **Go 소스를 읽어**
플러그인이 읽는 필드 이름이 데몬이 보내는 이름인지 대조하고, 짝을 너무 적게 찾으면 그것부터
실패한다. 새 클라이언트마다 같은 시험을 붙이는 것이 조건이다 — 안 그러면
`ignoreUnknownKeys` 류가 어긋난 필드를 예외가 아니라 **기본값**으로 만들고, 화면은 「없다」고
말한 뒤 아무것도 실패하지 않는다.

### (나) 얇은 심(shim) 하나 — `magi ide-bridge`

편집기 쪽은 **stdio 로 JSON 을 주고받는 얇은 층**만 쓰고, 프로토콜·조립·승인은 전부 코어
바이너리가 한다. 새 편집기 하나가 늘 때 드는 값이 (가)보다 훨씬 작다.

값: 클라이언트가 이미 코어 바이너리를 받아 두고 있다(§1 표 마지막에서 두 번째 줄) — 그러니
프로세스를 하나 더 띄우는 것이 새 요구가 아니다.

비용: 편집기와 코어 사이에 층이 하나 더 생기고, 그 층의 계약이 또 하나의 정본이 된다.
`docs/CLIENTS` 가 이미 「새 문 원칙 5」를 세워 둔 자리라 거기에 얹어야 한다.

**권고: (나) 를 기본으로 삼되, VS Code 만 (가) 로 먼저 만든다.** 이유는 §6.

## 4. VS Code

### 대응이 뚜렷한 것

| 젯브레인 | VS Code |
|---|---|
| 도구창 둘 | `WebviewViewProvider` 둘 (`activitybar`/`panel`) |
| 상태 표시줄 | `window.createStatusBarItem` |
| 설정 화면 | `contributes.configuration` — 별도 화면을 안 짜도 된다 |
| 인라인 완성 | `languages.registerInlineCompletionItemProvider` |
| 인레이 | `languages.registerInlayHintsProvider` |
| 훑어보기 띠 | `window.showInformationMessage` 또는 편집기 데코레이션 |
| 편집 표식 | `TextEditorDecorationType` |
| Alt+Enter | `languages.registerCodeActionsProvider` |
| 커밋 초안 | `scm/inputBox` 메뉴 기여 — 내장 Git 확장이 그 자리를 연다 |
| 손(`apply_edit`) | `workspace.applyEdit(WorkspaceEdit)` |
| 데몬 기동·코어 받기 | `child_process` + `https` |

### 갈리는 것

- **콘솔 출력 물어보기.** 젯브레인은 Run 콘솔에 컨텍스트 메뉴를 단다. VS Code 의 터미널은
  xterm 이라 선택 영역만 얻을 수 있다(`terminal.selection`). 「스택트레이스 자리에서 바로」는
  약해지고, 대신 **문제 패널**(`languages.registerCodeActionsProvider` + 진단)이 더 자연스러운
  자리다. 같은 기능을 그 편집기가 이미 가진 자리로 옮기는 것이지, 흉내 내는 것이 아니다.
- **원격/웹.** VS Code 는 원격 SSH·Codespaces·web 에서 돈다. 그때 확장은 **원격 쪽**에서 돌고
  유닉스 소켓도 그쪽 것이다 — 우리 모델과 어긋나지 않는다(데몬도 그 기계에 있다). 다만
  `vscode.dev`(브라우저 전용)에서는 프로세스를 못 띄우므로 **기능을 끄고 그렇게 말해야 한다.**
  「모름을 없음으로 읽지 않는다」는 이 저장소의 규칙이 여기에도 걸린다.

## 5. Visual Studio

> ⚠ **이 절은 낡았다**(2026-09-09). 아래는 **VSSDK(VSIX + MEF)** 를 전제로 쓴 것인데, 그 뒤에
> 확장 모델이 셋이고 마이크로소프트가 새 확장에 **`VisualStudio.Extensibility`** 를 권한다는
> 것을 읽었다. 그 모델은 .NET 을 쓰고, IDE 밖에서 돌고, WPF 대신 Remote UI 로 그린다 —
> 아래 「WPF 로 손수」라는 판단이 거기서 달라진다. 지금 설계는
> [`clients/visualstudio/docs/DESIGN.ko.md`](../../clients/visualstudio/docs/DESIGN.ko.md) 다.
> 이 절은 **그때의 근거로** 남긴다.

- **VSIX + MEF.** 편집기 확장은 `IWpfTextViewCreationListener`·`ITaggerProvider` 계열이고,
  도구창은 WPF `ToolWindowPane` 이다.
- **인라인 완성**은 버전에 갈린다. VS 2022 는 IntelliCode 의 회색 이어쓰기가 있지만 서드파티에
  열린 안정 API 인지가 판마다 다르다. **여기는 짐작하지 말고, 대상 VS 판을 정한 뒤 그 판의
  SDK 로 실물을 한 번 띄워 보고 적어야 한다.** 이 문서는 그것을 안 재고 썼다.
- **인레이**는 선언적 API 대신 태그/어도너먼트로 손수 그린다. 되지만 젯브레인보다 코드가 는다.
- **윈도우 전용.** VS for Mac 은 2024 에 단종됐다. macOS 사용자는 VS Code 쪽으로 간다.
- 유닉스 소켓: 윈도우 10 1803+ 는 AF_UNIX 를 지원하고 .NET 도 `UnixDomainSocketEndPoint` 를
  준다. 우리 오피스 클라이언트가 이미 윈도우에서 그 길을 쓰고 있다 — **다만 `%APPDATA%` 아래
  AF_UNIX 가 이상하게 구는 사정을 실측으로 겪었다**(오피스 헬퍼의 붙기 타임아웃). 그 함정을
  물려받는다.

## 6. MATLAB — 「플러그인」이 이 뜻이 아니다

정직하게 적는다. **MATLAB 은 위 표의 대부분을 허락하지 않는다.**

- MATLAB 편집기에는 **서드파티 인라인 완성·인레이 힌트·코드 액션 API 가 없다.** VS Code 와
  Visual Studio 가 여는 그 확장 지점이 애초에 없다.
- 있는 것은 `matlab.desktop.editor` 다 — 열린 문서를 얻고, 텍스트를 읽고, 넣을 수 있다. 그래서
  **손(`apply_edit`)은 된다.** 편집기 안에 무엇을 그리는 일이 안 되는 것이다.
- 화면은 **App Designer 앱**이나 별도 창으로 띄운다. 즉 「편집기에 붙은 패널」이 아니라
  **옆에 뜬 창**이다.
- 전송은 문제없다: MATLAB 은 외부 프로세스를 띄우고(`system`), Java 를 그대로 부를 수 있어
  소켓과 HTTP 둘 다 닿는다. 애드온은 `.mltbx` 로 포장한다.

그래서 MATLAB 에서 만들 수 있는 것은 **대화 + 계획판 + 손**이고, 편집기 안의 것(완성·인레이·
표식·Alt+Enter)은 **못 만든다**. 「젯브레인 기능을 다 넣어서」는 MATLAB 에서는 성립하지 않는다.

판단이 필요한 자리다:

1. **부분만 만든다** — 대화·계획·손. 쓸모는 있다(MATLAB 사용자는 대개 한 파일을 오래 붙든다).
2. **안 만든다** — MATLAB 사용자는 코드를 VS Code 에서 쓰고 MATLAB 은 돌리는 데만 쓰는 경우가
   많다. 그러면 VS Code 확장이 이미 그 사람을 덮는다.
3. **MCP 로 끝낸다** — MATLAB 을 클라이언트가 아니라 **도구**로 본다. 코어가 이미 MCP 를
   말하므로, MATLAB 쪽에 작은 MCP 서버를 두면 컴패니언이 MATLAB 을 부린다(스크립트 실행,
   변수 읽기, 그림 얻기). 이쪽이 분량 대비 값이 가장 크다.

**권고: 3 번.** 2 번을 각오하고 1 번을 만드는 것보다, MATLAB 을 부릴 수 있게 하는 편이
「MATLAB 을 쓰는 사람」에게 더 준다. 다만 이것은 사용자가 정할 일이다 — 요청은 「플러그인」이었고
이 권고는 그 요청을 바꾸자는 제안이다.

## 7. 순서와 값

| 걸음 | 무엇 | 왜 이 순서 |
|---|---|---|
| ✅1 | **VS Code, (가) 방식으로** — 섰다([clients/vscode](../../clients/vscode/README.md)) | 대응이 1:1 이라 「무엇이 진짜 공통인지」가 여기서 드러난다. 심을 먼저 설계하면 젯브레인 하나만 보고 지은 계약이 된다 |
| 2 | 1 에서 드러난 공통을 **`magi ide-bridge`** 로 뽑는다 | 두 벌을 보고 나서 뽑는 공통이 한 벌 보고 뽑은 것보다 낫다. **두 벌째 설계가 그 공통을 여덟으로 셌다** — [VS 설계 §3](../../clients/visualstudio/docs/DESIGN.ko.md) |
| 3 | **Visual Studio**, 심 위에 | 편집기 층만 새로 쓴다. 설계는 섰고 ([clients/visualstudio](../../clients/visualstudio/README.md)) **짓는 것은 Windows 기계에서** |
| 4 | MATLAB 은 §6 의 판단 뒤에 | |

**각 걸음마다 조건 하나**: 새 클라이언트는 `WireConformanceTest` 에 해당하는 시험을 함께
가져온다 — 데몬이 보내는 필드 이름을 **Go 소스에서 읽어** 대조하고, 짝을 너무 적게 찾으면
그것부터 실패하는 그 시험이다. 이것 없이 늘리면 클라이언트 수만큼 조용한 드리프트가 는다.

## 8. 이 문서가 재지 않은 것

- **Visual Studio 의 인라인 완성 API.** 판마다 다르다고만 적었다. 실물 SDK 로 안 띄워 봤다.
  (2026-09-09: 새 모델의 공식 확장점 목록에도 **안 보인다**. 여전히 안 재봤다는 뜻이고, [VS 설계 §2](../../clients/visualstudio/docs/DESIGN.ko.md) 의 물음표 넷 중 하나다.)
- **VS Code 확장 마켓 배포 절차**(퍼블리셔·서명)와 **VS Marketplace/OpenVSX 갈림.**
- **MATLAB 애드온 배포**(`.mltbx` 서명·MathWorks File Exchange 규약).
- 셋 각각의 **분량 추정.** 젯브레인이 9,778 줄이라는 것만 재 두었고, 그것이 다른 언어에서
  몇 줄이 되는지는 짐작이라 안 적는다.

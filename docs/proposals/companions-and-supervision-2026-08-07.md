# 제안: 컴패니언과 감독 — 사람이 무엇을 하고, 화면이 무엇을 해야 하는가

상태: 제안(uncommitted). 브랜치 `engine-ui-split`.
**측정으로 확인한 것과 판단을 구분해 표시한다.** 측정한 것에는 경로와 수치를 붙였다.

> 2026-08-07 논의의 기록이다. 결론만이 아니라 **내가 틀렸던 지점과 그것이 뒤집힌 근거**도
> 남긴다 — 뒤집힌 이유가 다음 결정의 재료이기 때문이다.
> 앞선 문서 [distributed-magi-2026-08-06](distributed-magi-2026-08-06.md)이 프로세스 분리와
> UI 분리를 다뤘다. 이 문서는 그 위에 **누가 무엇을 하는가**를 얹는다.

---

## 0. 한 줄

**컴패니언**이 태스크를 수행하고, **사람은 결과를 책임진다.** 사람의 시간은 감시가 아니라
**개입 한 번을 영구적인 규칙으로 바꾸는 데** 쓰여야 하고, 화면은 그 일을 하도록 만들어진다.

```
사람 1명  ─감독→  컴패니언 N개
                   각자 자기 워크스페이스·자기 기록·자기 프로젝트 지식
                   안쪽 게이트(카운슬)가 "이 턴이 끝났나"를 판정
                   바깥 게이트(사람)가 "방향이 맞나, 되돌릴 수 없나"를 판정
```

## 1. 용어

| 말 | 뜻 | 코드에서 |
|---|---|---|
| **컴패니언** | magi 하나가 워크스페이스 하나에 묶여 도는 환경 | 데몬 하나 = 함대 테이블의 한 행 |
| **감독자** | 그 컴패니언들의 결과를 책임지는 사람 | (아직 없음 — §6) |
| 에이전트·카운슬·서브에이전트 | 컴패니언 **안쪽**의 구조 | `AgentSpec`, council, `magi.spawn` |

컴패니언 안에서 카운슬 3인이 돌고 서브에이전트가 갈라지므로 엄밀히 단일 에이전트는 아니다.
그러나 **밖에서 보면 하나의 워커**이고, 감독의 단위는 그 바깥 면이다.

★**용어를 안쪽까지 밀지 않는다.** `AgentSpec`(29곳), `agent-groups`(14곳)는 이미 다른 층의
개념이다. 컴패니언은 **위층에 새로 붙는 이름**이지 개명이 아니다 — 그래서 비용이 거의 없다.

### 왜 "에이전트"가 아니라 "컴패니언"인가

사내 배포에서 "에이전트"는 **감시 소프트웨어의 어휘**이기도 하다(EDR 에이전트, 자산관리
에이전트). 직원 PC에 설치되는 것에 그 단어를 쓰면 첫인상이 "회사가 내 PC에 심는 것"이 된다.
컴패니언은 소유 방향이 반대로 읽힌다 — **내게 배정된 것**.

다만 이름이 부드럽다고 사실이 바뀌지는 않는다. 우리가 만드는 콘솔은 **남의 컴패니언을 들여다보고
중단시킬 수 있는 화면**이다. 그 권한을 누가 갖는지는 §8에서 정해야 하고, 정하지 않으면
기본값(전원이 전원을 봄)이 결정이 된다.

## 2. 격리 — 무엇이 왜 갈라지나 (측정)

컴패니언이 나뉘어야 하는 이유는 보안이 아니라 **컨텍스트 위생**이다. 그리고 그 경계는
**이미 파일 배치가 긋고 있다**:

| 무엇 | 어디 | 컴패니언 사이 |
|---|---|---|
| 대화 기록 | `<data>/projects/<워크스페이스별>/*.jsonl` | **안 섞임** (워크스페이스로 파티션) |
| 프로젝트 지식 | `<워크스페이스>/.magi/experience` | **안 섞임** (레포 안, 팀과 공유) |
| 일하는 방식 | `<config>/experience` (global 층) | **섞임 — 의도적으로** |
| 모델·규칙·자격증명 | `<config>/config.toml`, `plugin-data` | 섞임 |

경험 스토어는 이미 2층이고(`internal/adapter/experience/layered`), 쓰기는 `Scope`로
라우팅되며 **기본이 project**, 조회는 두 층을 병합한다. 즉 지금 상태로도
**"프로젝트 사실은 안 섞이고, 일하는 방식은 따라온다"**가 성립한다. 새 기전이 필요 없고,
남은 일은 **그 경계를 보이게 하고 통치하는 것**이다.

### 격리의 강도를 과장하지 않는다

지금은 **이름공간 격리이지 강제 격리가 아니다.** 같은 OS 사용자로 도는 컴패니언 둘은 서로의
스토어를 읽을 수 있다 — 소켓 `0600`은 *다른 사용자*를 막지, 같은 사용자의 다른 컴패니언을
막지 않는다.

컨텍스트 위생에는 이걸로 충분하다: 오염은 파일을 읽을 수 있어서가 아니라 **조회가 어느 층을
향하느냐**로 생기고, 그건 갈라져 있다. 하지만 "직원 PC"라는 말이 붙으면 누군가는 강제 격리로
읽는다. 문서에 못 박는다:

> **컴패니언 격리 = 컨텍스트 경계.** 실행 격리(한 컴패니언의 bash가 다른 컴패니언의 파일에
> 닿지 못하게)가 필요하면 **OS 사용자 분리나 컨테이너**가 필요하고, magi는 그것을 주지 않는다.

## 3. 사람의 역할

### 조련사는 절반만 맞다

컴패니언이 아무리 좋아져도 사람이 **구조적으로** 대체 불가능한 것:

1. **무엇이 중요한가** — 이번 주에 이게 저것보다 먼저인 이유는 코드베이스 안에 없다.
2. **되돌릴 수 없는 것에 대한 책임** — 컴패니언은 위험을 *추정*할 수 있어도 **결과를 짊어질 수
   없다.** 책임은 위임되지 않는다.
3. **바깥의 사실** — 고객이 실제로 한 말, 회의에서 정해진 것, 정치적으로 불가능한 것.
4. **좋음의 기준** — 이 조직에서 무엇이 잘한 것인지.

조련은 4번의 일부다. 그래서 역할의 이름은 **결과를 책임지는 사람**이고, 감독과 조련은 그
책임을 감당하는 방법이다. 이 정의가 실용적 규칙 하나를 준다:

> **당신이 답변해야 할 일이면 올라와야 하고, 아니면 올라오면 안 된다.**

### 조련이 경제학으로는 정확하다

한 사람이 컴패니언 10개를 드는 유일한 방법은 **개입 한 번이 미래의 개입을 영구히 줄이는 것**
이다. 그러지 않으면 개입 횟수가 컴패니언 수에 비례하고 감독 범위는 2~3에서 멈춘다.

굳히는 기전은 이미 있다: 권한의 `always`/`persist`(세션 규칙 / 프로젝트 allow 규칙),
경험 스토어의 스킬, `Scope`로 정하는 적용 범위, 그리고 매 스텝이 사람에게 오지 않게 하는 카운슬.

### 균형추 — 일을 아예 안 하는 조련사는 기준을 잃는다

직접 하지 않는 영역의 산출물은 몇 달 뒤 판단할 수 없게 되고, 감독은 통과 의례가 된다.
증상은 측정 가능하다: **3초 안에 allow로 눌린 비율**. 인간은 감시 과업에 약하고, "혹시 모르니
물어보자"를 늘리면 안전이 아니라 고무도장이 늘어난다. **안전은 질문 수가 아니라 질문의
정보량에서 나온다.**

역할 설계에 **사람이 직접 하는 몫**을 남긴다: 취향이 걸린 것, 되돌릴 수 없는 것, 새로운 것.

## 4. 감독자의 하루 (인터페이스가 지원해야 하는 것)

| 시점 | 사람이 하는 일 | 화면이 답해야 하는 질문 |
|---|---|---|
| 아침 | 밤새 무엇이 끝났고 무엇이 막혔나 | 지금 나를 필요로 하는 게 있나? 몇 개인가? |
| 낮 | 대기 중인 것에 답한다 | 무엇을 결정하라는 건가? 근거는? |
| 개입 | 잘못된 길이면 방향을 돌리거나 멈춘다 | 지금 무엇을 하는 중인가? 어떻게 멈추나? |
| 저녁 | 오늘의 교정을 규칙·스킬로 승격한다 | **오늘 무엇을 몇 번 고쳤나?** ← 지금 없음 |
| 결과 | 내일의 개입이 줄어야 한다 | 개입 빈도가 줄고 있나? |

## 5. 인터페이스

원칙 셋:

- **예외만 올라온다**(management by exception). 정상은 세지 않아도 되게, 이상만 눈에 띄게.
- **행동이 관찰과 같은 자리에 있다**. 멈추려고 상세로 들어가야 한다면 그 사이에 30초가 탄다.
- **어디에 있는지 항상 보인다**. 돌아가는 길이 곧 위치를 말하는 요소여야 한다.

쿠버네티스 콘솔의 골격을 가져온다(`kubectl get pods`: 리소스 한 줄, 고정 열, 상태 단어, 행
액션, 브레드크럼 상세). 스무 개를 한눈에 보는 문제는 이미 그 동네가 푼 문제다.

### 5.1 컴패니언 목록 (첫 화면)

```
magi / fleet                                   ● 5 companions · 1 waiting on you
────────────────────────────────────────────────────────────────────────────────
  ● 1 WAITING    ● 2 WORKING    ● 1 IDLE    ● 1 GONE        ← 세면서 읽지 않도록
────────────────────────────────────────────────────────────────────────────────
STATUS    COMPANION        DOING                    STEPS  AGE   HOST      
● waiting api-gateway      ⏸ bash: rm -rf build         7   2m   mini·…12   open › stop
          /work/api-gateway   [allow] [always] [deny]
● working docs-site        rewrite the getting-…       12   4s   mini·…12   open › stop
● idle    scratch          "council gate: 3 members"    —   7m   mini·…12   open ›
● gone    old-experiment   make the fuzzer find…       23   3h   mini·…12   open ›
```

- **정렬은 곤란한 순서**: waiting → working → idle → gone. 읽어야 문제를 찾는 목록은 문제를
  숨기는 목록이다.
- **상태는 점 + 단어**. 색만으로 상태를 나르지 않는다(색각·흑백 인쇄·강제 색상 모드).
- **답은 질문 옆에서**. 권한 버튼이 그 행 안에 있다 — 상세로 들어가지 않아도 된다.
- **중단도 목록에서**. 멈추고 싶은 행은 이미 보고 있는 행이다.
- **호스트/주소** 열: ssh로 세 대를 포워딩해 세 탭을 열어두면 그것만이 셋을 구분한다.
- 요약 타일은 **필터**이기도 하다(WAITING만 보기).

### 5.2 컴패니언 상세

```
magi / fleet / api-gateway                                            ● live
────────────────────────────────────────────────────────────────────────────
STATUS     WORKSPACE          HOST            STEPS  LAST ACTIVITY  SESSION
waiting    /work/api-gateway  mini · …0.12    7      2m             s_8f2…
────────────────────────────────────────────────────────────────────────────
  [트랜스크립트]
────────────────────────────────────────────────────────────────────────────
  ⏸ bash: rm -rf build && make release  (destructive command detected)
      [allow] [always] [deny]
  ┌──────────────────────────────────────────────────────────────┐
  │ 여기서 다른 일을 시킬 수도 있다…                    [send] [stop] │
```

- 브레드크럼의 `fleet`이 **돌아가는 길이자 현재 위치의 표시**다.
- 헤더 줄이 "이게 무엇인지"를 말한다 — 트랜스크립트만으로는 알 수 없다.
- 프롬프트 바는 컴포저 **위**에 앉는다: 답하는 것과 방향을 바꾸는 것이 둘 다 가능해야 한다.

### 5.3 교정 (CORRECTIONS) ← 다음에 만들 것

**측정: magi는 "사람이 교정했다"를 따로 기록하지 않는다.** 스티어는 `prompt.submitted`
(actor=user)로 트랜스크립트에 섞여 사라지고, 새 지시와 교정이 같은 모양이다. 조련이 역할이라면
이건 재료가 없는 것이다.

교정을 일급으로 만든다:

```
magi / corrections                                     이번 주 12건 · 승격 3건
────────────────────────────────────────────────────────────────────────────
  4×  "테스트 돌리기 전에 끝났다고 하지 마"      api-gateway, docs-site      [규칙으로]
  3×  "그 파일은 건드리지 마"                    api-gateway                 [규칙으로]
  2×  "커밋 메시지에 이슈번호"                   전부                        [global 스킬로]
```

- **같은 교정의 반복이 승격 후보다.** 권한의 `always`가 하는 일을, 교정 전반으로 넓힌다.
- 승격 대상이 **project 층인지 global 층인지**를 사람이 고른다 — 그것이 컴패니언 경계를 넘는
  유일한 통로이므로 §7의 결론대로 **자동 승격은 하지 않는다.**

### 5.4 그다음 (순서와 이유)

| 순서 | 화면 | 왜 그 순서인가 |
|---|---|---|
| 1 | 컴패니언 목록·상세 | 감독의 최소 단위. 지금 만드는 중 |
| 2 | **교정** | 승격의 **재료**. 이것이 없으면 3번이 손으로 쓰는 메모장이 된다 |
| 3 | 스킬 | 승격의 **결과**, 그리고 층(project/global) 경계의 통치 화면 |
| 4 | 메모리·컨텍스트 | 무엇이 기억되고 무엇이 압축됐나 |
| 5 | MCP | 어떤 외부 도구가 붙어 있나 |
| 6 | 캐시 진단 | 프롬프트 캐시가 실제로 타는지 (★타당성 미확인 — §8) |

## 6. 지금 없는 것 (측정)

| 없는 것 | 근거 | 필요한 이유 |
|---|---|---|
| 교정의 기록 | `ActorUser` 프롬프트에 종류 구분 없음 | 5.3 전체가 여기 걸려 있다 |

| 컴패니언별 자격증명 | `plugin-data`·`config.toml`이 사람 단위 공유 | 고객사 프로젝트가 섞이면 틀리다 |

★앞선 문서에서 확인된 것은 여기 다시 쓰지 않는다: 다섯(+`status`+제어 넷)만 소켓을 건너고,
나머지는 붙는 쪽이 같은 로그에서 답한다.

## 7. 정한 것

1. **컴패니언 = 워크스페이스에 묶인 magi 하나** = 지금의 함대 행. 브레드크럼은 2단.
2. **global 층 승격은 사람이 승인한다.** 자동이면 프로젝트 A의 사실이 B로 새고, 조용히 일어나
   나중에 원인을 못 찾는다. 기본은 project 층(현재 그렇다).
3. **콘솔은 예외를 보여주고, 행동을 관찰과 같은 자리에 둔다.**
4. **컴패니언 격리는 컨텍스트 경계까지다.** 실행 격리는 OS의 일이라고 문서에 쓴다.
5. **교정이 스킬보다 먼저다.** 재료 없이 결과 화면을 만들면 손으로 쓰는 메모장이 된다.

## 8. 열린 질문

1. ~~**누가 누구의 컴패니언을 보는가.**~~ **정해짐: 우리가 구현하지 않는다.**
   접근 제어는 회사 계정 체계에 붙는 문제이고 회사마다 다르다. magi는 **자체 사용자 저장소도,
   역할 정의도 만들지 않는다** — 만들면 어느 회사와도 안 맞으면서 "우리도 권한이 있다"는
   착시만 준다. 대신 **가능하게 하는 환경**만 제공한다:

   - **데몬 소켓**: 파일 권한이 곧 경계이고, 유닉스 소켓은 피어의 uid/gid를 커널이 보증한다.
     같은 사용자냐 아니냐는 우리가 확인할 수 있고 그 이상은 OS의 일이다.
   - **magi-web**: 인증이 없고 루프백 전용이며 **그렇게 유지한다.** 회사의 SSO/리버스 프록시
     뒤에 두거나 `ssh -L`로 그 회사의 접근 통제를 그대로 쓴다. 우리가 로그인 화면을 만들면
     회사의 통제를 우회하는 두 번째 문이 된다.
   - **정책 훅**: 무엇을 누가 요청했는지가 한 자리(디스패치)를 지나므로, 회사가 자기 정책을
     끼울 지점은 있다. 우리가 정책의 *내용*을 정하지 않는다.

   ★이것은 git 자동설치·시크릿 전달을 거절한 것과 같은 판단이다 — 환경이 더 잘하는 일을
   흉내 내면, 안전한 줄 알게 만드는 것이 실제 위험이다.
2. **컴패니언끼리 무엇이 건너가는가.** 남의 머신에서 툴을 실행시키는 형태는 사내 RCE다.
   안전한 형태는 **작업을 요청하고 산출물(커밋 범위/PR)로 받는 것** — 그 기전은 이미 있다.
3. **캐시 진단이 가능한가.** 프롬프트 캐시 히트가 관측 가능한지 미확인. usage 이벤트가 캐시된
   토큰을 나르는지부터 재야 한다. **재기 전에는 화면에 약속하지 않는다.**
4. **감독 범위의 실측.** 컴패니언·시간당 개입 횟수와 "3초 안에 allow" 비율을 기록해야
   §3의 주장이 검증된다. 지금은 둘 다 안 센다.
5. ~~**컴패니언 하나에 워크스페이스 여럿을 허용할 것인가.**~~ **정해짐: 허용하지 않는다.**
   컴패니언 하나는 **워크스페이스 하나만** 본다. 여러 프로젝트에 참여하는 사람은 컴패니언을
   여러 개 갖는다. 하나가 여러 워크스페이스를 보면 에이전트끼리 작업 내용이 섞이고 관리가
   불가능해진다 — 컴패니언을 나눈 이유가 바로 그것이므로 그 안에서 다시 섞으면 의미가 없다.

   ★코드 변경은 없다: 데몬은 이미 시작한 디렉토리 하나에 묶인다(측정). 이 결정은 "멀티
   워크스페이스 컴패니언"을 **앞으로도 만들지 않겠다**는 뜻이고, 한 config 디렉토리 아래 여러
   데몬이 도는 것은 **한 사람의 여러 컴패니언**이지 하나의 컴패니언이 아니다.

## 9. 하지 않기로 한 것

- **자동 승격.** §7-2.
- **"혹시 모르니" 확인 늘리기.** 고무도장을 만든다. §3.
- **감시 지표.** 컴패니언별 처리량을 사람 평가에 쓰는 순간, 사람은 화면을 속이기 시작한다.
  콘솔의 숫자는 **감독을 돕는 것**이지 사람을 재는 것이 아니다.
  ※ 역할 **배치**가 맞았는지를 주기적으로 검토하는 것은 이것과 다른 이야기다 —
  [`companion-performance-2026-08-07.md`](companion-performance-2026-08-07.md). 그 문서도
  제안일 뿐이고, 재면 안 되는 것의 목록을 함께 들고 있다.
- **강제 격리를 magi가 구현하기.** 컨테이너와 OS 사용자가 이미 하는 일이고, 흉내 내면 안전한
  줄 알게 된다.
- **자체 인증·권한 체계.** §8-1. 회사 것에 붙을 자리만 남긴다.

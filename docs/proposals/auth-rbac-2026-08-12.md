# Who may open this console, and who may join this fleet

Status: **step 1 built** (the table, the gate, `auth.toml`); the rest is designed and not built. Follows
[`external-access-2026-08-12.md`](external-access-2026-08-12.md), whose open question — a proxy in
front (A) or authentication in magi (B) — the operator has answered: **B**.

Decisions already taken, so the rest of this document does not re-open them:

| | |
|---|---|
| Identity of PEOPLE | OIDC (GitHub / Google / a company issuer). magi never sees a password. |
| Authorization | **RBAC**: roles carry capabilities, people are given roles. |
| TLS | **magi terminates it** (`-tls-cert` / `-tls-key`). `-exposed` without them refuses to start. |
| Identity of COMPANIONS | a **per-daemon key**. Admitting one is trusting its fingerprint. |
| A companion before it is admitted | nothing. Not in the roster, not delegable, not reachable — the model does not know it exists. |
| Companion permissions | **not RBAC** — three states of admission. See §3. |
| Surfaces | every screen here exists in **both the TUI and the web console**. |

## The shape of it

Three things are being decided, and they are not the same thing:

1. **Is this person who they say they are** — OIDC answers it, and nothing in this repository has to
   be clever about it.
2. **What may this person do** — RBAC, ours, and the part worth designing carefully.
3. **Is this daemon one of ours** — a signature against an admitted key, and a queue for the ones
   nobody has decided about yet.

The audit record from the previous round already writes down who did what, and it grows a real
answer for "who" the moment 1 lands.

---

## 1. People: OIDC in, cookie after

```
/login              → provider (authorization code + PKCE, state in a short cookie)
/auth/callback      → exchange, read the verified email, look it up
                    → no assignment? 403 with "ask an operator", and a line in the audit
                    → assigned?    a session, and a redirect to where they were going
```

- **PKCE and `state`**, both, and the redirect target is validated against the configured base URL —
  an open redirect on a login page is how the whole thing gets handed to somebody else.
- **The session is an opaque id**, not a signed claim: a claim cannot be revoked, and revoking is
  half of why the operator wants this. It lives in `console-sessions.json` (0600, beside the audit),
  carries an expiry and a "last seen", and a logout or a revoke deletes it.
- **The cookie is httpOnly + Secure + SameSite=Lax**, and Secure is honest because magi is holding
  the certificate itself.
- **CSRF**: a per-session token on every state-changing request. `sameSiteOnly` stays — it is the
  cheap outer check — but it stops being sufficient the moment the attacker can be a *legitimate*
  user of some other origin.
- **Rate limit and lockout** on the callback path, counted per source and per email.
- **The TUI is not affected.** `magi --attach` speaks to a unix socket the operating system already
  protects by ownership. Adding a login there would be a second door with a worse lock. What the
  TUI gains here are the management screens, not a login.

## 2. RBAC

### Capabilities are read off the routes, not invented

A capability that does not correspond to something the console can do is a word in a config file.
So the list is derived from what exists:

| Capability | What it covers |
|---|---|
| `read` | the fleet, a transcript, history, search, the loop map, tools — everything that only looks |
| `answer` | answering a permission or a question, interrupting a turn |
| `prompt` | submitting a prompt, steering, dispatching, compacting, rewinding |
| `curate` | skills, remember/forget, the report format |
| `configure` | the model, the approval mode, cron |
| `admin` | people, roles, and admitting companions |
| `shell` | `/shell` — **not grantable while `-exposed`**, where it does not exist at all |

### Roles carry capabilities; people are given roles

Three come built in, because a fleet of one should not have to design a permission model before it
can log in. All three are editable; `admin` cannot be left with nobody in it.

```toml
# auth.toml — the global config directory, 0600. NOT config.toml: that one merges with a
# project's .magi/config.toml, and a repository must never be able to grant itself a role.

[roles.operator]
can = ["read", "answer", "prompt", "curate", "configure", "admin", "shell"]

[roles.responder]
can = ["read", "answer"]

[roles.viewer]
can = ["read"]

[people."kim@corp.com"]
role = "operator"

[people."lee@corp.com"]
role = "responder"
companions = ["docs", "palette"]   # empty or absent = every companion
```

### A scope is three checks, not one

The capability half of this is one table and one wrapper, and that holds. The SCOPE half does not,
and reading every route against it is what showed why. Routes fall into three shapes and only the
first is answerable at the front door:

| shape | routes | what has to happen |
|---|---|---|
| **names its subject** | `/events` `/transcript` `/plan` `/context` `/history` `/search` `/council` `/loop` `/handoffs` `/subagents` `/jobs` `/submit` `/answer` … | the wrapper checks `?d=` — this is what exists |
| **is a LIST** | `/fleet` `/interventions` `/push` | the wrapper has nothing to check. The ANSWER must be filtered, which means the function producing it takes "what may this person see" as an argument |
| **chooses its subject later** | `/dispatch` | checked again where the target is resolved, not only at the front door |

The list shape is the one that was missed and it is the worst of the three, because those routes
are exactly the ones that answer "what else is there". `/fleet` hands over every companion's name,
workspace path, host and current task; `/interventions` hands over what people have SAID to each of
them, verbatim, which is more sensitive than the list itself. `/push` is a third of the same: the
notifier wakes a subscriber for any companion that blocks, including ones they may not see.

`/skills` and `/console` are deliberately not in that group. The experience store is fleet-wide by
design, and the console's host and config directory are facts anybody with `read` may have.

### One gate, and it fails closed

The check is a wrapper in `routes()`, beside `sameSiteOnly` and `audited`, reading one table of
route → capability. **A route missing from that table is refused**, and a test walks `handlers()`
and fails when one has no entry. That is the whole reason to write it as a table: the next route
somebody adds cannot quietly default to "everyone", and the person adding it has to say what it is.

Scope (`companions`) is checked in the same place, against the companion the request names — the
`?d=` socket the audit record already writes down.

⚠ **Three defects in that sentence, found by reading the routes against it.** All three are in the
code today and all three make a scope weaker than it reads:

- **`/dispatch` decides its target AFTER the gate.** The route takes `to=<name>` in the body,
  resolves it against the whole fleet, and then rewrites `?d=` to the target it found
  (`dispatch.go`). So the gate checks the companion the caller NAMED in the query and the work goes
  to the one named in the body. Somebody scoped to `docs` can dispatch to `billing`. The scope has
  to be checked again once the target is resolved, which means the check cannot live only at the
  route's front door.
- **`/fleet` has no `?d=` at all**, so there is nothing for the gate to scope against and it
  answers with every companion: names, workspace paths, hosts, IPs, and what each is doing right
  now. The board reads the same list. A scope that hides nothing from the list it is read from is
  not a scope — the list has to be filtered by the same rule.
- **Scope is matched by NAME**, derived from the socket path, and two machines run companions with
  the same names. With `-peer`, `companions = ["docs"]` matches docs on every machine. The key has
  to be the peer and the socket together.

### The page hides what it cannot do — and that is not the check

`/me` answers with the person's capabilities and companion scope. The console uses it to leave out
the controls that would only produce a refusal — a composer for somebody who may not prompt is a
box that swallows what they typed. The server refuses regardless: hiding is courtesy, the gate is
security, and confusing the two is how a "read-only" console turns out to have been writable.

### The management screens

Same data, two surfaces, one file:

- **Web** — a `people` destination in the rail, `admin` only: the people (email, role, last seen,
  revoke), the roles (a capability per checkbox), and the companions waiting to join.
- **TUI** — `/people`, `/roles`, `/cluster`, built the way `/cron` was: a list, a toggle, an edit
  overlay, and a `cronPersister`-shaped writer for `auth.toml`.

Every change here is a line in the audit record. Granting somebody `admin` is the single most
consequential thing this console can do.

## 3. Companions: a key, and a queue

> ⚠ **Superseded in part.** What follows was the first design; walking it against the code turned up
> enough that the machine boundary became its own document —
> [`fleet-boundary-2026-08-12.md`](fleet-boundary-2026-08-12.md). It changes three things here: the
> gossip path is not the only way in (a relay reaches the whole protocol), `pending` IS propagated
> while decisions travel as signatures under an operator key, and a `watched` state sits between
> pending and admitted. Read that one for the companion half; this section stands as the reasoning
> that led to it.

### What is broken now

`LearnMembers` writes down whatever it is told. A member that arrives over the relay lands in
`cluster.json`, and from there into the roster the model is shown, the list it may delegate to, and
the ears it may speak into. Nothing approves it. That is the gap the operator named.

`-peer` and the local sockets are NOT that gap: a peer is a URL the operator typed, and a socket is
a file the operating system protects by ownership.

### The key

Each daemon generates an **ed25519 keypair on first start** (`id_ed25519`, 0600, in its config
directory) and publishes the public half in its record. Announcements are signed. A member whose
signature does not verify is not "unknown" — it is dropped, and the drop is recorded.

Approving is approving a **fingerprint**, which is what makes it worth anything: a name and a
hostname are strings anybody can send, and an approval bound to a string approves whoever says it
next.

### The queue

```
heard → pending   the operator sees it; nothing else does. Not in the roster the model reads,
                  not a delegation target, not an ear. The model does not know it exists.
      → watched   on the roster and delegable — I may hand IT work — but it may not hand ME any,
                  and may not speak into my ear.
      → admitted  everything: the roster, being handed work, the ear.
      → refused   remembered, so the same fingerprint does not queue again every thirty seconds.
```

`cluster.json` grows a state and a fingerprint. `Mine()` (this machine's own daemons, read from the
published records) is unaffected — a companion in your own config directory is already yours.

### Why three states and not roles

A person's job varies enough to be worth naming — viewer, responder, operator. A companion does
two things to me: it hands me work, and it speaks into my ear. A role system over two verbs is
ceremony, and this repository's own rule about capabilities applies to it — a capability with no
route behind it is a word in a config file.

The four-way split above is not four permissions either. Two of the lines are MY choice and not a
grant to them:

| | what it is |
|---|---|
| on the roster / the model is told it exists | mine — routing and display |
| I may delegate to it | mine |
| **it may hand me work** | **security** |
| **it may speak into my ear** | **security** |

The two that are security are one question — may this fingerprint start a turn in my workspace —
so `watched` is the state where the answer is no and everything else is yes. It has a concrete
case: a CI box you admitted in order to watch it, which must not queue work into your laptop.
Admission is `[admit] [watch] [refuse]`, three buttons, no role editor and no second config file.

### What a review of the above turned up

Six things, found by reading the design against the code rather than by imagining attackers. The
first three change it; the rest are written down so they are not discovered later as surprises.

1. **Each member record is signed by its OWN key, and relays forward the signature untouched.**
   Gossip is transitive: what mini sends me includes what mini heard about laptop. Signing the
   MESSAGE proves only "mini said this", so a compromised admitted peer could invent
   `billing@prod` and it would arrive in my queue indistinguishable from a real one. Per-record
   signatures are what stop trust being transitive.
2. **The signed blob carries a time, and stale ones are dropped.** Without it a captured record
   replays forever, which defeats the five-minute and one-hour decay that is the only thing
   retiring dead companions today.
3. **`Hand` and the ear check the caller's state.** Admission currently gates the roster,
   delegation and the ear — but `handover.Hand` checks nothing but that the request is non-empty
   (`cmd/magi/hand.go`), so an unadmitted machine with ssh access still queues work and still gets
   a side session. Until that check exists the admission screen decorates rather than protects,
   which is why it comes BEFORE the screens in the order below.
4. **A shared config directory would mean a shared key.** This repository already warns that two
   machines can share one (it is why "here or elsewhere" is decided by the record and not the
   hostname). Two daemons with one key are one fingerprint, so admitting either admits both. The
   key records the host it was made on and is regenerated when that no longer matches.
5. **Admission does not expire and can be withdrawn.** A certificate has a lifetime; a fingerprint
   in a file does not. There must be a way back to `refused`, and an admission unseen for long
   enough should decay to `pending` rather than stand forever.
6. **The queue is capped and the fingerprint is shown whole.** Anybody with ssh can fill the
   pending list otherwise, and a truncated fingerprint (`SHA256:9f2a…`) is a prefix somebody can
   grind. `magi --whoami` printing the local fingerprint is what makes an out-of-band comparison
   possible — without it, admission is trust-on-first-use with nothing to check against.

None of this removes the underlying assumption: **the transport is ssh**, and a daemon key protects
transitive trust, not the machine somebody has already logged into. That is the same place a
kubeadm bootstrap token sits.

### What a review of the SHIPPED half turned up

The people half is in the tree, so this pass read the routes rather than the design. Every handler
was sorted into the three shapes above and each shape checked at its own site. Found and fixed:

| Route | Shape | What it handed over |
|---|---|---|
| `/push` (the watcher) | neither — no request at all | A subscription recorded a browser, never a person, so the watcher told every phone about every companion. What the screens had stopped showing arrived in the pocket. |
| `/handoffs` | list | Asked without naming a companion: who asked whom, the question verbatim, and the answer. Both ends are checked now, because the row carries both. |
| `/mcp` (GET) | list | Every companion's servers — command line, arguments, the names of the variables they are handed. |
| `/skills` (GET) | list | The rules another team wrote for its own companion. |
| `/cron` (POST) | capability, not scope | `configure` bought a deferred `prompt`: a job is CreateSession + Submit on a timer. It asks for both now. |
| startup | — | An `auth.toml` with no `-user-header` started a console that refused every request, including the admin routes that would fix it. Refused at startup instead. |

Checked and found sound, so that the next pass does not re-derive them:

- **`/transcript`, `/loop`, `/council`** take a session id from the query and all three run it through
  `readable`, which bounds it to the companion's own workspace. A session id is not a way in.
- **`daemonEngine.Resume`** refuses a session that is not in its workspace, so moving a companion
  cannot point it at another one's log.
- **`?p=`** is caller-supplied and the gate scopes on it, but every handler that takes `?d=` also
  calls `forwarded` first, so naming a peer forwards the action there rather than acting locally
  under a qualified scope entry.
- **A POST to a read-only route** is refused: the table is consulted by method, and `mayWrite` has
  no entry for it.
- **The daemon socket is 0600 in a 0700 directory** and the published record is 0600, so the local
  boundary does not depend on any of this.
- **`proxy()` forwards no identity.** A cross-console action arrives at the far console unnamed and
  is recorded there unattributed — which is the justification for refusing `-exposed` together with
  `-peer`, now confirmed in code rather than assumed.

Still open, and not defects so much as edges the model does not reach: a **team** tier is named
rather than resolved from a companion, so `companions = [...]` does not narrow who may write to a
team's store; and `configure` remains console-wide, so somebody scoped to one companion can still
change settings that belong to the console itself.

### A second boundary the people model does not touch: the repository

Reading the routes turned up one axis that has nothing to do with who is logged in. A workspace is
a trust boundary too, and it was open — on a single-operator laptop, with no console involved.

| What a cloned repo carried | What it got | Now |
|---|---|---|
| `.magi/plugins/<name>/` | Lua, run at startup, with the permissions its own `plugin.toml` declared — and the bridge offers `exec`, `http`, `read_file`, `write_file`, `set_base_url` | Not scanned. Run it by naming it: `-plugins .magi/plugins`. What was skipped is printed |
| `permission = "allow"`, `sandbox = "full"`, `profile = "yolo"` | the approval gate and the confinement, off | Clamped: a project may tighten, never loosen, and a refusal says so |
| `allow`, `allow_domains` | commands that run unasked, domains the agent may reach | Not taken from a project at all |
| `[[hooks]]`, `[mcp.*]`, `[cron.*]`, `base_url` | `/bin/sh` on tool events, processes at daemon start, where prompts go | Still taken — the documented reason the file is committed — and named on startup |

The sandbox was never the answer for the first row and was not meant to be: it blocks `os` and `io`
so the BRIDGE can be the boundary, and the bridge is what a manifest asks for.

**What is still open**, and is the same missing piece in both directions: there is no per-workspace
trust decision. Hooks and tool servers are announced rather than approved, `.magi/skills` and
`.magi/experience` are read into prompts from whatever repo is open (instruction injection, bounded
by the approval gate this now protects), and the answer to all three is one prompt — "this
workspace wants to run things; allow?" — remembered per directory. That is the C1 item, widened.

## What lands, in order

Each step passes the gate on its own and leaves something usable behind.

1. ~~**`auth.toml` + the capability table + the gate**~~ — **done.** `internal/core/auth` is the
   decision (pure), `config.LoadAuth` reads the file from the global config directory only, and
   `clients/web/server/gate.go` is the wrapper: every GET needs `read`, every write needs what the table
   says, and a route in neither the table nor the read/public sets is REFUSED. A test walks
   `handlers()` and fails on any path nobody classified — it caught `/me` on its first run, which
   is the mechanism working before the feature it protects even exists. With nobody configured the
   console behaves exactly as it did.
2. **`/me` and the page's own hiding**, so the shape is visible before there is a login to test it
   with.
3. **OIDC + sessions + CSRF + lockout**, and `-exposed` starts requiring `-tls-cert`/`-tls-key`.
4. **The people and roles screens**, web then TUI.
5. **The daemon key**, published and used to sign each member record, with a time inside the
   signature and a regeneration when the recorded host stops matching.
6. **`Hand` and the ear refuse a caller that is not admitted.** Before any screen, because a screen
   in front of a check that does not exist is decoration.
7. **pending / watched / admitted / refused**, with the roster and delegation reading `watched` and
   `admitted`, and being handed work reading `admitted` alone.
8. **The admission screens**, web and TUI: three buttons, the whole fingerprint, and a line in the
   audit record for every decision.
9. **Docs** — `MANUAL`, `ARCHITECTURE`, `UI`, and both Korean mirrors.

## What I will not do

- Ship the login page before the table in step 1. A gate added after the routes exist is a gate
  with holes nobody enumerated.
- Let `auth.toml` be read from a project directory. A repository that can grant itself a role is a
  repository that owns the machine.
- Treat "the page hides it" as an answer to "may they do it".

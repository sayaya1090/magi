# IDE 가 내놓는 도구 — 코어 도구를 끄고 클라이언트 것을 넣는다 (제안)

[클라이언트 계약](../CLIENTS.ko.md) · [플러그인 API](../EXTENDING.ko.md) · [ide-bridge](../IDE_BRIDGE.ko.md) · [젯브레인](../../clients/jetbrains/README.md) · [VS Code](../../clients/vscode/README.md)

> **요청**(2026-09-09): 클라이언트가 **코어의 기존 도구를 끄고** 자기가 지원하는 **전용 도구를
> 주입**할 수 있게 한다. 그다음 **IDE 지원을 얹으면 더 좋아지는 도구**(편집·깃 등)를 그렇게 만든다.
> **젯브레인과 VS Code 둘 다.**
>
> 이 문서는 **조사와 설계까지**다. 코드는 없다.

---

## 1. 지금 있는 것 — 넷을 실측했다

| 기전 | 누가 쓸 수 있나 | 이름 | 위험 취급 | 끄는 길 |
|---|---|---|---|---|
| `Registry.Register` | **프로세스 안에서만** | 아무 이름 — 같은 이름이면 **내장을 덮는다**(“adds or replaces”) | `DangerTools` 맵에 그 이름이 있으면 | — |
| `Registry.Unregister` | 플러그인 호스트·MCP 매니저 **내부** | — | — | **밖에서 부를 길이 없다** |
| `mcp-attach` 문 | **클라이언트**(소켓) | `mcp__<서버>__<도구>` **강제** | **구조상 항상**(`dangerGated` 가 접두로 판정) | `mcp-detach` |
| Lua `register_tool` | 저장소가 로드하는 플러그인 | 아무 이름 | 맵에 따라 | 플러그인을 빼면 |

그래서 지금 두 클라이언트가 실제로 하는 것은:

- **젯브레인**: `mcp-attach` 로 **둘**을 넣는다 — `show`, `apply_edit`(`Hand.kt`). 이름은
  `mcp__jetbrains__show` · `mcp__jetbrains__apply_edit` 가 된다.
- **VS Code**: 아무것도 안 넣는다.
- **어느 쪽도 코어 도구를 하나도 덮지 않는다.** `register_tool` 은 **Lua 플러그인 API** 이고,
  젯브레인 클라이언트에는 `.lua` 가 **한 개도 없다**(실측). 클라이언트는 프로세스 밖이라 그 API 에
  손이 닿지 않는다.
- **코어 도구를 끄는 설정도, 문도 없다.**

## 2. 이름이 문제다 — 다섯 자리가 이름으로 판정한다

주입만으로 「더 좋아진다」가 안 되는 이유다. 코어는 내장 도구를 **이름으로** 알아본다.

| 자리 | 무엇을 이름으로 판정하나 | 주입한 도구가 겪는 일 |
|---|---|---|
| `app/config.go` `DefaultDangerTools` | 승인이 필요한가 | `mcp__` 접두 덕에 **항상 위험**으로 잡힌다 — 이쪽은 안전한 방향으로 틀린다 |
| `app/filetools.go` `builtinFileTools` | **이 호출이 파일을 바꾸나** | 아니라고 읽힌다 → 바뀐 파일 추적·비밀 거절·가드레일 경로·변경 기록에서 **빠진다** |
| `app/workflow.go` `wfEdit` 등 | 역할이 쓸 수 있는 도구 | 목록에 없어 **그 역할은 편집을 아예 못 한다** |
| `app/observed.go` | 「무엇을 고쳤나」 세기 | 안 세어진다 → 기록의 `changed:` 가 빈다 |
| `app/policy.go` | allow/deny 규칙 대조 | 사람이 써 둔 `Edit(...)` 규칙이 안 걸린다 |

⚠ 가운데 셋이 특히 비싸다. 편집이 **성공해도** 코어는 「아무것도 안 바뀌었다」고 기록하고, 카운슬은
그 기록을 보고 판단하며, 정체 가드는 진행이 없다고 읽는다. 도구는 잘 도는데 **주위 기계가 눈을
감는다** — 이 저장소가 되풀이해 값을 치른 「초록인데 안 재고 있다」의 모양이다.

## 3. ★ 선언할 자리는 이미 있는데, 채우는 쪽이 없었다 — **채웠다(2026-09-09)**

> ✅ **이 절의 결함은 고쳤다.** `internal/adapter/mcp/filetool.go` 가 producer 다: MCP 도구의 **자기
> 스키마**가 `path` 라는 문자열 속성을 선언하면 그 도구를 `port.FileTool` 로 감싸 등록하고,
> **고치는가 보는가**는 서버의 `annotations.readOnlyHint` 로 가른다. 젯브레인 쪽도 그 선언을 싣게
> 했다(`show`=읽기, `apply_edit`=쓰기). 그래서 이제 `apply_edit` 가 성공하면 기록에
> `changed: <경로>` 로 오른다.
>
> **스키마가 정하게 한 이유**: `WritesFile()` 은 인자를 안 받아 호출마다 답할 수 없다. 읽기전용이
> 아닌 모든 서버 도구를 쓰기로 치면 `add_slide` 같은 경로 없는 도구까지 쓰기가 되어, 코어가 **빈
> 경로에 대고 진단과 훅을 돌린다** — `filetools.go` 가 경고한 「없는 파일에 12초 LSP 왕복」이다.
>
> **실패도 적는다**: 돌았는데 안 먹은 쓰기는 `tried to write and it did not take: <경로> ×N` 으로
> 기록에 남는다. `changed` 에는 안 넣는다(디스크에 없다) — 사유는 툴 결과에 있고 접기가 그것을
> 가져가므로, 살아남는 이 블록에 사실만 남긴다. 거절된 호출은 시도가 아니다.

아래는 그때의 근거로 남긴다.

## 3.1 (그때) 선언할 자리는 이미 있는데, 채우는 쪽이 없다

`filetools.go` 머리말이 이 경우를 **이름으로 지목한다**:

> "An editor plugin that attaches its own edit tool — which is the case this exists for — is called
> `mcp__jetbrains__edit`, and by name it is nothing."

그래서 `port.FileTool` 이 있다 — 도구가 스스로 「내가 이 파일을 이렇게 건드린다」고 말하는 자리다:

```go
type FileTool interface {
    FileArg(args json.RawMessage) string  // 이 호출이 지목한 파일
    WritesFile() bool                     // 읽기만인가 바꾸는가
}
```

**그런데 구현체가 시험 말고는 하나도 없다**(실측: `func (…) WritesFile() bool` 이 비시험 코드에
0개). MCP 매니저도 Lua 호스트도 이 인터페이스를 채우지 않는다. 즉 **문은 나 있는데 그 문으로
들어올 방법이 아무에게도 없다.**

이것이 이 제안의 첫 걸음이 무엇인지 정한다: 새 기전을 만들기 전에 **이미 있는 기전에 producer 를
붙이는 것**이 먼저다.

## 4. 설계

### 4.1 주입 — 네임스페이스를 유지하고, 선언을 채운다

두 길이 있다.

| | (가) 내장 이름을 덮는다 | (나) `mcp__` 이름을 유지하고 선언한다 |
|---|---|---|
| §2 의 다섯 자리 | 그냥 통과한다 | 선언을 읽는 자리만 통과한다(고쳐야 한다) |
| 위험 취급 | **사라진다** — `edit` 는 맵에 있지만 그 구현이 IDE 라는 사실이 어디에도 안 남는다 | 유지된다(접두로 판정) |
| 사람의 allow 규칙 | 그대로 걸린다 | **안 걸린다** — 이름이 다르다 |
| 되돌리기 | 원래 구현이 사라진다. 클라이언트가 죽으면 편집 자체가 없다 | 끄기를 되돌리면 그대로 돌아온다 |

**권고: (나).** 근거는 위험 취급이다. 이름을 덮으면 `edit` 라는 이름 뒤에 **이 프로세스가 안 쓴
코드**가 서는데, 승인 모드가 「내장 편집은 물어보지 않는다」고 약속하는 것은 그 편집을 코어가
워크스페이스 안에 **묶어 두기 때문**이다(`confinedEdit` 주석이 그 말을 한다). 밖의 프로세스가
그 이름을 물려받으면 그 약속이 거짓이 된다.

(나)를 고르는 값은 **allow 규칙이 안 걸린다는 것**이고, 그건 §7 에 남긴다.

### 4.2 끄기 — 문 하나, 그리고 연결에 묶는다

`mcp-attach`/`mcp-detach` 옆에 짝을 둔다. 이름은 정하지 않았고 모양은 이렇다:

```
→ {"method":"tools-off","args":{"names":["edit","multiedit"]}}
← {"ok":true,"out":"edit, multiedit"}          ← 실제로 꺼진 것을 돌려준다
```

⚠ **꺼진 상태는 그 연결보다 오래 살지 않는다.** 클라이언트가 `edit` 를 끄고 제 도구를 넣은 뒤
창이 닫히면, 남는 것은 **편집을 못 하는 컴패니언**이다 — 터미널로 붙은 사람도, 크론이 깨우는
턴도 편집을 못 한다. 그리고 아무 데도 에러가 없다. 그래서:

- 끈 것은 **그 연결의 수명**에 묶고, 연결이 닫히면 되돌린다(`mcp-detach` 가 이미 그 모양이다).
- 되돌아간 사실은 **말한다.** 조용히 복구하면 「왜 갑자기 IDE 편집이 아닌가」를 아무도 못 쫓는다.
- 데몬은 **꺼진 이름을 광고한다**(`tools` 문). 안 그러면 클라이언트가 광고를 보고 없는 문을
  두드리는 그 함정을 도구 층에서 되풀이한다.

⚠ **쓸 가능성이 있으면 끄지 않는다**(사용자 원칙, 2026-09-09). 로그에 안 나오는 것은 「안 쓴 것」
이고 「안 쓸 것」이 아니다 — 파워포인트가 `edit` 를 130세션 동안 딱 한 번 불렀는데, 그 한 번이
필요했던 턴이다. 그래서 끄기는 **클라이언트가 그 이름을 실제로 대신할 때만** 쓴다: 제 도구로
대체하는 경우다. 「안 쓸 것 같아서」 끄는 것은 이 문의 용도가 아니다.

⚠ **끌 수 없는 것을 정해 둔다.** `council`(선언으로 턴을 끝내는 문)·`todowrite` 처럼 루프가
기대하는 것을 끄면 코어가 못 끝낸다. 목록은 코어가 들고, 문은 **거절 사유를 말한다.**

### 4.3 두 클라이언트에 같은 것을 준다

주입은 클라이언트마다 **서버 하나**다. 젯브레인은 이미 그 서버가 있고(`HandServer`), VS Code 는
**없다** — 그것이 VS Code 매뉴얼 §8 에 남은 다섯 중 하나다. 그래서 순서가 갈린다.

| | 젯브레인 | VS Code |
|---|---|---|
| 도구 서버 | 있다(`show`·`apply_edit`) | **없다. 먼저 만든다** |
| 이름 | `jetbrains` 고정 | `vscode` 고정 — 같은 이유로(allow 규칙이 이름에 걸린다) |
| 선언(`FileTool`) | 코어가 producer 를 갖게 되면 그때 | 처음부터 |

## 5. IDE 를 얹으면 좋아지는 도구 — 값과 비용

「IDE 를 지나면 나아지는가」로 판정한다. 나아지지 않는 것은 **옮기지 않는다** — 층이 하나 늘고
느려질 뿐이다.

| 도구 | IDE 를 지나면 무엇이 달라지나 | 판정 |
|---|---|---|
| `edit`·`multiedit`·`write` | **되돌리기 스택·로컬 히스토리·인스펙션 재실행·열린 편집기 갱신**이 돈다. 파일을 밖에서 고치면 그 넷이 다 안 일어난다 | **★ 값이 가장 크다.** 젯브레인이 `apply_edit` 를 둔 사유가 이것이고 그 근거가 `Hand.kt` 에 적혀 있다 |
| `read` | **저장 안 한 버퍼**를 읽는다. 지금은 디스크를 읽으므로 사람이 고치던 내용을 에이전트가 못 본다 | **값이 있다.** 다만 VS Code 는 이미 `open-file` 로 열린 버퍼를 보내고 있어 **겹친다** — 어느 쪽 하나로 정해야 한다 |
| `grep`·`glob` | IDE 의 색인은 빠르고 `.gitignore`·범위를 안다 | ⚠ **안 잰 것.** ripgrep 이 이미 빠르다. 재보고 정한다 |
| 깃 — 커밋·diff·이력 | IDE 의 VCS 창이 열리고, 부분 스테이징·충돌 해결이 사람 손에 남는다 | ⚠ **성격이 다르다.** 이건 도구를 대체하는 것이 아니라 **사람에게 넘기는 것**이다. 도구가 아니라 「이 자리를 열어 달라」는 요청이므로 `show` 계열에 가깝다 |
| 진단·오류 | 컴파일러·린터의 **실물 진단**을 그대로 읽는다. 지금은 셸로 빌드해 글자를 읽는다 | **★ 값이 크고 대체가 아니다** — 없던 도구다 |
| 리팩터링(이름 바꾸기·시그니처) | IDE 만 안전하게 한다. 텍스트 치환으로는 못 한다 | **★ 없던 도구.** 다만 편집기마다 API 가 갈려 이식 비용이 크다 |
| `bash` | 아무것도 나아지지 않는다 | **옮기지 않는다** |

**권고 순서**: ① 편집 셋 ② 진단 ③ `read` 겹침 정리 ④ 나머지는 재보고.

## 5.5 오피스 클라이언트에서는 무엇을 벌 수 있나 — 실측

물어본 것: 「모든 도구를 다 쓰지는 않을 테니, 끄면 효율이 오르나?」 도는 컴패니언 셋에게 직접
물었다(2026-09-09).

| | 도구 수 | 도구가 먹는 창 | 말 한마디 전 `used` |
|---|---|---|---|
| PowerPoint | 79 = 코어 30 + mcp 49 | **29,349 토큰** | — |
| Excel | 106 = 코어 30 + mcp 76 | **32,148 토큰** | **35,103**(메시지 0개) |
| Word | 96 = 코어 30 + mcp 66 | 23,507 토큰 | — |

창이 200,000 인데 **말을 걸기 전에 이미 16%가 도구다.** 그리고 매 요청마다 다시 낸다.

**그런데 무게는 코어에 없다.** 내장 도구 전부의 이름+설명+스키마를 재니 **18,239바이트 ≈ 4,559
토큰**이다(가장 큰 것부터: `remember` 702 · `schedule` 352 · `wait_for` 291 · `bash` 287 ·
`ask_user` 273). 즉 엑셀의 32,148 중 **코어는 14%뿐**이고 나머지 86%는 **그 클라이언트가 자기
손으로 넣은 76개**다.

⚠ **「안 쓸 것」이라는 가정도 실측으로 깨졌다.** 세션 로그에서 실제 호출을 셌다:

| | 세션 | 사람 프롬프트 | 실제로 쓴 코어 도구 |
|---|---|---|---|
| PowerPoint | 130 | 352 | **18 / 30** — `todowrite` 274회, `skill` 197, `websearch` 146, `council` 109 … 그리고 **`read` 14 · `grep` 15 · `glob` 8 · `write` 3 · `edit` 1** |
| Excel | 15 | 60 | 11 / 30 |
| Word | 11 | 25 | 2 / 30 |

파워포인트는 파일 도구까지 **실제로 쓴다.** 그러니 「덱을 고치는 컴패니언이니 파일 도구는 필요
없다」는 추측은 틀렸다. 워드가 2개뿐인 것도 「필요 없다」가 아니라 **표본이 25 프롬프트**라는
뜻이다 — 안 쓴 것과 안 쓸 것은 다른 말이다.

**그래서 값은 이렇게 갈린다.**

| 하려는 것 | 벌리는 것 | 판정 |
|---|---|---|
| 안 쓰는 코어 도구를 끈다 | 파워포인트에서 로그상 한 번도 안 불린 13개를 다 꺼도 **≈2,000 토큰**(도구 비용의 7%, 창의 1%) | ⚠ **작다.** 그리고 「쓸 가능성이 있으면 지우지 않는다」를 지키면 더 작아진다 |
| 클라이언트 자기 도구를 줄인다 | 도구 비용의 **86%**가 여기 있다 | **★ 여기가 진짜 자리다** — 다만 이 제안의 범위가 아니다 |
| **선언(`readOnlyHint`)을 쓴다** | 토큰이 아니라 **접을 때** 벌린다 | **★ 이미 벌고 있다** — 아래 |

### 선언은 이미 값을 내고 있다 (그리고 주석이 낡았다)

오피스 헬퍼는 도구마다 `annotations.readOnlyHint` 를 보낸다. 그 자리 주석은 **「오늘 magi 는
그것을 안 읽는다」**고 적혀 있는데, **지금은 읽는다** — `internal/adapter/mcp/manager.go:234` 가
그 값으로 `mcpTool.readOnly` 를 채우고, `internal/app/compact.go:102` 가 창이 닫힐 때 그것을
읽어 **다시 불러올 수 있는 결과부터 덜어낸다**(접기는 요약 호출과 재청구를 물어야 하므로 그것보다
싸다). 그래서 이 선언은 「미래를 위한 자리」가 아니라 **지금 도는 절약**이다.

⚠ 그러면 반대로, **선언을 안 한 도구는 접을 때 비싸게 굴려진다.** 오피스 도구 중 읽기만 하는
것들이 `readOnly` 로 표에 적혀 있는지가 그대로 값이 된다 — 표는 `tools()` 한 자리이므로 고칠
자리도 하나다.

## 6. 무엇을 재야 하나

- **끄기가 실제로 끊는가**: 끈 이름을 에이전트가 부르면 거절되고, `tools` 문이 그 이름을 더는 안
  광고한다.
- **되돌아가는가**: 연결을 닫으면 원래 도구가 돌아온다 — 그리고 그 사실이 기록에 남는다.
- **★ 선언이 실제로 읽히는가**: IDE 편집으로 파일을 바꾼 턴의 기록에 `changed:` 가 **그 경로를
  담는다.** 이 시험이 §2 의 값을 잡는 유일한 자리다. 없으면 「도구는 도는데 기계가 눈을 감은」
  상태가 초록으로 통과한다.
- **끌 수 없는 것을 못 끄는가**: `council` 을 끄려 하면 사유를 말하며 거절한다.
- **와이어 대조**: 새 문의 필드 이름을 Go 소스에서 읽어 두 클라이언트와 맞춘다.

## 7. 재지 않은 것 · 정하지 않은 것

- **allow 규칙을 어떻게 잇나.** (나)를 고르면 사람이 써 둔 `Edit(...)` 규칙이 `mcp__vscode__edit`
  에 안 걸린다. 규칙 쪽에 별칭을 두는 길이 있는데, 그건 정책 층의 결정이라 여기서 안 정했다.
- **문 이름과 필드.** `tools-off` 는 자리표시다. [새 문 원칙 5](../CLIENTS.ko.md)에 맞춰 정해야 한다.
- **`grep`·`glob` 을 IDE 로 옮길 값.** 안 쟀다.
- **`read` 와 `open-file` 의 겹침을 어느 쪽으로 정리할지.**
- **분량.** 젯브레인은 서버가 있고 VS Code 는 없다는 것만 안다. 줄 수는 짐작이라 안 적는다.

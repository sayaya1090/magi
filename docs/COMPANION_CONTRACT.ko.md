# 컴패니언의 목적, 접근 범위와 공개 기능

현재 자동 관리 경로는 아래 「내부 설명 관리 세션」 절을 따릅니다. 앞의 최초 빈 설명 추출 절차와 CLI는 구형 호환 경로로 유지하며 자동 갱신의 현재 동작으로 해석하지 않습니다.

상태: 구현 설계. 2026-10-17에 gwt 데몬의 `about`을 조회했을 때 공개 항목은 스킬 두 개뿐이었습니다. 입력 명세, 실행 조건과 직접 호출 경로는 없었습니다. 이 문서는 사용자 선언과 실제 실행 권한을 연결하는 설계입니다.

## 1. 선언과 권한

사용자는 목적(purpose), 운영 지침(instructions), 공개 기능(operations)을 작성합니다. 스킬은 학습한 절차이며 실행 권한을 부여하지 않습니다. 외부 도구 서버에 연결되어 있다는 사실도 그 서버의 모든 도구를 다른 컴패니언에 공개한다는 뜻이 아닙니다.

실행 권한은 사용자 설정 디렉터리의 `companion-policies/<workspace SHA-256>/policy.toml`에 둡니다. `magi --companion-policy-path`로 현재 작업 공간의 경로를 확인합니다. 작업 공간은 절대 경로를 정리하고 심볼릭 링크를 해석한 뒤 해시합니다. 프로젝트의 `.magi` 파일은 이 선언을 대체하지 못합니다. 정책 파일 자체의 심볼릭 링크도 거절합니다. 선언이 없으면 직접 호출 기능은 없습니다. 잘못된 선언은 오류로 처리하며 기존 도구 전체를 공개하는 폴백은 금지합니다.

```toml
version = 1
purpose = "GWT 빌드 플러그인의 개발과 검증"
instructions = ["소비 프로젝트는 검사만 합니다.", "배포는 사용자가 요청한 경우에만 수행합니다."]

[[operations]]
id = "read-plugin-source"
description = "플러그인 공개 소스 파일을 읽습니다."
kind = "read_file"
root = "/Users/me/projects/gwt/src"
```

`root`는 사용자가 허용한 실제 디렉터리입니다. 첫 구현은 `read_file`만 지원합니다. 호출 인자는 root 기준의 상대 경로 `path`이며, 호출자가 root를 바꿀 수 없습니다. `offset`과 `limit`으로 줄 범위를 지정합니다. 절대 경로, `..`, 외부 심볼릭 링크, 디렉터리와 특수 파일은 거절합니다. Go의 `os.Root`를 사용하여 경로 검사와 파일 열기 사이의 심볼릭 링크 교체로 root 밖을 읽는 문제를 방지합니다. 읽을 디렉터리에는 공개해도 되는 파일만 두어야 합니다. root 안의 비밀 파일을 자동 판별하는 보장은 없습니다.

운영 지침은 자신의 시스템 컨텍스트와 상대에게 제공하는 소개에 넣습니다. 자연어 지침 자체는 OS 샌드박스가 아닙니다. 첫 구현의 강제 범위는 공개된 `read_file` 실행이며, 자신의 일반 bash나 기존 `hand_off` 전체 권한까지 바뀌었다고 주장하지 않습니다. 컴패니언은 같은 사용자 계정으로 실행되므로, 악의적인 로컬 코드에 대한 OS 보안 경계도 아닙니다.

선언을 만들 때는 위 명령이 출력한 경로의 부모 디렉터리를 생성하고 TOML 파일을 저장합니다. 자동으로 현재 gwt 프로젝트를 공개하지 않습니다. 정책은 조회·호출마다 다시 읽습니다. 자신의 지침은 다음 컨텍스트 조립부터 반영됩니다. 데몬은 3초마다 목적과 작업 광고를 갱신합니다. 상대의 목록 캐시는 자체 새로고침 주기를 따릅니다.

호출 권한은 현재 컴패니언 연결 경계(로컬 사용자 소켓, 허용한 SSH/TLS fleet 연결)를 따릅니다. 첫 구현에는 상대 컴패니언별 ACL이 없습니다. 공개한 읽기 기능은 그 경계를 통과한 모든 호출자에게 허용됩니다. 상대별 제한이 필요하면 이 단계에서는 공개하지 않습니다.

## 2. 모듈과 실행 경로

```text
사용자 정책 → 목적·지침 → 자신의 시스템 컨텍스트
          → 공개 기능 목록 → 상대의 상세 조회 → 제한 실행기 → 원본 결과
```

계약 타입은 core, 정책 로딩·파일 접근은 adapter, 데몬과 도구 등록은 cmd가 맡습니다. 호출자 모델 → `companion_call` → 대상 데몬 → 정책 로더 → 제한된 실행기 순서입니다. 이 연결은 모델을 다시 호출하지 않습니다. 원래 결과와 오류를 구조적으로 반환합니다.

1. `companion_can`은 목적, 지침, 공개 기능 요약과 기존 스킬을 구분해 보여줍니다.
2. `companion_call`의 `list`는 기능 요약만 반환합니다. `describe`는 한 기능의 입력·출력 스키마와 접근 범위를 반환합니다.
3. `call`은 현재 정책을 다시 읽고 등록된 기능만 실행합니다. 인자 오류, 제거된 기능과 범위 위반은 실행 전에 거절합니다.
4. 읽기 호출은 대상의 모델 턴과 독립적입니다. 각 호출은 별도의 root 핸들을 사용합니다. 제한은 최대 파일 크기 1 MiB, 반환 200줄 기본·최대 1000줄이며 바이너리는 거절합니다. 반환 JSON이 64 KiB를 넘으면 범위를 줄이도록 오류를 돌려주며 원문을 몰래 자르지 않습니다.
5. 데몬 메서드 `capabilities`, `capability`, `capability-call`은 SSH fleet door에도 명시적으로 등록합니다. 구형 데몬은 지원하지 않는 메서드로 응답하며 작업 위임으로 자동 전환하지 않습니다.

공개 목록에는 원본 스키마 전체를 넣지 않습니다. 각 조회와 실행은 그 호출에서 읽은 정책 스냅샷으로 해석합니다. 조회 뒤 정책이 바뀌었다면 실행 시 최신 정책을 적용합니다. 변경 작업의 후속 실행기에는 조회한 명세의 revision 확인을 추가해야 합니다. 읽기 전용 호출은 중복 실행되어도 외부 변경이 없지만 자동 재시도는 하지 않습니다. 응답 유실은 실패로 보고하며 대상 모델의 답변으로 대체하지 않습니다.

## 3. 설계 결정과 품질

| 결정 | 근거 | 비용과 한계 |
|---|---|---|
| 기존 데몬을 브로커로 사용 | 컴패니언 주소와 SSH 경계를 재사용 | 대상 데몬이 중지되면 호출할 수 없음 |
| 사용자 디렉터리에 권한 저장 | 저장소 변경만으로 기능 공개를 늘리지 않음 | 선언 작성 UI가 추가로 필요 |
| 상세 명세 지연 조회 | 모든 기능의 스키마가 매 턴 컨텍스트를 차지하지 않음 | 첫 사용에는 조회 왕복이 필요 |
| 첫 실행기는 제한된 파일 읽기 | 셸 없이 접근 범위를 실제 강제 | 빌드·브라우저 조작은 후속 실행기가 필요 |
| 스킬과 실행 기능 분리 | 학습 기록을 권한으로 오인하지 않음 | 기존 집계에 `call:` 접두어를 붙여 구분하며, 게시 수량은 시작 시점의 스냅샷 |

## 4. 후속 구현 순서

다음 단계는 제한된 명령 실행기입니다. 사용자 고정 실행 파일·argv 템플릿과 허용 cwd를 사용하며 요청 문자열을 셸에 보간하지 않습니다. 작업 ID, 상태 조회, 취소, 제한 시간, 결과 보존, 변경 작업 직렬화와 감사 기록을 먼저 구현합니다. 실행 승인 및 네트워크·자식 프로세스·쓰기 경계가 정의되기 전에는 빌드 기능을 공개하지 않습니다. gwt의 Gradle 검증은 이 단계에서 실제 테스트 워크스페이스로 검증합니다.

그 뒤 브라우저·오피스 등 클라이언트 도구의 선택적 프록시를 붙입니다. MCP의 readOnlyHint만으로 안전하다고 판정하지 않습니다. 도구 제공자가 지원하는 세션·문서·탭 범위를 실행 시 검사해야 합니다. 호출자가 지정한 도구 서버 URL이나 임의 툴 이름으로 허용 목록을 우회할 수 없어야 합니다.

설정 UI와 TUI 편집기는 같은 정책 모델을 사용합니다. 자신의 일반 도구에도 적용할 접근 정책은 별도 단계에서 기존 파일 가드·프로세스 샌드박스와 통합합니다. 자연어 금지 목록만 추가하고 완료로 처리하지 않습니다.

## 5. 인수 기준

정책 없음·잘못된 TOML·알 수 없는 버전·중복 ID·미지원 kind는 fail closed로 검사합니다. 목적과 지침은 자신의 프롬프트 및 상대 소개에서 확인합니다. 직접 호출은 모델 호출 없이 실행하고 결과의 content/isError를 보존합니다. 상대 경로 정상 읽기, 줄 범위, root 밖 경로, 외부 링크, 링크 교체, 바이너리·특수 파일·대용량 파일, 취소된 요청과 정책 제거를 검증합니다. 데몬 실제 소켓을 통한 조회·실행과 fleet door 허용 목록도 검사합니다.

## 6. 첫 구현 범위

첫 구현은 사용자 정책 로더, 자신의 지침 주입, 공개 소개, `companion_call` 조회·읽기, 데몬/SSH 경로입니다. 정책 파일을 편집하는 설정 화면, 명령·변경 실행, 상대별 ACL과 일반 에이전트 전체의 접근 강제는 아직 구현하지 않았습니다. 실제 gwt 프로젝트에는 공개 권한을 추가하지 않았습니다. 테스트는 임시 작업 공간을 사용합니다.

## 7. 사용자 선언 중심 광고

`magi --companion-policy-write < declaration.toml`로 사용자 선언을 검증하여 원자적으로 저장합니다. `magi --companion-policy-show`는 현재 선언을 JSON으로 출력합니다. 잘못된 입력은 기존 선언을 덮어쓰지 않습니다. 이 저장 경로는 명시적 로컬 CLI에만 있으며, 모델 도구나 원격 fleet 메서드로 제공하지 않습니다.

사용자는 목적 `purpose`, 책임 `responsibilities`, 운영 지침 `instructions`, 맡길 수 있는 작업 `tasks`, 접근 범위 `access`를 작성합니다. `tasks`는 모델에게 맡길 일이며, 모델을 거치지 않는 직접 호출 `operations`와 구분합니다.

```toml
version = 1
purpose = "GWT 플러그인 개발과 검증"
responsibilities = ["플러그인 소스와 테스트를 관리합니다."]
instructions = ["요청 없이 배포하지 않습니다."]

[[tasks]]
id = "diagnose-build"
description = "GWT 빌드 실패를 조사하고 수정합니다."
constraints = ["변경 전후 검증 결과를 보고합니다."]

[[access]]
resource = "/Users/me/projects/gwt"
mode = "write"
description = "이 프로젝트의 소스와 테스트 관리"
```

`can`과 `does`는 선언한 `tasks`와 `operations`에서만 계산합니다. `task:`와 `call:` 접두어로 구분합니다. 스킬 학습과 MCP 연결은 광고를 추가하지 않습니다. 상세 조회는 목적·책임·작업과 제약·접근 범위를 먼저 보여 주고, 학습한 스킬은 경험 정보로 별도 표시합니다. 선언을 삭제하면 광고를 비우며, 잘못된 선언은 이전 광고를 지우고 오류 상태로 표시합니다. 기존 `companion.role`은 호환용 소개이며 권한이나 작업 목록을 부여하지 않습니다.

접근 모드는 `read`, `write`, `execute`, `deny`, `approval`입니다. 자신의 모델과 요청자에게 경계를 전달하며 일반 셸의 OS 권한을 제한하지는 않습니다. 직접 읽기의 실행 권한은 별도 `operations.root`로만 결정합니다. 사용자가 선언한 전체 경계를 일반 도구에서도 강제하는 작업은 후속 단계입니다. 코딩 컴패니언은 워크스페이스를 파악한 뒤 빈 자기소개를 등록할 수 있습니다. 접근 권한은 자동으로 추가하지 않습니다.

## 워크스페이스를 파악한 뒤 자기소개 등록

대화형 코딩 컴패니언(VS Code·JetBrains·TUI)은 프로젝트 파일을 `read`로 읽는 데 성공한 턴이 정상 종료되면 비어 있는 목적·담당 범위·제공 작업을 자동으로 추출합니다. 주 모델이 등록 CLI 실행을 기억해야 하는 구조를 대체합니다. 준비된 coding_task 실행기는 별도 컴패니언으로 자신을 등록하지 않습니다.

제공 작업과 직접 호출 기능이 모두 비어 있으면 대화형 채팅을 여는 즉시 승인 질문을 표시합니다. 사용자가 메시지를 입력할 때까지 기다리지 않습니다. 하네스가 기존 질문 UI로 읽기 전용 조사 범위와 모델 사용량을 설명합니다. 승인하면 같은 채팅에 범위를 제한한 조사 요청을 추가하고 그때 모델을 실행합니다. 보류·창 닫기·시간 초과 시에는 조사나 모델 요청을 시작하지 않습니다. 접근 권한·직접 호출 도구·프로젝트 파일은 변경하지 않습니다.

데몬 기동 후 한 번만, 실시간 이벤트 구독이 연결된 뒤 묻습니다. 여러 화면이 동시에 연결돼도 질문을 중복으로 만들지 않습니다. 연결이 끊기면 미응답 질문을 취소하며 재연결 시 다시 물을 수 있습니다. 자동 정리를 끄면 질문도 취소합니다. 진행 중인 작업을 방해하지 않도록 유휴 상태에서만 시작합니다. 단순 대화 기록 조회는 질문을 유발하지 않습니다. 실시간 클라이언트가 `transcript`에 `name: "interactive"`를 보내 명시적으로 요청하며 `text`로 UI 언어를 전달할 수 있습니다. 구형 클라이언트에는 첫 사용자 턴의 모델 넛지를 대체 경로로 유지합니다. 기존 사용자 작업과 그 근거를 이용한 자동 설명 추출은 이 선택적 조사와 별개입니다.

헤드리스 실행에서는 넛지와 자동 설명 추출을 모두 하지 않습니다. 예약 작업·자식 세션·준비된 coding_task·다른 컴패니언이 시작한 턴에도 소개 넛지를 주지 않습니다. IDE 클라이언트가 사용하는 데몬은 프로세스에 TUI가 없어도 대화형 실행으로 취급합니다.

기본값은 `companion_auto_describe = "on"`입니다. `"off"`로 바꾸면 데몬 재시작 없이 자동 추출을 중지합니다. 메모리·스킬 학습과는 별도 설정입니다. 신뢰하지 않은 프로젝트 설정에서는 변경할 수 없습니다. 꺼도 이미 저장된 설명은 유지합니다.

추출기는 사용자 턴이 끝날 때까지 기다린 뒤 최대 24 KiB의 대화 근거로 도구 없는 모델 요청을 한 번 실행합니다. 제한 시간은 90초입니다. 새 사용자 요청이 시작되면 취소합니다. 데몬당 하나만 실행하며 시도 간격은 10분입니다. 취소된 경우 다음 성공한 턴 뒤에 다시 시도할 수 있습니다. 근거가 부족하면 모델은 `null`을 반환할 수 있습니다. 실패는 로그에 남기며 기존 선언이나 사용자 턴의 결과를 바꾸지 않습니다. 별도 요청은 해당 세션의 프로바이더 경로와 모델을 사용하므로 모델 사용량이 발생합니다.

생성한 설명은 기존 프로필 저장기의 검증을 거칩니다. 비어 있는 항목만 채우며 기존 설명·접근 범위·지침·직접 호출 도구는 보존합니다. 저장에 성공하면 컴패니언 광고를 갱신합니다. 학습한 스킬을 자동으로 제공 작업으로 광고하지 않습니다.

추출을 시작하면 같은 채팅에 진행 안내를 남깁니다. 저장과 광고 갱신에 성공한 뒤 저장된 선언을 다시 읽고, 등록된 목적과 제공 작업 개수·설명·제약을 완료 안내에 표시합니다. 모델이 제안한 원본이 아니라 사용자 작성 항목까지 보존한 실제 저장 내용을 보여 줍니다. 근거 부족, 저장 실패, 재확인 실패, 추출 중단은 완료로 표시하지 않으며 이유를 알립니다. 이 안내는 시스템 메시지로 저장되어 이전 대화를 열어도 볼 수 있습니다. 안내를 쓰기 위해 모델을 다시 호출하지 않습니다.

JetBrains 설정의 **컴패니언 역할 자동 정리** 체크박스로 켜고 끕니다. **컴패니언 목적·담당 범위·제공 작업**에서는 목적과 담당 범위를 입력하고 표에서 작업을 추가·삭제할 수 있습니다. VS Code에서는 **Magi 상세 설정 변경**에서 자동 정리 설정이나 컴패니언 설명을 선택한 뒤 항목별로 편집하고 **저장**합니다. 편집 화면에서는 기존 설명을 바꾸거나 삭제할 수 있으며 접근 권한과 직접 호출 도구는 유지합니다. 일부 항목을 의도적으로 비워 두려면 자동 정리를 꺼 둡니다.

데몬의 `config-get`·`config-set`에도 연결합니다. `companion_auto_describe`는 `on`·`off`를, `companion.profile`은 `purpose`·`responsibilities`·`tasks`만 담은 JSON 객체를 받습니다. 프로필 편집은 CLI와 같은 프로세스 간 잠금과 원자적 검증을 사용합니다. 잘못된 입력은 저장된 정책을 바꾸지 않습니다.

터미널에서는 원본 워크스페이스에서 `magi --companion-policy-show`로 조회하고 프로필 JSON을 `magi --companion-profile-write`의 표준입력으로 전달합니다. 이 CLI는 비어 있는 항목만 채웁니다. 권한을 의도적으로 변경할 때에는 기존 전체 정책 CLI를 사용합니다. 자동 추출은 설명을 저장하지만 모델이 워크스페이스를 정확히 이해했다는 보장은 아니므로 제공 작업을 검토한 뒤 사용합니다.

## 동시 질문과 응답 대기 표시

같은 요청자가 보낸 질문은 수신 컴패니언의 같은 보조 대화를 재사용합니다. 이 대화의 이전 질문이 끝날 때까지 다음 질문을 대기열에 두고, 실제 시작 시점의 로그 위치를 접수 번호에 연결합니다. 읽기 전용 질문도 같은 대화 안에서는 순서대로 처리합니다. 다른 대화의 읽기 작업과 사용자의 주 작업은 병렬로 진행할 수 있습니다.

`jobs` 응답의 `outgoing`에는 선택한 세션이 다른 컴패니언에게 보내고 답변을 기다리는 요청이 담깁니다. 각 항목은 `receipt`, `to`, `request`, `started`를 제공합니다. JetBrains의 작업 영역과 VS Code의 위임한 작업 영역에는 대상과 질문을 표시하고 응답 대기를 스피너로 나타냅니다. 질문 전문과 접수 번호는 툴팁에서 확인합니다. 응답이 대화 기록에 저장되면 해당 대기 행을 제거합니다. 같은 대상에게 같은 질문을 반복해도 접수 번호로 구분하므로 하나의 응답이 다른 요청을 지우지 않습니다. 대기 목록은 실행 중인 데몬의 상태이며 응답 본문은 대화 기록에 남습니다.

## 내부 설명 관리 세션

최초 등록 뒤에도 새 프로젝트 근거로 제공 작업을 보완합니다. 컴패니언별 사용자 정책 디렉터리의 `maintenance.json`을 일반 대화 목록에 나타나지 않는 내부 세션으로 사용합니다. 사용자 대화를 새로 만들거나 선택하지 않으며 코딩 에이전트의 턴·카운슬·도구 루프를 실행하지 않습니다. 관리 세션에는 ID, 원본 대화별 처리 위치(최대 256개), 마지막 시도·성공·오류, 대기 중인 원본별 기록 위치, 최근 32회 이력, 자동 작성한 내용의 기준값과 실행 lease를 저장합니다. 근거 본문을 별도 복제하지 않습니다.

대화형 컴패니언에서 정상 종료한 작업에 새로운 읽기 근거가 있을 때 예약합니다. 코딩 컴패니언은 성공한 `read` 결과를, 다른 클라이언트는 자신의 역할에 허용된 등록 도구 중 읽기 전용으로 선언된 도구의 성공 결과를 사용합니다. 클라이언트 종류를 함께 보내 네이티브 문서 작업공간을 코드베이스로 소개하지 않게 합니다. 사용자·다른 세션 작업이 끝나고 10분 갱신 간격을 지난 뒤 최대 24 KiB의 설명 정보(접근 권한·운영 지침·공개 기능 제외)와 최대 24 KiB의 새 근거를 도구 없는 모델 요청으로 보냅니다. 요청 제한은 90초, 게시 lease는 2분입니다. 여러 원본 세션은 한 작업자로 모으며 기기 내 다른 프로세스의 중복 시작도 파일 잠금·lease로 거절합니다. 도구 호출 ID와 읽은 순서를 제외한 근거 해시가 같으면 모델을 다시 호출하지 않습니다. 준비된 coding_task와 헤드리스 실행은 제외합니다. 새로운 사용자 작업이나 자동 정리 off는 요청을 취소합니다.

기존 사용자 작성 목적·담당 범위·작업은 보존합니다. 최초 자동 관리 이전의 작성 출처를 추측하지 않으며 기존 항목도 사용자 소유로 취급합니다. 새 작업은 충돌하지 않는 ID로 추가합니다. 관리 세션이 전에 작성한 값과 현재 값이 정확히 같을 때만 해당 항목을 자동 수정합니다. 사용자가 편집한 값이나 삭제한 자동 작업은 복원하지 않습니다. 근거에 나타나지 않는다는 이유로 기존 작업을 제거하지 않습니다. 자동 폐기 판단은 이번 단계에 포함하지 않습니다.

분석 시작 시 정책 revision을 저장하고 게시 직전에 다시 확인합니다. 사용자가 분석 도중 편집하면 게시를 거절합니다. 제안은 목적·담당 범위·제공 작업만 포함할 수 있으며 권한·운영 지침·직접 호출 기능은 변경하지 못합니다. 본문과 ID 한도는 기존 정책 검증기로 검사합니다. 게시 후 내부 세션 저장이 실패한 경우에는 다음 실행에서 현재 내용을 사용자 편집처럼 보수적으로 보존할 수 있습니다. 정책과 관리 세션 두 파일을 하나의 트랜잭션으로 갱신한다고 주장하지 않습니다.

JetBrains 현황 패널의 **컴패니언 설명 관리 세션**, VS Code의 같은 이름 명령(`magi.profileMaintenance`)과 현황 추가 메뉴에서 마지막 시도·성공·오류 및 추가·수정 작업 ID를 확인합니다. **갱신 요청**은 선택한 대화의 새 근거를 대상으로 같은 유휴·간격 제한을 사용하며 강제 모델 호출이 아닙니다. `profile-maintenance`는 조회, 같은 요청의 `name=refresh`와 원본 `session`은 갱신 요청입니다. `out`에는 관리 상태 JSON이 옵니다. 자동 정리 on/off는 기존 `companion_auto_describe` 설정을 재사용합니다. 게시된 변경은 원본 채팅에 시스템 메시지로 요약합니다.

현재 작업자는 성공한 파일 읽기 또는 역할에 허용된 네이티브 읽기 전용 결과를 근거로 삼습니다. 셸만으로 읽거나 빌드만 수행한 작업, 외부 상태 변화, 오래된 설명의 자동 폐기는 지원하지 않습니다. 대기 중인 원본 세션 ID와 처리할 기록 위치는 근거 본문 없이 `maintenance.json`에 원자적으로 저장합니다. 같은 세션의 반복 요청은 최신 위치로 합치며, 이전 분석이 끝나도 그동안 추가된 근거는 대기 목록에 남깁니다. 대화형 실행 시작과 자동 관리 다시 켜기 시 대기 원본을 복원하며, 성공한 사용자 턴 뒤에도 다시 확인합니다. 사용자 작업이나 갱신 간격을 기다리는 동안에는 기존 12분 만료를 적용하지 않습니다. 모델 요청은 계속 90초로 제한합니다. 분석에 실패하면 다음 성공한 턴·재시작·수동 갱신 때 다시 처리할 수 있도록 대기 근거를 보존합니다. 비동기 대기 저장이 완료되기 전에 프로세스가 비정상 종료되면 해당 신규 요청은 유실될 수 있습니다. 정상 종료 시 이미 접수한 메타데이터 저장은 최대 5초까지 마무리합니다. 256개 원본 세션 한도에서 기록을 조용히 지우지 않고 새 소스 처리를 거절합니다. 근거 해시는 최근 256개만 보존합니다.

설명 관리 화면에는 자동 관리가 꺼져 있을 때도 대기 중인 원본 대화와 처리할 기록 위치를 표시합니다. 끄면 실행·게시를 중단하되 대기 작업을 보존합니다. 다시 켜면 같은 유휴·갱신 간격 조건으로 이어서 처리합니다. 복원 시에도 원본 대화 기록과 역할에 허용된 읽기 전용 도구를 사용할 수 있어야 합니다. 사용할 수 없으면 대기 목록을 보존하고 사유를 로그에 남깁니다.

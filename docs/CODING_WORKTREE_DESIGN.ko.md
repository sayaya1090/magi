# 코딩 작업의 격리·복구·검토 설계

[English](CODING_WORKTREE_DESIGN.md) · [앱 클라이언트 설계](APPLICATION_CLIENTS_DESIGN.ko.md)

이 문서는 구현 전 설계입니다. 현재 저장소에는 사용자 작업을 관리하는 공통 워크트리 서비스가 없습니다. `git worktree`를 직접 실행하는 것과 작업 수명·컴패니언 소유권을 관리하는 것은 다릅니다. 새 서비스는 터미널·VS Code·JetBrains 등 기존 코딩 에이전트에서도 사용합니다.

2026-10-16 보완: 기능은 코딩 에이전트 전용으로 제한합니다. Git 없는 작업도 지원하며 임의로 `git init`하지 않습니다. §1–§6의 Git 준비·실행·정리 계약에 §7–§15의 환경 선택, 영속 변경 저널, 복구, PR·통합 수명주기를 추가합니다. 아래 API·상태는 제안이며 구현 완료를 뜻하지 않습니다.

## 1. 배치 위치

`작업 원본 → 코딩 작업 → 격리 작업 공간 → 전담 컴패니언 → 세션` 순서로 연결합니다. `internal/app`의 작업 서비스가 수명과 기록을 소유하고, Git 명령 실행과 프로세스 기동은 포트 뒤의 어댑터가 담당합니다. 각 UI는 동일한 작업 API를 호출합니다. 브라우저 확장이나 IDE마다 Git 명령과 복구 상태를 따로 구현하지 않습니다.

컴패니언은 워크트리의 정규 경로를 작업 공간으로 사용합니다. 기존 저장소 컴패니언은 원래 작업 공간을 계속 소유합니다. 부모 세션의 workdir을 바꾸거나 그 대화를 새 작업으로 강제 이동하지 않습니다. Figma·메일·Slack·Office는 코딩 작업을 위임할 수 있지만 워크트리 도구를 기본 제공하지 않습니다.

## 2. 생성과 에이전트 실행

두 조작을 구분합니다.

| 조작 | 수행 내용 | 모델 실행 |
|---|---|---|
| 워크트리 준비 | 기준 commit 확인, 작업 branch·worktree 생성, 작업 기록 저장 | 없음 |
| 코딩 작업 시작 | 준비 작업 수행 또는 기존 준비 재사용, 컴패니언 마련, 작업 세션 생성, 첫 요청 전달 | 요청 전달 후 시작 |

사용자가 ‘이 이슈 작업 시작’을 누르면 전담 코딩 에이전트까지 연결하는 것이 기본입니다. 단순 ‘워크트리 생성’은 비용이 드는 턴을 시작하지 않습니다. 컴패니언 프로세스를 준비하는 것과 모델 호출을 구분해서 UI에 표시합니다.

## 3. 작업 기록과 API

작업 레코드는 `taskId`, 정규 `repositoryCommonDir`, 기준 commit SHA, branch, 정규 worktree 경로, 목적(이슈·PR·사용자 설명), 소유 컴패니언 소켓, sessionId, 상태, 생성·갱신 시간을 가집니다. 모델 키나 토큰을 저장하지 않습니다. 저장 위치는 사용자 설정 디렉터리의 작업 목록이며 저장소에 자동 커밋하지 않습니다.

예정 API는 `coding-task-prepare`, `coding-task-start`, `coding-task-list`, `coding-task-status`, `coding-task-stop`, `coding-task-remove`입니다. 이는 설계 이름이며 아직 데몬에 등록되지 않았습니다. 임의 클라이언트가 경로를 지정하는 문 대신, 신뢰된 기존 코딩 컴패니언의 저장소를 기준으로 작업을 생성합니다. 외부 브라우저 연결은 사용자가 등록한 저장소 식별자로만 접근합니다.

`prepare`는 taskId·branch·worktree·상태를 반환합니다. `start`는 sessionId·컴패니언 정보를 추가합니다. 같은 요청 ID의 재시도는 기존 작업을 반환하고, 새 branch를 하나 더 만들지 않습니다. `list/status`는 Git의 실제 등록 상태와 작업 레코드를 함께 대조합니다.

## 4. 상태와 실패 복구

상태는 `preparing → ready → starting → active → stopped`이며, 단계 실패는 `failed`로 기록합니다. Git 등록과 레코드의 불일치는 `recovery-required`로 표시합니다. 프로세스 실행·모델 작업 중·사용자 응답 대기는 별도 관측값입니다. 작업 상태 하나로 모두 표현하지 않습니다.

생성 전에 `git rev-parse --git-common-dir`, 기준 SHA, `git worktree list --porcelain`, branch와 목적 경로의 점유를 확인합니다. 저장소별 프로세스 간 잠금 아래 생성과 레코드 쓰기를 수행합니다. branch는 `magi/<taskId>`처럼 사용자가 만든 branch와 구분합니다. 자동 `stash`, `reset --hard`, `clean`, branch 덮어쓰기는 하지 않습니다.

Git 생성은 성공했지만 레코드 저장이 실패하면 작업 경로·branch·SHA를 포함한 복구 안내를 반환합니다. 레코드 저장은 원자적으로 교체합니다. 재시작 후 Git 등록을 다시 읽어 복구 가능한 작업을 표시합니다. 임의 디렉터리를 새 작업이라고 자동 채택하지 않습니다. 컴패니언 기동 실패는 준비된 워크트리를 보존하므로 `start`를 재시도할 수 있습니다.

## 5. 중단과 정리

`stop`은 해당 작업의 턴을 중단하거나 컴패니언을 종료하며 워크트리와 branch는 보존합니다. 세션 로그도 보존합니다. 사용자가 검토·다시 시작할 수 있어야 합니다.

`remove`는 작업 레코드와 Git 등록이 같은 경로·branch를 가리키는지, 실행 중인 턴이 없는지 확인합니다. 변경 파일, 추적되지 않은 파일, Git 충돌, 다른 컴패니언 소유가 있으면 자동 삭제하지 않습니다. 삭제 전 상태와 보존할 commit을 보여줍니다. 워크트리 제거와 branch 제거는 별도 조작이며 기본값으로 branch를 지우지 않습니다. 작업 레코드는 정리 결과와 세션 위치를 남깁니다.

## 6. 구현 순서와 인수 기준

1. 작업 레코드·상태·정규 저장소 ID·API의 구조를 먼저 구현합니다. Git 없는 단위 테스트로 상태 전이와 요청 ID 재사용을 확인합니다.
2. 실제 임시 Git 저장소에서 prepare를 연결합니다. 공백 경로, linked worktree, branch 충돌, 다른 프로세스와 동시 생성, 저장 실패 복구를 검증합니다.
3. start를 컴패니언 기동에 연결합니다. 작업별 workdir·소켓·세션이 고정되는지, 생성만 해서는 모델을 호출하지 않는지 확인합니다.
4. 기존 CLI를 첫 호출자로 연결하고 VS Code·JetBrains 순서로 UI를 연결합니다. 같은 작업이 모든 화면에서 동일하게 조회돼야 합니다.
5. stop/remove를 구현합니다. 변경 파일·미추적 파일·활성 턴·외부 소유 worktree가 있으면 정리를 거절하는 테스트가 필요합니다.
6. CLI 실물과 브라우저 Playwright를 실행하고, 담당자 외 교차 검토로 경로·명령 인자·복구·삭제 계약을 확인합니다. 실제 실행 결과를 기록한 뒤 구현 완료로 표시합니다.

초기 앱 클라이언트는 아직 이 서비스가 없는 상태에서도 사용할 수 있습니다. 이 문서의 API를 구현하기 전에는 UI에 동작하지 않는 워크트리 버튼을 추가하지 않습니다.

## 7. 코딩 전용 기능과 환경 선택

서버가 확인한 `ClientCoding`에만 작업 API와 도구를 제공합니다. VS Code·IntelliJ·TUI·CLI는 같은 서비스를 사용합니다. 역할 문자열을 모델이 바꿔도 권한이 생기지 않습니다. 비코딩 앱은 기존 위임 경로를 사용하며 작업 원본의 임의 경로를 지정하지 않습니다.

| 환경/선택 | 작업 공간 | 결과 반영 |
| --- | --- | --- |
| 정상 Git 저장소, HEAD 있음 | 전용 branch와 worktree | PR 또는 명시적 로컬 통합 |
| Git 없음/저장소 아님, 격리 선택 | 파일 manifest 기반 독립 복사본 | 원본과 기준 snapshot 비교 후 선택 반영 |
| 원본 직접 작업을 명시적으로 선택 | 고정된 원본 폴더 | 영속 변경 저널이 지원하는 변경만 복구 보장 |
| Git 초기 commit 없음 | 명시적인 snapshot 복사 또는 초기화 결정 대기 | 원본에 자동 commit/init하지 않음 |
| Git 접근 오류·손상·권한 부족 | 실패/복구 필요 | Git 없음으로 조용히 강등하지 않음 |

기본은 준비와 격리입니다. 원본 직접 작업과 Git 작업의 미커밋 내용 포함은 별도 선택입니다. 준비만으로 모델 호출·원격 push·PR·병합을 시작하지 않습니다. 정상 Git의 기준은 commit SHA이며 원본의 미커밋 변경은 그대로 보존하고 포함 여부를 표시합니다. PR 미지원과 네트워크/인증 장애는 다릅니다. PR 정책이 있는 작업을 장애 때문에 로컬 완료로 바꾸지 않습니다.

## 8. 현재 재사용 가능한 구현과 한계

`internal/app/workspace.go`는 선택적 자식 clone과 미커밋 변경 반영을 이미 지원합니다. 새 작업 서비스와 같은 API는 아니므로 기존 spawn 의미를 자동 변경하지 않습니다. `restore.go`의 자식 복원 저널은 메모리 중심이며, `trash.go`의 비 Git 편집 백업은 원자적 교체를 전제로 한 hardlink입니다. 이를 임의 셸 변경·재시작 복구의 완전한 보장으로 설명하지 않습니다.

새 영속 백업은 독립적인 파일 복사 또는 독립성이 보장되는 copy-on-write snapshot을 사용합니다. 원본이 in-place 수정될 수 있는 경로에서 hardlink를 불변 백업이나 격리 복사본으로 사용하지 않습니다. 기존 복원 결과처럼 경로별 성공/실패를 명시하는 계약은 재사용합니다.

## 9. 영속 변경 저널

작업 기록과 백업은 `<config>/coding-tasks/tasks/<taskId>`에 두고 원본 밖에 저장합니다. `taskId`, requestId, 원본 정규 경로·파일시스템 식별, 작업 공간, mode, 기준 manifest/commit, session, journal, 검증 결과, 통합 상태를 연결합니다. 사용자 파일·백업에는 private 접근 권한을 적용하고 원격 전송·저장소 자동 커밋을 하지 않습니다.

각 연산에는 operationId, 대상 상대 경로, 종류, before/after의 존재 여부·파일 종류·내용 digest·지원 속성, 백업 blob 참조, 단계와 실패 사유를 기록합니다. 먼저 독립 백업과 intent를 영속화하고 prepared를 확인한 뒤 변경합니다. 변경 후 관측한 상태를 applied로 기록합니다. 결과 저장 전에 중단되면 uncertain으로 남기고 실제 파일을 대조합니다. 알려진 before/after 모두와 다르면 충돌로 처리합니다. 임의 셸 명령은 uncertain 상태에서 재실행하지 않습니다.

수정·생성·삭제·이동을 별도 연산으로 표현합니다. 이동은 출발/도착 양쪽의 기준과 덮어쓸 기존 파일을 보존합니다. 디렉터리 삭제는 영향받는 모든 지원 파일이 보존됐을 때만 복구 가능으로 분류합니다. 백업 실패·용량 초과·지원하지 않는 속성은 변경 전에 실패하며 강한 복구 보장을 조용히 낮추지 않습니다.

복구 보장의 초기 범위는 일반 파일의 바이트·존재 여부·실행 권한입니다. ACL/xattr·소유권·파일 링크·특수 파일·열려 있는 파일·교차 볼륨 이동은 지원 가능성을 따로 표시합니다. 시간/크기만으로 변경 여부를 판단하지 않습니다. 경로의 대소문자 충돌·symlink·junction·부모 경로 교체와 workspace 밖 쓰기를 검증합니다.

## 10. 격리 복사와 원본 반영

비 Git 기본안은 작업 시작 시 manifest를 만들고 독립 복사본에서 개발하는 것입니다. 소스 범위·제외 목록·파일 수·바이트 예산을 준비 결과에 표시합니다. 환경 파일·의존성·빌드 산출물을 자동으로 모두 복사하지 않습니다. 필요한 제외 파일은 명시적으로 선택하며 누락 상태를 숨기지 않습니다. 읽는 동안 원본이 바뀌어 일관된 snapshot을 얻지 못하면 실패 또는 재시도를 기록합니다. 일반 복사가 OS 수준 원자적 snapshot이라고 주장하지 않습니다.

원본에 적용할 때 기준 B, 작업 결과 W, 현재 원본 C를 비교합니다. B=W면 변경 없음, C=B면 적용 후보, C=W면 이미 반영됨, 나머지는 충돌입니다. 충돌 파일을 덮어쓰지 않습니다. 적용 전 원본을 다시 백업하며 다중 파일 반영 중 중단은 경로별 결과와 재개 지점으로 복구합니다. 확인한 digest·경로·종류를 재검사하고 Magi writer를 직렬화하지만, 비협조적 외부 writer와의 모든 TOCTOU를 없앴다고 보장하지 않습니다.

복사본 실행은 셸의 외부 경로·네트워크·DB 변경까지 격리하지 않습니다. 권한 정책과 OS sandbox는 별도입니다. 하드코딩된 원본 절대 경로·symlink·공유 서비스는 영향 범위로 표시하고, 필요한 통제를 제공하지 못하면 해당 실행을 복구 가능으로 분류하지 않습니다.

## 11. 복구·중단·보존

복원은 현재 상태가 해당 작업의 after와 일치할 때만 before를 원래 위치에 되돌립니다. 생성 파일은 내용이 그대로일 때만 제거하고, 사람이 수정했다면 보존합니다. 새 디렉터리에 외부 파일이 생겼으면 재귀 삭제하지 않습니다. 충돌 시 before를 별도 위치에 내보내고 선택을 기다립니다. 복원 자체도 새 operation으로 기록하며 부분 복원을 전체 성공으로 표시하지 않습니다.

stop은 모델·백그라운드 작업 종료와 파일 복원을 구분합니다. 실행 중 writer를 멈추기 전에 복원하지 않습니다. 프로세스 종료는 이미 수행한 외부 부작용을 취소하지 않습니다. 작업별 복구 결과에는 restored/conflict/unsupported/uncertain을 표시합니다.

삭제·보존 예산은 준비 시 정합니다. 활성 작업·미해결 충돌·불확실 연산의 마지막 복구 자료를 자동 정리하지 않습니다. 정상 종료 후에도 검토·통합·보존 정책이 끝나기 전에는 백업을 지우지 않습니다. 공간이 부족하면 변경을 멈추고 상태를 보존합니다.

## 12. 검토·PR·병합 수명주기

작업 실행 상태와 integration 상태를 분리합니다. 실행은 ready/running/stopped/failed/recovery-required, 통합은 unreviewed/verified/review-pending/changes-requested/ready-to-integrate/integrated로 표현합니다. 모델의 “완료”는 실제 검증·병합 상태를 바꾸는 증거가 아닙니다.

Git 원격 제공자는 PR URL·번호·base/head SHA·필수 CI 결과·리뷰 상태를 기록합니다. PR 생성 재시도는 작업 식별자와 기존 PR을 조회해 중복을 방지합니다. push·PR 생성·병합은 각각 정책과 권한을 확인합니다. 병합 직전 동일 head의 검증과 미해결 리뷰, 현재 base를 재확인합니다. 자동 병합은 저장소가 명시적으로 허용한 경우만 가능하며 기본은 사용자 통합 결정입니다.

PR 없는 Git은 검토한 commit의 로컬 통합, 비 Git은 검토한 manifest/diff의 원본 적용으로 대체합니다. 모두 사전 상태가 달라지면 재검토가 필요합니다. 워크트리·복사본·branch 삭제는 통합과 별도이며 기본 자동 삭제하지 않습니다. Git worktree도 공통 refs/config/hooks·서비스·포트·자격증명을 완전히 격리하지 않습니다.

## 13. 책임·대안·품질 요구

`internal/app`은 코딩 역할 검사, 작업 orchestration과 세션 바인딩을 담당합니다. 작업 저장소·journal/snapshot·Git·원격 PR·프로세스 실행은 포트 뒤에 둡니다. UI가 자체 복구/병합을 수행하지 않습니다. 명령은 인자 배열로 실행하고 경로를 셸 문자열에 삽입하지 않습니다.

| 선택 | 이유 | 비용/한계 |
| --- | --- | --- |
| Git worktree | branch/index/작업 파일 충돌을 줄임 | Git 공통 상태와 외부 부작용은 공유 |
| 독립 복사본 | Git 없이 임의 로컬 변경을 원본과 분리 | 디스크·복사 시간, 제외 자료 관리 |
| 직접 작업 + 저널 | 큰 프로젝트의 복사 비용 회피 | 도구 밖 변경 포착과 외부 writer 충돌에 한계 |
| 자동 git init 배제 | 사용자 저장소 정책 보존 | Git 없는 diff/통합 기능을 별도 제공 |
| 영속 intent + 제한 재시도 | crash 이후 중복/미확정 변경 구분 | 기록 I/O와 복구 상태 복잡성 |

내결함성은 중단 지점별 재개와 경로별 결과, 사용성은 “원본 변경 여부·복구 범위·다음 행동”의 일관된 표시로 평가합니다. 보안은 경로·역할·권한 검사, 성능은 파일/바이트/시간 예산과 취소 가능성, 변경 용이성은 공통 API와 adapter 분리로 평가합니다. 구체 시간·용량 기본값은 실제 측정 후 정하며 무제한 복사로 시작하지 않습니다.

## 15. 단계적 구현

1. 환경 판정·역할 검사·영속 작업 기록·prepare/list/status와 Git worktree/비 Git copy를 구현합니다.
2. snapshot/diff·원본 선택 적용·충돌 검사·재시작 후 복구를 연결하고 실제 파일로 검증합니다.
3. 모델 세션을 작업 공간에 고정하고 CLI·TUI·IDE 공통 도구/API로 연결합니다. prepare만으로 모델은 실행하지 않습니다.
4. 직접 작업 저널과 안전한 복원, stop/remove를 완성합니다. 미지원 mode는 명확히 거절합니다.
5. 원격 PR/CI/review adapter와 통합 정책을 연결합니다. 기존 PR 기능을 재사용하되 head 기준의 증거를 검증합니다.
6. 실제 개발 요청, 오류 주입, Playwright가 필요한 UI 변경, 교차 검토의 결과를 기록합니다. 단계별 구현/미구현을 명시합니다.

## 16. 현재 구현과 사용 절차 (2026-10-16)

이 절은 `feat/coding-task-recovery` 브랜치의 구현 범위입니다. 앞 절의 전체 목표를 완료했다는 뜻은 아닙니다. `internal/adapter/codingworkspace`가 파일·Git 어댑터를, `port.CodingTasks`가 공통 계약을 담당합니다. `internal/app`은 코딩 역할과 세션의 실제 workdir을 검사합니다.

### 16.1 제공 기능

- `magi coding-task prepare/list/status/diff/review/run/apply/restore/recover`를 제공합니다. prepare는 모델을 호출하지 않습니다. run은 작업 폴더에서 기존 Magi 실행기를 사용하고, 모델·도구를 소유하는 같은 프로세스가 작업 잠금을 유지합니다.
- VS Code·IntelliJ·TUI의 코딩 세션은 공통 `coding_task` 도구로 prepare/list/status/diff/review를 호출할 수 있습니다. 이 도구는 현재 세션의 작업 폴더를 자동으로 바꾸지 않습니다. 격리 실행은 CLI run으로 시작합니다. 전용 IDE 작업 선택 UI와 자동 컴패니언 전환은 아직 없습니다.
- Git에서는 새 branch/worktree를 만들고 원본 index를 변경하지 않습니다. 기본 기준은 clean HEAD입니다. 미커밋 변경이 있으면 명시적 `--base HEAD` 또는 `--mode copy`가 필요합니다. 저장소 하위 폴더의 Git 모드는 저장소 루트를 안내하며 거절합니다.
- 비 Git에서는 독립 복사본을 만들며 자동 init/commit하지 않습니다. diff는 변경 경로·digest·권한을 보여주고 review는 선택 파일의 원문 before/after를 보여줍니다. 바이너리와 256 KiB를 넘는 파일은 원문 응답을 생략하고 이유를 표시합니다.
- copy 모드의 apply는 선택 경로만 반영합니다. 기준과 달라진 원본은 충돌로 보존합니다. restore는 작업이 반영한 내용과 일치할 때만 되돌립니다. 작업 기록·저널을 다시 읽으므로 프로세스 재시작 후에도 복원할 수 있습니다. CLI는 partial/uncertain 결과를 JSON으로 남기고 종료 코드 1을 반환합니다.
- 실행 중 중단된 작업은 잠금을 얻은 뒤 recover할 수 있습니다. 준비가 불완전한 작업은 자동 승인하거나 삭제하지 않고 보존 위치와 새 request ID 사용을 안내합니다. 기존 통합 저널이 있으면 재적용을 거절합니다. 복원 후 추가 개발을 반영하려면 새 작업을 준비합니다.

기본 복사 예산은 5,000개 일반 파일·128 MiB입니다. 작업별 누적 blob은 512 MiB·20,000개로 제한하며, 반복 조회로 이전 버전이 무제한 쌓이지 않도록 합니다. 한도 초과 시 기존 복구 자료를 지우지 않고 실패합니다. `.git`, `.magi`, `.codex`, `.ssh`, `.aws`, `node_modules`, `.venv`, `venv`, `.DS_Store`, `.env`, `.env.*`를 제외하며 `.env.example`은 포함합니다. 이 목록이 모든 비밀 파일을 찾아낸다는 뜻은 아닙니다. symlink와 특수 파일은 거절합니다. 기본 작업 저장소는 `<config>/coding-tasks`이고 원본과 서로 포함될 수 없습니다. 기존 부모의 경로 별칭까지 정규화해 macOS `/var`·`/tmp` 경로의 재시작 식별을 유지합니다.

각 CLI 연산의 기본 시간 예산은 10분이며 `--timeout 20m`처럼 바꿀 수 있습니다. 조회 응답은 큰 기준 manifest 대신 파일 수·총 바이트·제외 목록을 반환합니다. 전체 manifest와 독립 blob은 private 작업 저장소에 남습니다.

### 16.2 사용 예

```sh
# 저장소 루트에서 실행. Git 없는 폴더라면 auto가 copy를 선택합니다.
magi coding-task prepare --request feature-001 --purpose '입력 검증 추가'
# 반환된 taskId를 사용합니다. prepare만으로 원본 변경이나 모델 호출은 없습니다.
magi coding-task run --id TASK_ID --prompt '입력 검증을 추가하고 테스트해 줘'
magi coding-task diff --id TASK_ID
magi coding-task review --id TASK_ID --path src/example.go
# 비 Git 또는 명시적으로 선택한 copy 작업: 검토한 경로만 지정합니다.
magi coding-task apply --id TASK_ID src/example.go
magi coding-task restore --id TASK_ID
# 실행 중 프로세스가 끊겼을 때 작업 폴더를 검사한 뒤 사용합니다.
magi coding-task recover --id TASK_ID
```

기본 source는 현재 폴더입니다. 다른 폴더에서 조회하려면 모든 명령에 같은 `--source /path/to/project`를 사용합니다. `--store`도 바꿨다면 같은 값을 사용해야 합니다. 옵션은 apply의 경로 목록보다 앞에 둡니다. Git 작업은 파일 apply를 거절하므로 해당 workspace에서 commit·검증·PR 검토를 수행합니다. 아직 PR 생성·CI 확인·병합을 자동 수행하는 작업 서비스는 없습니다.

### 16.3 검증과 남은 범위

실제 임시 Git 저장소와 비 Git 파일에서 독립 수정, 요청 ID 재사용·동시 준비, 경로·symlink·용량 거절, 백업 손상, 삭제 복원, 재시작, 기록 전 중단된 쓰기의 복원, 사용자 변경 보존을 검사했습니다. 빌드한 CLI에 모의 provider를 연결하는 회귀 검사는 실제 도구 실행과 작업 폴더 고정을 확인합니다. 이 검사를 실모델 검증으로 세지 않습니다.

별도 실모델 검증에서는 이 머신의 `qwen3.8:27b-mlx`가 임시 `calculator.py`의 뺄셈 오류를 덧셈으로 수정하고 `python3 -m unittest -v`를 exit 0으로 실행했습니다. 원본 불변, 검토 후 선택 반영, 반영된 원본 테스트 통과, 후속 사용자 수정이 있을 때 partial 복원과 내용 보존, 명시적으로 작업 버전을 선택한 뒤 기준 복원을 확인했습니다. 카운슬은 이 격리 기능 검사에서 껐습니다. 원격 PR/카운슬 승인을 검증한 결과가 아닙니다.

재현 도구는 `python3 tools/test-coding-task.py --binary /path/to/magi --model MODEL`입니다. 기존 프로젝트와 설정을 건드리지 않고 임시 디렉터리의 로그·판정 JSON을 남깁니다. 모델 실행 권한은 이 임시 작업에서 allow로 설정하므로 테스트용 환경에서 사용합니다. 로컬 모델을 자동으로 찾거나 다운로드하지 않습니다.

미완료 범위는 전용 IDE/TUI 작업 관리 화면, 자동 작업 세션 전환, 직접 편집 mode의 영속 저널, stop/remove·보존 정책, PR/CI/review 서비스입니다. Windows는 크로스 빌드 범위이며 실물 인수는 남았습니다. 복사본은 셸·DB·네트워크의 외부 부작용을 격리하지 않으며, 비협조적인 외부 writer와의 경로 교체 경쟁 및 전원 장애까지의 파일시스템 내구성을 보장하지 않습니다. 부분 실패는 전체 성공으로 보고하지 않습니다.

### 16.4 턴·동시성 추가 검증 (20회 반복)

`-race`와 고정 shuffle seed `20261016`으로 다음 검사를 반복했습니다. CLI 실물 검사는 실행하는 Magi 바이너리도 `-race`로 빌드했습니다. 여기의 모델은 순서를 통제하는 모의 provider이며, 실모델 20회 실행 결과는 아닙니다. 실제 파일·프로세스·Git·잠금·영속 이벤트는 그대로 사용합니다.

| 검사 묶음 | 최상위 테스트 수 | 반복 | 통과 |
| --- | --- | --- | --- |
| 작업공간·복구·동시성, 소유권 검사 수정 후 | 20 | 20 | 400 |
| 코어의 턴 중 요청·취소·종료 경계·모델 설정 경합 | 11 | 20 | 220 |
| CLI 선택 반영·부분 실패·정상 턴·취소 턴 | 4 | 20 | 80 |
| 별도 프로세스 2개의 동일 작업 동시 준비 | 1 | 20 | 20 |

표는 하위 subtest를 중복 합산하지 않았습니다. 정상 턴과 취소 턴을 각각 20회 확인했습니다. JSONL 감사는 session/workdir 일치, 증가하는 seq, 도구 호출 뒤 정확히 한 번 오는 결과, 한 번의 완료, 완료 후 추가 답변 부재를 확인합니다. 정상 턴은 대화 모델 요청 두 번을 기대하고, Engram의 종료 후 교훈 분석은 별도 요청으로 분류합니다. 분석이 답변이나 중복 완료로 기록되지 않는지도 확인합니다.

추가한 경합 검사는 같은 원본에 두 작업을 동시에 반영해 하나만 성공하고 다른 하나는 충돌로 남는지, 실패한 작업의 복원이 성공한 작업의 파일을 되돌리지 않는지, 같은 작업의 중복 반영이 하나의 저널만 만드는지 확인합니다. 실행 잠금이 잡혀 있으면 반영·복원은 기다리다가 취소되며 원본을 바꾸지 않습니다. 프로세스 두 개가 같은 request ID를 사용해도 하나의 작업만 준비됩니다.

검사 중 소유 작업공간 확인보다 잠금 대기가 먼저인 문제를 재현했습니다. 실행 중인 작업 ID를 다른 source에서 사용하면 소유권 오류를 즉시 돌려주는 대신 시간 제한까지 기다렸습니다. 작업 폴더 안의 모델이 원래 작업 ID로 조회하면 자기 실행 잠금을 기다릴 수도 있습니다. `lockExisting`에서 source와 작업 식별을 먼저 확인하고, 잠금 획득 후 기존 검사를 다시 수행하도록 수정했습니다. review/diff/apply/restore/recover/run 여섯 경로를 각각 20회 검사했습니다. 수정 후 위 반복 검사에서 실패나 race detector 보고는 없었습니다.

재실행은 `go test -race -shuffle=20261016 -count=20 ./internal/adapter/codingworkspace`와 `go test -race -shuffle=20261016 -count=20 -run '^TestCodingTask' ./cmd/magi`를 사용합니다. 코어 경합 테스트는 `interject_races_test.go`, `steer_finish_race_test.go`, `cancel_then_ask_test.go`, `cancel_clears_queue_test.go`, `routing_race_test.go`의 대상 11개를 선택했습니다. 개별 검사 이름·반복 수와 원본 로그 digest는 `docs/qa/coding-task-race20-20261016.json`에 보존했습니다. 이 검사는 Windows 실물, 실제 모델의 비결정적 판단, 모든 외부 writer의 경쟁을 검증한 것은 아닙니다.

### 16.5 도구 계약과 Gradle 출력 처리 보완

격리 폴더 준비와 그 폴더에서의 실행을 구분합니다. `coding_task`는 현재 세션을 옮기지 않습니다. prepare/status 응답에는 `sessionWorkdir`, `sessionWorkdirChanged:false`, 다음 행동과 별도 실행기의 `runCommand` 인자 배열을 제공합니다. 배열의 각 항목은 하나의 인자이므로 공백이 있는 경로를 따옴표 없이 셸 문자열로 합치면 안 됩니다. 현재 세션에서 작업 결과를 볼 때는 taskId로 diff/review를 호출합니다.

| operation | 필수 입력 | 추가 입력과 범위 |
| --- | --- | --- |
| prepare | requestId | mode/base/purpose. path·taskId는 받지 않음. base는 Git 기준 commit/ref이며 copy와 함께 사용할 수 없음 |
| list | 없음 | 현재 세션의 source에 속하는 작업 목록. taskId·path를 받지 않음 |
| status / diff | taskId | prepare가 반환한 ID. path를 받지 않음 |
| review | taskId, path | path는 `src/main.go`처럼 작업 폴더 기준의 상대 파일 경로 |

알 수 없는 필드와 해당 operation에서 사용하지 않는 입력은 명확한 오류로 거절합니다. prepare의 path를 원본 폴더로 해석하거나 조용히 무시하지 않습니다. 파일 도구의 설명에도 같은 세션 경계를 표시하고, bash의 cd가 그 경계를 바꾸지 않음을 명시합니다. 기본 권한 정책과 sandbox는 유지합니다.

Gradle 출력은 실제 모듈의 `build.gradle`, `build.gradle.kts`, `settings.gradle`, `settings.gradle.kts` 옆에 있는 `build` 디렉터리로 인식합니다. `.gradle`, `.kotlin`, `.gradle-test-kit` 캐시 디렉터리도 제외합니다. 이 추가 규칙은 Git 추적 파일이나 기존 baseline 파일을 포함하는 디렉터리에는 적용하지 않습니다. `src/build`처럼 모듈 표시가 없는 소스 폴더를 이름만 보고 제외하지 않습니다. 기존 작업의 baseline을 새 제외 규칙으로 축소하지 않으므로 관리하던 파일을 삭제로 오인하지 않습니다. 기존의 비밀 파일·메타데이터 제외 규칙은 그대로 적용합니다.

재현에 사용한 실제 Gradle 프로젝트는 이전에 생성된 `gradle-api-9.4.1.jar` 때문에 복사 예산을 초과했습니다. 수정한 실행기가 원본을 읽어 별도 임시 저장소에 copy 작업을 준비했을 때 93개 파일·454,829바이트로 ready가 됐으며, build/cache 제외 경로를 반환했습니다. 원본의 캐시나 빌드 디렉터리는 삭제하지 않았습니다. 이 검사는 원본을 읽는 준비 과정이며 해당 프로젝트의 빌드 성공을 뜻하지 않습니다.

`bash.timeout`은 전경 실행 시간입니다. 백그라운드 작업에는 적용되지 않습니다. `wait_for`의 job 대기 시간만 끝나고 작업이 계속 실행 중이면 `IsError=false`인 상태 조회 결과를 반환합니다. 작업을 자동 재시작하거나 종료하지 않으며 다음 wait_for 호출을 안내합니다. 명시적 취소·없는 job·잘못된 인자는 오류로 유지합니다. 기존 문자열 응답 형식은 보존합니다.

Gradle 출력 제외, 일반 소스·Git 추적 파일·기존 baseline 보존, 대기 시간 초과와 취소 구분, operation별 인자 검증과 실행 안내를 회귀 검사에 추가하고 각각 20회 반복했습니다. 대상 패키지의 전체 race 검사도 통과했습니다. 도구 정의는 실행 중인 데몬의 메모리에 있으므로 설치된 바이너리를 교체해도 기존 데몬에는 즉시 적용되지 않습니다. 진행 중인 작업이 끝난 뒤 데몬을 재시작해야 새 명세와 동작을 사용합니다.

# 코딩 작업과 워크트리 설계

[English](CODING_WORKTREE_DESIGN.md) · [앱 클라이언트 설계](APPLICATION_CLIENTS_DESIGN.ko.md)

이 문서는 구현 전 설계입니다. 현재 저장소에는 사용자 작업을 관리하는 공통 워크트리 서비스가 없습니다. `git worktree`를 직접 실행하는 것과 작업 수명·컴패니언 소유권을 관리하는 것은 다릅니다. 새 서비스는 터미널·VS Code·JetBrains 등 기존 코딩 에이전트에서도 사용합니다.

## 1. 배치 위치

`저장소 → 코딩 작업 → 워크트리 → 전담 컴패니언 → 세션` 순서로 연결합니다. `internal/app`의 작업 서비스가 수명과 기록을 소유하고, Git 명령 실행과 프로세스 기동은 포트 뒤의 어댑터가 담당합니다. 각 UI는 동일한 작업 API를 호출합니다. 브라우저 확장이나 IDE마다 Git 명령과 복구 상태를 따로 구현하지 않습니다.

컴패니언은 워크트리의 정규 경로를 작업 공간으로 사용합니다. 기존 저장소 컴패니언은 원래 작업 공간을 계속 소유합니다. 부모 세션의 workdir을 바꾸거나 그 대화를 새 작업으로 강제 이동하지 않습니다. Figma·메일·Slack·Office는 코딩 작업을 위임할 수 있지만 워크트리 도구를 기본 제공하지 않습니다.

## 2. 생성과 에이전트 실행

두 조작을 구분합니다.

| 조작 | 수행 내용 | 모델 실행 |
|---|---|---|
| 워크트리 준비 | 기준 commit 확인, 작업 branch·worktree 생성, 작업 기록 저장 | 없음 |
| 코딩 작업 시작 | 준비 작업 수행 또는 기존 준비 재사용, 컴패니언 마련, 작업 세션 생성, 첫 요청 전달 | 요청 전달 후 시작 |

사용자가 ‘이 이슈 작업 시작’을 누르면 전담 코딩 에이전트까지 연결하는 것이 기본입니다. 단순 ‘워크트리 생성’은 비용이 드는 턴을 시작하지 않습니다. 컴패니언 프로세스를 준비하는 것과 모델 호출을 구분해서 UI에 표시합니다.

## 3. 작업 기록과 API

작업 레코드는 `taskId`, 정규 `repositoryCommonDir`, 기준 commit SHA, branch, 정규 worktree 경로, 목적(이슈·PR·사용자 설명), 소유 컴패니언 소켓, sessionId, 상태, 생성·갱신 시간을 가집니다. 모델 키나 토큰을 저장하지 않습니다. 저장 위치는 사용자 설정 디렉터리의 작업 목록이며 저장소에 자동 커밋하지 않습니다.

예정 API는 `coding-task-prepare`, `coding-task-start`, `coding-task-list`, `coding-task-status`, `coding-task-stop`, `coding-task-remove`입니다. 이는 설계 이름이며 아직 데몬에 등록되지 않았습니다. 임의 클라이언트가 경로를 지정하는 문 대신, 신뢰된 기존 코딩 컴패니언의 저장소를 기준으로 작업을 생성합니다. 외부 브라우저 연결은 사용자가 등록한 저장소 식별자로만 접근합니다.

`prepare`는 taskId·branch·worktree·상태를 반환합니다. `start`는 sessionId·컴패니언 정보를 추가합니다. 같은 요청 ID의 재시도는 기존 작업을 반환하고, 새 branch를 하나 더 만들지 않습니다. `list/status`는 Git의 실제 등록 상태와 작업 레코드를 함께 대조합니다.

## 4. 상태와 실패 복구

상태는 `preparing → ready → starting → active → stopped`이며, 단계 실패는 `failed`로 기록합니다. Git 등록과 레코드의 불일치는 `recovery-required`로 표시합니다. 프로세스 실행·모델 작업 중·사용자 응답 대기는 별도 관측값입니다. 작업 상태 하나로 모두 표현하지 않습니다.

생성 전에 `git rev-parse --git-common-dir`, 기준 SHA, `git worktree list --porcelain`, branch와 목적 경로의 점유를 확인합니다. 저장소별 프로세스 간 잠금 아래 생성과 레코드 쓰기를 수행합니다. branch는 `magi/<taskId>`처럼 사용자가 만든 branch와 구분합니다. 자동 `stash`, `reset --hard`, `clean`, branch 덮어쓰기는 하지 않습니다.

Git 생성은 성공했지만 레코드 저장이 실패하면 작업 경로·branch·SHA를 포함한 복구 안내를 반환합니다. 레코드 저장은 원자적으로 교체합니다. 재시작 후 Git 등록을 다시 읽어 복구 가능한 작업을 표시합니다. 임의 디렉터리를 새 작업이라고 자동 채택하지 않습니다. 컴패니언 기동 실패는 준비된 워크트리를 보존하므로 `start`를 재시도할 수 있습니다.

## 5. 중단과 정리

`stop`은 해당 작업의 턴을 중단하거나 컴패니언을 종료하며 워크트리와 branch는 보존합니다. 세션 로그도 보존합니다. 사용자가 검토·다시 시작할 수 있어야 합니다.

`remove`는 작업 레코드와 Git 등록이 같은 경로·branch를 가리키는지, 실행 중인 턴이 없는지 확인합니다. 변경 파일, 추적되지 않은 파일, Git 충돌, 다른 컴패니언 소유가 있으면 자동 삭제하지 않습니다. 삭제 전 상태와 보존할 commit을 보여줍니다. 워크트리 제거와 branch 제거는 별도 조작이며 기본값으로 branch를 지우지 않습니다. 작업 레코드는 정리 결과와 세션 위치를 남깁니다.

## 6. 구현 순서와 인수 기준

1. 작업 레코드·상태·정규 저장소 ID·API의 구조를 먼저 구현합니다. Git 없는 단위 테스트로 상태 전이와 요청 ID 재사용을 확인합니다.
2. 실제 임시 Git 저장소에서 prepare를 연결합니다. 공백 경로, linked worktree, branch 충돌, 다른 프로세스와 동시 생성, 저장 실패 복구를 검증합니다.
3. start를 컴패니언 기동에 연결합니다. 작업별 workdir·소켓·세션이 고정되는지, 생성만 해서는 모델을 호출하지 않는지 확인합니다.
4. 기존 CLI를 첫 호출자로 연결하고 VS Code·JetBrains 순서로 UI를 연결합니다. 같은 작업이 모든 화면에서 동일하게 조회돼야 합니다.
5. stop/remove를 구현합니다. 변경 파일·미추적 파일·활성 턴·외부 소유 worktree가 있으면 정리를 거절하는 테스트가 필요합니다.
6. CLI 실물과 브라우저 Playwright를 실행하고, 담당자 외 교차 검토로 경로·명령 인자·복구·삭제 계약을 확인합니다. 실제 실행 결과를 기록한 뒤 구현 완료로 표시합니다.

초기 앱 클라이언트는 아직 이 서비스가 없는 상태에서도 사용할 수 있습니다. 이 문서의 API를 구현하기 전에는 UI에 동작하지 않는 워크트리 버튼을 추가하지 않습니다.

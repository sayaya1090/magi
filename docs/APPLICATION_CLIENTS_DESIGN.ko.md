# 앱 클라이언트 설계와 구현 계약

[English](APPLICATION_CLIENTS_DESIGN.md) · [클라이언트 개요](CLIENTS.ko.md)

Figma, 일반 IMAP/SMTP 메일, Slack, GitHub를 Magi의 새 클라이언트로 연결합니다. 이 문서는 현재 구현의 공통 계약과 검증 요구사항을 정합니다. 각 앱 매뉴얼은 설치·계정 설정·사용법을 설명합니다. 실제 계정에서 확인하지 않은 기능은 모의 테스트 통과와 구분합니다.

## 1. 역할과 화면

| 클라이언트 | 사용자 화면 | 에이전트의 업무 | 기본 제공하지 않는 작업 |
|---|---|---|---|
| Figma | Figma 개발 플러그인 패널 | 선택한 디자인 조회, 텍스트 수정, 프레임 생성 | 셸·소스 편집, 파일 전체 스캔, 외부 게시 |
| 메일 | 로컬 브라우저 메일 화면 | 선택 메일 정리, 요청 사항 파악, 서신 초안 | 모델의 직접 발송, OAuth·첨부파일 처리 |
| Slack | App Home, DM, 멘션 스레드 | 대화 요약, 업무 조율, 메시지 초안 | 셸·코드 편집, 다른 채널에 임의 게시 |
| GitHub | github.com의 Chrome/Chromium 사이드 패널 | 저장소·이슈·PR에 연결된 코딩 작업 | 사용자 지시 없는 댓글·push·merge |
| 기존 Office | PowerPoint·Word·Excel 작업창 | 발표자료·문서·스프레드시트 작성과 검증 | 기본 코딩 정체성, 앱 밖의 셸·소스 편집 |

`--client-role`과 `MAGI_CLIENT_ROLE`이 역할을 선택합니다. 빈 값은 기존 코딩 동작을 유지합니다. `github`도 코딩 역할입니다. 나머지는 `internal/app/client_role.go`에서 앱별 시스템 지침을 사용하고, 모델에 광고하는 도구 목록과 실제 실행 경로에서 같은 역할 제한을 적용합니다. 앱의 MCP 네임스페이스와 질문·카운슬·계획·기억 조회 같은 공통 도구만 허용합니다. 모델이 숨겨진 `bash`나 다른 앱의 도구를 직접 요청해도 실행하지 않습니다.

Office는 새 컴패니언을 시작할 때 앱 역할을 전달합니다. 이미 실행 중인 구형 컴패니언은 새 프로그램을 설치하는 것만으로 역할이 바뀌지 않습니다. 마이그레이션 인수에서는 새 역할로 기동한 프로세스와 구형 프로세스의 재시작을 각각 확인해야 합니다.


## 1.1. 역할별 고유 프롬프트

역할 원문은 `internal/app/client_role.go`, 기본 코딩 지침은 `cmd/magi/main.go`의 `systemPrompt`에 있습니다. 아래는 원문의 의미를 정리한 표이며 별도 실행 설정이 아닙니다.

| 역할 | 고유 지침 |
|---|---|
| 기본 코딩(터미널·VS Code·JetBrains) | 프로젝트 직접 조사, 기존 관례 준수, 계획·구현·검증 수행 |
| GitHub 코딩 | 연결 저장소·이슈·PR 확인, 저장소·브랜치 귀속 검증, 테스트 수행, 명시적 지시 없는 댓글·push·merge 금지 |
| Figma 디자인 | 디자인 의도·타이포그래피·간격·컴포넌트·접근성 보존, 수정 전 선택 영역·파일·페이지 확인 |
| 메일 서신 | 요청 사항 파악과 사용자 어조의 초안, 사실·약속·수신자 창작 금지, 초안과 발송 구분 |
| Slack 협업 | 결정·제안 구분, 담당자와 후속 작업 정리, 요청자의 채널·스레드에 한정 |
| PowerPoint 발표자료 | 논리 구성·디자인·검증, 한국어 개조식, 편집 가능한 구조 보존, 불필요한 전체 조회 억제 |
| Word 문서 | 사실·구조·작성 의도 보존, 자연스러운 문장과 일관된 제목, 필요한 절 중심 조회 |
| Excel 분석 | 수식·자료형·구조 보존, 계산 검증, 관측값과 가정 구분, 필요한 범위 중심 조회 |

앱 역할 6종은 사용자 언어 사용, 실제 수행 결과만 보고, 외부 내용을 데이터로 취급, 셸·소스 편집 금지를 공유합니다. GitHub는 기본 코딩 시스템 지침을 유지하고 `clients/github/github.go`의 MCP 지침을 추가합니다. Figma·Slack·메일의 MCP 지침도 연결된 세션의 사용 가능한 도구에만 적용됩니다. `looking`은 별도 앱 정체성이 아니라 동일 역할의 읽기 전용 세션이며, 카운슬은 완료 증거를 판단하는 별도 게이트입니다.

MCP initialize의 `instructions`는 실제 모델 요청의 후행 컨텍스트에 전달됩니다. 지침은 사용자 요청·앱 역할·승인 정책을 덮어쓰지 못하며, 도구가 분리되면 해당 지침도 제거됩니다. `internal/app/mcp_instructions_test.go`는 모델 요청 도달과 세션·역할 귀속을 검증합니다.

### 타입 선언과 콘솔 연결 상태

역할 값의 정본은 `internal/app/client_kind.go`의 `ClientKind` 상수 8개입니다. 유효성 검사와 프롬프트 선택은 이 선언을 사용하고, 알 수 없는 역할은 도구 실행을 허용하지 않습니다. 세션의 Agent(default/looking), 사용자가 작성한 Role 설명, 콘솔 화면 타입은 별개입니다.

콘솔의 `CompanionType.java`에는 아직 코딩 타입 `1`만 등록돼 있습니다. `daemon.Identity` → `daemon.Info` → 로컬 roster·fleet 응답은 이제 type을 전달합니다. 기본 코딩과 GitHub는 1, 앱 역할은 각 역할 키를 기록합니다. `FleetAgent.type` → `CompanionType`의 콘솔 매핑은 아직 미완료입니다. 원격 cluster 전달은 서명 대상 JSON과 구버전 검증 호환성을 별도로 확인해야 합니다. 앱을 코딩 자식 모듈에 연결하면 파일·셸 UI를 잘못 노출하므로 공용 대화 기능을 제공하는 앱 자식 모듈부터 준비합니다.

인수 조건은 역할별 실제 데몬 기록과 `/fleet` 타입 일치, 코딩 타입 `1` 호환 유지, 앱 화면의 파일·셸 기능 미노출, 미지 타입의 결정적 처리, 데스크톱·좁은 화면 Playwright 통과입니다. 현재 이 콘솔 통합은 미완료입니다.

## 2. 공통 연결 계층

`clients/appbridge`는 로컬 HTTP와 데몬 제어 소켓 사이의 연결 계층입니다. Figma의 도구 호출은 이 계층을 거쳐 플러그인의 main sandbox로 전달합니다. 메일·Slack·GitHub의 API 작업은 각각의 헬퍼에서 수행합니다. 모델 API 자격 증명은 앱 UI에 전달하지 않습니다.

```text
앱 화면 / Slack 이벤트
    ↓ 로컬 bearer 인증 또는 Slack Socket Mode 인증
앱 헬퍼 → appbridge → 대상에 고정된 Magi 세션
    ↑                       ↓ MCP 도구 호출
앱 도구 실행 ← 대상 binding에 고정된 MCP 주소
```

| 기본 주소 | 용도 |
|---|---|
| `127.0.0.1:8734` | Figma 플러그인의 로컬 헬퍼 |
| `127.0.0.1:8793` | 메일 UI와 IMAP/SMTP 헬퍼 |
| `127.0.0.1:8736` | Slack 헬퍼의 MCP 콜백 |
| `127.0.0.1:8737` | GitHub 사이드 패널 헬퍼 |

수신 주소는 명시적인 루프백 IP만 허용합니다. 로컬 API와 MCP에는 `Authorization: Bearer <token>`이 필요합니다. 토큰을 지정하지 않으면 암호학적 난수로 256비트 값을 생성합니다. 브라우저 확장이나 sandbox iframe의 교차 출처 호출은 bearer 인증으로 제한하며, CORS 허용 자체를 인증으로 취급하지 않습니다. 브라우저에 보이는 텍스트는 `textContent`로 렌더링합니다.

## 3. 대상과 세션 귀속

| 앱 | 대상 식별자 | 별도 확인 사항 |
|---|---|---|
| Figma | 파일 키 또는 사용자가 지정한 영속 문서 ID | 도구 요청 시 페이지·선택 ID를 캡처하고 변경 직전 다시 확인 |
| 메일 | 계정 / mailbox / UIDVALIDITY / UID | UIDVALIDITY가 바뀌면 이전 UID 조회 거절 |
| Slack | team / channel / thread timestamp / 요청 user | 다른 사용자가 승인 버튼을 눌러도 거절 |
| GitHub | owner / repo 및 이슈·PR 번호 | 로컬 origin과 연결 저장소의 일치 확인 |

`POST /api/connect`는 `{target}`를 받아 `{binding, session, target}`를 반환합니다. binding은 헬퍼가 만든 불투명한 연결 ID입니다. 앱 화면이 소켓 경로·작업 디렉터리·임의 session ID를 지정하지 못하게 합니다. 세션은 `session-new`의 `keep` 계약과 `for` 태그로 생성·복구합니다. 다른 문서에 연결해도 기존 컴패니언의 활성 대화를 바꾸지 않습니다.

Figma·메일·Slack의 기본 연결은 대상별 해시 디렉터리를 작업 공간으로 사용합니다. GitHub는 사용자가 명시한 로컬 체크아웃에 연결합니다. 본문이나 제목을 작업 디렉터리로 사용하지 않습니다. binding은 프로세스 메모리에 있으며 재시작 뒤 다시 연결합니다. 저장된 세션은 `for` 태그로 다시 찾습니다.

## 4. 채팅과 도구 프로토콜

`POST /api/request`는 binding과 제한된 명령만 받습니다. `say` 또는 `prompt`는 `submit`, `model`은 `set-model`, `reply`는 질문의 `answer`, `permission`은 승인 응답으로 전달합니다. `new`, `interrupt`, `status`, `models`, `context`, `compact`도 지원합니다. 새 세션 생성 후 UI는 반환된 session을 적용하고 이전 이벤트 스트림을 취소합니다. 임의 `shell`, `config-set`, `shutdown` 같은 관리 명령은 이 API에서 받지 않습니다.

`GET /api/events?binding=...`는 데몬 transcript를 SSE로 전달합니다. 영속 이벤트와 실시간 승인·질문 이벤트를 함께 사용합니다. 화면은 `part.appended`의 원문과 승인·질문 카드를 구분합니다. 이벤트의 session ID와 현재 연결을 대조하고, 다른 대상의 늦은 응답을 버립니다. Slack은 과거 답변을 채널에 다시 게시하지 않도록 별도의 재생 경계를 둡니다.

`POST /mcp/<binding>/<session>`은 MCP `2025-06-18`의 initialize, ping, tools/list, tools/call을 받습니다. 등록한 앱 도구 이름만 실행하고 호출 대상은 URL의 binding과 session으로 결정합니다. 이전 세션 주소는 새 세션에서 사용할 수 없습니다. 호출 인자로 다른 문서나 수신 대상을 선택할 수 있는 도구는 앱 핸들러에서 원래 대상과 대조해야 합니다. 읽기 전용 여부는 MCP annotations에 표시합니다.

Figma는 `/api/figma/poll`로 도구 요청을 받고 `/api/figma/result`로 결과를 반환합니다. callId는 난수이며 binding에 고정됩니다. 다른 binding의 응답·중복 응답·시간이 지난 응답은 거절합니다. 도구 제한 시간은 30초이고, polling 대기는 최대 20초입니다. 작업 시간 초과는 ‘변경 없음’을 의미하지 않으므로 실제 변경 여부를 확인한 뒤 재시도해야 합니다.

## 5. 계정과 외부 조작

메일의 IMAP/SMTP 자격 증명, Slack 앱·봇 토큰, GitHub API 토큰은 헬퍼 환경에만 둡니다. `CompanionEnv`는 새 컴패니언을 시작할 때 앱 토큰과 메일 비밀번호를 제거하고 모델 제공자 자격 증명은 유지합니다. 이미 실행 중인 프로세스의 환경은 변경할 수 없으므로 마이그레이션 시 재시작해야 합니다. 서버 오류 메시지나 도구 결과에 값을 포함하지 않습니다. Figma 플러그인은 디자인 API를 main sandbox에서 호출하므로 Figma API 토큰을 요구하지 않습니다.

메일 모델에는 읽기와 초안 저장 도구만 제공합니다. SMTP 발송은 사람이 수신자·제목·본문을 확인하는 별도 UI 조작입니다. Slack 모델에는 현재 스레드 읽기와 초안 도구만 제공합니다. 시작한 Magi 대화에 대한 응답은 그 스레드에 게시하고, 다른 채널에 보내는 도구는 제공하지 않습니다. GitHub의 초기 API 도구는 읽기 전용입니다. 원격 쓰기는 구현·시험에 필요한 행위라고 자동으로 간주하지 않습니다.

## 6. 코딩 작업과 워크트리

워크트리는 코딩 클라이언트 공통 작업 계층에 둡니다. 저장소를 고른 뒤 작업을 시작하면 별도 브랜치와 워크트리를 만들고 해당 작업 공간을 소유하는 컴패니언에 연결합니다. 디렉터리를 만드는 것과 모델의 첫 턴을 시작하는 것은 구분합니다. 일반 코드 에이전트, VS Code, JetBrains, 터미널, GitHub가 같은 계약을 사용할 수 있어야 합니다.

Figma·메일·Slack·Office에는 워크트리 조작을 기본 제공하지 않습니다. 코딩 작업이 필요하면 별도 코딩 컴패니언에 위임합니다. 상세 생성·복구·정리 계약은 [코딩 워크트리 설계](CODING_WORKTREE_DESIGN.ko.md)에 둡니다. 워크트리 서비스는 이번 초기 클라이언트의 구현 완료 범위에 포함하지 않습니다.

## 7. 구현과 검증 순서

1. 공통 연결·세션·인증·역할 제한을 구현하고 실제 소켓을 쓰는 테스트로 확인합니다.
2. 각 앱에서 chat, 승인, 질문, 이벤트 수신을 연결합니다. 새 세션·모델 변경·연결 실패에서 입력과 대상이 보존되는지 확인합니다.
3. 앱 도구의 성공·실패·다른 대상·잘못된 인자·큰 응답을 검증합니다. 메일과 Slack의 전송은 모의 서버·모의 transport에서 시험합니다.
4. 브라우저 화면이 있는 Figma·메일·GitHub는 Playwright를 실행합니다. 기존 VS Code 전체 전사 하네스도 실행합니다.
5. 담당자 자체 검토 후 다른 담당자가 코드·문서·테스트를 교차 검토합니다. 발견한 결함을 수정한 뒤 관련 검증을 다시 실행합니다.
6. 실제 계정 검증은 별도 기록합니다. 계정이 없으면 인증·앱 설치·실제 메시지 전달을 통과했다고 쓰지 않습니다.

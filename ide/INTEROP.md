# magi와 PowerPoint 플러그인 — 무엇이 뒤집혔고 무엇이 남았나

`powerpoint-agent/DESIGN.md`가 이 파일을 가리키며 "무엇이 어떻게 뒤집혔는지 여기 남겼다"고 한다.
두 설계가 하루 사이에 서로를 읽고 각자 방향을 바꿨으므로, 그 경위와 지금 남은 것을 한 곳에 적는다.

**지금 상태 한 줄: 합칠 코어가 없어졌으므로 연동 질문도 없어졌다. 남은 것은 magi 쪽 결함 하나다.**

---

## 1. 뒤집힌 것

### 첫 판본 (`f89c01a2`)

문서 에이전트가 **자기 코어 데몬**을 갖는 설계였다. 사용자당 하나, 루프·기록·종료 판정을 자기가 갖고,
호스트 플러그인은 얇은 원격 손. 그 위에서 magi와의 관계를 물었다.

그 판본에 대해 이 문서가 준비했던 답은 "코어는 못 합친다, 연동은 플릿 문
(`about, hand, hand-state, watch`)으로"였다. 근거는 셋이었다.

1. 데몬 범위가 다르다 — magi는 워크스페이스당 하나, 그쪽은 사용자당 하나.
2. 툴 실행 모양이 다르다 — magi의 `port.Tool`은 `Execute(ctx, args, env)`로 제자리에서 끝나고
   (`internal/port/port.go:356`), 그쪽은 WebView 안의 손에 시켜 왕복해야 한다.
3. 문이 다르다 — magi는 포트를 안 열고, 그쪽은 WebView 때문에 루프백 HTTPS가 필요하다.

### 지금 판본

**코어를 안 만들기로 뒤집혔다.** magi가 코어이고, PowerPoint 쪽은 덱을 만지는 **도구를 MCP로
내놓는 서버**다. 도구는 `mcp__ppt__set_text` 같은 이름으로 magi의 도구 목록에 들어간다.

그러면 위 세 근거가 **전부 사라진다.**

1. magi 데몬은 그대로 워크스페이스당 하나다. 사용자당 하나인 것은 헬퍼뿐이고, 헬퍼는 데몬이 아니다.
2. MCP 툴은 `port.Tool`의 세 번째 구현으로 이미 존재한다. 왕복은 MCP 서버 안의 일이라 magi가 알
   필요가 없다.
3. 포트를 여는 것은 헬퍼이고 magi가 아니다. magi는 클라이언트로 붙는다.

**즉 "두 에이전트를 어떻게 연동하나"라는 질문 자체가 없어졌다.** 에이전트는 하나다. 플릿 문 안은
쓸 자리가 없어졌으므로 접는다.

---

## 2. 이 이음매가 이미 있다는 것을 확인했다

MCP를 고른 판단을 코드로 대조했다. 네 가지가 실제로 있다.

| 필요한 것 | 어디 | 확인 |
|---|---|---|
| HTTP 전송(stdio 아님) | `internal/adapter/mcp/manager.go:83` `AddHTTP`, `http_transport.go:17` Streamable HTTP | 있음 |
| 이름 네임스페이스 | `mcp__<서버>__<도구>`, `internal/app/execute.go:52` | 있음 |
| 외부 서버 도구는 위험 도구 | `execute.go:59` — `mcp__` 접두면 무조건 퍼미션 게이트 | 있음 |
| 서버가 죽으면 도구가 사라짐 | MCP 매니저가 자동 제거 | 있음 |

전송을 HTTP로 고른 것도 맞다. stdio면 magi 데몬이 서버를 자식으로 띄우는데 **데몬이 워크스페이스마다
있으므로 헬퍼가 워크스페이스 수만큼 뜬다.** 헬퍼가 먼저 서고 데몬들이 클라이언트로 붙는 쪽이라야
헬퍼 하나가 여러 워크스페이스를 받는다.

---

## 3. 막고 있는 것 하나 — magi가 MCP 이미지 블록을 버린다

그쪽 §4.4 ①의 지적이고, **코드로 확인했다. 사실이다.**

```go
// internal/adapter/mcp/jsonrpc.go:82
type contentBlock struct {
    Type string `json:"type"`
    Text string `json:"text"`
}
```

```go
// internal/adapter/mcp/tool.go:41
for i, c := range res.Content {
    if i > 0 { sb.WriteString("\n") }
    sb.WriteString(c.Text)
}
```

MCP의 이미지 컨텐트 블록은 `data`와 `mimeType`을 싣고 `text`를 싣지 않는다. `contentBlock`에 그
두 필드가 아예 없으므로 언마샬에서 버려지고, 이어붙이기는 빈 문자열을 더한다. **슬라이드 렌더를
돌려주는 도구는 지금 아무것도 못 돌려준다.**

이게 뼈아픈 이유는 그 제품이 코딩 에이전트보다 유리한 지점이 바로 픽셀 증거라서다. 텍스트로 "고쳤다"고
말하는 대신 렌더를 보여 줄 수 있다는 것이 §2.2의 논지인데, 그 통로가 막혀 있다.

**고침의 모양은 작다.** `session.PartImage`가 이미 있다(`internal/core/session/session.go:117`).
`contentBlock`에 `Data`·`MimeType`을 더하고, `Execute`가 `type`을 보고 텍스트 블록은 지금처럼
이어붙이되 이미지 블록은 이미지 파트로 옮기면 된다.

**다만 이건 magi 쪽 변경이고 이 문서가 결정할 것이 아니다.** 여기서 하는 일은 그 결함이 실재하고
정확히 어디인지를 못 박아 두는 것까지다. 착수 전에 확인할 것 둘: 툴 결과에 이미지 파트를 실을 수 있는
경로가 `session.ToolResult`에 있는지, 그리고 백엔드가 이미지를 안 받는 모델일 때 무엇으로 대체할지.

## 4. 수명주기 규율 — 공유 패키지는 만들지 않는다

`DESIGN.md` §12.7이 물은 것이다. 답은 **안 만든다**이고, 이유는 재사용할 코드가 없어서다.

magi의 `claim_unix.go`는 Go이고, IntelliJ 플러그인은 JVM, 헬퍼와 애드인은 또 다른 런타임이다. 공유
패키지 하나로 셋을 덮을 수 없다. 실제로 공유되는 것은 **규율과 그것을 지키는지 보는 시험**이다.
세 시나리오를 양쪽 검증 절에 같은 문장으로 두는 편이 값이 크다.

- 데몬 없음 / 살아있음 / 죽은 소켓만 남음 / 동시 기동 셋 — 결과가 언제나 "하나"인가
- 자기재시작 창에서 감시자가 경쟁 프로세스를 띄우지 않는가
- 끝내 못 붙었을 때 화면이 "할 일 없음"처럼 보이지 않는가

서로 빌린 것도 적어 둔다. `ide/README.md` §2는 그쪽 §5.3에서 **백오프와 지터**, **못 붙었을 때
말하기**를 가져왔고, 그쪽 §5.1과 §5.3은 magi의 "락 먼저, 바인드, 그다음 공표"와 이쪽의 "락을 열어
보는 행위가 상태를 바꾼다"를 가져갔다.

## 5. 그쪽에 넘기는 관찰 셋

### (a) `<socket>.stopped`를 쓰지 않는 편이 낫다 — 출처가 그 안을 버렸다

`DESIGN.md` §5.3의 흐름도와 §5.4가 그 표식을 채택하면서 `ide/README.md` §2를 출처로 든다.
**그 §2는 지금 그 안을 버렸다.** 사유는 이 트리 자신의 규칙이다 — "아무것도 status 파일을 쓰지 않으므로
낡을 수가 없다"(`docs/ARCHITECTURE.md:976`, `docs/UI.md:671`). 표식 뒤에는 커널도 defer도 없어서,
누가 터미널에서 다시 켜면 그 표식은 낡은 채 영원히 남는다. **헬퍼가 사용자당 하나이므로 이 사고가 더
크다.** magi에서는 워크스페이스 하나가 감시에서 빠지지만, 거기서는 하나뿐인 헬퍼가 통째로 빠진다.

대신 유도할 수 있다. 깨끗한 종료는 소켓 파일을 지우고 나가고(`daemon.go:724`) 죽임을 당하면
남는다(`daemon.go:616`). 그러니 **소켓 파일이 없으면 되살리지 않고, 있는데 dial이 안 되면
되살린다.** 표식이 필요 없다. 대가는 자기 오류로 스스로 나간 프로세스도 안 살아나는 것인데, 나가기로
결정한 프로세스를 다시 세우지 않는 쪽이 맞다고 본다.

### (b) 작별 프레임은 magi 쪽 소켓에서는 안 된다

표식 대신 "나가면서 열린 연결에 말하기"를 고려한다면, magi의 컨트롤 소켓에서는 그것이 프로토콜을
깬다. 소켓이 **락스텝**이라 청하지 않은 프레임이 진행 중인 호출의 답으로 소비되고, 그 뒤 모든 교환이
한 칸씩 밀린다. 데몬이 그 불변식을 주석으로 적어 두었고 `watch`가 유일한 예외인 이유가 연결을 통째로
넘겨받기 때문이라고 밝힌다(`internal/adapter/daemon/daemon.go:980`). 헬퍼의 HTTP/WebSocket 전송은
사정이 다를 수 있지만, 소켓 쪽에 같은 것을 요구하지는 말 것.

### (c) §5.3의 unlink 앞에 프로브가 빠졌다

흐름도가 락을 잡은 뒤 곧바로 잔재 소켓을 지운다. magi는 락을 잡고 **dial로 "정말 아무도 안 듣는다"를
증명한 뒤에** 지우고, 이유를 코드 옆에 적어 두었다(`daemon.go:683`: "This Remove is only safe BECAUSE
the dial above proved nothing is listening"). 프로브가 잡는 것은 **클레임을 모르는 옛 빌드**가
살아있는 소켓을 쥔 경우다. 락은 비어 있으므로 새 프로세스가 락을 잡고 남의 살아있는 소켓을 지운다.
magi는 그때 전용 에러를 낸다("another magi is already listening"). 자기 업데이트가 있는 제품이면
이 상황이 실제로 온다.

## 6. 남은 열린 것

- **`DESIGN.md` §12.5(어디에 살 것인가)는 계속 열려 있다.** 다만 근거가 바뀌었다. 코어를 공유하지
  않기로 했으므로 "코드 공유량"으로 답할 질문이 아니고, 남은 이유는 교훈이 오가는 속도다. 지금
  실제로 그 값이 나오고 있다 — `.stopped`를 한쪽이 채택하고 다른 쪽이 버리는 일이 같은 트리 안이라
  하루 만에 보였다.
- **이미지 블록 고침을 누가 언제 하나.** §3의 결함은 그쪽 제품의 핵심 논지를 막고 있는데 고칠 자리는
  magi다. 순서가 정해져야 한다.
- **헬퍼가 여러 magi 데몬에게 동시에 도구를 줄 때의 범위.** 워크스페이스 둘이 같은 덱을 만지면
  누가 이기는지는 `DESIGN.md` §5.6이 다루지만, magi 쪽에서 그게 어떻게 보이는지는 아직 안 그렸다.

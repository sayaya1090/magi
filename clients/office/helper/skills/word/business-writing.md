# 업무 문서 — 읽는 사람이 30초 안에 결론을 쥐게

## 공통 적용 기준

사용자가 지정한 산출물 언어와 문체를 우선합니다. 지정이 없으면 기존 문서의 언어·표기 관례를 유지하고, 새 문서는 사용자 요청의 언어를 따릅니다. 대화 언어와 산출물 언어가 다를 수 있습니다. 혼합 언어, 직접 인용, 고유명사는 임의로 번역하지 않습니다. 한국어 개조식·공문 형식을 다른 언어에 강제하지 않습니다. 날짜·소수점·통화·단위는 대상 문서의 지역 관례를 따릅니다. 도구 이름·인자·수식 문법은 번역하지 않고 API 규약을 따릅니다.

아래 수치·배치·호출은 예시입니다. 사용자 지정 내용과 기존 템플릿이 우선하며, 예제의 숫자·날짜·이름을 사실로 복사하지 않습니다. 현재 도구 목록과 인자 설명을 확인한 뒤 제공된 도구만 호출합니다. 운영체제나 Office 연도만으로 지원을 단정하지 않습니다. 완료 검증 도구가 없으면 호출하지 않고 수행 결과·검증 범위·미완료 항목을 답변으로 보고합니다.


업무 문서는 **읽는 사람 쪽에서** 짠다. 받는 사람은 바쁘고, 첫 몇 줄에서 「무엇을 해 달라는가·왜·언제까지」를
찾는다. 거기 없으면 나머지를 안 읽는다. 아래는 한국 직장 보고서 관행(두괄식·개조식)과 영어권 plain language
지침(BLUF, 짧은 문장, 능동태)이 겹치는 부분이다.

## ✔ 체크리스트 — 다 쓴 뒤 한 번

| # | 확인 | 지우는 기준 |
|---|---|---|
| 1 | 결론이 첫 문단 | 「요약」 또는 첫 문단에 **결론·요청·기한**이 있다(두괄식) |
| 2 | 제목이 내용을 말한다 | 「검토 결과」가 아니라 「A 안 채택 건의 — 비용 18% 절감」 |
| 3 | 제목은 스타일 | 제목 1·2·3 을 `set_style`/`insert_paragraphs{style}` 로 — 굵은 글자로 흉내 내지 않았다. 단계를 건너뛰지 않았다(1 → 3 금지) |
| 4 | 문장이 짧다 | 한 문장 한 뜻, 대략 **40자(영문 25단어) 안쪽**. 긴 문장은 둘로 |
| 5 | 사실과 의견이 갈린다 | 「~로 확인됨」(사실)과 「~이 필요하다고 판단됨」(의견)을 섞지 않았다 |
| 6 | 숫자에 단위·기준 | 「18%」가 아니라 「전년 대비 18% 감소(2025년 3분기 기준)」 |
| 7 | 맞춤법을 봤다 | Windows 면 `proofread` 한 번(아래 §5), 짚인 것을 고쳤거나 그대로 둔 이유를 답에 적었다 |
| 8 | 눈으로 봤다 | `read_html` 로 쓴 구간을 한 번 봤다 |

## 1. 두괄식 — 결론부터

- 첫 문단(또는 「요약」 절) = **결론 한 줄 + 근거 둘셋 + 요청(누가·무엇을·언제까지)**.
- 본문은 결론을 떠받치는 순서로: 배경 → 현황 → 문제 → 대안 비교 → 건의 → 향후 계획.
- 영어 문서도 같다: *Bottom Line Up Front* — 요점을 10단어 안팎으로 말할 수 있어야 하고, 그것이 맨 앞에 선다.

## 2. 개조식 — 명사형으로 끊는다

한국어 내부 보고서는 개조식(「증가」「검토 필요」「추진 예정」)을 선택할 수 있습니다. 명령형으로 바꾸지 않습니다. 대외 문서·서신·서술형 보고서는 목적과 기존 문체를 따릅니다. 영어 등 다른 언어에는 한국어 명사형 종결을 강제하지 않습니다.

| 서술식 | 개조식 |
|---|---|
| 3분기 매출은 전년보다 12% 늘었습니다. 이는 신규 고객 유입 때문입니다. | ○ 3분기 매출 전년 대비 12% 증가 — 신규 고객 유입이 주요인 |
| 다음 달까지 시스템 교체를 끝낼 계획입니다. | ○ 시스템 교체: 다음 달까지 완료 예정 |

- 항목 기호는 문서 안에서 하나로: `□ → ○ → -` (한국 공공·기업 보고서 관행) 또는 Word 글머리(`insert_list{kind:"bulleted", levels}`).
  기호를 글자로 치는 방식과 Word 목록을 한 문서에 섞지 않는다 — `list_paragraphs` 의 `list` 칸으로 이 문서가 어느 쪽인지 먼저 본다.
- 순서가 있는 것(절차·일정)만 번호 목록(`kind:"numbered"`), 나머지는 글머리.
- 받는 사람이 밖(고객·공문)이면 서술식이 예의에 맞을 때가 있다 — 이 문서의 기존 문체를 따른다.

## 3. 표기

- **날짜**: 공문은 `2026. 9. 27.`(점 뒤 띄움, 마지막 점 포함), 일반 보고서는 `2026-09-27` 또는 `9월 27일(일)`. 한 문서 안에서 하나로.
- **숫자**: 천 단위 쉼표(12,500), 금액은 단위 명시(「1,250만 원」「$1.2M」). 표 안 숫자는 오른쪽 정렬(`format_table_cells{align:"Right"}`).
- **비율**: 「%」와 「%p」를 가른다 — 10% → 12% 는 「2%p 상승」이며, 상대 증가율은 20%입니다. 두 지표를 구분합니다.
- **전문용어**: 처음 나올 때 괄호로 풀고(「CAC(고객 획득 비용)」), 약어는 한 번 풀어 쓴 뒤에만 쓴다.
- **능동태**: 「검토가 진행될 예정임」보다 「인사팀이 10월 5일까지 검토함」 — 누가 하는지가 보인다.

## 4. 문서 종류별 뼈대 — 예제

모든 예제는 같은 순서를 밟는다: **읽기 → 스타일 확인 → 한 번에 넣기 → 서식 → 눈으로 보기.**

### 예제 A — 「3분기 실적 보고서 써 줘」

```
list_paragraphs {}                                   # 빈 문서인지, 기존 내용 어디까지인지
describe_style {}                                    # 이 문서의 제목·본문 스타일 이름
insert_paragraphs {at:"end", lines:[
  "3분기 실적 보고",
  "요약",
  "3분기 매출 125억 원으로 목표 대비 104% 달성 — 신규 고객 40곳이 견인함. 4분기 마케팅 예산 10% 증액을 건의함(10월 10일까지 결정 요청).",
  "1. 실적 현황",
  "2. 증감 요인",
  "3. 4분기 계획 및 건의"
]}
set_style {from:<제목 번호>, builtin:"Title"}
set_style {from:<"요약" 번호>, builtin:"Heading1"}  # 절 제목마다 Heading1
insert_table {after:<"1. 실적 현황" 번호>, has_header:true, table_style:"GridTable4_Accent1",
  values:[["구분","목표","실적","달성률"],["매출","120억","125억","104%"],["영업이익","12억","13.1억","109%"]]}
format_table_cells {table:1, columns:[1,2,3], align:"Right"}
insert_list {after:<"2. 증감 요인" 번호>, kind:"bulleted", items:["신규 고객 40곳 유입(+8억)","물류비 절감(+0.6억)","환율 영향(-0.4억)"]}
read_html {from:1, to:<끝>}                          # 눈으로 확인
```

- 「요약」 한 문단이 결론·근거·요청을 다 들고 있다(두괄식).
- 표 제목·단위(「단위: 억 원」)는 표 위 문단으로 따로 넣는다.

### 예제 B — 「이 회의 메모로 회의록 만들어 줘」

뼈대: **회의 개요(일시·장소·참석자) → 결정 사항 → 실행 항목(담당·기한) → 논의 요지 → 다음 회의.**
결정과 실행 항목이 논의 요지보다 **앞**이다 — 회의록을 여는 사람이 찾는 것이 그것이다.

```
insert_paragraphs {at:"end", lines:["주간 운영 회의록","회의 개요","일시: 2026. 9. 26.(토) 14:00–15:00","참석: 김○○, 이○○, 박○○","결정 사항","실행 항목","논의 요지"]}
set_style ... (제목 Title, 절 제목 Heading1)
insert_list {after:<"결정 사항">, kind:"numbered", items:["신규 물류사 B 로 10월부터 전환","주간 회의를 격주로 변경"]}
insert_table {after:<"실행 항목">, has_header:true, values:[["할 일","담당","기한"],["B 사 계약서 검토","이○○","10. 2."],["공지 발송","박○○","9. 29."]]}
```

### 예제 C — 「기획안 초안」

뼈대: **제안 요지(한 문단) → 배경·필요성 → 목표(측정 가능한 숫자) → 추진 방안 → 일정 → 예산 → 기대 효과 → 위험과 대응.**
「목표」는 숫자로: 「고객 만족 향상」이 아니라 「NPS 32 → 40(2027년 1분기)」.

### 예제 D — 「공문 보내게 정리해 줘」

뼈대: **수신·(경유)·제목 → 1. 관련 근거 → 2. 본문(요청 사항) → 붙임 → 끝.**
- 항목 번호는 `1. → 가. → 1) → 가) → (1) → (가)` 순서(공문서 관행).
- 본문 마지막에 「끝.」 — 붙임이 있으면 붙임 목록 뒤에 「끝.」.
- 날짜는 `2026. 9. 27.` 꼴.

## 5. 다 쓴 뒤 — 교정과 확인

1. **맞춤법·문법**: Windows 의 Word 면 `proofread {}`(쓴 구간만이면 `from/to`). Word 가 밑줄 친 것과 제안이 온다.
   - 고칠 것은 `replace_all{find, replace, from, to}` 또는 `replace_paragraph`. 고유명사·업계 용어는 그대로 두고 답에 그렇게 적는다.
   - 결과가 비어도 오류가 없거나 교정 도구가 없다고 단정하지 않습니다. 검사 범위·문서 언어·교정 설정을 확인하고 직접 검토한 범위를 보고합니다.
2. **분량**: 「두 쪽 이내」 같은 요구가 있으면 `document_stats {}` 로 쪽 수를 잰다(Windows). Office.js 는 쪽 수를 모른다.
3. **모양**: `read_html` 로 쓴 구간을 본다 — 제목 단계, 목록 들여쓰기, 표 머리글.
4. **보낼 판**: 「PDF 로 줘」면 `export_pdf {}`(Windows) — 경로를 안 주면 문서 옆에 같은 이름으로 생긴다. 만든 경로를 답에 적는다.

## 6. 하지 않는 것

- 빈 문단 여러 개로 간격 만들기 → `format_paragraph{space_before, space_after}`.
- 굵은 글자 + 큰 글씨로 제목 흉내 → 스타일. 제목 스타일은 탐색 창·목차·보조 기술이 문서 구조를 파악하는 데 도움이 됩니다.
- 한 문단에 결론·배경·요청을 다 섞기 → 문단을 나눈다.
- 사람 이름·숫자를 지어내기 → 모르면 「○○」 자리표시로 두고 답에 「채워야 할 자리」로 적는다.

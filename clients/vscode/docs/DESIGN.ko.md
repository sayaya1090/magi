> 「VS Code 부터」였다. 이 문서는 그 하나를 **어떻게 만들지**를 정한다.

> 말을 세우는 자리로 옮기는 것이다.

## 1. 무엇을 만드는가 — 한 문단

VS Code 가 연 폴더의 magi 컴패니언에게 말을 걸고, 그가 이 편집기를 부릴 수 있게 하는 확장.
데몬은 이미 그 폴더에 있거나, 없으면 이 확장이 띄운다. 대화·계획은 패널에 살고, 훑어보기·완성·
표식은 편집기 안에 산다. **새 프로토콜을 만들지 않는다** — [`docs/CLIENTS`](../../../docs/CLIENTS.ko.md) 가
정본이고 이 확장은 그 문을 두드리는 여섯 번째 클라이언트다.

## 2. 모듈 갈림 — 두 층, 젯브레인과 같은 이유로

젯브레인이 `core`(순수 코틀린 3,687줄) / `intellij`(IDE 층 6,091줄)로 갈려 있고, 그 갈림 덕에
프로토콜·전사 조립·승인 어휘가 **IDE 없이 시험된다**. 같은 갈림을 그대로 쓴다.

```
src/core/     vscode 를 import 하지 않는다. node 만으로 돈다 → node:test 로 시험한다.
  src/ide/      vscode API 가 사는 유일한 자리.
  src/extension.ts
  test/         core 만 시험한다. ide 층은 §7.
```

**규칙 하나를 시험으로 세운다: `src/core/**` 안에 `from 'vscode'` 가 있으면 실패한다.**
젯브레인의 `ArchitectureTest` 가 계층 방향을 그렇게 잡고 있고, 그 시험이 없으면 편한 쪽으로
한 줄씩 새어 결국 core 를 못 시험하게 된다.

### core 가 지는 것

| 파일 | 무엇 | 시험 |
|---|---|---|
| `workspace.ts` | 소켓 경로 유도(§5) | **골든**(아래) |
| `protocol.ts` | Request/Response 타입 | 와이어 대조(§7) |
| `daemon.ts` | 줄 단위 JSON 왕복 + 스트림 | 가짜 소켓 |
| `caps.ts` | `about` 이 광고한 문으로 화면을 켜고 끈다 | 순수 |
| `transcript.ts` | 사건 → 말풍선 | 순수 |
| `permission.ts` | 승인 어휘(allow/deny/always) ↔ 화면 글자 | 순수 |
| `coreRelease.ts` | 어느 판을 어디서 받나 | 설정 파일 실물 |
| `once.ts` | 창 여럿이 동시에 와도 한 번만(§6) | 순수 |

## 3. 이식표 — 젯브레인 매뉴얼에서 유도한다

**이 표는 손으로 쓰지 않는다.** 처음에는 `plugin.xml` 의 액션과 UI 파일 이름으로 열여섯을
셌는데, 매뉴얼은 그 안의 **동작들**을 센다 — 멘션·칩·대화 탭·옮겨 적기·「변경 보기」처럼 액션
이름이 없는 것들이다. 사용자가 물었을 때에야 그 차이가 드러났고, 세어 보니 **마흔여덟**이었다.
셋 배다.

그래서 목록의 출처를 사람의 기억에서 **문서**로 옮긴다. `manual.test.ts` 가
`clients/jetbrains/docs/MANUAL.ko.md` 를 읽어 굵은 항목을 뽑고, 그 하나하나가 아래 표에 있는지
본다. 없으면 빨갛다. 젯브레인이 `ManualTest` 로 「문서가 모든 시험을 이름 대는가」를 재는 것과
같은 규율이고, 같은 이유다 — 표는 사람이 적는 글이라 표만으로는 안 선다.

세는 자리는 §1·§1a 를 뺀 전부다. 그 둘은 **코어 바이너리를 어떻게 깔까**이지 플러그인 기능이
아니다.

판정은 넷이다. **못 함**과 **자리 다름**을 가르는 것이 이 표의 값이다 — 「다 넣는다」는 말이
어디서 참이 아닌지가 거기 있다.

| 판정 | 뜻 |
|---|---|
| ✓ | 그대로 온다 |
| ↷ | **자리가 다르다** — VS Code 가 그런 말을 세우는 자리로 옮긴다(§4) |
| ✗ | **못 한다** — 플랫폼이 그 자리를 안 준다 |
| ○ | 안 옮긴다 — 이 편집기에서 할 일이 없다 |

## 4. 자리가 달라지는 넷 — 흉내 내지 않는다

**(가) 훑어보기 띠.** 젯브레인은 편집기 위에 `EditorNotificationPanel` 을 세운다. VS Code 에는
그 자리가 없다. `showInformationMessage` 는 **화면 오른쪽 아래 토스트**라 성격이 다르다 —
지나가는 알림이지 그 파일에 붙은 말이 아니다. 그래서 **첫 줄 위의 데코레이션**(`before`
장식)으로 세우고, 할 말이 없으면 아예 없다. 젯브레인의 그 띠도 「할 말이 있을 때만」이 규칙이다.

**(나) 콘솔 출력 물어보기.** 젯브레인은 Run 콘솔에 컨텍스트 메뉴를 단다. VS Code 의 터미널은
xterm 이라 선택 영역만 얻을 수 있고(`window.activeTerminal` + `terminal.selection`),
「스택트레이스 그 줄에서 바로」가 안 된다. **자리를 옮긴다**: 진단(`vscode.Diagnostic`)이 있는
줄의 코드 액션으로 「magi 에게 이 오류 물어보기」를 세운다. 빌드 에러·린트 오류가 사는 자리는
VS Code 에서는 문제 패널이고, 흉내보다 그 편집기의 자리가 낫다. 터미널 선택 영역 경로는
명령으로 남겨 둔다(선택하고 명령 팔레트).

**(다) 설정.** 젯브레인은 화면을 손으로 짠다(`MagiConfigurable`). VS Code 는 `configuration`
기여만으로 그려 준다. **화면을 짜지 않는다** — 짜면 그 편집기 답지 않고, 검색·동기화·프로파일도
잃는다. 다만 모델 목록처럼 **데몬이 답해야 아는 값**은 정적 스키마에 못 넣으므로 명령
(`magi: Choose the model`)으로 고른다.

**(라) 승인 대화.** 젯브레인은 도구창 안에 답 단추를 세운다. VS Code 에서도 웹뷰 안이 맞다 —
`showQuickPick` 는 포커스를 뺏고 대화의 맥락(무엇을 왜 하려는지)을 못 싣는다.

## 5. 소켓 계약 — 여기가 틀리면 나머지가 다 조용히 죽는다

`workspaceKey` 가 **한 글자라도 다르면 에러가 안 난다.** 이쪽은 아무도 없는 소켓을 찾고,
「실행되지 않음」이라 말하고, 같은 트리에 **둘째 데몬**을 띄우자고 권한다. 양쪽 다 제대로
동작하는데 서로 다른 워크스페이스 얘기를 하는 것이다.

규칙(`internal/adapter/daemon/publish.go`):

```
socketPath = socketDir(configDir) / "daemon-" + workspaceKey(workdir) + ".sock"
workspaceKey(w) = sanitize(basename(realpath(abs(w)))) + "-" + shortHash(realpath(abs(w)))
shortHash      = FNV-1a 64비트 → 36진수 8자리, 낮은 자리부터
sanitize       = [A-Za-z0-9_-] 아니면 '-'
```

**포팅에서 떨어뜨리기 쉬운 둘**을 문서에 박아 둔다:

1. **심볼릭 링크를 푼다.** macOS 에서 `/tmp` 는 `/private/tmp` 다 — 예외가 아니라 보통의 경우다.
   안 풀면 셸에서 `cd /tmp` 한 사람과 스스로 chdir 한 프로세스가 **같은 디렉토리에 다른 해시**를
   낸다. 코어에서 실제로 그렇게 겪었다.
2. **해시는 64비트로 넘친다.** JS 의 `number` 로 하면 곱셈의 낮은 비트를 잃는다 —
   **짧은 경로에서는 맞고 실제 경로에서 어긋난다.** 결함이 가질 수 있는 가장 나쁜 모양이다.
   `BigInt` 로 하고 마스크를 씌운다.

### 골든 — 코어가 직접 답한 값

아래는 **`daemon.WorkspaceKey` 를 실행해 받은 것**이지, 코틀린 사본이나 이 문서 저자가 계산한
것이 아니다. 시험은 이 표를 그대로 물어야 한다.

| 경로 | 키 |
|---|---|
| `/tmp` | `tmp-pstqlaw1` |
| `/usr` | `usr-a74ztgfv` |
| `/Users` | `Users-cghuwblp` |
| `/var/log` | `log-clkllm93` |
| `/etc` | `etc-ydppqbth` |
| `/` | `--ov1j1jmu` |

마지막 줄이 값싸 보이지만 아니다: `basename("/")` 는 `"/"` 이고 sanitize 가 `-` 로 만들어 이름이
대시 둘로 열린다. 「베이스네임은 비어 있겠지」로 짠 포팅이 여기서 갈린다.

### 전송

줄 단위 JSON. 데몬은 `json.NewEncoder(conn)` 로 쓰고 `bufio.Scanner` 로 읽는다 — 요청 하나가 한
줄, 응답 하나가 한 줄이다. 스트림 문(`transcript`·`watch`)은 같은 연결에 응답 줄이 계속 온다.

⚠ **`status` 는 세션 id 를 안 준다.** 실물 데몬에 물어보니 답은 `ok`·`permission`·`backend`
셋뿐이다. 어느 대화를 읽을지는 `sessions` 가 안다(최신 순). 여기서 `status.session` 을 기대하면
빈 문자열이 가고 전사가 **0 프레임으로 조용히** 끝난다 — 에러가 없어서 그대로 나갈 뻔했다.

⚠ **쓰기 쪽을 반만 닫지 않는다.** 보내고 write half 를 shutdown 하는 one-shot 모양(`nc -w`)은
끊김으로 읽혀 프레임 0개로 끝난다. `docs/CLIENTS` 가 이미 적어 둔 계약이다.

## 6. 없는 것을 만들어 내는 자리 — 코어 받기와 데몬 띄우기

젯브레인의 `CoreBinary`·`StartDaemon` 이 하는 일이고, 그 둘에서 **오늘 실측으로 고친 것**을
설계에 미리 싣는다.

- **바이너리는 계정에 하나.** `<config>/bin/<판>/magi`. 워크스페이스마다 받지 않는다.
- **`PATH` 가 먼저다.** 사람이 이미 깔아 둔 것이 있으면 그것이 그 사람의 판이다. 그리고
  **사람의 셸이 아는 PATH** 를 본다 — 확장 프로세스의 environ 을 보면 Dock 으로 띄운 macOS 에서
  그 가지가 통째로 죽는다(젯브레인 리뷰 R1).
- **창이 여럿이면 한 번만 받는다.** VS Code 는 창마다 확장 호스트가 **따로** 뜬다 — 젯브레인보다
  나쁘다. 젯브레인에서는 창 여럿이 한 프로세스라 `object` 하나로 막았지만
  (`OnceAcross`, 2026-09-08 실사용 보고: 받는다는 대화가 여러 번 떴다), VS Code 에서는 그 방법이
  **안 통한다.**
  그래서 프로세스 밖의 자리로 막는다: `<config>/bin/.fetching` 잠금 파일(`wx` 로 배타 생성,
  나이 지나면 무시). 다른 창은 그것을 보고 묻지 않고 **파일이 생기기를 기다렸다가** 제 데몬을
  띄운다 — 물러나면 그 창은 이 세션 동안 데몬을 못 띄운다.
- **거절도 창을 넘어 기억한다.** 한 번 미룬 사람에게 창마다 묻지 않는다.
  `globalState`(VS Code 가 창들 사이에 공유하는 저장소)에 둔다.
- **자리를 비운다.** 취소·실패·창 닫힘 셋 다 「비행의 끝」이다. 안 비우면 한 번 실패한 기계는
  다시 못 받는다.

## 7. 무엇을 어떻게 재나

젯브레인의 `docs/TESTING.ko.md` 가 층마다 무엇을 재는지 적고, `ManualTest` 가 **문서가 모든
시험을 이름 대는지**까지 잰다. 같은 규율을 가져온다.

| 층 | 어떻게 |
|---|---|
| `core/**` | `node:test`. VS Code 없이 돈다 |
| **와이어 대조** | 젯브레인 `WireConformanceTest` 에 해당. **Go 소스를 읽어** 데몬이 보내는 필드 이름과 이쪽이 읽는 이름을 맞춘다. 짝을 너무 적게 찾으면 **그것부터 실패한다** — 안 짚고 통과하는 것을 막는다 |
| 소켓 키 | §5 의 골든. Go 에서 뽑은 값만 쓴다 |
| 계층 | `src/core/**` 에 `from 'vscode'` 가 없다 |
| `ide/**` | `@vscode/test-electron` 으로 실물 인스턴스. **1단계에서는 안 한다**(§9) |

**왜 와이어 대조가 조건인가.** TypeScript 는 JSON 을 읽을 때 모르는 필드를 조용히 버리고 없는
필드를 `undefined` 로 준다 — 코틀린의 `ignoreUnknownKeys` 와 같은 함정이다. 이름이 어긋나면
예외가 아니라 **기본값**이고, 화면은 「없다」고 말한 뒤 아무것도 실패하지 않는다. 클라이언트를
하나 늘릴 때마다 이 시험을 같이 가져오지 않으면 클라이언트 수만큼 조용한 드리프트가 는다.

## 8. 손 — 데몬이 편집기를 부리는 방향

젯브레인은 `HandServer` 를 루프백에 띄우고 그 주소를 데몬에게 준다(`mcp-attach`). 포트는
0 으로 열고 **실제로 받은 포트를 읽는다**. 토큰을 먼저 검사한다 — 루프백이라도 이 기계의 다른
프로세스가 닿기 때문이다. 알림에는 몸 없이 **204** 를 답한다(202 는 당시 코어 전송이 에러로
읽었다 — 명세가 아니라 상대에 맞춘 것이고, 그 사실이 주석에 적혀 있다).

VS Code 도 같은 모양이다. 도구는 `apply_edit` 하나로 시작하고, 적용은 `workspace.applyEdit`.
나갈 때 `mcp-detach`.

⚠ **`applyEdit` 는 저장하지 않는다.** 편집은 더티 버퍼에 남는다. 그것이 맞다 — 사람이 보고
`Ctrl+Z` 할 수 있어야 하고, 젯브레인도 같다.

## 9. 단계와 완료 조건

각 단계는 **그 단계만으로 쓸모가 있어야** 한다. 반쪽으로 멈춰도 사람이 쓸 수 있는 것이 남는다.

| 단계 | 무엇 | 조건 | 상태 |
|---|---|---|---|
| **1. 척추** | 발견 → 악수 → 대화 웹뷰 → 상태 표시줄 → 데몬 기동 | 골든·와이어·계층 시험 초록 · 실물 데몬에 붙기 | **착지** |
| **2. 편집기 안** | 인라인 완성 · 훑어보기(+인레이·띠) · 편집 표식 · 승인 답하기 | 코어 시험 초록 · 실물 VS Code 에서 활성화 | **착지** |
| **3. 진입점** | 코드 액션 · 첨부 · 커밋 초안 · 누가 썼나 · 진단 자리(§4-나) | 명령 전부 실제로 등록됨(실물 자기검사) | **착지** |
| **4. 계획판·설정** | 사이드바 웹뷰 · 모델·승인·대화 고르기 명령 | 뷰 둘이 실제로 열림(실물 자기검사) | **착지** |
| **5. 배포** | `.vsix` · 릴리스 레인 `vscode-v*` · `badges/vscode-latest.txt` | 패키징되고 설치됨 | **착지**(마켓플레이스 게시는 §10) |

**여기까지 다 섰다. 이제 EDITORS §7 로 돌아갈 자리다** — 거기 적힌 순서가 「VS Code 를 만들고, **두 벌을
본 뒤에** 공통을 `magi ide-bridge` 로 뽑는다」이기 때문이다. 1단계가 서면 무엇이 진짜 공통인지가
비로소 두 벌로 보인다.

## 10. 이 문서가 재지 않은 것

- **`vscode.dev`(브라우저 전용).** 프로세스도 유닉스 소켓도 없다. 기능을 끄고 그렇게 말해야
  한다는 것까지는 정했지만, 확장 매니페스트의 `browser` 진입점을 어떻게 가를지는 안 봤다.
- **원격(SSH·Codespaces·WSL).** 확장이 원격 쪽에서 도는 것이 우리 모델과 맞다고 판단했지만
  (데몬도 그 기계에 있다) 실물로 안 띄워 봤다.
- **웹뷰 안의 전사 렌더.** 젯브레인은 IDE 의 마크다운 엔진을 빌린다(`RichAnswer`). VS Code
  웹뷰에는 그런 것이 없어 렌더러를 싣거나 직접 그려야 하는데, 어느 쪽인지 안 정했다.
- **Marketplace 퍼블리셔 등록과 서명 절차.**
- **분량 추정.** 젯브레인이 9,778줄이라는 것만 재 두었고, TypeScript 로 몇 줄이 되는지는 짐작이라
  안 적는다.

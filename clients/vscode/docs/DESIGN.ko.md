## 1. 개요 및 목적

VS Code가 연 작업 폴더의 magi 컴패니언과 통신하고, 컴패니언이 에디터를 제어할 수 있도록 연동하는 확장입니다.
데몬은 작업 폴더에 이미 실행 중인 프로세스를 감지하거나 부재 시 확장이 직접 구동합니다. 대화와 계획은 패널 및 사이드바에 위치하고, 인라인 제안·코드 훑어보기·편집 표식은 에디터 버퍼 내에 통합됩니다. **독자적인 신규 프로토콜은 정의하지 않으며**, [`docs/CLIENTS`](../../../docs/CLIENTS.ko.md) 명세를 정본으로 삼아 통신하는 클라이언트로 동작합니다.

## 2. 모듈 아키텍처 — 2계층 분리

JetBrains 플러그인이 `core`(순수 Kotlin 3,687줄)와 `intellij`(IDE 연동 계층 6,091줄)로 엄격히 분리되어 IDE 종속성 없이 프로토콜·전사 조립·승인 어휘를 **단위 테스트할 수 있었던 구조**를 그대로 계승합니다.

```
src/core/       vscode 모듈을 import 하지 않으며 Node.js 런타임만으로 동작 → node:test 기반 단위 테스트 수행
src/ide/        vscode API를 사용하는 유일한 계층
src/extension.ts 확장 진입점
test/           core 계층 테스트 중심 (ide 계층은 §7 참조)
```

**아키텍처 규칙 검증: `src/core/**` 내부에 `from 'vscode'` 구문이 존재할 경우 빌드/테스트가 실패합니다.**
JetBrains의 `ArchitectureTest`와 동일한 계층 규율을 적용하여, 구현 편의를 이유로 core 계층에 IDE API 종속성이 침투하는 현상을 방지합니다.

### core 계층의 책임 영역

| 파일 | 주요 역할 | 검증 방식 |
|---|---|---|
| `workspace.ts` | 소켓 경로 유도(§5) | **골든 테스트**(아래 참조) |
| `protocol.ts` | Request/Response 타입 정의 | 와이어 프로토콜 정합성 대조(§7) |
| `daemon.ts` | 줄 단위 JSON 송수신 및 스트림 처리 | 목 소켓 기반 통신 테스트 |
| `caps.ts` | `about` 엔드포인트 응답 기반 기능 켜기/끄기 제어 | 순수 단위 테스트 |
| `transcript.ts` | 이벤트 스트림 → 메시지 말풍선 변환 조립 | 순수 단위 테스트 |
| `permission.ts` | 승인 어휘(allow/deny/always) ↔ UI 텍스트 변환 | 순수 단위 테스트 |
| `coreRelease.ts` | 코어 바이너리 릴리스 탐색 및 다운로드 | 설정 파일 실물 파싱 테스트 |
| `once.ts` | 다중 창 동시 실행 시 단일 실행 보장(§6) | 순수 단위 테스트 |

## 3. 이식표 — JetBrains 매뉴얼 기반 역유도

**이식표의 «이름»은 자동 검증하지만 «✓»는 아니었습니다.** 초기 설계 시 `plugin.xml`의 액션과 UI 파일명을 기준으로 16개 항목을 도출하였으나, 실제 사용자 매뉴얼은 멘션, 칩, 대화 탭, 전사 복사, 「변경 보기」 등 별도 액션 ID가 없는 **세부 인터랙션 동작**까지 포괄하고 있었습니다. 이를 전수 집계한 결과 대상 항목은 **총 48개**(초기 추정의 3배)였습니다.

따라서 항목 누락을 원천 차단하기 위해 목록의 출처를 문서 기반 테스트로 강제합니다. `manual.test.ts`가 `clients/jetbrains/docs/MANUAL.ko.md`의 굵은 글씨 항목을 추출하여 아래 표에 전량 포함되어 있는지 검증하며, 누락 시 테스트가 즉시 실패합니다. 이는 JetBrains 측의 `ManualTest`와 동일한 엔지니어링 규율입니다.

집계 대상은 코어 바이너리 설치 절차를 다루는 §1·§1a를 제외한 매뉴얼 전 섹션입니다.

「근거」 칸이 백틱으로 코드 식별자를 인용하는 행은 **해당 심볼의 실존 여부를 독립적으로 검증합니다**.
커맨드 식별자는 `manual.test.ts`의 이식 항목 가드가 `package.json`과 1:1 대조하며, API 상수나 클래스명 등
비커맨드 식별자는 전용 정적 테스트 가드를 통해 정합성을 보장합니다.

판정 기준은 다음 네 가지로 분류됩니다. 특히 **미지원**과 **배치 변경**을 명확히 구분하여 플랫폼별 차이를 기록합니다.

| 판정 | 설명 |
|---|---|
| ✓ | 원형 그대로 이식 |
| ↷ | **배치 변경** — VS Code 네이티브 UI 규약에 맞추어 제공 위치 재조정(§4) |
| ✗ | **미지원** — VS Code 플랫폼 API 제약으로 인해 지원 불가 |
| ⋯ | **미구현 (향후 구현 예정)** — 플랫폼 제약이 아닌 개발 우선순위에 따른 미착수 항목입니다 (`✗`와 구분) |
| ○ | 이식 제외 — 해당 편집기 환경에서 불필요한 기능 |

## 4. 제공 위치가 변경되는 4가지 기능

**(가) 훑어보기 띠 (Review Banner).** JetBrains는 에디터 상단에 `EditorNotificationPanel` 컴포넌트를 배치합니다. VS Code에는 동일한 헤더 슬롯이 존재하지 않습니다. `showInformationMessage`는 화면 우측 하단에 일시적으로 노출되는 토스트 알림이므로 소스 파일에 고정된 맥락을 전달하기에 부적합합니다. 따라서 **첫 번째 코드 라인 상단의 데코레이션(`before` 가상 요소 장식)**으로 구현하며, 전달할 의견이 없을 때는 DOM을 일체 생성하지 않습니다(JetBrains의 표출 규칙과 동일).

**(나) 콘솔 출력 물어보기 (Explain Output).** JetBrains는 Run 콘솔 도구 창에 컨텍스트 메뉴를 직접 연결합니다. 반면 VS Code의 통합 터미널은 xterm 기반이어서 선택 텍스트(`window.activeTerminal` + `terminal.selection`) 외에 특정 스택트레이스 라인 위치를 직접 캡처하기 어렵습니다. 따라서 오류가 보고된 진단(`vscode.Diagnostic`) 라인의 코드 액션으로 「magi에게 이 오류 물어보기」를 배치합니다. VS Code 생태계에서 빌드 및 린트 오류의 표준 집결지는 문제(Problems) 패널이므로, 플랫폼 관례에 부합하는 자연스러운 진입점을 제공합니다. 터미널 선택 영역 기반 명령 역시 커맨드 팔레트를 통해 보조적으로 유지합니다.

**(다) 설정 (Configuration).** JetBrains는 설정 GUI를 수동 조립(`MagiConfigurable`)하지만, VS Code는 `package.json`의 `contributes.configuration` 선언을 통해 설정 화면을 자동 렌더링합니다. 별도의 웹뷰 설정 창을 억지로 구축하지 않음으로써 VS Code의 기본 설정 검색, 설정 동기화(Settings Sync), 프로파일 기능과 완벽히 연동되도록 합니다. 단, 사용 가능한 모델 목록 등 **데몬 런타임 질의를 거쳐야 하는 동적 데이터**는 정적 스키마에 담을 수 없으므로 별도 명령(`magi: Choose the model`)을 통해 퀵픽(QuickPick)으로 제공합니다.

**(라) 승인 대화 (Approval Flow).** JetBrains는 도구 창 내부에 인라인 승인 버튼을 배치합니다. VS Code에서도 대화 웹뷰 내부에 인라인 버튼으로 렌더링하는 것이 타당합니다. `showQuickPick`나 `showInformationMessage`와 같은 네이티브 팝업은 에디터 포커스를 강제로 탈취하며, 작업의 상세 맥락(수정 대상 파일 및 변경 사유)을 충분히 담아내기 어렵기 때문입니다.

## 5. 소켓 통신 계약 및 정합성 보장

`workspaceKey`의 계산 결과가 데몬과 **단 한 글자라도 어긋나면 통신 에러가 발생하지 않고 침묵 실패(Silent Failure)합니다.** 확장은 존재하지 않는 소켓을 조회하여 데몬을 「미실행(not running)」 상태로 오진하고, 이미 데몬이 기동된 작업 디렉토리에 **중복 데몬 구동**을 시도하게 됩니다.

경로 생성 공식 (`internal/adapter/daemon/publish.go` 기준):

```
socketPath = socketDir(configDir) / "daemon-" + workspaceKey(workdir) + ".sock"
workspaceKey(w) = sanitize(basename(realpath(abs(w)))) + "-" + shortHash(realpath(abs(w)))
shortHash      = FNV-1a 64비트 → 36진수 8자리, 낮은 자리부터
sanitize       = [A-Za-z0-9_-] 이외 문자를 '-'로 치환
```

### 포팅 시 반드시 준수해야 하는 두 가지 결함 방지 규칙:

1. **심볼릭 링크(symlink)를 완전 해소합니다.** macOS 환경에서 `/tmp`는 `/private/tmp`의 심볼릭 링크입니다. 셸 환경에서 `cd /tmp`를 실행한 사용자와 자체적으로 `chdir`을 수행한 프로세스가 서로 다른 경로를 참조하면 **동일한 물리 디렉토리에 대해 상이한 해시값**이 생성됩니다. 이는 코어 데몬 개발 과정에서 실제로 확인된 결함입니다.
2. **해시 연산은 64비트 정수 오버플로를 처리해야 합니다.** JavaScript의 표준 `number`(IEEE 754 배정밀도 부동소수점)를 사용할 경우 곱셈 연산 시 하위 비트의 정밀도가 손실됩니다. 이 경우 **짧은 경로에서는 우연히 일치하다가 실제 긴 작업 디렉토리 경로에서 해시가 어긋나는 최악의 잠재 결함**이 발생합니다. 반드시 `BigInt` 자료형을 사용하고 64비트 마스크를 적용해야 합니다.

### 골든 데이터 검증 — 코어 데몬 실측값

아래 표는 **Go 코어의 `daemon.WorkspaceKey` 함수를 실제 실행하여 산출한 기준값**입니다. 단위 테스트(`workspace.test.ts`)에서 이 골든 데이터를 상시 검증합니다.

| 작업 디렉토리 경로 | 산출된 workspaceKey |
|---|---|
| `/tmp` | `tmp-pstqlaw1` |
| `/usr` | `usr-a74ztgfv` |
| `/Users` | `Users-cghuwblp` |
| `/var/log` | `log-clkllm93` |
| `/etc` | `etc-ydppqbth` |
| `/` | `--ov1j1jmu` |

루트 디렉토리(`/`)의 경우 `basename("/")`이 `"/"`가 되며, sanitize 치환 규칙에 따라 `-`로 변환되어 키가 대시 2개(`--`)로 시작합니다. 예외 케이스 처리 누락을 방지하는 필수 테스트 벡터입니다.

### 전송 프로토콜

Windows에서는 Node의 경로 기반 연결을 Unix 소켓에 직접 사용하지 않고 `src/core/daemon.ts`의 Go relay 경로를 사용합니다. `--raw-socket`은 JSON 요청을 감싸는 기존 `ide-bridge` 메서드와 달리 데몬 바이트 스트림을 직접 전달합니다. 상위 전사 의미와 재연결 커서는 변환하지 않습니다.

줄 단위 구분 JSON(Newline-delimited JSON) 방식을 따릅니다. 데몬은 `json.NewEncoder(conn)`로 전송하고 `bufio.Scanner`로 수신하므로, 단일 요청과 단일 응답이 각각 1줄 단위로 처리됩니다. 스트리밍 엔드포인트(`transcript`, `watch`)는 동일한 소켓 연결을 유지하며 지속적으로 응답 라인을 수신합니다.

- ⚠ **`status` 응답에는 세션 ID가 포함되지 않습니다.** 실물 데몬 질의 결과 반환 필드는 `ok`, `permission`, `backend` 3가지입니다. 현재 활성 대화 세션의 식별은 `sessions` 엔드포인트를 별도 호출하여 최신순 목록에서 조회해야 합니다. `status.session`을 참조하도록 잘못 구현할 경우 빈 문자열이 전달되어 전사 스트림이 0개 프레임 상태로 조용히 종료되는 결함이 발생합니다.
- ⚠ **소켓의 쓰기 채널(write-half)을 조기 종료하지 않습니다.** 요청 전송 직후 쓰기 채널을 종료(`nc -w` 형태)할 경우 연결 단절로 간주되어 수신 프레임이 유실됩니다. 이는 `docs/CLIENTS`에 명시된 핵심 통신 규약입니다.

## 6. 프로세스 생명주기 — 현행 구현과 안정화 목표

설치부터 종료까지의 목표 동작과 인수 기준은 [대표 클라이언트 수명주기 설계](../../../docs/CLIENT_LIFECYCLE.ko.md)를 따릅니다. 해당 문서의 신규 인터페이스는 구현 인계 대상이며 현재 지원 기능으로 안내하지 않습니다.

현재 `src/core/binary.ts`는 확장 호스트의 `process.env.PATH`를 먼저 보고 `<config>/bin/<판>/magi`의 기존 파일을 찾습니다. 사용자 로그인 셸의 PATH를 직접 조회하거나 바이너리를 자동 다운로드하지 않습니다. 바이너리가 없을 때 수동 시작 명령은 설치 안내를 제공합니다. 창 간 다운로드 잠금과 거절 상태 공유는 미구현이며, 기존 설계에 있던 `.fetching`·`globalState` 설명은 완료된 기능의 근거로 사용할 수 없습니다.

`src/core/lifecycle.ts`의 `OwnedCompanion`은 이 창에서 직접 시작한 foreground 프로세스를 보관합니다. 기존 데몬에는 관찰자로 연결합니다. 준비 확인은 최대 30초 동안 공개 PID와 연결 가능 여부를 확인하며, 종료는 자신의 프로세스를 대상으로 합니다. Windows 업데이트가 후계 PID를 만드는 경우까지의 소유권은 공통 설계 §4의 코어 인계 계약으로 보완해야 합니다.

현재 자동 기동은 15초마다 확인하고 60초 이동 구간에 최대 3회 시도합니다. 연결 성공 시 예산을 즉시 초기화하므로 짧게 연결됐다가 반복 종료되는 경우도 시험해야 합니다. 공통 목표는 60초 안정 연결 후 초기화하고 예산 소진 뒤 명시적 재시도를 기다리는 것입니다. 연결 재시도와 새 프로세스 기동 횟수는 별도로 관리합니다.

Windows 연결은 `magi ide-bridge --raw-socket` 자식 프로세스를 거칩니다. 해당 기능이 없는 코어를 명확히 식별하는 절차, 설치된 VS Code의 종료·강제 종료 시험, 구형 코어 조합과 복구 중 입력 보존을 공통 인수 매트릭스로 검증합니다.

---

자동 업데이트는 [공통 설계 §9](../../../docs/CLIENT_LIFECYCLE.ko.md#9-자동-업데이트--이번-안정화에-포함)의 인수 범위입니다. 최초 코어 설치 자동화와 구분하며, 코어 updater가 교체·롤백을 담당하고 VS Code는 호환성·상태·수명 채널을 담당합니다. 확장 자체의 업데이트는 IDE 업데이트 관리자에 맡깁니다.

## 7. 계층별 품질 검증 기준

아래 표는 개별 검사 방법입니다. 제품 수명주기 안정화 완료는 [공통 인수 매트릭스 L01–L13](../../../docs/CLIENT_LIFECYCLE.ko.md#8-인수-매트릭스)로 판정합니다. 소스 필드 검사, mock 테스트, 패키징 성공만으로 실제 설치·재연결·종료 검증을 대체하지 않습니다.

JetBrains 클라이언트의 `docs/TESTING.ko.md` 및 `ManualTest` 검증 체계와 동등한 품질 게이트를 구축합니다.

| 계층 | 검증 방식 |
|---|---|
| `core/**` | `node:test` 프레임워크 기반 순수 단위 테스트 (VS Code 런타임 종속성 배제) |
| **와이어 대조** | JetBrains의 `WireConformanceTest`에 대응. **Go 코어 소스 코드를 정적 분석하여** 데몬이 송출하는 JSON 필드명과 클라이언트가 역직렬화하는 필드명이 1:1 일치하는지 전수 검증합니다. 매칭 건수가 기준치에 미달할 경우 테스트가 즉시 실패합니다 |
| 소켓 키 정합성 | §5의 골든 데이터셋 대조 검증 |
| 아키텍처 계층 분리 | `src/core/**` 내부에서 `from 'vscode'` 임포트 존재 여부 검사 |
| `ide/**` | 통합 테스트 환경 구축 (§9 참조) |

**와이어 대조가 필수적인 이유:** TypeScript는 JSON 파싱 시 미정의 필드를 런타임 오류 없이 무시하고 누락된 필드를 `undefined`로 처리합니다. 프로토콜 필드명이 불일치할 경우 예외가 발생하지 않고 기본값으로 폴백되어, UI에는 단순히 「데이터 없음」으로 표시되며 조용히 실패합니다. 이 정합성 테스트를 클라이언트마다 필수 배치하지 않을 경우 플랫폼 증가에 비례하여 프로토콜 드리프트가 누적됩니다.

## 8. 편집기 연동 제어 — HandServer 메커니즘

JetBrains 클라이언트는 루프백 인터페이스에 `HandServer`를 기동하고 해당 주소를 데몬에 등록(`mcp-attach`)하여 편집기 원격 제어를 수행합니다. 포트는 0번(임의 할당)으로 개방한 후 실제 바인딩된 포트를 취득하며, 동일 기기 내 타 프로세스의 무단 접근을 방지하기 위해 토큰 인증을 선행 검증합니다. 알림 처리 시 본문 없이 **HTTP 204** 상태 코드를 응답합니다.

VS Code 확장 역시 동일한 구조로 동작합니다. 초기 도구는 `apply_edit`을 지원하며, 내부적으로 `workspace.applyEdit` API를 호출하여 파일 수정을 적용합니다. 세션 종료 시 `mcp-detach`를 수행합니다.

- ⚠ **`applyEdit` 호출 시 파일을 즉시 디스크에 저장하지 않습니다.** 수정 사항은 편집기 버퍼(Dirty buffer)에 유지되어야 합니다. 개발자가 변경 내용을 직접 육안으로 확인하고 필요 시 Undo(`Ctrl+Z`)할 수 있도록 제어권을 보장하는 원칙이며, JetBrains 구현과 동일합니다.

## 9-A. 빈 대화 안내 — 설계안 (IDE_NATIVE §6.5, 구현 전)

실물에서 잰 것에서 출발합니다(2026-09-20, VS Code 1.137.0). **대화가 0행일 때 전사 영역은 완전한
백지입니다.** 사람이 보는 것은 아무 말 없는 빈 판과 입력줄 하나이고, 거기서는 「아직 아무 말도 안
했다」와 「컴패니언이 안 뜬다」와 「연결이 끊겼다」가 **같은 화면**입니다.

### 9-A.1 상태 공급원 — 지금 있는 것

| 자리 | 하는 일 |
|---|---|
| `core/activity.ts` `State` | `not-running` · `attached` · `working` · `waiting` · `unknown`. ⚠ `attached` 는 **「데몬이 더 말하지 않았다」**이지 「놀고 있다」가 아니고, `unknown` 은 **「물어보지 못했다」**이지 「안 돈다」가 아닙니다. 이 파일이 그 혼동을 주석으로 이미 적어 뒀습니다 |
| `activity.panelNote(a)` | 문구와 「Start one」 제공 여부를 **코어가** 정합니다. `not-running`·`unknown` 만 말하고, idle/working/waiting 은 **일부러 침묵**합니다(상태줄이 이미 말하므로) |
| `ide/chat.ts` | `companion.onChanged` 마다 `{kind:'state', state, note: panelNote(...)}` 를 웹뷰로 보냅니다 |
| `web/chat_html.ts` `drawState(note)` | 그 문구와 단추를 `#note` 에 그립니다. **그리는 일만 하고 아무것도 안 정합니다** |

**그러므로 빈 화면의 원인은 「상태를 모른다」가 아닙니다.** 상태는 이미 옵니다. 비어 있는 갈래가
`attached` + 0행이고, 그 조합에 대해 아무도 할 말을 안 정해 뒀을 뿐입니다.

### 9-A.2 먼저 고쳐야 하는 것 — **한 자리에 두 가지가 산다**

`drawState` 는 `#note` 를 **먼저 비우고** 문구를 씁니다. 그런데 같은 `#note` 에 일시적인 사건도
씁니다 — `sending…`, `reply already in flight…`. 둘이 한 싱크라 서로를 지웁니다.

```
1. 컴패니언이 죽는다        → drawState: #note = "No companion is running." + [Start one]
2. 사람이 무언가 보낸다      → #note = "sending…"            ← 지속 상태가 지워진다
3. 4초 뒤 타이머            → #note = ""                     ← 빈 판으로 끝난다
4. 다음 state 사건이 올 때까지 「컴패니언이 없다」는 사실과 그 단추가 **화면에 없다**
```

거꾸로도 같습니다: 사건이 떠 있는 동안 상태가 바뀌면 `drawState` 가 먼저 비우므로 사건이 사라집니다.

**설계 결론:** 빈 대화 안내를 `#note` 에 얹지 않습니다. 얹으면 위 사슬에 똑같이 걸립니다. 두 가지를
**타입으로 가릅니다** — 지속 상태(수준)와 일시 보고(사건)는 다른 자리에 그립니다.

### 9-A.3 세 상태의 문구와 조작

빈 대화 안내는 **전사 영역**(행이 설 자리)에 서고, `#note`·입력줄·초안·질문 상태를 **덮지 않습니다.**

| 상태 | 무엇이 그렇게 정하나 | 화면 문구(사용자 말) | 할 수 있는 것 |
|---|---|---|---|
| 아직 모름 | `state === unknown` | 「컴패니언 상태를 아직 알 수 없습니다.」 | **컴패니언 시작** |
| 안 돌고 있음 | `state === not-running` | 「이 폴더에서 도는 컴패니언이 없습니다.」 | **컴패니언 시작** |
| 연결됐지만 대화 없음 | `state ∈ {attached, working, waiting}` **그리고** 행 0 | 「아직 주고받은 말이 없습니다. 아래에 무엇을 할지 적어 보세요.」 | (입력줄로 유도만) |

⚠ **행이 0인 것으로 데몬 부재를 추정하지 않습니다.** 네 번째 줄만 행 수를 봅니다. 나머지 셋은
`activity` 가 정하고, 그 셋에서는 행 수를 아예 묻지 않습니다. 반대로 네 번째 줄은 컴패니언의 상태를
말하지 않습니다 — 「아직 말이 없다」는 전사에 대한 사실이지 컴패니언에 대한 사실이 아닙니다.

⚠ **구현 용어를 안 씁니다.** 화면에 `not-running`·`unknown`·소켓·데몬·세션을 쓰지 않습니다. 위 문구의
영어 원문(`No companion is running for this workspace.`)도 한국어 화면에서는 그대로 두지 않습니다 —
다만 **전송 토큰이 아니라 표시 문구**이므로 §6.7 의 승인 단추와 같은 방식으로 가릅니다.

### 9-A.4 전이 — 안내가 낡게 남지 않아야 한다

| 일어난 일 | 안내가 해야 할 일 |
|---|---|
| 「컴패니언 시작」을 눌렀다 | 안내는 **안 바뀝니다.** 누른 것은 요청이지 결과가 아닙니다 — 단추만 눌린 표시로 바꿔 두 번 눌리지 않게 합니다 |
| 시작이 성공하고 **연결이 확인됐다** | 그때 「아직 주고받은 말이 없습니다」로 갑니다. **상태가 확인된 뒤에만** 갈아탑니다 |
| 시작이 실패했다 | 「컴패니언을 시작하지 못했습니다.」 + **다시 시도**. 실패를 성공처럼 지나가지 않습니다 |
| 눌렀는데 응답이 늦다 | 「아직 모름」 문구를 **유지한 채** 진행 중임을 표시합니다. 없는 성공을 먼저 그리지 않습니다 |
| 첫 행이 도착했다 | 안내가 **사라집니다**(행이 답을 대신합니다) |
| 세션을 바꿨다 | 새 세션의 행 수로 **다시 정합니다**. 옛 세션의 안내가 남아 있으면 안 됩니다 |
| 연결이 끊겼다(행은 이미 있음) | 전사 안내는 **안 섭니다**(행이 있으니 빈 대화가 아닙니다). 끊긴 사실은 `#note`/상태줄이 맡습니다 |
| 다시 붙었다 | 「연결하지 못했습니다」를 **지웁니다**. 사람이 아무것도 안 눌러도 지워져야 합니다 |

마지막 줄이 이 표가 있는 이유입니다 — **끝만 알리고 시작을 안 알리면 마지막 말이 영구 거짓**이 되고,
그 화면은 「연결 안 됨」을 붙인 채 정상 동작합니다.

### 9-A.4b 소유권 확정 — 지속 상태와 일시 알림은 **다른 자리**에 산다

9-A.2 가 「한 싱크라 서로 지운다」를 적었고, 그 결함은 **전사 행이 있을 때도 그대로 남습니다** —
행이 있으면 빈 대화 안내는 안 서지만 연결이 끊긴 사실은 여전히 `#note` 가 맡고, 그 자리는 4초
타이머가 지웁니다. 그러니 「빈 대화일 때만」 피해 가는 설계로는 안 됩니다.

**확정: DOM 과 상태를 가릅니다.** 한 표시 함수가 둘을 합치는 안은 **안 씁니다** — 합치면 「무엇이
무엇을 이겨야 하는가」를 매번 정해야 하고, 그 규칙이 틀리는 것이 지금 일어난 일입니다.

| | 지속 상태(수준) | 일시 알림(사건) |
|---|---|---|
| 무엇 | 컴패니언에 닿는가 — 안 돎 · 아직 모름 | 방금 일어난 일 — `sending…`, 이미 보내는 중 |
| 자리 | 제 요소(`#state-note`) | `#note` |
| 누가 정하나 | 코어(`panelNote`) | 화면 |
| 지워지는 때 | **상태가 바뀔 때만** | 제 타이머, 또는 다음 사건 |
| 단추 | 「컴패니언 시작」이 여기 붙습니다 | 없음 |

**전이 규칙 둘을 못 박습니다.**

- **일시 알림의 만료는 지속 상태를 안 건드립니다.** `sending…` 이 4초 뒤 사라져도 「컴패니언이
  없습니다」와 그 단추는 **그대로 있습니다.** 지금은 그것이 같이 지워지고, 다음 state 사건이 올
  때까지 안 돌아옵니다.
- **지속 상태의 다시 그리기는 일시 알림을 안 지웁니다.** 지금 `drawState` 는 먼저 비우므로, 보내는
  중에 상태가 한 번 갱신되면 `sending…` 이 사라집니다.

⚠ **화면에 둘이 동시에 설 수 있습니다.** 그것이 옳습니다 — 「컴패니언이 없다」와 「방금 보냈다」는
서로를 부정하지 않습니다. 좁은 폭에서 두 줄이 입력줄을 밀지 않게 하는 것은 배치의 일이지, 하나를
지워서 풀 일이 아닙니다.

회귀로 남길 것: `sending…` → 만료 → **지속 상태와 단추가 남아 있는가**. 그리고 보내는 중 상태
갱신 → **`sending…` 이 남아 있는가**. 둘 다 지금은 빨갛습니다.

### 9-A.5 화면 시안

```
┌─────────────────────────────────────────────┐
│                                             │   ← 전사 영역(행이 설 자리)
│        아직 주고받은 말이 없습니다.          │
│      아래에 무엇을 할지 적어 보세요.         │
│                                             │
├─────────────────────────────────────────────┤
│ state-note — 지속 상태(+시작 단추)           │
│ note — 일시 알림(sending… 등)                │
├─────────────────────────────────────────────┤
│ [ 입력줄                          ] [ 보내기 ]│
└─────────────────────────────────────────────┘

컴패니언이 없을 때:
┌─────────────────────────────────────────────┐
│   이 폴더에서 도는 컴패니언이 없습니다.      │
│            [ 컴패니언 시작 ]                 │
└─────────────────────────────────────────────┘
```

### 9-A.6 구현 전에 정할 것

- **확정: 두 줄을 하나로 합치고, 문구는 중립으로 둡니다.** 소스를 다시 보니 `unknown` 은 둘이 아니라
  **셋**을 겸합니다 — ① 아직 안 물어본 초기값(`status.ts`·`workspace.ts` 가 `cannotSay()` 로 시작합니다)
  ② 응답이 없음(`of(null)`) ③ 응답은 왔는데 `ok` 가 아님(`of(resp)` 의 `!resp.ok`). 자리는 갈려 있지만
  **타입에 표식이 없어 소비자는 못 가릅니다.**
  그래서 「연결하지 못했습니다」로 합치지 **않습니다** — 아직 안 물어본 상태에 실패를 단정하는 말이고,
  그 말은 자주 거짓이 됩니다. 「컴패니언 상태를 아직 알 수 없습니다」가 셋 모두에 참입니다. 단추는
  그대로 답니다: `panelNote` 가 이미 `unknown` 에 시작을 제안하며 그 사유를 적어 뒀습니다 — **나가는
  길이 우리가 확신하는지에 달려 있으면 안 됩니다.**
  조회 시작/완료를 실제로 나르는 안은 **나중 일로 남깁니다.** 그 구분이 화면에서 필요해질 때
  `Activity` 에 칸을 더하는 것이 순서이고, 그 전에는 없는 구분을 문구로 지어내지 않습니다.
- 문구를 코어(`panelNote`)가 계속 정할지, 전사 안내만 화면이 정할지. 지금 규칙은 「코어가 정하고 화면은
  그린다」이고, 전사 안내도 그 규칙을 따르는 편이 낫습니다 — 그래야 JetBrains 가 같은 문구를 씁니다.
- 회귀 입력: 상태 다섯 × 행 0/n, 그리고 9-A.4 의 전이 다섯.

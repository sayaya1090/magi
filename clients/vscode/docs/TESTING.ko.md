# 테스트 및 품질 검증 사양

[↑ 클라이언트 개요](../README.md) · [설계](./DESIGN.ko.md) · [형제: 젯브레인](../../jetbrains/docs/TESTING.ko.md)

> **검증 계층의 2단계 분리.** VS Code 확장의 품질 검증은 에디터 종속성 없이 Node.js 환경에서 순수 로직을 검증하는 `core` 단위 테스트와, **실제 VS Code 프로세스를 기동하여 매니페스트 및 UI 기여점을 검증하는 통합 테스트**로 명확히 구분됩니다. 두 계층을 분리함으로써 단위 테스트의 초고속 실행 속도를 유지하면서도 매니페스트 오작동을 차단합니다.

---

## 1. 단위 테스트 (`src/test/` — `node --test`)

VS Code 인스턴스 없이 순수 Node.js 런타임 상에서 동작하며, 프로토콜·상태 머신·이벤트 스트림·뷰 조립의 무결성을 검증합니다.

| 테스트 대상 | 검증 목적 및 불변식 |
|---|---|
| `workspace.test.ts` | **소켓 키 골든 데이터 검증.** Go 코어의 `daemon.WorkspaceKey`가 실제 산출한 기준값과 1:1 대조합니다. 키가 한 글자라도 어긋나면 런타임 에러 없이 존재하지 않는 소켓을 조회하여 데몬 미실행으로 오판합니다. 다국어(한글·악센트·일본어) 경로 처리, 3개 설정 디렉토리 분기, 플랫폼별 최대 소켓 경로 길이 제한을 전수 검증합니다 |
| `wire.test.ts` | **와이어 프로토콜 정합성.** Go 소스 코드를 직접 정적 파싱하여 클라이언트가 참조하는 필드명이 데몬 직렬화 태그와 일치하는지 전수 검증합니다. 프로토콜 버전 및 승인 어휘도 포함하며, 매칭 태그가 40개 미만일 경우 테스트 하네스 이상으로 간주하고 즉시 실패합니다 |
| `wire.test.ts` (타입 형태) | ⚠ **`unknown` 타입 방지:** `unknown` 선언 시 타입 순회가 차단되어 실질적으로 필드를 소비하지 못하는 결함을 차단합니다. ⚠ **구조체 누락 방지:** `ContextState` 누락 사례와 같이 스캐너가 대상을 건너뛰지 않도록 전수 스캔합니다. ⚠ **인라인 인터페이스 검증:** `ConfigItem` 등 응답 내부 인라인 선언의 타입(`unreadable` 필드 등)까지 정밀 검사합니다. `RosterRow` 5개 필드의 타입 불일치(bool/string/number 혼선)를 정적 타입 수준에서 방지합니다 |
| `wire.test.ts` (첨부 포맷) | **프롬프트 첨부의 `refs` 전송 검증.** 에디터 컴포저가 첨부 파일을 메시지 텍스트에 문자열로 이어붙이지 않고 독립된 `refs` 배열로 전송하는지 검증합니다. 코어는 워크스페이스 샌드박스 내부에서 캡(단일 ref 16KB, 전체 64KB)을 적용하여 발췌를 렌더링하고 프롬프트와 함께 영속화합니다. `submit` 요청이 `r.Refs`를 정확히 전달하는지, 라인 범위 파싱 실패 시 전체 파일로 안전하게 폴백하는지 검증합니다 |
| `stream.test.ts` (요청 분기) | **컴포저의 `steer` 및 `submit` 분기 검증.** `submit`은 신규 최상위 턴을 개시하여 `resetForNewTopLevel`을 호출하므로, 실행 중인 턴에 개입할 때 잘못 사용되면 기존 계획이 초기화됩니다. 확장은 전사 스트림의 미응답 `pending` 상태를 감지하여 턴 진행 중에는 적절히 개입 명령을 분기합니다 |
| `webview.test.ts` (전송 실패) | **전송 실패 시 입력 상태 보존 검증.** 컴포저는 Enter 입력 시 입력창을 비우므로, 백엔드 거절 발생 시 입력 텍스트와 첨부 칩을 그대로 복원해야 합니다. 사유 메시지, 텍스트, 참조 칩 3요소가 유실 없이 사용자에게 환원되는지 검증합니다 |
| `webview.test.ts` (응답 처리) | **사용자 인터랙션 핸들러의 응답 확인 검증.** UI 버튼 핸들러가 비동기 액션 결과를 단순히 호출하고 무시하지 않고, 반환된 `.ok` 상태를 판별하여 오류 처리를 수행하는지 전수 검사합니다 |
| `webview.test.ts` (인용 서식) | **카운슬 판정 근거(`cite`) 렌더링 스타일 검증.** 실측 라이브 전사(이벤트 95건, 판정 12건) 분석 결과 `cite`의 대다수가 diff 블록이었습니다. 가독성을 위해 고정폭 폰트 적용, 높이 상한 제한, 줄바꿈 유지, `keep` 속성과의 스타일 분리 규칙을 준수하는지 검증합니다 |
| `webview.test.ts` (정보 카드) | **웹뷰-확장 호스트 간 커맨드 호출 화이트리스트 검증.** 웹뷰 내 스크립트가 임의의 내부 명령을 호출하지 못하도록 허용된 명령 목록(`drawInfo` 내 6개 이상)만을 검증 및 디스패치하는지 검증합니다 |
| `webview.test.ts` (상태 인디케이터) | **컴패니언 실행 상태별 시각 표식 검증.** `core/activity.ts`에 정의된 상태 열거형 전체에 대해 고유한 클래스 및 스타일 규칙이 누락 없이 매핑되는지 검증합니다 |
| `plan.test.ts` (도구 연동) | **에디터 도구 서버 연동 상태 안내 검증.** HandServer 미등록, 포트 부재, 다중 창 충돌 등 도구 연동 실패 케이스에서 단순 침묵하거나 로그에만 남기지 않고, 사용자 화면에 구체적인 원인 안내를 표출하는지 검증합니다 |
| `setup.test.ts` (유휴 상태 오판) | **불완전한 런타임 상태의 `idle` 오판 방지.** `status` 응답의 빈 필드를 무단으로 `idle` 상태로 둔갑시키지 않고, 정확한 실행 상태(`attached` 등)를 화면에 반영하는지 검증합니다 |
| `stream.test.ts` (도구 호출 행) | **도구 호출별 식별 정보 표기 검증.** 동일 도구(`bash` 등)의 반복 호출 시 인자 요약을 축약 보존하여 개별 호출을 명확히 식별할 수 있도록 단일 행 렌더링을 구성하는지 검증합니다 |
| `stream.test.ts` (도구 결과 판정) | **도구 실행 성공과 권고 사항(`Advisory`)의 분리 검증.** 린트 경고 등으로 인해 `isError` 플래그가 설정되더라도 파일 저장이 정상 완료된 경우 이를 실패로 오인하지 않고 참고 사항으로 구분 렌더링하는지 검증합니다 |
| `stream.test.ts` (카운슬 투표) | **3인 카운슬 투표 전수 렌더링 검증.** 발언 없이 찬반 투표만 행사한 멤버(`silent`)를 생략하여 카운슬이 누락 표시되는 현상을 방지하고, 전원 투표 내역과 사유를 화면 행으로 생성하는지 검증합니다 |
| `manifest.test.ts` (이벤트 전수 수신) | ★ **코어 이벤트 수신 누락 방지 검증.** Go 코어가 발행하는 모든 이벤트 타입(`council.decided`, `interjection.deferred`, `interjection.answered` 등)을 확장이 처리하거나 명시적 사유와 함께 예외 처리하는지 전수 검증합니다 |
| `stream.test.ts` (대기 큐 표식) | **큐 대기 중인 프롬프트의 시각 표식 검증.** 작업 큐에 대기 중인 요청이 일반 요청과 명확히 구분되어 대기 인디케이터가 적용되는지 검증합니다 |
| `setup.test.ts` (사용자 레이블) | **SSO 및 데몬 설정 사용자명 반영 검증.** 데몬이 통지한 사용자 식별자(`magi.set_user_label`)를 화면에 올바르게 투영하는지 검증합니다 |
| `setup.test.ts` (환경 설정 3종) | **실행 환경 3요소(`permission`, `model`, `council`) 수신 검증.** 데몬이 전송한 3가지 핵심 설정 필드가 누락 없이 클라이언트 상태에 반영되는지 검증합니다 |
| `wire.test.ts` (엔드포인트 응답) | ★ **호출 엔드포인트 응답 타입 완전 선언 검증.** 확장이 호출하는 모든 데몬 API의 응답 구조체가 타입스크립트 인터페이스로 100% 선언되어 있는지 대조합니다 |
| `touched.test.ts` (질의 유형) | ★ **승인 요청과 선택지 질의의 분리 검증.** `permission`과 `question.requested`가 상이한 UI 컴포넌트(승인 단추 vs 선택지 카드)로 정확히 분기 렌더링되는지 검증합니다 |
| `touched.test.ts` (승인 맥락) | ★ **승인 대상 작업의 세부 맥락 표기 검증.** 승인 요청 시 도구명뿐만 아니라 인자(`args`), 수정 사유(`reason`), 변경 diff를 화면에 함께 렌더링하는지 검증합니다 |
| `touched.test.ts` (질의 순번) | **다중 질의의 진행 순번 표기 검증.** 복수 질문이 발생했을 때 총 질의 건수와 현재 순번(`(1/3)`)을 사용자에게 명시하여 단일 질문으로 오인하지 않도록 지원합니다 |
| `touched.test.ts` (결정 근거) | **질의 발생 근거(`rationale`) 렌더링 검증.** 에이전트가 질문을 생성하게 된 배경 맥락을 사용자에게 함께 제시하는지 검증합니다 |
| `stream.test.ts` · `webview.test.ts` (열린 라운드) | ★ **실물 전사를 두 판의 접기에 다 먹여** 찾았다 — 95 사건에 VS Code 54행 / 젯브레인 59행, 나머지는 정확히 같고 빠진 다섯이 전부 `council.convened` 였다. 면제 사유는 「그것이 나르는 근거는 계획판의 것」이라 했는데 **계획판에 `council` 이 한 번도 안 나온다** — 사유가 없는 독자를 가리켰다. 같이 떨어진 것이 라운드의 **문턱**이다: 판정 셋(`continue` 둘·`done` 하나)이 과반이면 되는 것인지 셋 다여야 하는 것인지 읽을 수 없었다. `rule` 은 `lens` 와 다른 칸이고(렌즈는 자리, 문턱은 라운드), 여는 행에는 표 대신 문턱이 선다. ⚠ 변이가 가드 하나를 더 요구했다 — **페이지가 그것을 그리는지**는 접기 시험이 못 본다 |
| `manifest.test.ts` (면제 사유) | ★ **두 사유가 서로 바뀌어 달려 있었다.** `labels.changed` 는 세션 작업의 **주제 라벨**이고 사람 이름은 `user.label.changed` 인데, 라벨 칸에 「사람 이름을 안 바꾼다」가 달리고 사람 칸에는 **「첫째와 같다」**가 달려 그 틀린 문장을 가리켰다 — 어느 것도 자기에 대한 사유를 안 갖고 있었다. **다른 칸을 설명하는 사유는 아무도 판단하지 않은 면제를 보증한다.** 그리고 「살아서 온다」는 사유는 **검사 가능한 주장**이라 그것도 잰다: 사유에서 `` `status.X` `` 를 뽑아 그 읽기가 실제로 있는지 본다(손으로 적은 목록은 비워도 통과했다 — 변이가 잡았고, 이끌어 내니 내가 몰랐던 셋째 주장 `status.doing` 이 나왔다) |
| `hand.test.ts` · `webview.test.ts` (워크스페이스 경계) | ★ **편집기 손이 밖의 파일을 열었다.** `resolve` 가 컴패니언이 대는 경로를 그대로 풀었다 — 절대면 그대로, 상대면 붙여서, 검사 없이. `show`·`apply_edit`·`problems` 가 전부 이 기계의 아무 파일이나 닿았다. 짝인 젯브레인은 그 선을 지킨다(`find` 가 프로젝트 밖이면 null). **남이 지키는 가둠은 내 것이 아니다** — 편집기 손은 둘째 문이다. **푼 경로**로 판정하고(`..` 가 못 걸어 나간다) **경로 조각**으로 견준다(`startsWith` 면 `/a/bc` 가 `/a/b` 안이 된다 — 그 흔한 새는 방식을 변이가 확인했다). ⚠ 심링크는 안 푼다고 함수 주석에 적었다 |
| `hand.test.ts` (빈 old) | **이 판은 안 뚫려 있었다 — 그런데 아무도 그렇게 말하지 않았다.** 막는 것은 스키마가 아니라 `need` 가 빈 문자열을 「없음」으로 거절하는 것이고, 편집기 층에는 **닿지 않는 죽은 검사**가 하나 더 있었다(지웠다). 무엇을 막는지도 적었다 — 젯브레인에서 JVM 으로 잰 것: 빈 바늘은 글자 사이마다 맞아 파일을 갈고 도구는 성공을 보고한다. `need` 를 느슨하게 고치면 조용히 열리므로 **두 방향**으로 못박는다(빈 것은 막고, 공백만인 것은 통과) |

## 2. 통합 검증 하네스 (`src/live/` — 실제 VS Code 인스턴스 구동)

매니페스트(`package.json`)의 구문 오류나 기여점 누락은 순수 단위 테스트만으로는 감지할 수 없습니다. 선언이 잘못된 뷰나 커맨드는 오류를 발생시키지 않고 단순히 에디터 UI에 나타나지 않기 때문입니다.

`selfcheck.ts`는 실제 구동된 VS Code 인스턴스 내부에서 다음 항목을 엄격히 검증합니다:

- 확장이 정상적으로 활성화되는지 여부 (`activate` 완료 대기)
- 매니페스트에 선언된 모든 커맨드가 런타임에 실제 등록되었는지 여부
- 선언된 뷰가 정확히 2개(대화 웹뷰, 계획 웹뷰)이며 올바른 컨테이너에 배치되었는지 여부
- 계획 뷰 컨테이너(`magi-side`)가 우측 **보조 사이드바(Secondary Sidebar)**에 정상적으로 바인딩되었는지 여부
- 환경설정 화면이 별도 웹뷰가 아닌 네이티브 설정 시스템에 바인딩되었는지 여부
- 대화 뷰 프로바이더가 예외 없이 정상적으로 렌더링(Resolve)되는지 여부
- 확장이 계산한 로컬 소켓 경로에 실제 실행 중인 데몬이 존재하는지 여부

```sh
cd clients/vscode && npx tsc -p . && node out/live/run.js
```

## 3. CI 환경 검증 범위 및 향후 과제

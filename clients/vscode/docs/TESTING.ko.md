# 테스트 및 품질 검증 사양

[↑ 클라이언트 개요](../README.md) · [설계](./DESIGN.ko.md) · [형제: 젯브레인](../../jetbrains/docs/TESTING.ko.md)

> **검증 계층의 2단계 분리.** VS Code 확장의 품질 검증은 에디터 종속성 없이 Node.js 환경에서 순수 로직을 검증하는 `core` 단위 테스트와, **실제 VS Code 프로세스를 기동하여 매니페스트 및 UI 기여점을 검증하는 통합 테스트**로 명확히 구분됩니다. 두 계층을 분리함으로써 단위 테스트의 초고속 실행 속도를 유지하면서도 매니페스트 오작동을 차단합니다.

---

## 1. 단위 테스트 (`src/test/` — `node --test`)

VS Code 인스턴스 없이 순수 Node.js 런타임 상에서 동작하며, 프로토콜·상태 머신·이벤트 스트림·뷰 조립의 무결성을 검증합니다.

| 테스트 대상 | 검증 목적 및 불변식 |
|---|---|
| `workspace.test.ts` | **소켓 키 골든 데이터 검증.** Go 코어의 `daemon.WorkspaceKey`가 실제 산출한 기준값과 1:1 대조합니다. 키가 한 글자라도 어긋나면 런타임 에러 없이 존재하지 않는 소켓을 조회하여 데몬 미실행으로 오판합니다. 다국어(한글·악센트·일본어) 경로 처리, 3개 설정 디렉토리 분기, 플랫폼별 최대 소켓 경로 길이 제한을 전수 검증합니다. ⚠ **골든은 어느 기계에도 없는 경로로만 만듭니다** — 있는 경로는 제 실제 이름으로 풀리므로 답이 글자만의 함수가 아니게 됩니다(`/tmp` 는 맥에서 `/private/tmp` 로 가는 링크, 리눅스에선 진짜 디렉토리). 한때 `/tmp`·`/etc`·`/var/log` 가 맥에서 찍힌 채 표에 있어 **CI 의 `test-vscode` 가 들어온 날부터 계속 빨갰습니다** — 포트는 멀쩡한데 `tmp-d6rgiolj !== tmp-pstqlaw1` 이라고 말하면서. 두 기계에서 다른 골든은 골든이 아닙니다 |
| `workspace.test.ts` (링크 해석) | **한 디렉토리가 두 키를 갖지 않는지 — 이 시험이 만든 링크로.** 골든이 이것을 못 잽니다: 없는 경로는 `realpathSync` 가 전부 실패하므로 **해석을 통째로 빼도 표가 다 초록입니다**(실측). 예전엔 `/tmp` 가 그 몫이었고, 그래서 표에 있었고, 그래서 리눅스에서 빨갰습니다. 임시 디렉토리에 링크를 직접 만들어 재면 같은 사실이 어느 기계에서나 같습니다(링크를 못 만드는 자리에서만 건너뜁니다) |
| `wire.test.ts` | **와이어 프로토콜 정합성.** Go 소스 코드를 직접 정적 파싱하여 클라이언트가 참조하는 필드명이 데몬 직렬화 태그와 일치하는지 전수 검증합니다. 프로토콜 버전 및 승인 어휘도 포함하며, 매칭 태그가 40개 미만일 경우 테스트 하네스 이상으로 간주하고 즉시 실패합니다 |
| `wire.test.ts` (타입 형태) | ⚠ **`unknown` 타입 방지:** `unknown` 선언 시 타입 순회가 차단되어 실질적으로 필드를 소비하지 못하는 결함을 차단합니다. ⚠ **구조체 누락 방지:** `ContextState` 누락 사례와 같이 스캐너가 대상을 건너뛰지 않도록 전수 스캔합니다. ⚠ **인라인 인터페이스 검증:** `ConfigItem` 등 응답 내부 인라인 선언의 타입(`unreadable` 필드 등)까지 정밀 검사합니다. `RosterRow` 5개 필드의 타입 불일치(bool/string/number 혼선)를 정적 타입 수준에서 방지합니다 |
| `wire.test.ts` (첨부 포맷) | **프롬프트 첨부의 `refs` 전송 검증.** 에디터 컴포저가 첨부 파일을 메시지 텍스트에 문자열로 이어붙이지 않고 독립된 `refs` 배열로 전송하는지 검증합니다. 코어는 워크스페이스 샌드박스 내부에서 캡(단일 ref 16KB, 전체 64KB)을 적용하여 발췌를 렌더링하고 프롬프트와 함께 영속화합니다. `submit` 요청이 `r.Refs`를 정확히 전달하는지, 라인 범위 파싱 실패 시 전체 파일로 안전하게 폴백하는지 검증합니다 |
| `launches.test.ts` | **자동 기동 예산·물러서기를 「공유 계약」으로 검증.** 사례를 이 파일에 적지 않고 `clients/contract/lifecycle-policy.json` 을 읽어 돌립니다 — 젯브레인 시험이 **같은 파일**을 읽으므로, 두 편집기가 「둘 다 초록인데 서로 다른 규칙」이 되는 것을 막습니다(2026-09-11 실측: 이 클라이언트는 60초 이동 구간 3회, 젯브레인은 평생 3회·60초 간격이었습니다). 시계는 가상입니다 — 예산 하나가 60초라 실제로 기다리는 시험은 쓸 수 없고, 안 재는 시험은 없는 것과 같습니다. 물러서기는 무작위를 굴리지 않고 **양 끝(0·1)을 직접 넣어** 경계를 잽니다 |
| `launches.test.ts` (부르는 자리) | **정책이 옳은 것과 창이 그것을 쓰는 것은 다른 사실입니다.** `OwnedCompanion` 은 제 규칙(기동 시각 배열)을 따로 들고 있었고, 그 상태로도 계약 시험은 영원히 초록입니다. 그래서 `lifecycle.ts` 를 글자로 훑어 다섯을 봅니다: 정책을 쓰는가 · 옛 `this.attempts` 가 남았는가 · `connected` 로 안정 구간을 알리는가 · `may`/`spawned` 로 묻고 알리는가 · `failed`/`lost` 를 알리는가. 정책 숫자를 창에 다시 적는 것도 막습니다 — 한 사람만 고치는 둘째 사본이 생기는 자리입니다 |
| `launches.test.ts` (소유 모드·릴레이) | **바이너리에 먼저 묻고 쓰는지 검증.** `magi ide-bridge --features` 가 `owned-daemon-v1` 을 답할 때만 `--client-owned` 로 띄우고, `raw-socket-v1` 이 없으면 윈도우 릴레이를 **띄우기 전에** 거절합니다(구형 코어는 플래그를 거절하고 2로 끝나는데, 그러면 위층이 멀쩡한 데몬을 두고 「아무도 안 답했다」고 보고합니다 — `docs/CLIENT_LIFECYCLE` §2 가 이름 댄 구멍입니다). 판정은 `whyNoRelay` 로 빼내 **직접 불러서** 잽니다 — 처음엔 소스 글자로 쟀는데 낱말을 다 남긴 채 검사만 끄는 변이(`… && false`)가 통과했습니다 |
| `lifecycle.test.ts` (소유할 수 없는 코어) | **조용히 물러서지 않는지 검증.** 소유 모드가 없는 코어로 띄운 창은 **기동당 한 번** 그 사실을 말해야 합니다 — 창이 닫히면 자식을 끄지만 확장 호스트가 **강제로 죽으면** 컴패니언이 남는다는 것까지. 폴이 15초라 되풀이하면 소음이 되고, 소음은 진짜 경고가 안 읽히게 됩니다. 알리는 자리는 `start.ts` 가 `vscode` 를 import 해 부를 수 없으므로 소스로 재되 **문장 전체**를 못박습니다 — 묻고 답을 버리는 변이가 낱말만 보는 검사를 통과합니다(실측) |
| `lifecycle.test.ts` (파이프를 못 쥔 창) | **`held` 를 아무도 안 읽던 것을 검증(R8).** 코어에 소유 모드가 **있는데** 창이 파이프를 못 쥔 경우입니다 — 물러선 자리가 정확히 R2 가 고친 수명이라, 윈도우에서는 업데이트 한 번이 컴패니언을 끝냅니다. 기동당 한 번 사유가 나오고 두 번째는 빈 문자열이어야 합니다. 채널은 **주입**합니다 — 진짜 실패는 `owner.test.ts` 가 선점으로 만들고, 여기서 재는 것은 창이 그 사유를 **밖으로 나르는지**입니다. `start.ts` 가 실제로 그리는지는 소스로 재되, 무엇을 잃는지(「END it」)까지 못박습니다 |
| `lifecycle.test.ts` (한가할 때로 미룬 교체) | **미룬 교체도 사람이 누른 단추인지 검증.** `update` 에 `idle` 을 보내면 빌드는 지금 놓이고 재기동은 **컴패니언이 다음에 조용해질 때** 일어납니다 — 턴이 돌고 있으면 몇 분 뒤이고, 그게 이 선택지를 고르는 이유입니다. 그것을 즉시 교체용 5초 창에 견주면 뒤늦게 온 종료가 **추락으로 세이고**, 그건 `c5373a08` 가 다른 문에서 고친 결함이 새 문으로 돌아온 것입니다. 그래서 걸쇠(1시간 천장)로 잽니다 — 4분 뒤의 종료는 교체, 천장을 넘긴 종료는 여전히 추락(안 그러면 잊힌 걸쇠가 진짜 추락에 면죄부를 줍니다) |
| `lifecycle.test.ts` (사람이 부탁한 교체) | **재시작 버튼이 추락으로 안 세이는지 검증.** 윈도우엔 execve 가 없어 `magi.updateCore`·`magi.restartDaemon` 이 **소유 자식을 종료시킵니다**(실측: 문 응답 27ms 뒤). 그것을 `lost` 로 세면 세 번 누른 사람의 컴패니언이 `Blocked` 로 갑니다. 계약의 사례 「사람이 부탁한 교체는 실패가 아니다」에 **부르는 데가 없었습니다.** 살아 있는 데몬 대신 `ended` 로 몹니다 — 재려면 프로세스가 사라지는 그 플랫폼이 필요하기 때문입니다 |
| `lifecycle.test.ts` (닫기 경합의 뒤끝) | **진 경합이 무엇을 남기는지 검증(R7).** 로그 fd 를 `launch` 첫머리 — 기능 조회 **앞** — 에서 열었는데, R1 로 새로 생긴 `closed` 반환 둘이 그 열기와 닫는 `finally` 사이에 있었습니다. 아무것도 실패하지 않고 핸들만 한 방향으로 쌓입니다. 들여다보지 않고 **셉니다**: 진 경합 여덟 번 전후로 `/dev/fd` 를 세어 안 늘어나는지 봅니다(POSIX 에서만, 결함은 플랫폼 무관이므로 한 쪽에서 재면 충분합니다) |
| `fetch.test.ts` | **코어를 받아 자리에 놓기 — 네트워크 없이, 진짜 아카이브로.** 전선은 메서드 둘짜리 인터페이스라 시험이 라이브러리를 흉내 내는 게 아니라 **계약을 구현합니다**. 나머지는 다 진짜입니다: `tar` 가 만든 tar.gz · 진짜 sha256 · 진짜 풀기 · 탐색기가 찾는 그 자리(`bin/<판>/`)에 실제로 놓이는지. 재는 것: 순서(**체크섬 표를 먼저 묻고 그 다음에 받는다** — 아무도 보증 안 한 것을 안 받습니다) · 체크섬 불일치면 **아무것도 안 남는가** · 표에 없는 자산은 받기 전에 거절하는가 · 체크섬이 **다른 호스트**에서 오면 표를 묻지도 않는가 · 없는 기계는 네트워크 오류가 아니라 그 사실을 말하는가 · 설정을 못 읽은 빌드는 제 탓이라고 말하는가 · `insecure` 면 표를 **아예 안 받는가**(확인하는 척 안 합니다) · 아카이브가 어떻게 중첩돼도 실행 파일을 찾는가 · 깨진 아카이브는 푸는 단계에서 터지는가 · 임시 디렉토리를 안 남기는가(**전후 스냅샷 차이**로 잽니다 — 0 과 견주면 남의 임시 디렉토리 때문에 빨개집니다) |

## 수명·릴레이 회귀 검증 (2026-09-11)

`lifecycle.test.ts`는 **실제 데몬 프로세스를 기동하여** 수명 주기 및 IPC 통신을 검증합니다. 환경 변수 `MAGI_VSCODE_TEST_BINARY`에 바이너리 경로가 지정되지 않으면 테스트를 건너뜁니다(LLM 모델을 호출하지 않도록 백엔드는 접속 불가능한 주소로 지정하며, 설정 및 소켓 디렉터리도 임시 격리 경로로 대체합니다). 단일 테스트 슈트에서 다음 항목들을 종합적으로 검증합니다:

- **동시 중복 기동 방지 (단일 프로세스 보장)** — `start()`가 이미 실행 중일 때는 기존 실행 프로미스(`Promise`)를 반환하여 중복 기동을 차단합니다.
- **바이트 릴레이 스트림 중계 검증** — `ide-bridge --raw-socket` 프로세스를 경유하여 2회의 RPC 왕복과 1회의 스트리밍 수신이 정상 통신됨을 확인합니다.
- **외부 기동 컴패니언 보존** — 외부에서 실행된 컴패니언의 연결을 닫더라도 해당 프로세스(PID)가 종료되지 않고 유지됨을 `kill(pid, 0)` 신호로 실측 확인합니다.
- **소유 프로세스 종료 및 소켓 정리** — 확장이 직접 기동한 자식 컴패니언 프로세스는 연결 종료 시 유닉스 도메인 소켓 파일까지 함께 정리하며, 명시적으로 종료된 인스턴스는 자동으로 재기동하지 않습니다.
- **바이너리 부재 및 지연 기동 중단 처리** — 실행 바이너리가 없을 경우 「failed to start」 오류로 거절하며, 접속 대기 중에 닫기 이벤트가 발생하면 지연 생성(`spawn`)이 발생하지 않도록 차단합니다.
- **미존재 소켓 릴레이 거절 검증** — 존재하지 않는 소켓 경로로의 릴레이 연결 시도를 올바르게 거절합니다.

> ⚠ **단위 검증 범위 외 항목:** 창을 실제로 닫을 때 실행되는 VS Code 네이티브 `deactivate` 경로, Windows 환경의 Named Pipe/AF_UNIX 분기 처리, 사용자에게 표출되는 경고 배너는 본 테스트의 검증 범위에서 제외됩니다.

### §4.6 복구 목록 재정렬 시 포커스·선택 보존 (P2 리뷰 잔여 결함 해결)

### §4.6 선택 복원 범위를 실제 선택 노드로 제한 (P2 리뷰 결함 해결)

1. **문제 정의 및 P2 결함 원인:**
   - `chat_adapter.ts:refresh`에서 전문이 열려 있을 때 선택의 anchor가 항목 root 안에 있으면 전문(`entry.fullPre`) 내부 선택으로 오판하는 결함이 있었습니다.
   - 선택 경계를 `fullPre`가 아닌 `root.contains`로 검사함에 따라, 전문을 열고 같은 항목의 사유(`reasonEl`), 제목(`titleEl`), 미리보기(`previewEl`) 등을 선택한 뒤 순서 변화 없이 동일한 rows로 refresh만 호출해도 선택이 본문 `fullPre`의 시작 부분으로 강제 변환되었습니다.
   - 또한 옛 선택 오프셋을 새 본문 길이에 맞추어 무조건 clamp하는 처리가 다른 노드나 삭제된 범위를 유효한 범위인 것처럼 둔갑시키는 원인이었습니다.

2. **해결 내용 및 엄격한 불변식:**
   - **원래 선택 상태의 완벽한 보관:** 원래 선택의 `anchorNode`, `focusNode`, `anchorOffset`, `focusOffset`, 선택 방향(`isBackwards`), 기대 텍스트(`expectedText`)를 온전히 캡처합니다.
   - **전문(fullPre) 범위 한정:** Range의 시작(`startContainer`)과 끝(`endContainer`)이 모두 동일한 `entry.fullPre` 내부 텍스트 노드인 경우에만 전문 오프셋 변환을 허용합니다. 사유·제목·미리보기·다른 항목·목록 밖을 걸친 선택은 결코 전문으로 변환하지 않고 원본 노드·오프셋 기반으로 격리합니다.
   - **불필요한 Selection 재설정 방지:** DOM 이동 전후 선택이 이미 동일한 경우 `removeAllRanges`/`addRange`를 호출하지 않아 불필요한 브라우저 선택 변경 이벤트를 차단합니다.
   - **클램핑(clamping) 제거 및 브라우저 정상 삭제 동작 준수:** 노드가 문서에 연결되어 있는지(`isConnected`, `doc.contains`, `recoveryItemsEl.contains`), 오프셋이 실제 노드 길이 내인지(`offset <= nodeLen`), 텍스트가 기대 텍스트와 일치하는지 엄격히 검증합니다. 선택한 텍스트가 변경되었거나 노드가 삭제된 경우 clamp하지 않고 복원을 건너뛰어 브라우저의 정상 삭제 동작을 따릅니다.
   - **목록 밖 선택 보존:** 목록 외부의 선택은 갱신 과정에서 지우거나 교체하지 않고 원본을 보존합니다.
   - **역방향 선택 및 스크롤 고정:** `Selection.setBaseAndExtent` API를 우선 활용하여 역방향 선택(`anchorOffset > focusOffset`)의 방향성을 완벽히 복원하며, 선택 복원으로 인해 스크롤 위치가 튀지 않도록 보장합니다.

### 브라우저 합성 한글 IME 이벤트 검증 (Synthetic Composition Events)

공통 E2E 하네스(`node clients/vscode/tools/transcript-test.mjs`, 시나리오 `asks_synthetic_ime_composition_and_recovery_lock`)를 통해 단일 실행 경로로 Chromium 브라우저 환경에서 합성 DOM 이벤트를 주입하여 `chat_adapter`의 이벤트 가드를 실측 검증합니다 (중복 standalone 도구는 제거되었습니다):

1. **한글 조합 중 Enter 억제 및 중복 전송 방지 (합성 이벤트):**
   - composer `#say`에서 한글 음절 조합 단계('ㅎ' → '하' → '한', `CompositionEvent: compositionstart`/`compositionupdate`, `KeyboardEvent: isComposing: true, keyCode: 229`) 동안 발생하는 Enter 키 입력이 메시지 전송을 유발하지 않음을 단언 (`postMessage` 발행 0건).
   - 음절 조합 완료(`compositionend`) 후 발생하는 정상 Enter(`isComposing: false, keyCode: 13`) 입력 시 단어 중복이나 글자 깨짐 없이 정확한 한글 문자열("한글")이 1회 전송되고 입력창이 즉시 비워짐을 실측 검증.
2. **조합 중 복구 초안 버퍼 파괴 방지 (합성 이벤트):**
   - 질문 답변 실패로 복구 초안 패널이 열려 있는 상태에서, composer에서 한글 조합이 시작(`compositionstart`)되는 즉시 복구 패널의 '복사'(`copy-btn`) 버튼이 비활성화(`disabled = true`)되어 조합 버퍼 파괴를 원천 방지함을 단언.
   - 한글 조합이 완료(`compositionend`)되면 복사 버튼이 다시 활성화(`disabled = false`)되어 정상적인 초안 복사/이어붙이기가 가능함을 실측 검증.
3. **검증 범위 및 한계 규정 (Verification Scope & Unverified Notice):**
   - **검증된 범위:** Chromium 웹뷰 내부의 DOM 이벤트 수신 및 어댑터 가드 로직 (`chat_adapter.ts`의 `isComposing` 상태 관리, `keyCode === 229` 필터링, 복구 버튼 잠금).
   - **미검증 범위 (Unverified Scope):**
     - **실제 OS 네이티브 IME(macOS Apple 2SetKorean, Windows MS-IME 등)는 계속 '미검증(Unverified)'** 상태로 분류합니다.

### §5.6 선택지 번호 중복 방지, CSS 목록 마커 제어 및 숫자 본문 보존

1. **번호 판단 및 표시 헬퍼 (`src/web/chat_adapter.ts`):**
   - 순수 함수 `formatChoiceOptions(options)` 및 인터페이스 `FormattedChoices`, `FormattedChoiceOption` 추가.
   - **판정 규칙:**
     - 목록 전체가 1부터 순서대로 시작하는 동일한 형식의 번호(`1. 내용`, `1) 내용`, `(1) 내용`)를 가진 경우에만 ‘이미 번호가 있는 목록’(`hideListMarker: true`)으로 판정합니다.
     - 번호 뒤에는 공백 또는 탭(`[ \t]+`)이 최소 하나 필요하며, 번호를 제외한 본문도 존재해야 합니다.
     - 항목 번호가 실제 인덱스+1과 정확히 일치해야 하며, 형식 혼합(`1. `와 `2) `), 번호 건너뜀(`1. `와 `3. `), 빈 본문(`1. `)은 번호 있는 목록에서 제외합니다.
     - `1.5배`, `2026. 계획`, `123.txt` 등 숫자 본문은 번호 없는 일반 목록으로 취급하여 접두사를 일체 제거하지 않고 원문 그대로 보존합니다.
     - 원본 `options` 배열과 원문 문자열을 절대 변조하지 않는 불변성(immutability)을 보장합니다.
   - **버튼 라벨 구성:**
     - 이미 번호가 있는 목록일 때만 확인된 번호 접두사를 제거하고, 첫 줄 기준 최대 20자 축약(`slice(0, 19) + '…'`)을 적용한 뒤 고유 순번(`(i + 1) + '. '`)을 부여합니다 (중복 번호 제거).
     - 번호 없는 목록 또는 숫자 본문은 원문 전체를 기준으로 축약 및 순번을 부여하여 숫자가 라벨에서 누락되지 않도록 보존합니다.
     - 버튼 `title` 및 클릭 시 전송값은 모든 경우 원문 전체를 verbatim으로 유지합니다.

2. **UI 표시 및 CSS 목록 마커 제어 (`src/web/chat_html.ts`):**
   - 본문 `ol.choices li`의 `textContent`는 모든 경우 원문 그대로 설정합니다.
   - 이미 번호가 있는 목록에만 `#ask-body ol.choices.hide-marker { list-style: none; margin-left: 4px; }` 규칙을 적용하여 브라우저의 기본 숫자 마커를 숨김으로써 중복 표시를 제거합니다.
   - 일반 목록은 기본 `list-style-type: decimal`을 유지하여 접근성과 시인성을 보장합니다.
   - 버튼 `textContent`는 `formatChoiceOptions`가 생성한 `item.buttonLabel`을 설정하고, 본문과 버튼이 단일 판정기를 공유합니다.

2. **`createSuggestController` RxJS 스트림 리팩터링 (`src/web/chat_adapter.ts`):**
   - 기존 컨트롤러의 `let timer: ReturnType<typeof setTimeout> | null = null;`, `clearTimeout(timer)` 등 수동 타이머 관리 코드를 전량 제거했습니다.
   - `Subject<SuggestCommand>` + `switchMap` + `timer(delayMs, scheduler)` + `takeUntil(destroy$)` 파이프라인으로 재설계했습니다.
   - `answer_state.ts`, `recovery_state.ts`는 초안·복구 자료·전송 시도의 단일 정본(Single Source of Truth)으로 유지하며, Subject 내부에 이중 상태를 보관하지 않습니다.
   - 빈 입력(`''`) 및 3글자 이하 미충족 입력도 이전 대기 작업을 즉시 무효화해야 하므로 debounce 앞에서 누락시키지 않고 `switchMap` 내부에서 `EMPTY`로 반환하여 이전 작업을 즉각 취소합니다.
   - 외부 `switchMap`에서 즉시 전환하고 내부 `timer`로 지연시켜 새 입력 후 지연 시간 동안 옛 응답이 적용되는 결함을 원천 차단했습니다.
   - `dispose()` 시 `destroy$` 완료 및 `subscription.unsubscribe()`를 통해 대기 중인 모든 타이머와 구독을 완전 해제하고, dispose 이후 새 입력 스케줄링 및 늦은 응답 수신을 차단했습니다.

### §5.8 axe-core 접근성 자동화 감사 (axe-core Automated Accessibility Audit)

1. **테스트 패키지 의존성 격리 및 제품 VSIX 무오염:**
   - `@axe-core/playwright` (^4.13.0) 및 `axe-core` (^4.13.0)는 `clients/web/e2e/package.json` 및 `package-lock.json`의 `devDependencies`에만 단독 설치했습니다.

   - 제품 웹뷰의 Content Security Policy(`default-src 'none'; style-src ${cspSource} 'unsafe-inline'; script-src 'nonce-${nonce}' ${cspSource};`)를 완화하지 않고, Playwright의 CDP 세션 기반 스크립트 실행 파이프라인을 통해 엄격한 보안 경계를 유지한 채 감사를 수행합니다.

2. **접근성 마크업 및 명도 대비 기본 개선 (`src/web/chat_html.ts`):**

# VS Code 확장 — 화면 설계

[↑ 클라이언트 개요](../README.md) · [설계](./DESIGN.ko.md) · [플랫폼 규약 대조표](./PLATFORM.ko.md) · [형제: 젯브레인 화면 설계](../../jetbrains/docs/UI.ko.md)

> **상태: 설계. 아직 아무것도 안 그렸다.**
>
> [설계](./DESIGN.ko.md) 가 **무엇을 만드나**를, [대조표](./PLATFORM.ko.md) 가 **VS Code 가 정해
> 둔 것**을 적는다. 이 문서는 **무엇이 어디에 어떻게 그려지나**를 정한다.
>
> §0 의 불변식은 젯브레인 UI 문서에서 그대로 물려받는다. 그것은 클라이언트별 취향이 아니라 이
> 저장소가 값을 치르고 얻은 규칙이고, 값을 치른 자리가 저기라고 해서 여기서 다시 치를 이유가 없다.

---

## 0. 불변식 — 물려받는다

젯브레인 UI 문서 §0 그대로다. 여섯 다 클라이언트를 안 가린다.

0-1. **한 대화의 행을 짓는 규칙은 한 벌이다.** 두 벌 적으면 안 재지는 쪽이 갈라진다. 실제로 치른 값이 있다. 상태 표시줄은 데몬이 안 말한 것을 「쉬는 중」으로, 우측 판은 같은 자리를 「도는 것
없음」으로 그렸다.

0-2. **화면은 얕게 그린다.** 무엇을 적을지는 데몬이 정한다. 화면이 페이로드를 파서 문장을 지으면
그 문장은 화면 수만큼 생긴다. **클라이언트가 여섯이 되면 여섯 벌이다.**

0-3. **모름과 없음을 갈라 그린다.** 「안 왔다」·「없다」·「이 빌드에 문이 없다」는 셋 다 다른
사실이다. 빈 자리로 뭉치면 화면이 모르는 것을 아는 척한다.

0-4. **보고와 수준은 다른 자리에 쓴다.** 「안 갔다: 사유」는 한 번 일어난 사건이고 「붙어 있다」는
지금 계속 참인 상태다. 한 자리에 쓰면 뒤엣것이 앞엣것을 지운다. 젯브레인은 이것을 타입으로
박았고(`Level`), 우리도 타입으로 박는다 — 셈으로 지키면 셈이 늙는다.

0-5. **편집기에 이미 있는 것은 만들지 않는다.** 그리고 그 역도 불변식이다: **VS Code 가 더 잘
그리는 것은 VS Code 에 넘긴다.** diff 를 웹뷰에 구겨 넣지 말고 `vscode.diff` 로, `파일:줄` 은 글자가 아니라 점프로 간다.

0-6. **워크스페이스는 신뢰 경계다.** 전사는 로컬 소켓 전용이다. ssh 문에는 어떤 클라이언트도
전사를 올리지 않는다.

**0-7 은 이 클라이언트가 더한다. 플랫폼이 요구하기 때문이다.**

0-7. **웹뷰는 둘뿐이다.** VS Code 가 "webviews should only be used if you absolutely need them"
이라고 못박는다([대조표 §3](./PLATFORM.ko.md)). 대화와 계획판 말고는 전부 네이티브 API 로 그린다.
젯브레인에서 웹뷰(JCEF)를 쓰던 자리도 여기서는 다시 판단한다.

## 1. 자리 옮김 — TUI 넷이 어디로 가나

TUI 는 한 격자에 넷을 쌓는다. 터미널에 자리가 하나뿐이라서다. VS Code 에는 그 넷이 갈 자리가
이미 있다. **옮기는 것이지 새로 만드는 것이 아니다.**

> **패널은 전사와 입력만. TUI 의 머리와 발치는 상태 표시줄로. TUI 의 우측 포스트잇은 사이드바로.**

| TUI 자리 | 무엇 | VS Code 자리 |
|---|---|---|
| 머리 — `model <이름>`, 승인 칩 | 무엇으로 도는가 | **상태 표시줄 왼쪽** — 워크스페이스의 사실이지 지금 연 파일의 것이 아니다([대조표 §1](./PLATFORM.ko.md)) |
| 머리 — `◐ 스텝 d/t`, `⚖ council` | 지금 무엇을 하는가 | **상태 표시줄** — 폭이 없어 「무엇을」은 안 적는다. 「무엇을」은 계획판이 그린다 |
| 뷰포트 | 전사 | **패널 웹뷰** (§2) |
| 발치 — 턴 미터(경과·토큰·ctx%) | 이 턴이 얼마나 갔나 | **계획판** (§3). 상태 표시줄에는 경과만 |
| 발치 — `esc interrupt` | 세우는 손 | 패널 툴바의 「세우기」 |
| 발치 — 키 힌트 | 배우는 자리 | **안 옮긴다** — 단추가 보이는 화면이다 |
| 우측 포스트잇 다섯 장 | 붙박이 사실 | **액티비티 바 + 사이드바** (§3) |
| 모달 — 승인·물음 | 답하는 손 | **패널 웹뷰 안** (§2.3). 모달이 아니다 — 사람이 시작한 일이 아니기 때문이다 |
| 모달 — resume·cron·subagents | 설정과 행동 | **명령 팔레트 + 설정**(§5) |
| 커맨드 팔레트 | 한 타로 아무 데나 | 편집기의 것을 쓴다. 자체 팔레트는 §0-5 위반 |
| 입력 + 컴포저 제안 | 손 | 패널 웹뷰 안 |

**젯브레인과 갈리는 두 자리**를 미리 적는다:

- 젯브레인은 포스트잇을 **설정 화면**에 접었다(사용자 결정). 여기서는 못 한다 — 설정 화면을
  우리가 못 짜기 때문이다([대조표 §5](./PLATFORM.ko.md)). 그래서 **사이드바로 돌아간다.**
- 젯브레인의 승인은 하단 독 안의 단추다. 여기서도 웹뷰 안이지만, **모달을 쓰지 않는 이유가
  다르다**: 규약이 "actions that are not explicitly initiated by the user" 에 모달을 금한다.

## 2. 패널 — 대화

### 2.1 왜 패널인가

규약이 두 가지를 말한다: 가로 폭에서 득 보는 것, 그리고 "supporting functionality". 전사는 둘 다다. 넓을수록 읽기 낫고, 사람의 주 작업은 코드이지 대화가 아니다.

대신 규약이 붙이는 조건도 받는다: **"users often minimize the Panel"**. 그래서 패널이 접혀
있어도 컴패니언이 도는지는 보여야 하고, 그것이 상태 표시줄이 따로 있는 이유다(§4).

그리고 **좁은 폭에서 살아남아야 한다.** 사람은 이 뷰를 사이드바로 끌 수 있고, 규약이 그때
깨지는 웹뷰를 금한다. 전사는 세로로 흐르는 글이라 원래 좁은 폭에 강하지만, **입력 줄과 툴바가
가로로 벌어지지 않게** 짠다.

### 2.2 무엇을 그리나

행을 짓는 규칙은 `core/transcript.ts` 한 벌이다(§0-1). 어휘는 웹 콘솔의 `line` 과 같다.

- **누가.** `who` 로 갈라 그린다. 사람의 행은 친 그대로, 컴패니언의 답은 마크다운.
- **마크다운을 무엇으로 그리나 — 아직 안 정했다.** 젯브레인은 IDE 의 마크다운 엔진을 빌리는데
  (`RichAnswer`), VS Code 웹뷰에는 빌릴 엔진이 없다. 갈래 셋:
  (가) 렌더러를 싣는다 — 번들이 커지고 CSP 를 다뤄야 한다.
  (나) 가벼운 부분집합을 직접 그린다 — 젯브레인 `Markup.markdown` 을 옮기는 것이고, 펜스·표·
  링크에서 틀린다.
  (다) 코드 펜스만 편집기의 하이라이터로 넘긴다.
  **정하지 않고 남긴다**(§7). 실물 없이 고르면 틀린 쪽을 고른다.
- **`thinking`** 은 접힌 채 흐리게, **`tool`** 은 이름+요약 한 줄에 `args`/`out` 은 접어서.
- **툴 호출은 한 행.** `ok` 가 오면 그 행에 ✓/✗ 를 얹는다. `note` 는 실패가 아니라 「됐고 읽을 것이 있음」이다.
- **`pending` 행.** 답 없는 프롬프트에 왼쪽 막대. 콘솔의 `.row.pending` 과 같은 뜻이다.
- **카운슬 행**은 멤버의 자리 색. melchior·balthasar·casper 셋 말고는 색을 안 준다.
- **`diff` 는 편집기에 넘긴다**(§0-5). 웹뷰 안에 diff 를 그리지 않고 `vscode.diff` 로 연다.
- **`파일:줄` 은 점프다.** 글자로 그리지 않는다.
- **Enter 는 보낸다.** Shift+Enter 가 줄바꿈. 웹도 터미널도 그렇다.

### 2.3 승인

컴패니언이 물으면 그 행 자리에 답 단추가 선다. **모달이 아니다.** 규약이 사람이 시작하지 않은 일에 모달을 금하고, 그것 말고도 모달은 맥락(무엇을 왜 하려는지)을 못 싣는다.

승인 어휘는 `core/permission.ts` 한 자리다. 와이어는 `allow | deny | always` 이고 화면 글자는 그것을 옮긴 것이다. 두 어휘를 두면 갈라진다.

### 2.4 고친 파일을 편집기가 보게 하기

데몬은 편집기 밖 프로세스다. 젯브레인에서 실측한 것이 여기도 그대로 온다: 사람은 「완료」 행
옆에서 **낡은 사본을 본다.** VS Code 는 파일 감시자가 있어 젯브레인보다 낫지만, 그것도 보장이
아니다(감시자는 워크스페이스 밖 파일을 안 보고, 대량 변경에서 이벤트를 합친다).

그래서 전사가 아는 것을 쓴다: 경로를 아는 변이(`edit`·`write`·`multiedit` 의 성공한 결과)는 그
문서를, 경로를 모르는 변이(`bash` 계열)는 턴이 끝날 때 한 번을 새로 읽는다. **더티 버퍼는 안 건드린다.** 사람이 고치던 것을 덮는 것보다 낡은 것을 보는 편이 낫다.

## 3. 사이드바 — 계획과 계기판

액티비티 바 아이템 하나 + 프라이머리 사이드바의 웹뷰 하나. 젯브레인의 우측 독과 같은 내용이다.

- **지금** — 무엇을 하는 중인가, 몇 스텝째인가, 무엇을 기다리는가.
- **계획** — todo 와 그 상태.
- **컨텍스트** — 창이 얼마나 찼나, 무엇으로 찼나(`context` 문이 답한다).
- **잡** — 도는 백그라운드와 그 상태.
- **플릿** — 이 기계의 다른 컴패니언.

⚠ **액티비티 바 아이템으로 웹뷰 「패널」을 열지 않는다** — 규약이 명시적으로 금한다. 우리가 여는 것은 컨테이너 안의 웹뷰 **뷰**다. 이름이 비슷해 어기기 쉬운 자리라 적어 둔다.

⚠ 이 판은 **접혀 있을 때가 많다.** 그래서 여기 있는 것 중 사람이 놓치면 안 되는 것(승인 대기)은
여기에만 두지 않는다. 상태 표시줄에도 선다.

## 4. 상태 표시줄 — 한 칸

규약이 세다: 왼쪽은 워크스페이스, **하나만**, 색을 안 정한다.

```
$(magi) magi: 도는 중 · ask          ← 왼쪽, 항상 한 칸
```

- **왼쪽.** 컴패니언은 워크스페이스의 것이다.
- **한 칸.** 상태와 승인 모드를 같이 담는다. 젯브레인도 그렇다.
- **색을 안 쓴다.** 승인 대기에도 경고 배경을 안 쓴다. 규약이 그것을 "last resort" 로 두고, 승인 대기는 오류가 아니다. 대신 **글자로** 말한다(`답을 기다리는 중`).
- **도는 중이면 스피너**(`$(loading~spin)`). 규약이 배경 작업에 지정한 그 모양이다.
- **누르면 패널을 연다.**

**모름과 없음을 가른다**(§0-3): 데몬에 못 물어본 것과 데몬이 「쉬는 중」이라 답한 것은 다른
글자다. 젯브레인이 `Activity.of` 로 한 자리에 모은 그 판단을 `core/activity.ts` 로 옮긴다.

## 5. 설정과 명령

**설정 화면을 안 짠다**(대조표 §5). `contributes.configuration` 만 쓴다.

| | 어디 |
|---|---|
| 승인 모드·훑어보기 스위치·표식 | 설정(정적 스키마로 적힌다) |
| 모델·프로파일 고르기 | **명령** — 데몬이 답해야 아는 값이라 스키마에 못 넣는다 |
| 대화 다시 열기(resume)·세션 새로 | 명령 |
| 예약(cron)·잡 죽이기 | 계획판 |

명령 이름은 전부 `magi:` 접두다. **기본 단축키를 안 준다** — 규약이 남의 키를 덮지 말라고
하는데 무엇이 비었는지 확인할 길이 없다(젯브레인에서 같은 이유로 보류한 자리다).

## 6. 편집기 안 — 무엇을 그리나

| 무엇 | 어떻게 | 규칙 |
|---|---|---|
| 인라인 완성 | `InlineCompletionItemProvider` | 사람이 타자 중일 때만. 취소되면 요청도 취소한다 |
| 훑어본 말 | `InlayHintsProvider` — 줄 끝 | 할 말이 있는 줄에만 |
| 훑어보기 띠 | 첫 줄 위 데코레이션 | **할 말이 있을 때만 존재한다.** 토스트를 안 쓴다 — 지나가는 알림은 그 파일에 붙은 말이 아니다 |
| 컴패니언이 고친 줄 | 거터 + 데코레이션 | 그 턴이 끝나면 지운다 |
| 「물어보기」 | `CodeActionProvider` | 선택이 있으면 그것, 없으면 그 줄 |
| 오류 물어보기 | 진단이 있는 줄의 코드 액션 | 터미널이 xterm 이라 그 줄을 못 잡는다 — 자리를 옮긴 것이지 흉내가 아니다([설계 §4-나](./DESIGN.ko.md)) |

**색을 안 정한다.** 데코레이션은 테마 토큰(`editorGhostText.foreground`,
`editorInlayHint.*`)만 쓴다.

## 7. 안 정한 것

- **웹뷰 안의 마크다운 렌더러**(§2.2). 갈래 셋을 적었고 고르지 않았다. 실물 없이 고르면 틀린
  쪽을 고른다.
- **전사가 길 때.** 젯브레인은 최근 넷만 리치로 그린다(`RichAnswer.KEEP`). VS Code 웹뷰에서
  같은 문제가 어떤 모양일지 안 재봤다.
- **테마 토큰 이름들.** 대조표 §3 이 말하듯 가이드라인이 변수 이름을 안 준다. 색 토큰 문서를
  아직 안 읽었다.
- **아이콘.** `$(magi)` 라고 적었지만 그런 내장 아이콘은 없다. 무엇을 쓸지 — 내장에서 고를지
  실을지 — 안 정했다.
- **접근성.** 규약이 "color contrast, ARIA labels, keyboard navigation" 을 요구하는데 그 문서를
  안 읽었다. 전사는 읽는 물건이라 이 자리가 나중에 비싸질 수 있다.

## 8. 남은 물음

- 계획판이 **접혀 있을 때** 승인 대기를 어떻게 알리나. 상태 표시줄 글자만으로 충분한가, 아니면
  알림 하나가 필요한가 — 규약은 알림을 아끼라 하고, 승인은 사람이 답해야 도는 일이다.
- 창이 여럿일 때 **패널이 창마다 뜬다.** 같은 워크스페이스를 두 창에 열면 대화가 둘이다.
  데몬은 하나이므로 전사는 같지만, 입력이 둘인 것이 맞나.
- **원격**(SSH·Codespaces)에서 이 배치가 그대로인가. 설계 §10 이 안 잰 것으로 남겨 둔 자리다.

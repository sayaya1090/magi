# VS Code 확장 — 화면 설계

[↑ 클라이언트 개요](../README.md) · [설계](./DESIGN.ko.md) · [플랫폼 규약 대조표](./PLATFORM.ko.md) · [형제: 젯브레인 화면 설계](../../jetbrains/docs/UI.ko.md)

> **상태: 화면 설계 및 구현 사양**
>
> [설계](./DESIGN.ko.md)가 **무엇을 구현하는가**를 다루고, [플랫폼 규약 대조표](./PLATFORM.ko.md)가 **VS Code 플랫폼 가이드라인의 제약 조건**을 정리하였다면, 본 문서는 **각 컴포넌트가 어디에 어떻게 렌더링되는가**를 구체적으로 정의합니다.
>
> §0의 불변식은 JetBrains UI 사양에서 직접 계승하였습니다. 이는 특정 클라이언트의 구현 취향이 아니라 실제 결함을 겪으며 확립된 엔지니어링 원칙이므로, VS Code 클라이언트에도 동일하게 적용합니다.

## 0. UI 설계 불변식

JetBrains UI 문서 §0의 원칙을 전면 계승하며 모든 클라이언트 공통으로 준수합니다.

0-1. **단일 전사 조립 규칙.** 대화 행을 생성하는 규칙은 단 한 벌만 유지합니다. 중복 구현 시 검증되지 않은 경로에서 불일치가 발생합니다. 실제로 상태 표시줄은 데몬이 명시하지 않은 상태를 임의로 「쉬는 중」으로 표기하고, 우측 패널은 동일한 상태를 「실행 작업 없음」으로 각각 다르게 렌더링하는 결함이 발생한 이력이 있습니다.

0-2. **얕은 화면 계층.** 화면에 표시할 텍스트와 상태는 데몬이 결정합니다. 프론트엔드가 페이로드를 임의 파싱하여 문장을 가공하기 시작하면 클라이언트 수만큼 텍스트 파편화가 발생합니다.

0-3. **미수신(Unknown)과 부재(None)의 엄격한 분리.** 「응답 미수신」, 「값 없음」, 「해당 빌드에서 엔드포인트 미지원」은 서로 다른 상태입니다. 이를 단일 빈 값으로 축약할 경우 UI가 확인되지 않은 사실을 단정하는 오류를 범하게 됩니다.

0-4. **일회성 통지와 지속 상태의 채널 분리.** 「전송 실패: 사유」는 단발성 이벤트이며 「연결됨」은 지속적인 런타임 상태입니다. 이 둘을 동일한 공간에 기록하면 후속 상태가 직전 오류 보고를 덮어씁니다. JetBrains에서 이를 `Level` 타입으로 분리했듯이, 본 확장에서도 타입 시스템으로 영역을 분리합니다.

0-5. **네이티브 컴포넌트 우선 원칙.** 편집기가 기본 제공하는 강력한 기능은 직접 재구현하지 않습니다. 그 역도 동일하게 성립합니다: **VS Code가 더 우수한 네이티브 뷰를 제공하는 영역은 VS Code에 위임합니다.** 웹뷰 내부에 자체 diff 뷰어를 임베딩하지 않고 `vscode.diff`를 호출하며, `파일:줄` 링크는 텍스트가 아닌 에디터 이동 명령으로 처리합니다.

0-6. **워크스페이스 신뢰 경계 준수.** 대화 전사 스트림은 로컬 소켓 전용입니다. SSH 등 원격 제어 포트에는 어떤 클라이언트도 세션 전사를 노출하지 않습니다.

0-7. **웹뷰 최소화 원칙 (플랫폼 고유 규약).** VS Code 가이드라인은 "webviews should only be used if you absolutely need them"이라고 엄격히 제한합니다([대조표 §3](./PLATFORM.ko.md)). 따라서 대화 패널과 계획 패널 **2곳에만 웹뷰를 제한적으로 사용**하고, 나머지는 모두 VS Code 네이티브 API로 렌더링합니다.

## 1. 컴포넌트 재배치 — TUI 4영역의 VS Code 매핑

TUI 환경에서는 터미널 화면 제약으로 인해 단일 격자에 4개 요소를 중첩하여 배치하였으나, VS Code에는 각 요소에 적합한 네이티브 슬롯이 이미 구비되어 있습니다. 기존 요소를 임의로 재창작하는 것이 아니라 적재적소로 이전합니다.

> **패널은 전사와 입력 전용. TUI의 상단/하단 정보는 상태 표시줄로. TUI의 우측 상태 카드는 보조 사이드바로 분산합니다.**

| TUI 구성 요소 | 역할 | VS Code 배치 위치 |
|---|---|---|
| 상단 — `model <이름>`, 승인 칩 | 실행 환경 정보 | **상태 표시줄 좌측** — 개별 열린 파일이 아닌 워크스페이스 전역 속성([대조표 §1](./PLATFORM.ko.md)) |
| 상단 — `◐ 스텝 d/t`, `⚖ council` | 현재 실행 작업 정보 | **상태 표시줄** — 표시 폭 한계로 세부 내역은 계획 패널에 위임하고 상태 요약만 표시 |
| 뷰포트 | 대화 전사 스트림 | **패널 웹뷰** (§2) |
| 하단 — 턴 미터(경과·토큰·ctx%) | 이 턴이 얼마나 갔나 | **계획판** (§3). 상태 표시줄에는 경과만 |
| 하단 — `esc interrupt` | 세우는 손 | 패널 툴바의 「세우기」 |
| 하단 — 키 힌트 | 배우는 자리 | **안 옮긴다** — 단추가 보이는 화면이다 |
| 우측 포스트잇 다섯 장 | 붙박이 사실 | **보조 사이드바**(오른쪽) (§3) |
| 모달 — 승인·물음 | 답하는 손 | **패널 웹뷰 안** (§2.3). 모달이 아니다 — 사람이 시작한 일이 아니기 때문이다 |
| 모달 — resume·cron·subagents | 설정과 행동 | **명령 팔레트 + 판 제목줄의 … 메뉴**(§5). 백엔드·데몬 설정·새 대화·resume·접기·되감기·자식·잡 멈추기·예약 제공 |
| 커맨드 팔레트 | 즉시 실행 명령 | 편집기의 것을 쓴다. 자체 팔레트는 §0-5 위반 |
| 입력 + 컴포저 제안 | 손 | 패널 웹뷰 안 |

**JetBrains 구현과 차별화되는 2가지 구조적 차이점:**

- JetBrains는 정보 카드를 사용자의 선택에 따라 설정 화면에 통합 배치할 수 있었으나, VS Code는 커스텀 설정 뷰 렌더링이 불가하므로([대조표 §5](./PLATFORM.ko.md)) **보조 사이드바로 일원화**합니다.
- JetBrains의 승인은 하단 도구 창 내 인라인 단추로 제공됩니다. VS Code 역시 웹뷰 내부 인라인 단추로 처리하지만, **모달 팝업을 배제하는 근거가 플랫폼 가이드라인에 명시**되어 있습니다("actions that are not explicitly initiated by the user"에는 모달 대화상자 사용 금지).

## 2. 패널 — 대화 영역

### 2.1 패널 컨테이너 선정 사유

VS Code 가이드라인은 두 가지 조건을 명시합니다: 충분한 가로 폭의 이점을 활용하는 뷰, 그리고 보조적 성격("supporting functionality")의 뷰. 대화 전사는 폭이 넓을수록 가독성이 뛰어나며, 개발자의 주 작업 흐름은 코드 편집이고 대화는 이를 보조하는 역할이므로 패널 컨테이너가 최적의 배치 공간입니다.

또한 가이드라인의 주의 사항을 충실히 반영합니다: **"users often minimize the Panel"**. 사용자가 패널을 자주 최소화하므로 컴패니언의 현재 동작 상태는 패널 외부(상태 표시줄)에서도 상시 식별할 수 있어야 합니다(§4).

더불어 **좁은 레이아웃 폭에서도 안정적으로 리플로우되어야 합니다.** 사용자가 대화 뷰를 사이드바로 드래그하여 재배치할 수 있으므로, 좁은 너비에서도 입력창과 툴바가 레이아웃을 깨뜨리지 않도록 반응형 스타일을 적용합니다.

### 2.2 렌더링 구성

메시지 행 조립 규칙은 `core/transcript.ts` 단일 모듈을 따릅니다(§0-1). 전사 어휘 체계는 웹 콘솔의 `line` 규격과 일치합니다.

- **발화 주체(`who`).** 사용자 메시지는 일반 텍스트로, 컴패니언의 응답은 마크다운으로 렌더링합니다.
- **마크다운 렌더링 전략.** JetBrains는 IDE 내장 마크다운 엔진(`RichAnswer`)을 사용하지만, VS Code 웹뷰에는 내장 렌더러가 제공되지 않습니다. 다음 세 가지 방안을 검토하였습니다:
  (가) 번들에 경량 렌더러 포함 — CSP 및 번들 크기 관리 필요.
  (나) 핵심 마크다운 서브셋 직접 렌더링 — 코드 펜스, 표, 링크 등의 표현 한계 존재.
  (다) 코드 펜스 영역만 에디터 문법 하이라이터로 전달.
  확장의 단계적 진화에 맞추어 안정성이 실측된 방식을 점진 적용합니다(§7).
- **`thinking` 블록.** 기본적으로 접힌 상태의 흐린 텍스트 스타일로 표시합니다.
- **`tool` 호출.** 단일 행에 도구 이름 및 요약을 출력하고 상세 `args`/`out`은 접이식으로 제공합니다.
- **도구 실행 결과.** 도구 응답 수신 시 해당 행에 상태 아이콘(✓/✗)을 덧붙입니다. `note` 상태는 실패가 아니라 정상 완료 후 참고 사항이 동봉된 케이스로 취급합니다.
- **`pending` 상태.** 응답 대기 중인 사용자 프롬프트 좌측에 진행 인디케이터 바를 표시합니다.
- **카운슬 합의 행.** 3인 카운슬 멤버(melchior, balthasar, casper)의 고유 식별 색상을 적용합니다.
- **`diff` 뷰어 연동.** 웹뷰 내부에 자체 diff DOM을 렌더링하지 않고 `vscode.diff` 명령을 호출하여 네이티브 에디터로 연결합니다(§0-5).
- **`파일:줄` 링크.** 단순 텍스트 표시가 아닌 에디터 라인 점프 명령으로 동작합니다.
- **키보드 조작.** Enter 키는 메시지 전송, Shift+Enter는 줄바꿈을 수행합니다.

### 2.3 승인 인터랙션

컴패니언의 확인 질의 발생 시 해당 전사 행 위치에 인라인 응답 단추를 표시합니다. 사용자가 명시적으로 트리거하지 않은 작업에 모달 대화상자를 띄우는 것은 가이드라인 위반일 뿐 아니라, 작업 맥락(수정 대상 파일 및 실행 사유)을 충분히 제공할 수 없기 때문입니다.

승인 어휘는 `core/permission.ts`에 단일 정의된 매핑을 따릅니다. 와이어 프로토콜 값(`allow | deny | always`)과 UI 표시 레이블을 1:1로 엄격히 유지하여 다국어 및 플랫폼 간 불일치를 방지합니다.

### 2.4 에디터 버퍼와의 동기화

데몬은 편집기 외부에서 독립 실행되는 프로세스입니다. JetBrains 플러그인 실측 과정에서 관찰되었듯이, 도구 작업 완료 시점에 사용자가 에디터에서 **수정 전 과거 버퍼 내용을 계속 보고 있는 현상**이 발생할 수 있습니다. VS Code의 파일 시스템 감시자는 워크스페이스 외부 경로를 감지하지 않거나 대량 변경 이벤트를 일괄 병합하는 한계가 있습니다.

따라서 전사 스트림이 수신한 변경 내역을 바탕으로 동기화를 보강합니다. 파일 경로가 명시된 도구 변이(`edit`, `write`, `multiedit`의 성공 결과)는 해당 문서를 즉시 다시 읽고, 경로를 특정하기 어려운 변경(`bash` 명령 계열)은 턴 완료 시점에 에디터를 갱신합니다. **단, 사용자가 직접 작업 중인 더티 버퍼(Dirty buffer)는 강제 갱신하지 않습니다.** 개발자의 미저장 작업을 덮어쓰는 것보다 일시적으로 과거 뷰가 남는 편이 안전하기 때문입니다.

## 3. 사이드바 — 계획 및 계기판

**보조 사이드바(오른쪽)**의 뷰 컨테이너(`magi-side`) 내부에 단일 웹뷰로 구현합니다. JetBrains의 우측 독과 동일한 성격의 뷰이며 화면 우측에 대칭 배치됩니다.

- ⚠ **배치 위치 결정 배경.** 과거 `contributes.viewsContainers` 슬롯은 `activitybar`와 `panel`만 지원하여 우측 사이드바를 지정할 수 없었습니다. **VS Code 1.106에서 `secondarySidebar`가 공식 추가됨**에 따라 우측 배치가 가능해졌습니다. 단, 1.106 미만 버전에서는 이 선언으로 인해 타 확장의 뷰 배치까지 교란되는 결함(QwenLM/qwen-code#2432)이 보고되어 엔진 최소 버전을 `^1.106.0`으로 상향 지정하였습니다(`src/test/manifest.test.ts`에서 상시 검증).
- ⚠ 매니페스트 스키마 대소문자 주의: 정적 스키마 검증상 카멜케이스 표기 오류(`secondarySideBar`)는 마켓플레이스 배포 에러를 유발하므로 정확한 키명을 준수해야 합니다.

주요 표시 항목:
- **지금** — 무엇을 하는 중인가, 몇 스텝째인가, 무엇을 기다리는가.
- **계획** — 단계별 TODO 항목 및 완료 상태.
- **컨텍스트** — 창이 얼마나 찼나, 무엇으로 찼나(`context` 문이 답한다).
- **잡** — 도는 백그라운드와 그 상태.
- **플릿** — 이 기계의 다른 컴패니언.

- ⚠ **액티비티 바 항목을 통해 웹뷰 「패널」을 띄우지 않습니다.** 가이드라인에서 명시적으로 금지하는 패턴입니다. 확장이 선언하는 것은 컨테이너 내부의 웹뷰 **뷰(View)**입니다.
- ⚠ 사이드바 패널은 사용자가 닫아 둘 수 있으므로, 사용자 응답이 필수적인 승인 대기 상태는 사이드바에만 의존하지 않고 상태 표시줄(§4)에도 병행 표시합니다.

## 4. 상태 표시줄 — 단일 통합 위젯

상태 표시줄은 패널 최소화 상태에서도 항상 노출되는 핵심 영역이므로, 현재 적용 중인 모델·백엔드·승인 모드를 **확인하고 변경할 수 있는 진입점** 역할을 수행합니다. 설정값이 컨텍스트 메뉴 내부에만 숨겨져 현재 상태를 직관적으로 파악하기 어렵다는 실사용 피드백을 반영하여, 상태 표시줄 레이블에 핵심 정보를 직접 노출하도록 구성하였습니다.

공식 가이드라인의 요구사항(워크스페이스 전역 항목 좌측 배치, 단일 아이콘 사용, 커스텀 배경색 자제)을 준수합니다.

```
$(magi) magi: 도는 중 · ask          ← 상태 표시줄 좌측, 단일 위젯
```

- **좌측 배치.** 컴패니언은 워크스페이스 레벨에서 동작하므로 상태 표시줄 좌측에 배치합니다.
- **단일 항목 통합.** 상태와 승인 모드를 하나의 위젯 텍스트로 결합하여 공간을 절약합니다.
- **시맨틱 배경색 배제.** 승인 대기 상태라 하더라도 경고용 커스텀 배경색을 남용하지 않고 명확한 텍스트(`답을 기다리는 중`)로 상태를 알립니다.
- **동적 로딩 아이콘.** 작업 진행 중에는 표준 로딩 스피너(`$(loading~spin)`) 아이콘을 적용합니다.
- **클릭 동작.** 상태 표시줄 위젯 클릭 시 대화 패널을 즉시 포커스합니다.

**미수신과 정상 대기의 명확한 구분(§0-3):** 데몬과의 통신이 두절되어 상태를 파악할 수 없는 상태(`cannot say`)와 데몬이 정상적으로 작업을 마친 상태(`attached`)를 상이한 텍스트로 명확히 분리하여 표시합니다(`core/activity.ts`).

## 5. 설정 및 커맨드 체계

별도의 설정 전용 화면을 직접 구축하지 않고([대조표 §5](./PLATFORM.ko.md)) `contributes.configuration` 표준 선언을 사용합니다.

| 설정 구분 | 관리 방식 |
|---|---|
| 승인 모드 · 훑어보기 스위치 · 에디터 표식 설정 | `contributes.configuration` 정적 스키마 선언 |
| 모델 및 프로파일 선택 | **명령** — 데몬 런타임 질의가 필요하므로 동적 퀵픽 처리 |
| 세션 재개(resume) 및 새 대화 시작 | 명령 |
| 예약 작업(cron) 및 백그라운드 작업 제어 | 계획판 |

모든 명령의 타이틀은 `magi:` 접두사로 통일합니다. **기본 글로벌 단축키는 강제 바인딩하지 않습니다.** 사용자의 기존 단축키 구성을 침범하지 않도록 사용자가 키맵 설정을 통해 자율적으로 지정하게 합니다.

## 6. 에디터 버퍼 통합 렌더링

| 기능 | 구현 API | 렌더링 규칙 |
|---|---|---|
| 인라인 자동완성 | `InlineCompletionItemProvider` | 사용자가 타이핑 중일 때만 동작하며 취소 시 백엔드 요청도 즉시 중단 |
| 훑어보기 의견 | `InlayHintsProvider` (라인 끝) | 검토 의견이 존재하는 해당 라인에만 힌트 표시 |
| 훑어보기 상단 띠 | 첫 줄 상단 데코레이션 | **검토 의견이 존재할 때만 생성.** 일시적 토스트 팝업은 파일 맥락 전달에 부적합하므로 배제 |
| 에디터 수정 표식 | 데코레이션 (라인 배경 및 눈금) | 해당 턴이 종료되면 자동 소거. `magi.showEditMarks` 설정으로 비활성화 가능 |
| 코드 질문 액션 | `CodeActionProvider` | 텍스트 선택 시 선택 영역, 미선택 시 해당 라인 대상 |
| 오류 진단 질문 | 진단(`Diagnostic`) 라인의 코드 액션 | xterm 터미널의 줄 단위 추적 한계를 보완하기 위해 문제 패널 진단 위치에 액션 배치([설계 §4-나](./DESIGN.ko.md)) |

**테마 변수 바인딩:** 하드코딩된 색상을 배제하고 VS Code 표준 테마 토큰(`editorGhostText.foreground`, `editorInlayHint.*`)만을 참조하여 테마 호환성을 확보합니다.

## 7. 미결정 사안 및 점진적 검증 항목

- **웹뷰 내부 마크다운 렌더러 구현 방식(§2.2).** 번들 크기, 보안(CSP), 신택스 하이라이팅 품질을 종합적으로 비교 검증하여 확정합니다.
- **대량 전사 기록 렌더링 최적화.** JetBrains의 최근 항목 제한 렌더링(`RichAnswer.KEEP`) 기법을 참고하여 장시간 세션에서의 DOM 메모리 및 렌더링 부하를 실측합니다.
- **테마 토큰 변수 완전 매핑.** 공식 테마 컬러 레퍼런스를 전수 검토하여 다크/라이트 테마 전반에서 최적의 대비율을 확보합니다.
- **공식 아이콘 자산.** 공식 Codicon 아이콘과 커스텀 SVG 자산 간의 가독성을 비교 적용합니다.
- **접근성(a11y) 가이드라인 준수.** 웹뷰 내부의 명도 대비율, ARIA 역할 선언, 키보드 포커스 탐색 체계를 지속 보완합니다.

## 8. 아키텍처 질의 및 검토 사항

- **보조 사이드바 최소화 시 알림 전달 정책.** 가이드라인은 불필요한 알림 팝업 남발을 경계하므로, 상태 표시줄 상태 변화 외에 긴급 승인 대기 시 네이티브 토스트 알림을 어느 수준으로 제한 제공할지 운영을 통해 검토합니다.
- **다중 창 환경에서의 세션 전사 동기화.** 동일 워크스페이스를 복수 창으로 오픈할 경우 단일 데몬에 접속된 각 창의 웹뷰 패널 간 입력 및 상태 동기화 정합성을 관리합니다.
- **원격 개발 환경(SSH/Codespaces)에서의 네이티브 동작 검증.** 설계 §10에 명시된 원격 에이전트 구동 구조의 실측 환경을 지속 평가합니다.

# 브라우저 기반 콘솔 통합 E2E 테스트

본 디렉토리의 테스트 스위트는 **브라우저 런타임 환경에서 실제 UI가 구동되는 동안에만** 검증 가능한 항목들을 다룹니다:
- DOM 렌더링 결과의 정확성
- 수신 데이터 처리 및 상태 반영 흐름
- 사용자 입력 및 상호작용의 **데몬 전달 여부**
- **네트워크 요청 발생 횟수 및 트래픽 검증** (과거 상세 패널 진입 시 `/jobs`·`/cron` 요청이 22회 반복 호출되던 회귀 결함 방지)

## 테스트 대상 및 환경 구성

본 테스트는 **실제 실행 중인 데몬 2개와 실제 `magi-web` BFF 인스턴스**를 대상으로 수행됩니다(`serve.mjs`에서 자동 구성). 정적 데모 환경에서는 명단 스트림이 실시간으로 흐르지 않고 mock 핸들러가 네트워크 요청을 가로채므로, 실제 네트워크 통신 규약과 비정상 요청 폭증을 검증할 수 없습니다. 또한 데몬 인스턴스를 2개 띄우는 이유는 단일 인스턴스 환경에서는 "컴패니언 단위 요청"과 "콘솔 전역 요청"의 호출 빈도 구분이 불가능하기 때문입니다.

테스트용 데몬은 모델 추론 턴을 직접 실행하지 않으며, 상태 조회(명단, 작업, 크론, 모델 목록, 승인 모드)만 제공하므로 외부 API 키나 LLM 설정 없이 독립 실행됩니다. 각 테스트 실행마다 격리된 임시 디렉토리가 생성되며, 해당 경로는 `.harness.json`에 기록되어 테스트 러너 프로세스와 공유됩니다.

## 실행 방법

```sh
cd clients/web/ui && ./gradlew assembleConsole
cd clients/web/e2e && npm install && npx playwright install --with-deps chromium
npx playwright test
```

콘솔 정적 자산은 **사전에 조립되어 있어야 합니다**. 누락 시 `serve.mjs`가 오류 메시지와 함께 실행을 중단합니다. `magi` 및 `magi-web` 바이너리는 테스트 러너가 자동으로 빌드하며, 포트는 `MAGI_E2E_PORT` 환경변수(기본값 8199)로 설정할 수 있습니다.

## 모듈별 Kotest 사양과의 역할 구분

개별 화면 컴포넌트의 렌더링 로직은 **모듈별 Kotest 스펙이 담당합니다** (`clients/web/ui/*/src/test/kotlin` 내 `GwtTestSpec` 계열). 단위 기능 및 화면 동작 검증은 mock 기반의 Kotest 단위 테스트(`./gradlew :<module>:test`)에서 우선적으로 수행하는 것이 결정적이며 빠릅니다.

본 E2E 테스트는 단위 테스트에서 **구조적으로 검증할 수 없는 통합 영역**에 집중합니다:

| 검증 항목 | 담당 계층 |
| --- | --- |
| 특정 데이터에 대한 화면 렌더링 형태 | 모듈별 Kotest (`GwtTestSpec`) |
| 실제 네트워크 회선 통신 및 호출 빈도 | **E2E 테스트** (mock은 네트워크 호출을 차단함) |
| 사용자 상호작용의 실제 데몬 도달 여부 | **E2E 테스트** (실제 프로세스 IPC 검증) |
| 데몬이 송출한 실제 와이어 패킷 값 검증 | **E2E 테스트** (실제 데몬 응답 데이터) |
| 전체 모듈이 조립된 통합 번들 구동 여부 | **E2E 테스트** (단일 화면 하네스가 아닌 전체 셸 통합) |

## 테스트 스위트 구성

| 파일 | 주요 검증 내용 |
| --- | --- |
| `asking.spec.mjs` | 활성화된 화면의 네트워크 폴링 및 요청 빈도 상한선 검증 |
| `detail.spec.mjs` | 컴패니언 명단 데이터의 상세 정보 패널 매핑 및 렌더링 검증 |
| `controls.spec.mjs` | 컨트롤 조작값의 데몬 전달 및 선택 UI 컴포넌트 동작 검증 |
| `screens.spec.mjs` | 통합 콘솔 번들에서 사이드 레일의 각 메뉴별 화면 정상 로드 검증 |

## 테스트 범위 및 유의 사항

`asking.spec.mjs`의 빈도 검증은 비정상적 요청 폭증 회귀를 방지하기 위한 상한선 검증입니다. 유휴(idle) 상태의 컴패니언에서는 "명단 변경 시 재요청"과 "주기적 타이머 요청"의 발생 횟수가 동일하게 측정되므로, 실제 턴을 수행 중인 부하 환경을 재현해야만 세부 동기화 차이가 드러납니다. 반면 `detail` 및 `controls`의 필드/컨트롤 검증은 회귀 발생 시 즉각 실패하도록 엄격한 불변식을 유지합니다.

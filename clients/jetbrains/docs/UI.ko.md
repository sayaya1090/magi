# JetBrains 플러그인 — 화면 설계

[↑ clients/jetbrains](../README.md)

> **문서 목적.** magi의 사용자 인터페이스는 웹 콘솔, 터미널 TUI, 그리고 본 IDE 플러그인 3종으로 구성됩니다.
> 본 문서는 JetBrains 플러그인이 대화 세션을 IDE 플랫폼 상의 어떤 위치에 어떻게 렌더링할지 정의합니다.
>
> **타 IDE 클라이언트(VS Code 등) 구현 시 지침:** 세부 구현은 플랫폼별로 상이하지만,
> **§0 불변식, §2 행 생성 규칙, §5 설정 분류, §7 제외 항목**은 플랫폼과 무관하게 준수해야 하는 공통 규약입니다.
> 레이아웃 배치(§4)에 대해서만 대상 IDE의 UI 슬롯(Panel, Sidebar, StatusBar 등)에 맞추어 매핑합니다.

---

## 0. 불변식

0-1. **단일 대화 행 생성 규칙 단일화:** 행 생성 규칙을 중복 선언하면 클라이언트 간 상태 표출이 어긋나기 쉽습니다.
상태 표시줄과 계획 패널 간의 상태 불일치를 방지하기 위해 공통 셰이퍼 및 상태 열거형(`Activity`)을 신뢰 원천으로 삼습니다.

0-2. **경량 렌더링 원칙:** 표출할 핵심 상태와 의미는 데몬 코어가 결정하며, UI 계층은 수신된 이벤트를 투영하는 역할에 집중합니다.

0-3. **미수신·부재·미지원 상태의 명확한 구분:** 데이터 미도착, 실제 데이터 부재, 데몬 엔진의 엔드포인트 미지원은 명확히 구분하여 표출합니다.

0-4. **일회성 사건과 지속 상태의 분리:** 일시적 사건 알림(전송 실패 등)과 지속적 런타임 상태(연결 중 등)는 서로 다른 UI 영역에 분리하여 표출합니다.

0-5. **플랫폼 네이티브 슬롯 및 뷰어 우선 활용:** IDE가 이미 잘 제공하는 인터페이스(상태 표시줄, 에디터 탭, 나란히-보기 diff 뷰어)를 적극 활용하며, 협소한 패널 내부에 무리하게 커스텀 뷰를 중복 구축하지 않습니다.

0-6. **워크스페이스는 신뢰 경계입니다.** 전사는 로컬 소켓 전용입니다. ssh 문(`cmd/magi/door.go`의 `doorMethods`)에는 어떤 클라이언트도 전사를 올리지 않습니다. 해당 통로는 원격 인증 키가 통과하는 제한된
경로이므로, 여기에 전사를 노출할 경우 제3자에게 대화 내용이 유출될 위험이 있습니다.

## 1. 지금 있는 것 — 실측 (2026-08-29)

### 1.1 터미널 (TUI) — 이 플러그인이 준하려는 기준

`internal/adapter/tui/model_view.go`의 `View`가 한 프레임을 조립합니다. 세로 구성은 다음과 같습니다:

| 자리 | 무엇 |
|---|---|
| 머리 2줄 | `✦ magi` · `model <이름>` · 승인 칩 · `◈ plan: <모드>` · `◐ <스텝> d/t` · `⚖ council rN: 이름` · `⛐ N: <에이전트>` · 오른끝 스크롤 미터, 그 아래 실선 |
| 가운데 | 전사 뷰포트 + 서브에이전트 타일 |
| 겹쳐서 | 우측 위 **포스트잇 판** — 레이아웃 폭을 안 뺏고(`panelCols()`=0) 위에 떠 있다 |
| 사이 | 모달 — resume · subagents · cron · route · search · 커맨드 팔레트 · 승인 · 물음 |
| 입력 | 입력 상자 + 컴포저 제안 한 줄(`Tab`) |
| 발치 | 스피너 + `working…` + 턴 미터(경과 · ↑토큰 · ctx% · 쓴/전체) + `esc interrupt`, 놀 때는 키 힌트 |

포스트잇 패널(`internal/adapter/tui/panel.go`의 `statusPanel`)이 표출하는 정보는 정확히 다섯 가지입니다: **Context** 막대,
**Plan d/t**와 스텝 목록, **Background**(실행 중인 작업과 완료된 명단, 시작 순서 유지), **Waiting N**
(현재 턴의 완료를 대기 중인 항목), **Scheduled**(실행 대기 작업 및 불능 작업). 그리고 **표출할 데이터가
없으면 패널 전체가 숨겨집니다**(`hasPanel`).

전사 행은 이벤트 스트림에서 **증분으로** 조립됩니다: `applyEvent` → `m.blocks` → `renderBlock` → lipgloss로
렌더링된 고정폭 문자열입니다. 해당 문자열은 터미널 격자에 밀착되어 있어, 클릭 히트테스트가 행의 화면 Y 좌표를
기억하고 너비가 변경되면 전체를 다시 계산합니다.

### 1.2 웹 콘솔 — 행이 데이터로 오는 유일한 화면

> ⚠ `clients/web/server`는 없어질 예정입니다(신규 콘솔은 `clients/web/ui`). 따라서 아래 실측값의 의의는 코드 위치가 아닌
> **어휘 규격**에 있습니다. 패키지가 재작성되더라도 `line`의 필드 목록과 주석이 정립한 실측 규칙들은
> 본 문서가 계승하여(§2.1) 불변의 계약으로 유지됩니다.

`clients/web/server/main.go`의 `events`가 단일 SSE 연결을 통해 세 종류의 데이터를 스트리밍합니다: **전사 행 전체 배열**,
`turn` 프레임(`{open, forSec}` — 턴 활성화 여부 및 경과 초), 명단 프레임입니다. 행 데이터는 브라우저가 아닌
**서버가 생성합니다**. `renderMessages`가 세션 로그를 재구성한 `[]session.Message`를 `[]line`
형태로 펼쳐서 전달합니다. `line`은 순수 데이터 구조입니다:

`who` `text` `tool` `args` `ok` `note` `out` `pending` `round` `decision` `member` `lens`
`confidence` `why` `feedback` `keep` `cite` `at` `diff` `abandoned` `by`

해당 구조체의 주석에는 이미 다음과 같은 규칙이 계약으로 명시되어 있습니다: **"필드로 전송하고, 렌더링된 텍스트에서 역으로
파싱하지 않는다."** 화면 간 상태 불일치는 이러한 역파싱 시도에서 비롯되기 때문입니다. 주요 특징 두 가지는 다음과 같습니다:

- `Ok`/`Note` — 도구 호출과 그 결과는 **단일 행**으로 표현합니다. 둘을 분리하여 렌더링하면 성공 여부를 확인하기 위해 하위 행을 찾아 펼쳐보아야
  합니다. `Note`는 **실행 완료 후 추가 검토 내용이 잔존하는** 호출(사후 훅, 린트 등)을 의미하며, 와이어 상에서는 에러 형식으로
  전달되더라도 실패로 간주하지 않습니다.
- `Diff` — 편집 도구 호출은 **해당 호출의 인자 정보만으로** 서버가 diff를 직접 생성하여 전송합니다. 거절된 편집은 diff를 생성하지
  않습니다(실제 반영되지 않은 변경을 렌더링하는 오류 방지).

### 1.3 이 플러그인 — 지금

세 자리가 서 있습니다(`plugin/intellij/src/main/resources/META-INF/plugin.xml`):

- `toolWindow id="magi" anchor="bottom"` — 전사·문제 두 판, 입력, 보내기·세우기 단추,
  컴포저 제안(`Tab`).
- ~~`toolWindow id="magi.facts"`~~ — 초기 구현 후 철회되었습니다(§4.2): 사실 및 플릿 정보는 설정 화면 내부로 통합.
- `statusBarWidgetFactory id="magi.status"` — 3초 폴링 주기, `magi: 도는 중 · <승인모드>` 형태.

전사는 데몬의 `transcript` 문을 통해 **원시(raw) 이벤트 스트림**으로 전달됩니다(웹 콘솔처럼 구조화된 행 형태가 아닙니다). 프로토콜
계층(`Wire.kt`의 `LogEvent`)은 페이로드(`data`)를 의도적으로 파싱하지 않으며, 이를 소비해야 할 UI 뷰 계층이
초기에 완전히 구현되지 않아 `MagiToolWindow.entry`가 `#seq type (actor)` 메타데이터만 렌더링하는 한계가 있었습니다.
실제 샌드박스 환경 실측 결과, 사용자의 입력 프롬프트와 에이전트의 응답 텍스트가 와이어를 통해 정상 수신됨에도 본문 내용이 화면에 표출되지 않는 현상을 확인했습니다.

이는 데이터 파이프라인의 부재 때문이 아닙니다. 동일 패키지의 `Problems.of`는 `data.part.toolResult`를 정상 파싱하여
`content` 문자열에서 파일 및 라인 정보를 정확히 추출하고 있습니다. 즉 통신 경로는 이미 확보되어 있었으며 전사 렌더러의 구현만 미비했던 상태였습니다.

## 2. 판정 — 행을 짓는 규칙이 어디 사는가

세 화면의 입력부터 상이합니다:

| | 입력 | 짓는 자리 | 결과물 |
|---|---|---|---|
| TUI | `event.Event` (증분) | `applyEvent`→`blocks`→`renderBlock` | 칠해진 고정폭 문자열 |
| 웹 | `[]session.Message` (전량 재구성) | `clients/web/server/main.go` `renderMessages` — 집째 헐릴 예정 | `[]line` — **데이터** |
| IDE | `LogEvent` (증분) | 없음 | `#seq type (actor)` |

본 문서의 초기 설계는 "웹의 셰이퍼를 코어로 이전하고 데몬에 전사용 행 엔드포인트를 신설한다"는 구상이었습니다. 그러나 `clients/web/server`
패키지가 폐기 예정이라는 사실이 확정되면서, **행 생성 책임은 각 클라이언트가 독립적으로 구현한다**는 방향으로 정리되었습니다
(2026-08-29). 데몬이 담당하는 범위는 원시 이벤트 스트림(`transcript`)까지이며, 그 상위 계층의 가공은 클라이언트의 책임입니다.

이러한 설계 방향에서도 불변하는 두 가지 원칙은 다음과 같습니다:

1. **TUI의 렌더링 결과물은 직접 재사용할 수 없습니다.** 단순 텍스트가 아닌 터미널 격자에 결합된 문자열이므로(lipgloss
   너비 계산, ANSI 이스케이프 절단, 화면 Y 좌표 히트테스트가 결합됨), Swing이나 DOM, WPF 환경으로 직접 이식할 수 없습니다.
2. **웹 `line`의 데이터 어휘는 그대로 공통 계약으로 유지됩니다.** "필드로 전송하고, 렌더링된 문자열에서 역파싱하지
   않는다"는 원칙은 구현 환경과 무관하게 참이며, 해당 필드 명세(§1.2)가 세 UI 환경에서 대화를 동일하게 해석하는
   표준 기준이 됩니다.

§0-1(단일 규칙)과의 정합성은 다음과 같이 확보합니다: **코드는 플랫폼별로 분산되더라도 명세 계약은 단일하게 유지합니다.** 계약의 실체는 본
문서의 어휘 명세와 규칙 목록(§2.1)이며, 각 클라이언트는 자체 셰이퍼를 골든 테스트를 통해 검증합니다(§6).
규칙의 복수 구현을 구조적으로 인지하고 관리하는 접근 방식입니다.

### 2.1 행은 이 클라이언트가 짓는다

> 구현 수준은 [전사 셰이퍼](./TRANSCRIPT.ko.md) — 행 모델, 이벤트→행 매핑, 골든.

셰이퍼는 `plugin/core`의 usecase 계층에 위치합니다. `Transcript.kt`가 이미 해당 역할의 기반을 담당하고 있습니다.
어떤 항목이 행으로 승격되어야 하는지 명확히 판별하며(`echoesFact`가 델타 중복을 필터링함: 동일 내용이 `part.appended` 팩트로
재수신되며, 재생 시에는 팩트 이벤트만 반영됨), 페이로드를 파싱하는 작업 역시 usecase 계층의 책임입니다(`Problems.of`가
이미 `data.part.toolResult`를 파싱하여 활용 중임). `Wire.kt`의 "이 계층은 페이로드를 직접 파싱하지 않는다"는 규칙은 전송 및 프로토콜 경계의 원칙일 뿐, usecase 계층의 파싱을 제한하는 의미가 아닙니다.

입력은 `LogEvent` 증분 스트림이며, 출력은 웹 `line` 어휘를 수용한 행 모델입니다. 웹 콘솔 실측을 통해 정립된
공통 규칙들은 플랫폼 구현이 다르더라도 동일하게 적용됩니다:

- **도구 호출과 그 결과는 단일 행으로 결합합니다.** call id를 기준으로 매핑합니다(병렬 호출은 순서와 무관하게
  완료될 수 있음). 이를 분리하여 렌더링하면 성공 여부를 확인하기 위해 하위 행을 찾아 펼쳐보아야 합니다.
- **note는 실패가 아닙니다.** 실행 성공 후 검토 사항이 잔존하는 호출(사후 훅, 린트 등)은 와이어 상에서 에러 형식으로 전달되더라도
  실패 상태로 표시하지 않습니다.
- **diff는 실제 반영된 편집에 대해서만 생성합니다.** 거절된 편집의 인자는 실제 발생하지 않은 가상의 변경을 보여주게 되므로 제외합니다.
- **턴 경과 시간은 세션 수준의 상태 사실입니다.** 개별 행에 종속시키면 행의 성격에 따라 의미가 왜곡될 수 있습니다.
  초 단위로 측정하고 IDE 로컬 타이머로 이어서 갱신합니다(타임스탬프 직접 비교는 머신 간 시계 오차가 발생할 때 오류를 유발함).
- **전사는 단순 append-only 로그가 아닙니다.** 재부상한 인터젝션이 선행 프롬프트를 대체하거나, 컴팩션 수행 시
  로그 전체를 재작성합니다. 따라서 평소에는 증분으로 조립하되, 재작성 이벤트 수신 시 **전체 행을 처음부터 재구성하는 방식**을
  정상 경로로 수용합니다(웹 콘솔 실측치: 4,000개 이벤트 세션 전체 재구성 시 12ms 소요).

로그 파일을 파일시스템에서 직접 재파싱하지 않고 소켓 스트림 엔드포인트를 신뢰 원천으로 삼습니다. 스트림에서 제공되지 않는 항목은
§8에 기록하고 데몬 프로토콜 확장 요청으로 해결합니다.

### 2.2 다른 두 화면도 각자 짓는다

TUI는 터미널 격자 제약으로 인해 독립 렌더러를 유지해야 하며, 신규 웹 콘솔(`clients/web/ui`) 역시 자체 셰이퍼를 보유합니다. 일관성을 보장하는 수단은
코드 공유가 아닌 **문서화된 공통 계약과 각 클라이언트의 골든 테스트**입니다(§6-2, §6-3).

## 3. 결정 — 이 플러그인의 자리 배치 원칙

TUI는 단일 터미널 격자라는 제약으로 인해 모든 정보를 한 화면에 적층합니다. 반면 IDE에는 이러한 정보를 분산 배치할 수 있는
네이티브 UI 슬롯들이 이미 존재합니다. **새로운 슬롯을 임의 신설하는 것이 아니라 플랫폼에 맞게 재배치하는 작업**입니다. 핵심 원칙은 다음과 같습니다:

> **하단 독은 전사와 입력창에 집중합니다. TUI의 상단 헤더와 하단 풋터는 IDE 상태 표시줄로 매핑합니다. TUI의 우측 상태 패널은
> 우측 독 패널로 배치합니다.**

⚠ 과거 본 지침에 "툴윈도 제목표시줄"이 포함되어 있었으나, **2026-09-01부로 철회되었습니다**(세부 사유는 하단 §3.1 참고).

| TUI 자리 | 무엇 | JetBrains 자리 |
|---|---|---|
| 머리 — `model <이름>`, 승인 칩 | 무엇으로 도는가 | **상태 표시줄** (`magi: Connected · ask · …`) — 제목표시줄이었다가 물렸다(3.1) |
| 머리 — `◐ 스텝 d/t`, `⚖ council`, `⛐ N` | 지금 무엇을 하는가 | **상태 표시줄** — 폭이 없어 「무엇을」은 안 적고, 「무엇을」은 설정 화면의 「지금」 장이 그린다 |
| 뷰포트 | 전사 | **하단 툴윈도 가운데** (§4.1) |
| 발치 — 턴 미터(경과·토큰·ctx%) | 이 턴이 얼마나 갔나 | **상태 표시줄** — 열렸는지·몇 초째인지는 셰이퍼(§2.1)가 이벤트에서 세고, IDE 시계로 이어 센다 |
| 발치 — `esc interrupt` | 세우는 손 | 이미 있다 — 「세우기」 단추 |
| 발치 — 키 힌트 | 배우는 자리 | 안 옮긴다 — IDE 는 단추가 보이는 화면이라 힌트 줄이 하는 일이 없다 |
| 우측 포스트잇 다섯 장 | 붙박이 사실 | **설정 화면의 정보 장** (§4.2 — 처음엔 우측 독이었다가 사용자 결정으로 접혔다) |
| 모달 — 승인·물음 | 답하는 손 | 이미 있다 — 하단 독의 프롬프트+단추 |
| 모달 — resume·route·cron·subagents | 설정과 행동 | **설정 화면과 제목표시줄 액션** (§5) |
| 커맨드 팔레트 | 한 타로 아무 데나 | IDE 의 것을 쓴다 — 액션을 등록하면 Search Everywhere 가 공짜로 줍는다. 자체 팔레트는 §0-5 위반 |
| 입력 + 컴포저 제안 | 손 | 이미 있다 |

### 3.1 왜 하단 머리의 `state` 라벨이 없어지나

현재 하단 독 상단에는 `Level` 라벨이 배치되어 있으며 대부분의 경우 "컴패니언 연결됨" 상태를 유지합니다.
**상태 변화 빈도가 극히 낮은 레이블이 전사 영역 상단의 상당한 공간을 상시 점유하고 있었습니다**(실제 사용자 피드백: "변화도 없는 고정 라벨이 너무 많은 면적을 차지함"). 이에 따라 §0-5 원칙에 맞추어 상태 정보는 상태 표시줄로 일원화하고,
하단 독에서는 해당 헤더 패널을 제거했습니다. `Level.Waiting`과 같이 사용자 개입이 필요한 활성 상태는
이미 프롬프트 입력창과 승인 버튼이 노출되는 것으로 충분히 시각화되므로, 중복 텍스트 라벨을 둘 이유가 없습니다.

**툴윈도 제목표시줄 역시 상태를 표출하기에 부적합합니다(2026-09-01).** 헤더 라벨을 정리하면서 툴윈도 타이틀로 상태 문자열을 옮긴 적이 있었으나, 툴윈도 제목은 뷰의 정체성을 정의하는 자리이지 동적으로 변하는 상태 텍스트를 흘려보내는 슬롯이 아닙니다. 실제로 영문
IDE 환경의 탭에 한국어 상태 문구가 노출되거나, 탭 드래그 앤 드롭 시 **인접한 보조 탭의 타이틀까지**
동일한 상태 텍스트로 오염되는 문제가 발생했습니다. 더욱이 해당 상태는 이미 상태 표시줄에서 안내되고 있었으므로 불필요한 삼중 중복이었습니다.

따라서 `Level` 열거형은 더 이상 UI 표출용 텍스트 문자열을 직접 보유하지 않습니다. 상태 분류 로직만 유지하며, 사용자 조치가 요구되는 연결 두절 상태만
상태 표시줄의 링크 인디케이터로 표출합니다. 검증 규칙 또한 "상태 문자열을 생성하는 단일 창구가 있는가"에서 **"상태가 UI 텍스트로 하드코딩되는 위치가 전무한가"**를 검증하는 방향으로 전환했습니다(`SourceTextTest`).

이 과정에서 추가적인 구조 결함도 발견되었습니다: `Level`이 `core` 패키지에 위치하면서 자체 문자열을 보유하고 있었는데, `core` 계층은 리소스 번들에
접근할 수 없어 해당 문자열이 **모든 로케일의 IDE에서 한국어로 고정 출력되는** 국제화 결함이 있었습니다. 기존 i18n 검증 스크립트가 `intellij` 모듈만을 대상으로 하여 적발하지 못했던 결함이었습니다.

## 4. 화면별 결정

### 4.1 하단 독 — 전사

셰이퍼(§2.1)가 생성한 행을 렌더링합니다. 데이터 어휘는 웹 콘솔의 `line` 규격과 동일하며, 동일한 계약을 다른 플랫폼 뷰로 표현한 것입니다:

- **발화 주체별 분기.** `who` 필드에 따라 분기하여 렌더링합니다: 사용자가 입력한 프롬프트는 원문 그대로 표출하고, 에이전트의 응답은 **마크다운으로 자동 렌더링**합니다. 경량 서브셋 파서(코어 `Markup.markdown`, 이스케이프 처리 선행)를 기본으로 적용하며, 서브셋으로 처리 불가능한 복합 구조(코드 펜스, 표, 링크, 인용 등)가 포함된 경우 **IDE 내장 마크다운 엔진을 패널 내에 임베드**합니다
  (`RichAnswer` — Mermaid 다이어그램 포함, 렌더링 엔진 부재 시 경량 서브셋으로 안전 폴백, 브라우저 뷰는 최근 4개로 제한(`RichAnswer.KEEP`)).
  이는 '하단 플러그인 화면에서 마크다운을 자동 렌더링할 것'과 '일일이 클릭하여 뷰어를 여는 번거로움을 배제할 것'이라는 사용자 요구사항을 반영한 결과입니다. `thinking` 블록은
  접힌 상태로 흐리게 표출하고, `tool` 호출은 이름과 요약 1줄로 표시하며 `args`/`out`은 기본 접힘 처리합니다. 카운슬 합의 행은 `member`의
  지정 좌석 색상을 적용합니다(`Look.seat` — Melchior, Balthasar, Casper 외에는 고유 색상을 부여하지 않음).
- **도구 호출과 결과는 단일 행으로 결합.** `ok` 결과가 도착하면 해당 호출 행에 ✓/✗ 표식을 결합합니다. `note`는 실패가 아닌 '실행 완료 후 잔여 검토 항목 존재'로 취급합니다.
- **수정된 디스크 파일은 IDE가 자동으로 재감지하지 않습니다.** 데몬은 IDE 외부 프로세스로 동작하므로, IDE 에디터의 파일 재스캔은 창 포커스가 외부로 나갔다 복귀할 때 트리거됩니다. 그러나 플러그인 화면이 IDE 내부 독에 위치하므로 창 포커스 전환이 일어나지 않아 사용자가 완료 표식 옆에서 낡은 파일 사본을 보게 되는 결함이 있었습니다(실측 확인). 이에 따라 뷰 계층이
  셰이퍼의 디스크 수정 변경 대장(`drainDisk`, core 단위 테스트 포함)을 참조하여 VFS(Virtual File System) 동기화를 능동적으로 트리거합니다. 경로가 특정된
  변이(edit, write, multiedit의 성공 결과)는 해당 파일을 즉시 갱신하고, 경로를 특정하기 어려운 변이(bash 계열 — 백그라운드 detach 프로세스 포함)는 턴 완료 시점에
  워크스페이스 전체를 1회 재스캔합니다. 뷰는 갱신 요청을 수집하여 **0.5초 디바운스 코얼레싱을 통해 일괄** 반영합니다.
  `turn.finished` 이벤트가 세션 재생 시에도 수신되어 창 초기 오픈 시 과거 턴 수만큼 전체 스캔이 중복 실행되던 문제를 방지하도록 최적화되었습니다(배치 내에 전체 스캔이 포함되면 개별 경로 갱신은 생략). 디스크 IO는 풀드 백그라운드 스레드에서 수행하여 EDT(UI 이벤트 디스패치 스레드) 블로킹을 엄격히 방지합니다. IDE Hand를 통한 직접 편집은 Document 레이어를 거치므로 해당 동기화 이슈가 없으며, 백그라운드 exec 선언 도구는 별도 처리됩니다.
- **`pending` 행과 턴 경과 표출.** 응답 대기 중인 프롬프트 좌측에는 진행 바를 표시하고(`Look.pending()`), 턴이 활성화된 동안 하단에 경과 초를 실시간 갱신합니다.
- **`diff`는 IDE 네이티브 연동.** 서버에서 생성된 diff 문자열을 접이식으로 렌더링하되, 행에 파일 경로가 포함된 경우 클릭 시 IDE 에디터로 해당 파일을 즉시 엽니다.
- **전사는 덧붙이기 전용.** 시스템 안내 메시지(`— 전사에 기록됨.` 등)는 `—` 접두어를 붙여 전사 로그에
  추가합니다. 보고는 전사로, 지속 상태는 라벨로 분리하는 원칙(§0-4)을 준수합니다.
- **Enter 키 전송 기본화.** Enter 키는 메시지를 전송(`say()`)하고, Shift+Enter는 줄바꿈을 입력하도록 매핑합니다(웹 및 TUI 콘솔과 일관된 조작성 제공).

전사 및 문제 2개 탭 구조는 유지합니다. 왼쪽 패널은 데몬이 발행한 전체 이벤트 로그를, 오른쪽 패널은 사용자의 즉각적 조치가 요구되는 항목만을 선별하여 표출합니다.

### 4.2 사실과 플릿 — 설정 화면의 정보 장 (옛 우측 독)

초기 설계는 우측 독 패널(`magi.facts`)이었습니다. 그러나 **사용자 결정(2026-08-29)에 따라 해당 패널을 철회했습니다**. 상시 표시되는 내용이 대부분 단순 연결 상태였고, 자주 참조하지 않는 정적 데이터가 상시 독 슬롯을 점유하고 있었기 때문입니다. 상시 파악이 필요한
**연결 상태**는 상태 표시줄이 전담하고, 세부 내역은 **필요 시 설정 창에서 열어보는 방식**으로 정리했습니다(설정 화면은 진입 시 `reset()`이 수행되므로 최신 상태 갱신이 자연스럽게 보장됨).

현재 설정 화면(Settings › Tools › magi)은 3개 섹션으로 구성됩니다:

- **지금(Now)** — 현재 실행 작업, 승인 모드, 활성 세션 ID, 접근 불가능한 콘텐츠 루트 경고(데몬 미구동 시에도 표출).
- **설정(Settings)** — §5 명세 테이블 준용.
- **플릿(Fleet)** — `roster` 엔드포인트 기반 명단: 사용자 응답 대기 행 강조, 이전 활동 기록은 경과 시간과 함께 표시, 미지원
  데몬의 경우 상태 텍스트로 안내.

**우측 독 패널은 작업 계획 및 컨트롤 대시보드로 재정의되었습니다**(사용자 결정, 2026-08-29): **설정 화면보다 자주 참조하지만 대화 창보다는 조작 빈도가 낮은 제어 기능의 중심지**로 구성합니다. 상단에서 하단 순으로:

- **계획(Plan)** — 대화 스크롤과 함께 흘러가지 않도록 별도 고정 표출합니다. `todos.changed`는 영속 이벤트이므로
  정상 재생되며, 대화 창 셰이퍼가 보유한 계획 목록을 직접 참조합니다. 미설정 상태와 빈 계획은 텍스트로 구분합니다.
- **대기·작업(Queue & Jobs)** — `jobs` 엔드포인트 기반: 대기 중인 작업 목록(사용자 직접 지시 우선 — 위임 작업은 발신자 표기 포함), 실행 중인
  백그라운드 및 자식 작업 현황.
- **플릿(Fleet)** — `roster` 엔드포인트 기반: 각 컴패니언의 상태, 대기 큐 크기, 마지막 활동 경과 시간 표시. 동일 워크스페이스에 복수 데몬이 상주할 경우 **⚠동거(Co-located)** 배지를 부여하여 동시 수정 충돌 위험을 경고합니다. **활성 로컬 행은 클릭 시 인터랙션이 가능합니다**: 질문(읽기 전용 — looking
  격리는 수신 측 데몬이 강제함)과 작업 위임을 구분하여 **해당 컴패니언의 전용 소켓**으로
  `hand` 요청을 전송합니다. 거절 응답(턴 진행 중 등) 역시 정상적인 결과로 표출합니다.
- **위임 작업 상태(Handed Tasks)** — 외부 컴패니언에 위임한 작업의 접수증 상태를 추적합니다: 주기적 폴링 시 **미종결 접수증마다 독립 소켓 연결**을 수립하여
  `hand-state`를 질의하고 실행 중/응답 요약/종료 상태(사유 포함)를 렌더링합니다. 접수증 만료나 데몬 재시작 등으로 인한 거절은 연결 실패와 구분하여 **종결 처리**하고 추가 폴링을 중단합니다. 원격 통신은 백그라운드 폴링 스레드에서 수행됩니다. 응답이 없는 블로킹 상태는 `DaemonClient`의 타임아웃 워치독
  (기본 2분 — 모델 호출이 경유하므로 지나치게 짧게 설정하지 않음)에 의해 감지되어 `DaemonGone` 예외로 안전하게
  처리됩니다.
  ⚠ 전사 스트림의 경우 정상적인 침묵 구간이 존재하므로 별도의 타임아웃을 강제하지 않습니다(데몬 프로세스가 종료되면 소켓 EOF로 자동 감지되어 복구 루프로 진입함).
- **예약 작업(Cron)** — 데몬 크론 조회 엔드포인트 연동 시 활성화.
- **계기 및 제어(Gauges & Controls)** — 컨텍스트 사용량 게이지(미수신 시 0%로 오인 표출하지 않고 미측정 상태로 표시), 대화 목록 드롭다운(`sessions`) 및 신규 세션 생성(`session-new` — 생성과 전환이 단일 동작으로 수행되며 활성 턴 진행 중에는 거부), 모델 선택 드롭다운(`set-model`), 컨텍스트 압축(Compact) 버튼. 대화 세션이 변경되면
  대화 창이 `session.moved` 이벤트를 감지하여 신규 전사 스트림으로 자동 재연결합니다.

TUI 상태 패널의 나머지 항목(지시 목록 등)은 데몬 엔드포인트가 신설되면 연동합니다. '데이터 부재 시 숨김'과 '조회 실패'를 구분하는 원칙(§0-3)을 철저히 준수합니다.

### 4.2b 세션 탭 (착지)

사용자 결정: **대화도 Run 창처럼 세션마다 탭으로 구성.** 구조적으로 이미 지원 가능합니다: `transcript` 엔드포인트가 세션
ID를 인자로 수신하므로, 탭마다 독립된 스트림과 셰이퍼 인스턴스를 유지하면 됩니다(`Transcript`는 이미 단일 창당 단일 스트림
원칙을 따르며, 여기서 '창'의 개념이 '탭'으로 매핑됩니다).

- **단순 조회와 활성 전환의 분리.** 탭 간 전환은 단순 조회 동작이며 `resume`을 호출하지 않습니다. 세션 전환(시스템 전체에 공표되는 현재 세션 변경)은 우측 독의 드롭다운이나 신규 세션 생성을 통해 명시적으로 수행합니다.
- **입력은 현재 활성화된 탭의 세션으로 전달.** 통신 계약 확정 사항(docs/CLIENTS §2): submit/steer는
  지정된 세션에 턴을 시작하며, 턴의 직렬화는 **세션 단위로만** 보장됩니다(단일 워크스페이스 내에서 서로 다른 세션의 동시 턴 실행은 데몬 엔진이 임의로 제어하지 않음). 이에 따라 탭마다 독립된 입력창을 제공하되,
  **동일 워크스페이스의 다른 세션에서 이미 활성 턴이 진행 중인 경우 전송 전 확인 다이얼로그를 띄웁니다**. 파일 수정 충돌 위험을 사용자에게 사전에 알리고 통제권을 제공하기 위함입니다.
- 탭 오픈 진입점은 기어 메뉴 내 '대화 탭 열기…' 액션입니다. 목록은 `sessions` 엔드포인트에서 조회하며, 선택 시 해당 세션에 **고정된 탭(Pinned Tab)**이
  생성됩니다(공표 세션 변경이나 `session.moved` 이벤트에 영향받지 않고 해당 세션만을 지속 관찰함). 탭을 닫으면 연결된 스트림도 함께 정상 종료됩니다. 전체 세션을 무조건 탭으로 나열하지 않으며, 상시 관찰이 필요한 세션만 선별하여 엽니다.
- 발송 게이트는 **양방향으로 감지**: 현재 패널이 가리키는 세션 외에 다른 세션에서 턴이 실행 중이면 예/아니오 확인을 거칩니다. 동시 턴 실행 여부의 최종 판단을 사용자에게 위임합니다. '현재 워크스페이스의 데몬'은 세션 이름이 아닌 **소켓 경로를 기준으로** 식별합니다(roster는 머신 단위 엔드포인트이므로 인접 프로젝트 데몬이 함께 열거될 수 있음).
- 데몬 재시작 등으로 소멸된 세션의 고정 탭은 **빈 화면과 커서 거절 사유 툴팁**으로 표출합니다. 저장소 엔진이 미존재 세션 ID에 대해 에러가 아닌 빈 로그로 응답하기 때문입니다(코어 실측 동작).
- **세션 간 에이전트 통신**(A 세션 에이전트가 B 세션에 프롬프트 전달)은 코어 레벨의 도구 확장이 필요한 영역이므로 향후 과제로 분류합니다.

### 4.2c 첨부 (①②③ 착지)

와이어 프로토콜: `submit`/`steer`의 `refs[]`(`internal/core/command/command.go`의 `FileRef` — path +
라인 범위 "12-40" 또는 "12", 미지정 시 파일 전체). **코어 엔진이 디스크에서 해당 발췌본을 읽어 프롬프트와 함께 영속 로그에
기록하므로** 전사, 재생, 웹 콘솔이 완전히 동일한 컨텍스트를 공유합니다. 플러그인은 파일 경로와 라인 범위 메타데이터만 전송하며, **첨부 등록 시점에
문서를 디스크에 강제 저장합니다**(에디터 버퍼 기준으로 계산된 줄번호가 미저장 디스크 파일과 어긋나면 잘못된 본문이 영속되는 결함 방지 — 실측 확인).
첨부 규격: 워크스페이스 경계 준수, ref당 16KB 및 전체 64KB 상한 적용(초과분은 'not shown' 표기), 사유 누락 없는 결함 안내(디렉토리나 잘못된 범위도 해당 위치에 사유 칩 표출), 줄범위 파싱 실패 시 전체 파일로 안전 폴백.

1. **에디터 선택영역 첨부** — 우클릭 컨텍스트 메뉴 'magi: 대화에 첨부': 입력창 **상단** 칩 영역에 `경로:시작줄-끝줄` 칩이
   생성됩니다. 멀티캐럿 환경에서는 캐럿별로 개별 칩을 생성합니다. 본문 직접 복사가 아닌 파일 참조 방식입니다.
2. **프로젝트 뷰 첨부** — 프로젝트 툴윈도 동일 액션 매핑: 선택된 파일들의 경로 칩이 생성됩니다.
3. **입력창 `@` 멘션 완성** — 커서 직전 단어가 `@파일명` 패턴인 경우(단어 시작의 `@`, 2자 이상, 공백으로 구분)
   디바운스 후 일반 제안 대신 데몬의 읽기 전용 `glob`(`**/*이름*`, 특수문자 이스케이프 처리)을 질의합니다.
   결과 목록은 알파벳순 최대 20개를 표출하며, 선택 시 멘션 텍스트가 칩으로 치환됩니다. ESC로 닫으면 동일 토큰으로는 재팝업되지 않습니다. 워크스페이스 격리 및 denyFloor 규칙은 동일하게 적용됩니다.
   ⚠ 멘션 팝업이 포커스를 획득한 상태에서 타이핑 지속 시 검색어로 흡수되는 현상은 실측 테스트를 거쳐 추후 개선합니다.

첨부 칩은 ✕ 버튼으로 개별 삭제 가능하며, `say()` 호출 시 refs 목록에 포함된 후 **실제 전송 완료된 항목만** 비웁니다(전송 대기 중 추가 등록된 칩은 다음 턴을 위해 유지됨).

### 4.2d 요소요소 진입점 (사용자 지시 — "일 있는 자리에 단추를")

타 IDE 및 AI 어시스턴트의 공통 UX 패턴(SURVEY §1)을 본 플러그인에 수용합니다: **작업이 실제로 일어나는 네이티브 슬롯에 진입점을 배치하되, 실행과
결과는 컴패니언의 대화 인터페이스로 수렴시킵니다.**

| 자리 | 진입점 | 문 | 규칙 |
|---|---|---|---|
| Git 커밋 칸 툴바 | 「magi: 커밋 메시지 초안」 | `git-msg`(웹 커밋 카드와 **동일한 엔드포인트** — 두 UI가 동일한 초안 생성) | 실패 메시지를 커밋 메시지 입력칸에 직접 쓰지 않음(해당 칸은 실제 커밋될 텍스트 전용). 실패는 풍선 알림으로 표출 |
| Run·터미널 콘솔 우클릭 | 「magi: 이 출력 물어보기」 | `say`(선택된 콘솔 출력을 코드 펜스로 감싸서 프롬프트에 주입) | 콘솔 출력은 파일이 아닌 일회성 텍스트이므로 refs 첨부가 아닌 프롬프트 본문으로 취급 |
| Alt+Enter 컨텍스트 액션 | 「magi에게 이 코드 물어보기」 | 현재 선택 영역/캐럿 라인을 refs로 자동 첨부 + 컴포저 프롬프트 프리필 | 구체적 지시는 사용자가 작성 — 실제 코드 편집 및 diff 검토는 컴패니언과 승인 게이트의 몫 |
| 승인 프롬프트 | 「변경 보기」(diff 가 실린 승인에만 노출) | 전부 **IDE 에디터 탭**으로 라우팅: 치환 편집이면 인자의 old/new **원문 양면을 나란히-보기(Side-by-side diff)**로 표시(재계산 금지 원칙 준수), 그 외(코어가 diff를 직접 제공하는 write 등)는 diff 원문을 텍스트 탭으로 표출(헤더 없는 헝크로 인해 패치 에디터 파싱 오류가 발생하는 문제를 방지하기 위해 일반 텍스트 뷰어 우선). 좁은 독 패널 내부에 diff를 억지로 구겨 넣던 인라인 패널은 사용자 실측 피드백에 따라 완전히 제거 | **IDE가 더 잘 표출하는 네이티브 뷰어에 책임을 위임** |

컴포저 프리필은 **입력창이 비어 있을 때만** 수행합니다(작성 중이던 프롬프트 덮어쓰기 방지).

### 4.3 상태 표시줄

현재 표출 형식(`magi: 도는 중 · auto · 못 만지는 루트 N`)에 두 가지 실시간 지표를 추가합니다: 턴 활성화 시 경과 시간
(`턴 3m12s`), 카운슬 심의 진행 시 `⚖ rN`. 협소한 공간이라는 원칙에 따라 구체적 작업 내용은 상태 표시줄에
적지 않습니다.

## 5. 설정 — 슬래시 커맨드를 IDE 설정 화면으로

현재 플러그인에는 설정 화면이 등록되어 있지 않습니다(`plugin.xml`에 `projectConfigurable` 미등록). 모델,
승인 모드, 크론, 자동완성 설정을 변경하려면 외부 터미널을 열거나 `config.toml`을 직접 편집해야 하는 한계가 있었습니다.

터미널의 단일 원천은 `internal/adapter/tui/model.go`의 `slashCommands` 정의입니다. **설정**(지속되는
상태 값)과 **행동**(1회성 즉시 실행)과 **조회**를 명확히 구분합니다. 설정 화면은 지속되는 상태를 관리하는 공간이며, 1회성
실행 커맨드를 설정 창에 배치하면 '적용' 버튼을 눌러야 실행되는 것으로 사용자가 오인하게 됩니다.

| 갈래 | 슬래시 | 이 플러그인의 자리 | 데몬 문 |
|---|---|---|---|
| 설정 | `/route` (`/model`) | Settings › Tools › magi › 모델·라우팅 | `models` · `set-model` · `use-backend` |
| 설정 | `/permission` | 같은 화면 › 승인 모드 | `set-permission` |
| 설정 | `/cron` | 같은 화면 › 예약 | `jobs` · `reload-cron` |
| 설정 | (자동완성) | 같은 화면 › 거들기 — `[autocomplete]` 프로필과 이 IDE 의 켬끔 | `complete` · `suggest` |
| 설정 | `/providers` | 같은 화면, **읽기 전용** | 쓰기 문이 **없다** |
| 설정 | `/subagents` | 같은 화면, **읽기 전용** | 쓰기 문이 **없다** |
| 설정 | `/context <n>` | 같은 화면, **읽기 전용** | 쓰기 문이 **없다** |
| 행동 | `/compact` `/clear` `/rewind` `/resume` | 하단 툴윈도 **제목표시줄 액션**(기어 메뉴) | `compact` · `rewind` · `resume` |
| 행동 | `/fork` `/replay` `/init` `/ultra` | 안 만든다 — 감독 화면이 아니라 운전 화면의 동사다. 필요해지면 그때 |
| 읽기 | `/cost` `/loop` `/tools` `/sessions` | 설정 화면 정보 장 또는 제목표시줄 메뉴 | `status` · `tools` · `about` |
| 읽기 | `/diff` | 안 만든다 — IDE 의 Git 창이 그 자리다(§0-5) | |

**지원되지 않는 기능은 상태를 있는 그대로 표출합니다.** 쓰기 엔드포인트가 없는 항목을 편집 가능한 UI 컴포넌트로 제공하면 사용자가 변경을 시도하더라도 시스템에 반영되지 않습니다.
엔드포인트가 신설되기 전까지는 읽기 전용 뷰로 제공하고 편집 불가의 구체적 사유를 명시합니다(§0-3).

### 5.1 설정은 어디 저장되나

본 설정 화면이 제어하는 대상은 IDE 로컬 환경설정이 아닌 **워크스페이스 컴패니언의 런타임 설정**입니다.
IDE의 `PersistentStateComponent`에 동일 설정을 중복 저장하지 않습니다. 상태를 복제하면 IDE가 인지하는 값과 데몬이 인지하는 값이
어긋나 화면이 왜곡되기 때문입니다. **화면은 데몬에 질의하여 표시하고 데몬에 직접 씁니다.** 설정 창을 열 때 데몬에서 최신 값을 읽어오고, 적용 시 데몬에 전달하며, 재조회를 통해 변경 사항을 상호 확인합니다.

유일한 예외는 IDE 클라이언트 자체에 국한된 동작 설정뿐입니다(예: 인라인 코드 완성을 본 IDE 환경에서 비활성화할지 여부). 이러한 항목에 한해서만 IDE 로컬 설정으로 격리 관리합니다.

## 6. 무엇으로 붙드나

6-1. **전사는 본문 내용을 온전히 표출해야 합니다.** 행 배열을 주입했을 때 사용자의 입력 프롬프트와 에이전트의 응답 텍스트가 패널에 정상 렌더링되어야 합니다. 단순히 `#seq type` 메타데이터만 표출하고 테스트를 통과하던 기존 테스트의 공백을 해소하고 본문 렌더링 검증 테스트를 필수 배치합니다.

6-2. **셰이퍼의 정합성은 골든 테스트로 보증합니다.** 이벤트 JSONL 스트림을 입력받아 구조화된 행 모델을 반환하는 순수 함수로 구성하고(usecase 계층 — IDE SDK 의존성 없이 독립 실행), 본문 추출, 행 결합(짝맞춤), pending 상태 관리가 기대치와 일치하는지 골든 테스트를 통해 지속 검증합니다. 색상이나 스타일링은 검증 대상에서 분리하여 계약 정합성에 집중합니다.

6-3. **데이터 어휘 변경 시 문서 명세를 반드시 동기화합니다.** 행 모델의 필드 구성은 §2.1의 공통 어휘(웹 콘솔 `line` 필드 목록)와 1:1로 일치해야 하며, 신규 필드 추가 시 본 문서에 선행 정의합니다. 코드와 문서 간 심볼 일치 여부는 자동화된 검증 도구(citecheck)를 통해 검증합니다.

6-4. **UI 슬롯 계약 준수.** 상태 문자열이 UI 레이블로 하드코딩되는 위치가 없어야 합니다(`SourceTextTest`). 상태 표시줄이 지속적 런타임 상태를, 전사 패널이 일회성 사건 흐름을 담당합니다. 툴윈도 제목은 뷰 식별 용도로만 한정합니다(§3.1).

6-5. **데이터 부재와 조회 실패의 엄격한 분리.** 정보 패널(플릿 등)의 각 컴포넌트에서 두 상태를 분리하여 검증 테스트를 구성합니다.

6-6. **설정 동기화 검증.** 설정 화면의 각 입력 필드는 데몬에서 조회한 실제 값을 반영해야 하며, 적용 후 재조회한 결과가 화면 상태와 일치해야 합니다. 쓰기 엔드포인트가 없는 항목은 UI 레벨에서 편집 불가가 엄격히 보장되어야 합니다.

# 무엇을 어디서 재나

[↑ 클라이언트 개요](../README.md) · [사용자 매뉴얼](./MANUAL.ko.md) · [플랫폼 규약 대조표](./PLATFORM.ko.md) · [화면 설계](./UI.ko.md)

> **문서 목적.** JetBrains 플러그인 테스트 레인은 5단계 계층으로 나뉘며, 각 계층마다 **실행 조건과 검증 대상이 상이합니다.**
> 어떤 계층은 push마다 동작하고, 어떤 계층은 데몬이 실행 중일 때만 동작하며, 릴리스 태그 배포 시에만 가동되는 계층도 있습니다.
> 이러한 조건을 구분하지 않으면 실행되지 않고 건너뛴 상태를 통과한 것으로 오인하기 쉽습니다.

**마지막 실측: 2026-09-12 — 총 349개 통과, 실패 0, 건너뜀 6**(모델 적합성 5건 — 명시적 요청 시에만 실행됩니다).
`LiveDaemonTest`는 로컬 머신에 데몬이 실행 중일 때 정상 실행됩니다.
건너뜀 수치가 5건과 6건 사이에서 변동하는 것은 데몬 프로세스 상주 여부에 따른 정상 동작입니다. 본 문서는 커밋마다 실측 수치를 갱신합니다.
테스트 통과는 단순한 기억이 아니라 실측 날짜와 수치로 보존되어야 검증 근거가 확보됩니다.

## 층 다섯

| 층 | 어디 | 언제 도나 | 무엇을 아나 |
|---|---|---|---|
| 1. 단위 | `plugin/core/src/test` | push 마다 | 셰이퍼·전송·파서의 규칙 |
| 2. 소스 글자 | `SourceTextTest` (51) | push 마다 | 컴파일러가 안 잡는 규칙 |
| 3. 유도 가드 | `ManualTest`·`ArchitectureTest`·`PaletteTest` | push 마다 | 광고면과 문서·구조가 갈렸나 |
| 4. 헤드리스 IDE | `plugin/intellij/src/test` (10) | push 마다 | 진짜 IDE 안에서 우리 것이 서나 |
| 5. 라이브 | `live/`·`LiveDaemonTest` (6) | 청해야 | 진짜 데몬·진짜 모델과 맞나 |

릴리스 태그(`jetbrains-v*`)를 밀면 여기에 **여섯째**가 붙는다 — `verifyPlugin` 이 세 IDE
(IU-261·IU-262·PY-261)의 바이트코드에 대고 검증한다. 1.7GB 를 받고 6분이 걸려 push 레인에는
없다. **태그를 밀기 전에 로컬에서 한 번 돌릴 것** — 2026-08-31 에 그것으로 첫 릴리스가 죽을
뻔했다(내부 API 사용 여섯).

## 1. 단위 — 규칙이 사는 자리

`plugin/core`는 IntelliJ SDK에 의존하지 않는 순수 JVM 모듈입니다. 수 초 내에 고속 실행되므로 **비즈니스 규칙은 되도록
이 계층으로 집중합니다.**

- **셰이퍼**(`RowsTest` 16, `TranscriptTest` 17) — 데몬의 사건을 화면 행으로 바꾸는 규칙.
  사실과 전이의 갈림, 타자기(부분 조각), 재부상, 접힘.
- **전송**(`SocketPathTest` 11, `SocketReachTest` 5, `CompanionTest` 17) — 소켓 이름이 코어의
  Go 와 같은가, 붙어 보고 만난 것을 어느 갈래로 가르는가, 문마다 무엇을 싣는가.
- **파서**(`LookNotesTest` 4, `MarkdownTest` 5, `RowTextTest` 11) — 모델이 준 글자에서 줄번호를
  뽑고, 마크다운을 펴고, 행의 글자를 정한다.
- **규칙 층**(`DaemonLifecycleTest` 11) — 소켓 없이 「살았나·죽었나·나갔나」 판정만.

`RowTextTest`는 UI 컴포넌트 내부에 사설 함수로 흩어져 있던 문자열 계산 로직 6종을 core 계층으로 분리하여
IDE 인스턴스 기동 없이 순수 단위 테스트로 상시 검증할 수 있도록 개선한 테스트입니다.

## 2. 소스 글자 — 컴파일러가 안 잡는 것

`SourceTextTest`는 컴파일된 클래스가 아니라 **소스 코드 원문**을 정적 분석합니다. 타입 시스템과 일반 테스트를 통과하지만
런타임 화면 표출에서 미묘한 결함을 유발하는 규약을 사전에 탐지합니다.

지금 재는 것 중 몇 가지:

- 달러를 글자로 박아 두면 화면에 템플릿 원문이 찍힌다.
- 라벨에 붙는 남의 글자는 거르는 함수를 거쳐야 한다.
- **창을 거두는 자리는 클래스를 처음 로드하지 않는다** — IDE 가 나갈 때 우리 클래스로더는 이미
  닫혀 있을 수 있고, 터진 `dispose` 는 그 아래 정리를 통째로 거른다(라이브에서 실제로 났다).
- **설정 디렉토리를 정하는 자리는 하나다** — 두 곳이 각자 정하고 있었고, 셸에서
  `MAGI_CONFIG_DIR` 을 쓰는 기계에서 창과 열린 버퍼가 다른 소켓을 봤다.

## 3. 유도 가드 — 두 벌이 갈리는 것을 막는다

목록을 중복 관리하면 정합성이 훼손되기 쉬우므로, 다음 세 테스트는 **코드 및 설정 원천에서 직접 유도**합니다.

- `ManualTest` — `META-INF/*.xml` 전부에서 액션·그룹의 글자를 뽑아, 번들 양쪽에 있는지와
  매뉴얼에 적혔는지 본다. 디스크립터에 `text=`/`description=`/`displayName=` 을 직접 적으면
  거기서 운다. 번들 값이 MessageFormat 으로 서는지, 홑따옴표가 짝인지, **값이 비지 않았는지**도
  같이 잰다(여러 줄 문구에 진짜 줄바꿈을 적으면 값이 끊기는데 파일은 겉보기에 멀쩡하다).
- `ArchitectureTest` — 계층 방향과 `usecase/` 의 파일 목록. 목록을 못박은 이유는 그 시험이
  **빈 목록을 보고 조용히 초록**이 되는 것을 막기 위해서다.
- `PaletteTest` — 화면 색이 TUI 의 원본(`internal/adapter/tui/styles.go`)과 같은가.

## 4. 헤드리스 IDE — 창 없이 진짜 IDE

`plugin/intellij/src/test`는 실제 IDE 헤드리스 런타임 환경에서 플랫폼 통합 동작을 검증합니다.
액션 노출 조건, 인텐션 활성화 시점, 다국어 번들 바인딩, 레이아웃 컴포넌트 최소 폭 규약 등을 자동 검증합니다.

`TestFrameworkType.Platform` 이 창 없이 `Project`·`Editor`·액션 시스템을 프로세스 안에 세운다.
우리는 사람이 쓰는 것과 같은 입구로 들어간다.

지금 열셋을 잰다. 그중 여덟은 **사람이 IDE 를 띄워 눈으로 보던 점검표 항목**을 옮겨 온 것이다 —
우클릭이 하위 메뉴 하나인가, 그 안에서만 접두를 벗기는가, 설명문 라벨이 판을 가로로 안 벌리는가
(사람이 「가로로 쭉 늘어남」으로 잡았던 자리다. 재는 것은 선호 폭이 아니라 **최소 폭**이다 —
그것이 글자 길이만큼이면 판은 그 아래로 못 좁혀진다), 도구창 아이콘이 로드되는가, 스위치 기본값.

수동 검증 항목을 자동화하여 매 push마다 지속 검증합니다.

IntelliJ SDK의 `BasePlatformTestCase` 상속 요구사항에 따라 이 모듈은 JUnit 4로 동작하며, `core` 모듈은 JUnit 5를 유지합니다.

## 5. 라이브 — 진짜 데몬, 진짜 모델

실물 연동 검증은 2가지가 존재하며 **명시적 실행 요청 시**에만 가동됩니다. 타 프로세스 간섭을 방지하고 실제 모델 호출 비용을 관리하기 위함입니다.

### 5.1 데몬에 붙는다

```sh
MAGI_IDE_PROBE_SOCK=/tmp/mw1/daemon-ws1-b1lp9vc8.sock ./gradlew :core:test
```

호출 대상은 `about` 및 `models` 엔드포인트이며 읽기 전용으로 안전하게 동작합니다. 해시 정합성뿐만 아니라 실제 소켓 전송 프로토콜의 정합성을 최종 검증합니다.

### 5.2 모델을 갈아 끼웠을 때 — 적합성 배터리

```sh
MAGI_IDE_CONFORMANCE=1 ./gradlew :core:test --tests '*ModelConformance*' --rerun-tasks
```

**코어의 E2E 가 못 보는 자리를 잰다.** 코어(`internal/app/e2e_test.go`)는 에이전트 루프를 본다 —
툴을 부르고 파일이 생겼나. 그런데 이 플러그인이 쓰는 문 셋(`complete`·`suggest`·`look-over`)과
커밋 초안은 **그 루프를 안 탄다.** 한 번 왕복하고 글자 하나를 돌려줄 뿐이고, 그 글자를 우리가
파싱해서 화면에 꽂는다. 그래서 모델이 바뀌면 코어 시험은 전부 초록인데 IDE 만 이상해진다:

- 완성을 ``` ``` ``` 으로 감싸 보내면 그대로 커서 자리에 백틱이 꽂힌다.
- 완성이 접두를 되풀이하면 같은 줄이 두 번 써진다.
- 「다음은 완성입니다:」 같은 머리말도 코드로 들어간다.
- 훑어보기가 줄번호를 계약과 다른 모양으로 붙이면 지적이 **줄에서 떨어져** 전부 띠로 밀린다.
  화면에서는 「할 말이 없다」와 구분이 안 간다.

검증 목적은 **응답 텍스트의 구문 형태(Shape)**입니다. 모델별 발화 차이를 넘어 에디터 버퍼에 정상 삽입 가능한 형태인지, 파서가 정확히 해석하는지, 파일시스템 변경이 발생하지 않는지를 확인합니다.
마지막 것은 부른 전후로 `git status --porcelain` 을 견준다 — 완성 한 번이 파일을 바꾸면 사람은
자기가 안 한 변경을 보게 된다.

끝에 성적표가 찍힌다. **통과한 것까지 적는다** — 초록이 「안 재고 지나감」과 같아 보이면 안 된다.

판정 로직은 라이브 환경 외부의 순수 함수(`Shapes`)로 분리되어 있으며, `ShapesTest`(9)가 실측된 오류 패턴을 주입하여 판정 정확성을 단위 테스트합니다.

## 명단 — 시험 클래스 전부

**이 표에 누락된 테스트 파일이 존재할 경우 `ManualTest`가 실패합니다.** 새로운 기능 및 테스트 추가 시 본 명단에도 등록해야 합니다.

### 규칙 (`plugin/core/src/test/.../usecase`)

| 클래스 | 무엇을 재나 |
|---|---|
| `SourceTextTest`(실패의 짝) · `PhasesTest`(던진 뒤의 왕복) | ★ **안 뜬 것이 「뜨는 중」으로 남고 있었습니다.** 기동 실패는 예산과 상태 **둘에** 적혀야 하는데, 시한을 넘긴 갈래는 나란히 적고 `ProcessBuilder.start()` 가 던지는 갈래(실행 권한·바이너리 없음)는 **예산만** 적었습니다. 그러면 상태가 `Starting` 에 갇히고 자동 기동의 `Absent` 도, 사람이 시킨 기동도 「이미 기동 중」으로 거절되어 **IDE 를 다시 켜야** 풀립니다. ⚠ 가드는 **자리를 짚지 않고 짝을 셉니다** — 「catch 안에 있나」로 재면 갈래가 하나 더 생길 때 다시 비고, 이 결함이 정확히 그렇게 생겼습니다. 실패를 정책에 알리는 자리가 n 곳이면 상태 전이도 n 곳 이상이어야 합니다. 왕복도 함께 잽니다(던짐 → 실패 적기 → 사람이 다시 시킴 → 붙음) — 실패를 적는 것만으로는 사람이 되돌릴 수 있다는 말이 안 됩니다 |

| `SourceTextTest`(대화의 시각) | **대화를 고르는 목록이 마지막으로 움직인 때를 말하는가.** 같은 실측에서 나왔다 — 대화 241개, 그중 쉰한 개는 제목도 없는데 목록은 제목과 id 여섯 자뿐이었다. ⚠ 이 가드가 처음엔 **제 주석에 걸려** 초록이었다: 그리는 식을 통째로 지웠는데도 바로 위 주석의 「코어는 늘 보낸다(lastActivity)」가 그 낱말을 대신 물었다. **주석을 걷어내고, 둘을 따로 묻지 않고 한 식으로** 못박는다 |
| `TranscriptTest`(재생의 끝) · `SourceTextTest`(그리는 자리) · `WireConformanceTest`(면제가 지워졌다) | ★ **전선에 칸을 늘린 사람이 화면에 안 닿게 두면 같은 결함입니다.** 코어가 전사 스트림에 「재생이 여기서 끝났다」를 대기 시작했고(`Response.live`), 이 창은 그 프레임을 **사건이 없다는 이유로 조용히 버리고** 있었습니다 — 칸이 생긴 날 화면은 아무것도 달라지지 않았습니다. 그 침묵의 대가가 가장 큰 자리가 **빈 판**입니다: 「아직 안 온 대화」와 「정말 빈 대화」가 같은 그림이었습니다. 시험 셋은 사실 셋입니다 — **제자리에서 오는가**(마지막 재생 사건 뒤·스트림의 끝이 아님), **화면이 그리는가**, **선언과 면제가 맞는가**. ⚠ **짝이 필요합니다**: 표를 안 보내는 구형 데몬에게 아무 말도 지어내지 않는지, 그리고 **기본 상태가 여전히 「연결됨」인지**. 기본을 「불러오는 중」으로 돌리면 그런 데몬에 붙은 창이 영원히 그 상태에 갇히고, 그것은 고친 것이 아니라 새 결함입니다. 이 줄이 직전 커밋의 면제 줄을 **지운** 첫 사례입니다 — 「면제도 늙는다」가 설계대로 동작했습니다 |
| `WireConformanceTest`(낡은 면제)·`SourceTextTest`(계기 배선) | **면제도 늙는다.** 「안 읽는다」는 면제 목록은 **주장**이라, 칸을 나중에 읽기 시작해도 줄이 남는다 — 파일에 거짓 사유가 서고, 더 나쁘게는 그 칸이 **다시 안 읽히게 돼도 아무도 안 운다.** 실제로 `parts`·`topics` 가 그랬다. 이제 **읽는 칸을 면제에 적으면 운다.** ⚠ 그 짝이 하나 더 필요했다 — 변이가 보여 줬다: 선언이 있고 그리는 코드가 이름을 대도, **문에서 판으로 값을 옮기는 줄**에서 `it.compactions` 를 `0` 으로 바꾸면 컴파일되고 아무도 안 울었다. `Rows.Ctx` 의 칸을 선언에서 읽어 **문이 준 값에서 오는지**까지 본다 |
| `RowTextTest`·`SourceTextTest`(가십의 나이) | **초는 화면까지 가지 않는다.** 이 판은 나이를 그리긴 했는데 초를 날것으로 찍었다 — 정상 범위가 0~3600 이라 대부분이 「3540초 전 확인」이었다. ⚠ 이 칸이 둘인 이유가 **변이가 잡은 것**이다: `RowText.ago` 를 시험이 재는 것과 **창이 그것을 부르는 것**은 다른 사실이고, 창에서 호출을 떼도 core 시험은 전부 초록이었다(그 모듈에 시험 소스셋이 없다). 그래서 `ageSeconds` 를 읽는 **모든 줄**이 `RowText.ago(` 를 지나는지 소스에서 본다 |
| `RowTextTest`·`SourceTextTest`(물음 카드) | **서 있는 물음이 언제 선 것인지 말한다.** `Waiting.since` 는 그 구조체에서 `omitempty` 가 없는 **유일한 칸**이라 늘 실려 오는데 안 읽고 있었다. 시각 자체를 재고(오늘/오늘 아님, 못 읽는 값에 「방금」 안 지어내기 — 시각은 `now` 에서 만들어 표준시간대에 안 걸린다), 그리는 자리는 소스를 글자로 읽어 잰다(그 모듈에 시험 소스셋이 없다). 목록은 와이어 선언에서 읽고 **`subject`·`ask` 같은 파생 속성을 따라간다** — 접는 자리가 칸을 떨어뜨려도 운다. 안 그리는 둘(`id`·`kind`)은 사유와 함께 적혀 있다 |
| `HandServerTest`(선택 인자) | **설명이 안 말하는 선택 인자는 모델에게 없는 기능이다.** 스키마는 필수 인자를 강제하지만 선택 인자는 강제하지 않으니, 말해 주지 않으면 안 보인다. `apply_edit.replaceAll` 이 그랬다 — 이 판의 구현은 **여러 번 나오는 글자를 만나면 편집을 거절하고** 그때서야 그 이름을 대므로, 모델은 한 번 실패해야 배웠다. **실물 도구 목록의 스키마를 읽어** 판정하니 도구가 늘어도 따라오고, 인자를 하나도 못 읽으면 그것부터 운다. 짝은 VS Code `hand.test.ts` |

## 여기서 안 재는 것

**사람의 눈이 아직 필요한 것.** 점검표에서 아직 못 옮긴 자리들이고, 못 옮긴 사유가 각각 있다.

| 항목 | 왜 아직 사람인가 |
|---|---|
| 탭의 ✕(주 탭엔 없고 연 탭엔 있다) | 탭을 세우려면 데몬에 붙는 뷰가 서야 한다 — 2026-09-01 사람 확인 |
| 상태 표시줄 클릭·툴팁 | 위젯이 상태 표시줄에 붙은 뒤라야 의미가 있다 |
| 터미널 우클릭 항목 | 새 터미널 엔진의 편집기가 있어야 한다 |
| 대화 목록이 열리는가 | 데몬과 대화가 필요하다 |
| 데몬 자동 실행·내려받기 | 프로세스를 띄우고 네트워크를 탄다 — 그래서 시험 안에서는 **아예 안 띄운다**(`StartDaemon.enabled`) — 2026-09-01 사람 확인 |
| 다크 테마에서 아이콘이 보이는가 | 색 패칭은 실제 테마가 서야 확인된다 |

- **진짜 창을 클릭하는 것.** 4층은 창을 안 띄운다. 마우스로 눌러 보는 것은
  `runIdeForUiTests` + Remote-Robot 의 몫이고, 디스플레이가 필요하며 잘 흔들린다. 지금 층으로
  못 재는 것이 나오면 그때 얹는다.
- **데몬의 에이전트 루프.** 툴 호출·계획·카운슬은 코어(Go)의 E2E 와 `internal/eval` 이 잰다.
  이쪽은 그 결과를 **받아서 그리는** 부분만 본다.
- **창을 여럿 띄운 상태의 행동.** 손이 하나뿐이라는 계약, 고정 탭의 스트림 수명 같은 것은
  주석과 사람의 손에 남아 있다.
- **자동 기동이 실제로 붙는 것.** 규칙(`Restarts` 6·`StartDaemon` 갈래)은 재지만, 프로젝트를
  열어 상태 표시줄이 실제로 `Connected` 가 되는 자리는 사람이 본다. 2026-09-01 에 확인했다 —
  이 경로가 **끝까지 돈 것은 이날이 처음**이다. 그 전에는 `magi: Not running` 에서 안 바뀌었고,
  원인은 JVM 이 띄운 데몬이 IDE 의 프로세스 그룹에 묶여 죽는 것이었다. 코어가 `--detach` 를
  내주면서 닫혔다(CLI 실측 1.6초·`PPID 1`·자기 PGID, IDE 실측 같은 날).
- **수준이 탭 제목으로 새지 않는 것.** 「수준이 글자가 되는 자리가 없다」는 `SourceTextTest` 가
  소스로 막지만, 그것은 **우리가 아는 자리**만 막는다. 2026-09-01 에 사람이 영문 IDE 에서
  확인했다 — 탭은 `Chat`·`Findings` 이고, 첫 탭을 드래그해 놓아도 둘째 탭 제목이 안 번진다.
  이 두 번째 절이 중요하다: 원래 결함이 **드래그했을 때만** 둘째 탭까지 물들이는 모양이었다.

- **창을 둘 띄웠을 때 데몬이 하나인가.** 2026-09-01 에 쟀다 — 같은 워크스페이스를 두 IDE
  인스턴스가 열게 하고(설정·시스템 자리만 갈라 준 둘째 인스턴스) 데몬 수를 셌다. **1개**였다:
  먼저 있던 것에 붙었지 새로 안 띄웠다.

  이 항목은 **하마터면 거짓 통과로 적을 뻔했다.** 첫 시도에서 둘째 인스턴스의 설정 디렉토리
  경로를 잘못 짚어 빈 설정으로 떴고, IDE 는 시작 마법사로 들어가 **프로젝트를 아예 안 열었다**.
  데몬은 당연히 1개였다 — 우리 플러그인이 돌지도 않았으니까. 로그에서 `Entering startup wizard
  workflow` 를 보고서야 알았다. 그래서 지금은 셋을 같이 확인한다: 마법사로 안 샜는가 ·
  `Opening existing project with .idea at …` 가 있는가 · 그러고 나서 데몬이 몇인가.

  아직 안 잰 것: **데몬이 없는 상태에서 둘이 동시에 띄우려 드는** 경합. 여기서 잰 것은 「이미
  있으면 안 띄운다」쪽이다.
- **Apply 단추가 살아나는가.** 값이 저장되는 것과 단추가 살아나는 것은 다른 일이라 따로 본다.
  헤드리스 픽스처에는 설정 대화상자가 없어 이 자리는 사람이 본다. 2026-09-01 최종: **넷 다

## 정책을 부르는 자리 (2026-09-11)

1. 첫 판은 `lost(now)` 직후 `may(now)` 를 불러 **언제나 유예로 거절**됐습니다. 감지와 판정이

   실제로 기다리는 그 5초와 정책이 같은 창을 말하게 했습니다.
2. 5초가 두 군데 있었습니다(`RESTART_GRACE`, `Launches.graceMs`). 우연히 같았을 뿐이고 둘 중
   하나만 고치는 날이 옵니다 — 창이 정책의 값을 읽습니다.

옛 `Restarts` 와 그 시험은 **지웠습니다.** 아무도 안 쓰는데 시험이 남아 있으면 초록의 이유가
흐려집니다.

**못 재는 것**: 실제 폴 주기에서의 동작, 진짜 데몬이 죽었다 살아나는 흐름. IDE 를 띄워야 압니다.

**두 소집이 서로에게 안 내려앉음**(회차 번호는 되풀이됩니다) · 늦은 프리뷰가 사실을 못 덮음 ·
비우면 자리 기억도 비움.

**변이 셋, 전부 잡힘.** 마지막 것(비울 때 자리 기억을 안 지움)은 **두 번 살아남았습니다** —
제 픽스처가 소집 셈을 우연히 어긋나게 만들어 옛 열쇠가 다시 나올 수가 없었습니다. **소집 사건
없이 붙는 창**(꼬리만 남기고 접힌 대화, 라운드 한가운데서 붙은 창)으로 겨눈 뒤 잡혔습니다.

**못 재는 것**: 실제 라이브에서 프리뷰가 사실로 바뀌는 순간의 깜빡임.

## 인레이의 한글 (2026-09-11)

`SourceTextTest > 인레이가 글리프 없는 글자를 대체 폰트로 넘긴다`.

**실측한 사실**: IDE 배포판이 번들한 `jbr/.../fonts/JetBrainsMono-Italic.ttf` 를 직접 열어
재 보면 `Font.canDisplayUpTo("한글이 깨진다")` 가 **0** 입니다 — 첫 글자부터 글리프가
없습니다. `Graphics.drawString` 은 주어진 폰트 하나로만 그리고 폴백을 안 하므로, 「에이전트
의견」이 한국어면 통째로 네모가 됩니다(사용자 보고).

⚠ **이 기계의 화면으로는 재현이 안 됩니다.** 맥의 시스템 폰트(Menlo·Monaco)는 자바가 합성해
주어 `canDisplayUpTo` 가 −1 입니다. 번들 폰트 **파일**을 직접 열어야 보입니다 — 화면만 보고
「우리 쪽은 멀쩡하다」고 하면 안 되는 자리입니다.

**변이 둘, 전부 잡힘**: 폴백 없이 에디터 폰트 그대로 · 폭만 딴 폰트로 잼(폭과 그림이 갈리면
인레이가 제 글자보다 좁거나 넓게 자리를 잡습니다).

**못 재는 것**: 실제로 그려진 픽셀. IDE 를 띄워야 압니다.

## 소유 모드와 정책 보고 (2026-09-11)

수명주기 설계(`docs/CLIENT_LIFECYCLE.ko.md` §3)의 R3·R4 를 `SourceTextTest > 창이 기동을
정책에 묻고, 제 규칙을 따로 쓰지 않는다` 가 같이 붙듭니다.

- **R4**: 연속 실패 셈에 **아무도 1을 안 더하고 있었습니다.** 준비 시한을 넘기거나 뜨자마자
  죽는 데몬은 붙은 적이 없어 `lost` 로도 안 세이므로, 1분이면 예산이 돌아와 같은 실패를 무한히
  되풀이합니다. 실패 두 갈래와 준비 성공을 다 알립니다.
- **R3**: 코어에 소유 모드가 생긴 뒤에도 창은 그냥 `--daemon` 으로 띄우고 자식 stdin 을 **곧바로
  닫고** 있었습니다. 소유 모드에서 그 닫힘은 「소유자가 떠났다」라 데몬이 뜨자마자 끝납니다.
  기능을 묻고, 있으면 소유 모드로 띄우며 파이프를 창 수명 동안 쥡니다.

**변이 다섯, 전부 잡힘**: 실패 안 알림 · 준비 안 알림 · 파이프를 안 쥐고 닫음 · 묻지 않고 소유
모드로 · 소유 모드로 안 띄움.

**못 재는 것**: 실제 IDE 강제 종료에서 EOF 가 데몬에 닿는지(L05–L07), 실제 기동 실패 3회 뒤의
차단. 둘 다 IDE 를 띄워야 압니다.
